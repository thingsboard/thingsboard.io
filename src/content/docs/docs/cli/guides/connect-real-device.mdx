Your solution runs on demo data. This page shows how to send real data from your device to the same ThingsBoard device over HTTP or MQTT. Your AI agent runs the commands. You only enter the connection settings on the device.

Before you start, deploy your solution to ThingsBoard. See <DocLink product={Products.CLI} path="getting-started">Getting Started</DocLink>.

## Connect with your AI agent

<Steps>

1. After the agent deploys a solution with devices, it asks: "Connect a real device?" Select **Yes**. You can also ask at any time: "How do I connect my sensor?"

2. Select how your device sends data: **MQTT** or **HTTP**. If you are not sure, select MQTT.

3. The agent sends a test value as the device and shows the dashboard link. The dashboard now shows the test value. The device itself is not connected yet.

4. The agent shows the settings for your device, like the host, port, topic, and username. Enter them on the device and turn it on.

   The agent does not show the access token in the chat. To see it, run the command that the agent gives you in your terminal.

5. The agent waits for data from the device. When the data arrives, it lists the keys and shows the dashboard link.

6. If the device has no dashboard yet, the agent offers to make a dashboard with the keys that the device sends, or a full solution. If no data arrives, the agent checks why and tells you what to change.

</Steps>

<Aside type="tip">
In Claude Code, the agent asks with buttons. In Antigravity, it asks with numbered options: answer with the number.
</Aside>

## Connect from the terminal

You can do the same steps yourself.

<Steps>

1. Run `tb device connect` with the device name from your solution:

   ```bash
   tb device connect "Office Sensor"
   ```

   In a terminal, the CLI asks what to do: **Send a test value over HTTP now** or **Show the commands to send it yourself**.

2. Select **Send a test value over HTTP now**. The CLI sends the example payload as the device and shows the dashboard link:

   ```text
   ✓ Test value sent: humidity=41, temperature=22.5
   The CLI sent a test value as the device. The device itself is not connected yet.
     Office Dashboard: https://thingsboard.cloud/dashboards/all/<id>
   ```

3. Show the commands and the settings with the real credentials:

   ```bash
   tb device connect "Office Sensor" --show-secrets
   ```

   The output has a `curl` command for HTTP and a `mosquitto_pub` command for MQTT. They contain the host, the credentials, and the example payload. Enter the same host and credentials on your device.

4. Wait for data from the device:

   ```bash
   tb device connect "Office Sensor" --wait
   ```

   The CLI waits up to 5 minutes. Use `--timeout <seconds>` to change the time. When the data arrives, the CLI shows the result:

   ```text
   ✓ Data received: humidity=41, temperature=22.5
     Office Dashboard: https://thingsboard.cloud/dashboards/all/<id>
   ```

</Steps>

The options work together. To send a test value without the question, add `--send`. To send it and then wait for the device, run:

```bash
tb device connect "Office Sensor" --send --wait
```

## Choose HTTP or MQTT

By default, `tb device connect` shows both transports for a device with an access token. Use `--transport` to show one:

```bash
tb device connect "Office Sensor" --transport mqtt
```

| Transport | Command | Host and port |
|---|---|---|
| HTTP | `curl` | The URL of your CLI profile |
| MQTT | `mosquitto_pub` | The MQTT host of the server, port 1883 |
| MQTT over TLS | `mosquitto_pub` with `--cafile` | The MQTT host of the server, port 8883 |

`--send` always uses HTTP. It needs an access token.

To install `mosquitto_pub`, install the `mosquitto-clients` package. On macOS, run `brew install mosquitto`.

For a profile with the MQTT transport, the command uses the telemetry topic of the profile.

## Use TLS

Add `--tls` to connect over TLS. MQTT then uses port 8883, and HTTP uses HTTPS:

```bash
tb device connect "Office Sensor" --transport mqtt --tls --show-secrets
```

The output starts with a command that downloads the server certificate to `tb-server-ca.pem`. The `mosquitto_pub` command uses this file with `--cafile`. Your device needs the same file.

## Change the host or port

The CLI gets the MQTT host and port from the device connectivity settings of the server. If the server has no MQTT settings, the CLI uses the host of your CLI profile. If your devices use a different host or port, like a load balancer or a port mapping, add `--host` and `--port`:

```bash
tb device connect "Office Sensor" --host 192.168.1.20 --port 1884
```

## Credentials and secrets

The command hides the access token and the MQTT password by default. It shows `<ACCESS_TOKEN>` and `<PASSWORD>` instead. Add `--show-secrets` to see the real values. The AI agent does not run `--show-secrets`, so your credentials do not appear in the chat.

| Credentials type | What the command shows |
|---|---|
| Access token | HTTP and MQTT commands. The token is part of the HTTP URL and the MQTT username. |
| MQTT Basic | An MQTT command with the client ID, username, and password. HTTP and `--send` are not available. |
| X.509 certificate | The files that the device needs and an MQTT command over TLS. |

For an X.509 certificate, the device needs three files: the device certificate `device-cert.pem`, its private key `device-key.pem`, and the server certificate `tb-server-ca.pem`. See <DocLink product={Products.PAAS} path="reference/mqtt-api/getting-connected">MQTT API: getting connected</DocLink>.

To change the credentials of a device, use `tb device set-credentials`. Run `tb device set-credentials --help` for the options.

## Example payload

The example payload uses the keys that your dashboard shows. The CLI takes the keys and values from these sources, in this order:

1. The emulator of the device in your project.
2. The telemetry keys that devices of the same device profile already send, with the latest values of the device, or `0` if it has none.
3. `{"temperature": 25}`, if there are no keys.

Your device must send the same key names. If your device sends other names or nested JSON, see <DocLink product={Products.CLI} path="guides/start-from-payload">Start from a device payload</DocLink>.

## Use the JSON output

Add `--format json` to get the result as JSON. Scripts and AI agents use this format. The JSON contains the settings for the device, the commands, and the example payload. The secrets are hidden in the JSON output too, unless you add `--show-secrets`. With `--send` and `--wait`, the JSON also contains the sent and received values and the dashboard links.

```bash
tb device connect "Office Sensor" --format json
```

## Troubleshooting

<details>
<summary>No telemetry within 5 minutes</summary>

The error message shows the likely cause:

- **The device is active:** The device reaches the server. Check the topic or the URL and the payload format.
- **The device has not connected:** Check the host, the port, and the credentials on the device.

Run `tb device status "Office Sensor"` to see the activity and the latest telemetry of the device.

</details>

<details>
<summary>New telemetry arrived, but not from the device</summary>

Something else writes telemetry for this device, like `tb emulator run`. The CLI waits for data from the device itself. Stop the emulator, then send the data again.

</details>

<details>
<summary>The test value arrived, but the device sends nothing</summary>

The test value shows that ThingsBoard and the dashboard work. The problem is on the device side: check the settings on the device and its network connection.

</details>

<details>
<summary>The dashboard shows no new value</summary>

Check that the device sends the same key names that the dashboard shows. The `Data received` line lists the keys that arrived.

</details>

<details>
<summary>Unauthorized or not authorised</summary>

The command still contains `<ACCESS_TOKEN>` or `<PASSWORD>`, so `curl` gets HTTP 401 and `mosquitto_pub` gets "not authorised". Run `tb device connect` with `--show-secrets` and copy the command again.

</details>
