Your solution runs on demo data. This page shows how to send real data from your device to the same ThingsBoard device over HTTP, MQTT, or CoAP. Your AI agent runs the commands. You only enter the connection settings on the device.

Before you start, deploy your solution to ThingsBoard. For details, see <DocLink product={Products.CLI} path="getting-started">Getting started</DocLink>.

## Connect with your AI agent

<Steps>

1. After the agent deploys a solution with devices, it asks: **Connect a real device to it?** Select **Yes**. You can also ask at any time: "How do I connect my sensor?"

   <ImageGallery product={Products.CLI} images={[
     { src: '/src/assets/images/user-guide/cli-solutions/connect-device-connect-question.png', alt: 'The agent asks whether to connect a real device, with the Yes and Later options', caption: 'The agent offers to connect a device right after the deployment.' },
   ]} />

2. Select how your device sends data: **MQTT**, **HTTP**, or **CoAP**. If you are not sure, select MQTT. For LoRaWAN, Modbus, and other protocols, select **Something else**.

   <ImageGallery product={Products.CLI} images={[
     { src: '/src/assets/images/user-guide/cli-solutions/connect-device-transport-question.png', alt: 'The agent asks how the office sensor sends data, with MQTT, HTTP, CoAP, and Something else options', caption: 'The agent recommends MQTT. Your device name can differ.' },
   ]} />

3. The agent sends a test value as the device over the transport that you selected. If your solution has an emulator, the test value uses its keys and values, so the dashboard shows realistic data. If the demo data stream is still running, the agent stops it first, so that the stream does not overwrite the test value. The dashboard now shows the test value. The device itself is not connected yet.

   <ImageGallery product={Products.CLI} images={[
     { src: '/src/assets/images/user-guide/cli-solutions/connect-device-test-value.png', alt: 'The agent stops the demo data stream and runs tb device connect with --send over MQTT; the result shows the payload that mosquitto_pub sent and that ThingsBoard stored it', caption: 'The agent runs the CLI itself. The note in the result says that the device is not connected yet.' },
   ]} />

   For MQTT and CoAP, the CLI uses `mosquitto_pub` or `coap-client` if they are installed on your computer. Otherwise, it sends the test value over HTTP and the agent tells you that MQTT or CoAP is not tested yet.

4. In the same message, the agent shows a table with the settings for your device, like the host, port, topic, and the access token, and a command to test from your computer. The payload in the table is the one that the agent sent. Enter the settings on the device and turn it on. This can take as long as you need.

   <ImageGallery product={Products.CLI} images={[
     { src: '/src/assets/images/user-guide/cli-solutions/connect-device-device-settings.png', alt: 'The agent reports the test reading it sent over MQTT, shows a table with the host, port, topic, access token, and payload, and a mosquitto_pub command to test from your computer', caption: 'The agent shows only what you enter on the device.' },
   ]} />

   If the device has no dashboard yet, the agent offers one. Tell the agent which keys your device will send, like "temperature, humidity", and it builds the dashboard right away. The key names in your firmware must match.

5. When the device is on, say "check my sensor". The agent waits up to five minutes for its data. When the data arrives, it lists the keys and shows the dashboard link. To see the settings again, say "show device settings".

   <ImageGallery product={Products.CLI} images={[
     { src: '/src/assets/images/user-guide/cli-solutions/connect-device-data-received.png', alt: 'The agent waits for the sensor data, then reports the temperature, humidity, and CO2 values it received and links the Office Climate dashboard', caption: 'The agent counts only the data that your device sends, not the test value.' },
   ]} />

6. If the device has no dashboard yet, the agent asks what to do next: **Dashboard for this device** builds a dashboard with the keys that the device sends, and **Full solution** designs a solution around the device and its real keys.

   <ImageGallery product={Products.CLI} images={[
     { src: '/src/assets/images/user-guide/cli-solutions/connect-device-next-step.png', alt: 'The agent reports the first data from Lab Sensor and asks what to do next, with Dashboard for this device, Full solution, and Not now options', caption: 'The agent offers a dashboard built from the keys that the device really sends.' },
   ]} />

   If no data arrives, the agent checks why and tells you what to change. When the data has arrived and the solution has more devices, the agent offers to connect the next one.

</Steps>

The CLI connects one device at a time. To connect many devices at once, see <DocLink product={Products.PE} path="user-guide/provisioning">Device provisioning</DocLink>.

## Connect from the terminal

You can do the same steps yourself.

<Steps>

1. Run `tb device connect` with the device name from your solution:

   ```bash
   tb device connect "Office Sensor"
   ```

   In a terminal, the CLI asks what to do: **Send a test value over HTTP now** or **Show the commands to send it yourself**.

2. Select **Send a test value over HTTP now**. The CLI sends the example payload as the device and shows the dashboard link:

   ```text
   OK Test value sent over HTTPS (port 443): humidity=41, temperature=22.5
   The CLI sent a test value as the device. The device itself is not connected yet.
     Office Dashboard: https://thingsboard.cloud/dashboards/all/<id>
   ```

   If the device has no dashboard, the output links the device page. The output ends with the commands for the next two steps.

3. Show the commands and the settings with the real credentials:

   ```bash
   tb device connect "Office Sensor" --show-secrets
   ```

   Select **Show the commands to send it yourself**. The output has a `curl` command for HTTP, a `mosquitto_pub` command for MQTT, and a `coap-client` command for CoAP, with a Docker variant for MQTT and CoAP and the command that installs the client on your OS. They contain the host, the credentials, and the example payload. Enter the same host and credentials on your device.

4. Wait for data from the device:

   ```bash
   tb device connect "Office Sensor" --wait
   ```

   The CLI waits up to five minutes. Use `--timeout <seconds>` to change the time. When the data arrives, the CLI shows the result:

   ```text
   OK Data received: humidity=41, temperature=22.5
     Office Dashboard: https://thingsboard.cloud/dashboards/all/<id>
   ```

</Steps>

The options work together. To send a test value without the question, add `--send`. To send it over MQTT or CoAP, add `--transport`. To send it and then wait for the device, run:

```bash
tb device connect "Office Sensor" --send --transport mqtt --wait
```

## Choose HTTP, MQTT, or CoAP

`tb device connect` shows the same transports as the **Check connectivity** dialog of the device in ThingsBoard. A device profile with the default transport gets HTTP, MQTT, and CoAP. A profile with the MQTT or CoAP transport gets its own transport. Use `--transport` to show one:

```bash
tb device connect "Office Sensor" --transport coap
```

| Transport | Command | Install the client | Host and port |
|---|---|---|---|
| HTTP | `curl` | Linux: `sudo apt-get install curl`; Windows and macOS have curl | The URL of your CLI profile |
| MQTT | `mosquitto_pub` | Linux: `sudo apt-get install curl mosquitto-clients`; macOS: `brew install mosquitto` | The MQTT host of the server, port 1883 |
| CoAP | `coap-client` | Ubuntu 24.04+ and Debian 12+: `sudo apt install libcoap3-bin`, older releases: `libcoap2-bin`; see also <DocLink product={Products.PE} path="reference/coap-api/getting-connected#command-line-tools">Install coap-client</DocLink> | The CoAP host of the server, port 5683 |

`libcoap3-bin` has no plain `coap-client`, only `coap-client-openssl`, `coap-client-gnutls`, and `coap-client-notls`. The CLI finds the one that is installed and shows it in the command.

For MQTT and CoAP, the output also has a `docker run` command. It runs the client in the `thingsboard/mosquitto-clients` or `thingsboard/coap-clients` image, so you do not have to install it.

HTTP and CoAP need an access token. For a profile with the MQTT transport, the command uses the telemetry topic of the profile. For LwM2M and SNMP, the CLI shows no commands and links to the docs. `--wait` works for them: it waits for telemetry from the device. For an MQTT profile with the Protobuf payload or Sparkplug, the CLI also shows no commands and links to the docs.

## Use TLS

Add `--tls` to connect securely: HTTPS, MQTTS on port 8883, and CoAPs on port 5684:

```bash
tb device connect "Office Sensor" --transport mqtt --tls --show-secrets
```

Before the client command, the output has `tb device server-cert`, which downloads the server certificate to `tb-server-ca.pem`. The `mosquitto_pub` and `coap-client-openssl` commands use this file. Your device needs the same file. The Docker variant downloads the certificate itself.

With `--tls`, the HTTPS URL uses the default port 443. If your server serves HTTPS on another port, add `--transport http --port <port>`.

## Change the host or port

The CLI gets the MQTT and CoAP hosts and ports from the device connectivity settings of the server, like the **Check connectivity** dialog. If the server has no settings for a transport, the CLI uses the host of your CLI profile. If your devices use a different host or port, like a load balancer or a port mapping, add `--host` and `--port`:

```bash
tb device connect "Office Sensor" --transport mqtt --host 192.168.1.20 --port 1884
```

`--port` sets the port of the transport that you select with `--transport`. Without `--transport`, it sets both the MQTT and the CoAP port.

## Credentials and secrets

The command hides the access token and the MQTT password by default. It shows `<ACCESS_TOKEN>` and `<PASSWORD>` instead. Add `--show-secrets` to see the real values. The access token is the device's own credential, the same one that the **Check connectivity** dialog shows. The AI agent shows it in the settings table, because you enter it on the device.

| Credentials type | What the command shows |
|---|---|
| Access token | HTTP, MQTT, and CoAP commands; the token is part of the HTTP and CoAP URLs and the MQTT username |
| MQTT Basic | An MQTT command with the client ID, username, and password; `--send` uses `mosquitto_pub` |
| X.509 certificate | The files that the device needs and an MQTT command over TLS; `--send` is not available |

For an X.509 certificate, the device needs three files: the device certificate `device-cert.pem`, its private key `device-key.pem`, and the server certificate `tb-server-ca.pem`. For details, see <DocLink product={Products.PE} path="reference/mqtt-api/getting-connected#mqtt-over-tls">MQTT over TLS</DocLink>.

To change the credentials of a device, use `tb device set-credentials`. Run `tb device set-credentials --help` for the options.

## Example payload

The example payload uses the keys that your dashboard shows. The CLI takes the keys and values from these sources, in this order:

1. The emulator of the device in your project.
2. The latest telemetry of the device.
3. The telemetry keys that other devices of the same device profile already send, with the value `0`. The CLI skips this step for the default device profile.
4. `{"temperature": 25}`, if there are no keys.

To send your own values, add `--payload` with a JSON object:

```bash
tb device connect "Office Sensor" --send --payload '{"temperature": 21.8, "humidity": 44}'
```

Your device must send the same key names. If your device sends other names or nested JSON, see <DocLink product={Products.CLI} path="guides/start-from-payload">Start from a device payload</DocLink>.

## Use the JSON output

Add `--format json` to get the result as JSON. Scripts and AI agents use this format. The JSON contains the settings for the device, the commands, the example payload, and the dashboard links. The secrets are hidden in the JSON output too, unless you add `--show-secrets`. With `--send` and `--wait`, the JSON also contains the sent and received values.

```bash
tb device connect "Office Sensor" --format json
```

## Troubleshooting

<details>
<summary>No telemetry within five minutes</summary>

The error message shows the likely cause:

- **The device is active:** The device reaches the server. Check the topic or the URL and the payload format.
- **ThingsBoard did not see the device connect:** Check the access token first, then the host, the port, and the transport on the device. ThingsBoard does not show rejected connections. On MQTT, `not authorised` (CONNACK 5) means a wrong token.

For LwM2M and SNMP devices, the message says what to check for them.

Run `tb device status "Office Sensor"` to see the activity and the latest telemetry of the device.

</details>

<details>
<summary>New telemetry arrived, but not from the device</summary>

Something else writes telemetry for this device, like `tb emulator run`. The CLI waits for data from the device itself. Stop the emulator, then send the data again.

</details>

<details>
<summary>The test value arrived, but the device sends nothing</summary>

The test value shows that ThingsBoard and the dashboard work. The problem is on the device side: check the settings on the device and its network connection.

</details>

<details>
<summary>The dashboard shows no new value</summary>

Check that the device sends the same key names that the dashboard shows. The `Data received` line lists the keys that arrived.

</details>

<details>
<summary>Unauthorized or not authorised</summary>

The command still contains `<ACCESS_TOKEN>` or `<PASSWORD>`, so `curl` gets HTTP 401 and `mosquitto_pub` gets "not authorised". Run `tb device connect` with `--show-secrets` and copy the command again.

</details>
