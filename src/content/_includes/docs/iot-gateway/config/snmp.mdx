The SNMP Connector reads data from SNMP manager objects and writes data back to them, forwarding the
results to ThingsBoard as device attributes and telemetry.

To enable this connector, add it to the `connectors` list in `tb_gateway.json` — see the
<DocLink product={props.product} path="config/general">General Configuration</DocLink> reference.

## Connector configuration: snmp.json

The connector reads its settings from a JSON file. Below is a full example with four device entries —
the first using built-in converters, the second using a custom converter class, the third using SNMPv3
for both polling and traps, and the fourth configured for traps only, without polling:

## Section "devices"

An array of device configurations. Each entry represents one SNMP manager device.

| Parameter | Default | Description |
|-----------|---------|-------------|
| `deviceName` | `SNMP router` | Device name in ThingsBoard |
| `deviceType` | `snmp` | Device type in ThingsBoard |
| `ip` | | IP address or hostname of the SNMP manager |
| `port` | `161` | SNMP port |
| `pollPeriod` | `5000` | Polling interval in milliseconds |
| `version` | `v2c` | SNMP version: `v1`, `v2c`, or `v3` |
| `community` | | Default SNMP community string (`public` or `private`); required for SNMPv1 and SNMPv2c |
| `security` | | SNMPv3 security settings; required when `version` is `v3` — see [Subsection "security"](#subsection-security) |
| `converter` | | *(Optional)* Custom converter class name; omit to use the built-in converter |
| `attributes` | | Array of attribute mappings — see below |
| `telemetry` | | Array of telemetry mappings — see below |
| `attributeUpdateRequests` | | *(Optional)* Array of attribute-write configurations |
| `serverSideRpcRequests` | | *(Optional)* Array of RPC-triggered SNMP operation configurations |

The gateway skips an SNMPv1 or SNMPv2c device without `community`, and an SNMPv3 device whose `security`
is missing or has an invalid format. If the credentials do not match the device, the gateway does not
skip it but cannot read data from it.

### Subsection "security"

<Aside type="note">
  SNMPv3 is available in ThingsBoard IoT Gateway v.3.8.7 and later.
</Aside>

Required for SNMPv3 devices. SNMPv3 uses the User-based Security Model (USM). The security level is
defined by the parameters you set: only `username` for `noAuthNoPriv`, plus authentication for
`authNoPriv`, plus privacy (encryption) for `authPriv`. The same settings are used for polling,
attribute updates, RPC requests, and checking traps from the device.

| Parameter | Description |
|-----------|-------------|
| `username` | USM user name |
| `authProtocol` | *(Optional)* Authentication protocol: `MD5` or `SHA` (SHA-1) |
| `authKey` | Authentication passphrase, at least 8 characters; required when `authProtocol` is set |
| `privProtocol` | *(Optional)* Privacy protocol: `DES` or `AES` (AES-128); requires `authProtocol` |
| `privKey` | Privacy passphrase, at least 8 characters; required when `privProtocol` is set |
| `contextName` | *(Optional)* Name of the context to read from, if the device provides data in several contexts, for example, for several virtual instances |
| `contextEngineId` | *(Optional)* Engine ID of that context as a hex string, for example, `80001f8880e1`; needed only if the context and device engine IDs are not the same, for example, behind an SNMP proxy |

<Tabs>
<TabItem label="noAuthNoPriv">

Messages are neither authenticated nor encrypted.

```json
"security": {
  "username": "noAuthUser"
}
```

</TabItem>
<TabItem label="authNoPriv">

Messages are authenticated but not encrypted.

```json
"security": {
  "username": "authUser",
  "authProtocol": "SHA",
  "authKey": "authPassphrase"
}
```

</TabItem>
<TabItem label="authPriv">

Messages are authenticated and encrypted.

```json
"security": {
  "username": "privUser",
  "authProtocol": "SHA",
  "authKey": "authPassphrase",
  "privProtocol": "AES",
  "privKey": "privPassphrase"
}
```

</TabItem>
</Tabs>

<Aside type="note">
  The gateway discovers the engine ID of the device automatically, so you do not need to configure it.
</Aside>

`username`, `authKey`, and `privKey` support placeholders in the `${VARIABLE_NAME}` format. This allows
you to keep passphrases out of the configuration file and pass them as environment variables instead:

```json
"security": {
  "username": "privUser",
  "authProtocol": "SHA",
  "authKey": "${SNMP_AUTH_KEY}",
  "privProtocol": "AES",
  "privKey": "${SNMP_PRIV_KEY}"
}
```

<Aside type="note">
  Placeholder names are case-sensitive and must exactly match the environment variable names. See
  <DocLink product={props.product} path="config/general/#environment-variables">Environment Variables</DocLink>
  for how to set them. If a variable is not set, the gateway logs an error and skips the device.
</Aside>

### Sections "attributes" and "telemetry"

Both sections share the same field structure. `attributes` entries are sent to ThingsBoard as device
attributes; `telemetry` entries are sent as time-series telemetry.

| Parameter | Description |
|-----------|-------------|
| `key` | ThingsBoard attribute or telemetry key name |
| `method` | SNMP operation to use — see [Supported methods](#supported-methods) |
| `oid` | Manager object identifier (string or array, depending on the method) |
| `community` | *(Optional)* Community string for this entry; overrides the device `community` (SNMPv1 and SNMPv2c only) |

Method-specific parameters (e.g. `timeout`, `scalarOid`, `valueOid`) are described in
[Supported methods](#supported-methods).

### Section "attributeUpdateRequests"

Configurations in this section are optional.
ThingsBoard allows the provision of device attributes and fetches some of them from the device application. You can treat this as a remote configuration for devices. Your devices are able to request shared attributes from ThingsBoard. See user guide for more details.

The “attributeUpdateRequests” configuration allows configuring the format of the corresponding attribute request and response messages.

| Parameter | Description |
|-----------|-------------|
| `attributeFilter` | Shared attribute name to subscribe to |
| `method` | SNMP write method: `set` or `multiset` |
| `oid` | Object identifier to write to (used with `set`) |
| `mappings` | OID-to-value map (used with `multiset`); values may reference `${attribute}` |
| `type` | SNMP data type for value encoding (see [Supported data types](#supported-data-types)) — **required only for `set` and `multiset` methods** |

```json
"attributeUpdateRequests": [
  {
    "attributeFilter": "dataToSet",
    "method": "set",
    "oid": "1.3.6.1.2.1.1.1.0",
    "type": "INTEGER"
  },
  {
    "attributeFilter": "dataToMultiSet",
    "method": "multiset",
    "mappings": {
      "1.2.3": "10",
      "2.3.4": "${attribute}"
    },
    "type": "OCTETSTRING"
  }
]
```

<Aside type="note">
  In `mappings` values, `${attribute}` is replaced at runtime with the incoming shared attribute value.
</Aside>

### Section "serverSideRpcRequests"

ThingsBoard allows sending RPC commands to the device connected to ThingsBoard directly or via Gateway.

Configuration, provided in this section is used for sending RPC requests from ThingsBoard to the device through the gateway.

| Parameter | Description |
|-----------|-------------|
| `requestFilter` | RPC method name to bind |
| `method` | SNMP operation to perform, except `trap` — see [Supported methods](#supported-methods) |
| `oid` | Object identifier (string or array, depending on the method) |

The gateway always replies to ThingsBoard: `{"result": <value>}` on success or `{"error": "<message>"}` on failure.

The connector also has built-in `get` and `set` RPC methods that read or write any OID without configuration. See the
<DocLink product={props.product} path="features/reserved-rpc/">Reserved RPC methods</DocLink> guide.

```json
"serverSideRpcRequests": [
  {
    "requestFilter": "setData",
    "method": "set",
    "oid": "1.3.6.1.2.1.1.1.0",
    "type": "IPADDRESS"
  },
  {
    "requestFilter": "dataToMultiSet",
    "method": "multiset",
    "mappings": [
      {
        "oid": "1.3.6.1.2.1.1.9.0",
        "value": "44"
      },
      {
        "oid": "1.3.6.1.2.1.1.10.0",
        "type": "INTEGER",
        "value": "${params.temperature}"
      },
      {
        "oid": "1.3.6.1.2.1.1.11.0",
        "type": "GAUGE",
        "value": "${params.pressure}"
      }
    ],
    "type": "INTEGER"
  },
  {
    "requestFilter": "dataToMultiSetBroadcast",
    "method": "multiset",
    "mappings": [
      {
        "oid": "1.3.6.1.2.1.1.12.0",
        "value": "${params}"
      },
      {
        "oid": "1.3.6.1.2.1.1.13.0",
        "value": "${params}"
      }
    ],
    "type": "INTEGER"
  },
  {
    "requestFilter": "getData",
    "method": "get",
    "oid": "1.3.6.1.2.1.1.1.0"
  },
  {
    "requestFilter": "runBulkWalk",
    "method": "bulkwalk",
    "oid": ["1.3.6.1.2.1.1.1.0","1.3.6.1.2.1.1.2.0"]
  }
]
```

## Section "trapListener"

<Aside type="note">
  Receiving SNMP traps is available in ThingsBoard IoT Gateway v.3.8.7 and later.
</Aside>

Optional. Configures the UDP listener that receives SNMP traps from devices. The listener starts only
when at least one device has a [`trap`](#trap) entry. If this section is omitted, the listener starts with
the default `address` and `port`.

| Parameter | Default | Description |
|-----------|---------|-------------|
| `address` | `0.0.0.0` | Local IP address to listen on; `0.0.0.0` listens on all network interfaces |
| `port` | `162` | Port to listen on |

```json
"trapListener": {
  "address": "0.0.0.0",
  "port": 162
}
```

<Aside type="note">
  On Linux, the default port `162` requires root privileges or the `CAP_NET_BIND_SERVICE` capability.
  Otherwise, set another `port`, for example, `1162`, and configure your devices to send traps to it.

  Also make sure each SNMP connector uses a different `port` — every connector opens its own listener.
</Aside>

## Supported methods

| Method | Operation | Accepts array OID | Extra parameters |
|--------|-----------|:-----------------:|------------------|
| `get` | Read a single object | No | `timeout` |
| `multiget` | Read multiple objects in one request | Yes | `timeout` |
| `getnext` | Read the next object after the given OID | No | `timeout` |
| `walk` | Walk the subtree rooted at OID | No | — |
| `multiwalk` | Walk multiple subtrees | Yes | — |
| `bulkwalk` | Walk multiple subtrees using BULK requests | Yes | — |
| `table` | Read an SNMP table | No | — |
| `bulkget` | Read scalars and repeating objects in one BULK request | — | `scalarOid`, `repeatingOid`, `maxListSize` |
| `trap` | Receive a value from SNMP traps sent by the device | No | `valueOid` |
| `set` | Write a value to a single object | No | `type` |
| `multiset` | Write values to multiple objects | — | `mappings`, `type` |

|-----------|-------------|


### trap

<Aside type="note">
  Receiving SNMP traps is available in ThingsBoard IoT Gateway v.3.8.7 and later.
</Aside>

Receives a value from SNMP traps sent by the device instead of polling it. Used only in `attributes`
and `telemetry`. Traps are received by the [trap listener](#section-traplistener) and processed as soon
as they arrive. A device that only receives traps does not need `port` and `pollPeriod`.

| Parameter | Description |
|-----------|-------------|
| `oid` | Trap OID (the value of `snmpTrapOID.0`) |
| `valueOid` | *(Optional)* OID of the trap variable to use as the value; a variable matches when its OID equals `valueOid` or starts with it; if omitted, all trap variables are sent as a JSON object |

```json
[
  {
    "key": "ReceivedFromTrapWithValueOid",
    "method": "trap",
    "oid": "1.3.6.1.6.3.1.1.5.3",
    "valueOid": "1.3.6.1.2.1.2.2.1.1"
  },
  {
    "key": "ReceivedFromTrap",
    "method": "trap",
    "oid": "1.3.6.1.6.3.1.1.5.3"
  }
]
```

A trap is assigned to the entry when it is sent from the device `ip` and its OID matches the entry
`oid`.

SNMPv1 traps have no trap OID, so the gateway builds it from the trap fields. Set `oid` as for other
SNMP versions, for example, `1.3.6.1.6.3.1.1.5.3` for `linkDown`, and use
`<enterprise OID>.0.<specific trap number>` for enterprise-specific traps.

The trap must use the device credentials — `community` for SNMPv1 and SNMPv2c, or
[`security`](#subsection-security) for SNMPv3 — otherwise it is ignored.

<Aside type="note">
  The `trap` method also receives SNMPv2c informs, and the gateway sends a response to the device.
  SNMPv3 informs are not supported.
</Aside>

### multiset

Writes values to multiple SNMP objects in a single operation. The shape of `mappings` depends on where the method is used.

**In `attributeUpdateRequests`** — `mappings` is an object mapping OIDs directly to values:

| Parameter | Description |
|-----------|-------------|
| `mappings` | Object mapping OIDs to values; values may use `${attribute}` to reference the incoming attribute value |
| `type` | SNMP data type for value encoding, default `OCTETSTRING` — see [Supported data types](#supported-data-types) |

```json
{
  "attributeFilter": "dataToMultiSet",
  "method": "multiset",
  "mappings": {
    "1.2.3": "10",
    "2.3.4": "${attribute}"
  },
  "type": "COUNTER"
}
```

**In `serverSideRpcRequests`** — `mappings` is an array of objects, each with its own `oid` and `value`, and an optional per-mapping `type` override:

| Parameter | Description |
|-----------|-------------|
| `mappings` | Array of `{ oid, value, type }` objects |
| `mappings[].oid` | Object identifier to write to |
| `mappings[].value` | Value to write to the OID; use a JSON-path expression to extract data packed in the RPC call's `params` object, or just a constant value |
| `mappings[].type` | *(Optional)* Per-mapping SNMP data type override — see [Supported data types](#supported-data-types) |
| `type` | Default SNMP data type applied to mappings that don't specify their own `type`, default `OCTETSTRING` — see [Supported data types](#supported-data-types) |

```json
{
  "requestFilter": "dataToMultiSet",
  "method": "multiset",
  "mappings": [
    {
      "oid": "1.3.6.1.2.1.1.9.0",
      "value": "62"
    },
    {
      "oid": "1.3.6.1.2.1.1.10.0",
      "type": "INTEGER",
      "value": "${params.temperature}"
    },
    {
      "oid": "1.3.6.1.2.1.1.11.0",
      "type": "GAUGE",
      "value": "${params.pressure}"
    }
  ],
  "type": "INTEGER"
}
```

<Aside type="note">
  A `value` such as `${params.temperature}` is a JSON-path expression that extracts a named field from the incoming RPC call's `params` object. For example, calling `dataToMultiSet` with `{"temperature": 22, "pressure": 1013}` makes `${params.temperature}` resolve to `22` and `${params.pressure}` resolve to `1013`, letting one `multiset` request write several independent values from a single RPC call. If the RPC call sends a single, unnamed value, use `${params}` to reference it directly.
</Aside>

## Supported data types


| Type | Description | Example |
|------|-------------|---------|
| `INTEGER` | Whole number (positive or negative) | `42`, `-100` |
| `COUNTER` | Non-negative integer that monotonically increases until reaching 4,294,967,295, then wraps to zero | `1500` |
| `COUNTER64` | 64-bit non-negative integer that monotonically increases until reaching 18,446,744,073,709,551,615, then wraps to zero | `9223372036854775807` |
| `GAUGE` | Non-negative integer for gauges and measurements that can increase or decrease | `75` |
| `TIMETICKS` | Time value in units of 0.01 seconds (hundredths of a second) | `12345678` |
| `OCTETSTRING` | String of bytes (octets) | `"hello"`|
| `IPADDRESS` | IPv4 address in dotted-decimal notation | `"192.168.1.1"` |

<Aside type="note">
  Specify the data type with the `type` field for `set` and `multiset` methods in both `attributeUpdateRequests` and
  `serverSideRpcRequests`. If `type` is omitted, `OCTETSTRING` is used.
</Aside>
