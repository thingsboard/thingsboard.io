ThingsBoard Platform Integrations act as a secure API bridge between external platforms, network servers, or protocol gateways and ThingsBoard — translating incoming messages into the ThingsBoard data model (telemetry, attributes, RPC) without changing device firmware.

Use integrations when devices cannot connect directly to ThingsBoard, or when they already communicate with another IoT platform or protocol gateway.

Common scenarios:

- Devices connected to external IoT platforms (AWS IoT, Azure IoT Hub, Google Cloud Pub/Sub)
- LoRaWAN network servers (ChirpStack, The Things Stack, Loriot, ThingPark)
- MQTT brokers, OPC-UA servers, and other protocol gateways
- Industrial gateways and NB-IoT / SigFox network servers

Once data is received through an integration, it is available to the full ThingsBoard feature set: device management, Rule Engine processing, telemetry storage, dashboards, and RPC commands.

## How integrations work

Integrations in ThingsBoard provide bidirectional communication between external platforms (devices, gateways, network servers) and the ThingsBoard platform. This communication is implemented through uplink and downlink message flows.

```plaintext
  ┌──────────────────────────────────┐
  │     ThingsBoard Rule Engine      │
  │  (telemetry, attributes, RPC)    │
  └──────────────────────────────────┘
     ▲                       │
     │                       ▼
  Uplink Converter      Downlink Converter
  (device → TB format)  (TB → device format)
     ▲                       │
     └───────────┬───────────┘
                 │
  ┌──────────────┴───────────────────┐
  │       ThingsBoard Integration    │
  │  (validates payload & security)  │
  └──────────────┬───────────────────┘
                 ▲
                 │
  External Platform / Device
```

<h4>1. Uplink Flow (Device &#8702; ThingsBoard)</h4>

The uplink flow describes how data from external systems enters the ThingsBoard platform.

**Step 1 — Message delivery to the Integration**  
An external device, gateway, or network server sends a message to the configured **integration endpoint** using a supported protocol (e.g., HTTP, MQTT, or a platform-specific integration protocol).

**Step 2 — Payload decoding (Uplink Data Converter)**  
The Integration forwards the message to the **Uplink Data Converter**, which transforms the raw payload into the ThingsBoard internal message format. The decoded message may contain: device or asset name, type, telemetry values, and attributes.

**Step 3 — Device provisioning**  
If the message references a device that does not yet exist in ThingsBoard, the platform can **automatically create the device** based on the data provided by the converter.

<Aside type="note">
  Auto-provisioning is **disabled by default** and must be configured in **Device profile &#8702; <DocLink product={props.product} path="user-guide/device-provisioning">Device provisioning</DocLink>**.
</Aside>

**Step 4 — Rule Engine processing**  
After conversion, the message enters the **Rule Engine** for further processing: storing telemetry and attributes, data transformation, triggering alarms, forwarding data to external systems, and updating dashboards.

<h4>2. Downlink Flow (ThingsBoard &#8702; Device)</h4>

The downlink flow describes how messages generated in ThingsBoard are delivered to external platforms or devices.

**Step 1 — Message generation in the Rule Engine**  
A **Rule Engine** node generates a message intended for an external system. Common examples include:
- shared attribute updates
- **RPC (Remote Procedure Call)** commands

**Step 2 — Message encoding (Downlink Data Converter)**  
The **Downlink Data Converter** transforms the internal ThingsBoard message into the format required by the external system. This may include defining:
- protocol-specific topics
- payload structure
- headers or metadata

**Step 3 — Message delivery**  
The Integration sends the encoded message to the target **external platform or device** using the configured protocol.

<Aside type="note">
  The downlink converter is optional. Integrations that only ingest data into ThingsBoard do not require a downlink converter.
</Aside>

## Creating an integration

Integrations are created through a 4-step wizard in **Integration center &#8702; Integrations**.

<Steps>
1. Go to **Integration center &#8702; Integrations**
2. Click the **+ Add integration**.
3. Select the **Integration type** from the dropdown (over 30 types available). Click **Next**.
4. **Uplink data converter** — select an existing converter from the dropdown, or create one inline:
   - **Select existing**: choose a previously created converter by name.
   - **Create new**: enter a name and write the decoder script directly in the wizard — no need to navigate to Data converters first.
   - **<DocLink product={props.product} path="user-guide/integrations#converters-library" target="_blank">From library</DocLink>** (supported types only): select vendor and model to auto-populate the decoder.
5. **Downlink data converter** (optional) — same options as above. Skip if the integration only ingests data into ThingsBoard.
6. **Connection settings** — configure integration-specific parameters: endpoint URL, credentials, topic filters, server address, security tokens, etc. These fields vary by integration type.
7. Click **Add**.
</Steps>

<Aside type="tip">
A single converter can be reused across multiple integrations. Create converters in advance from **Integration center &#8702; Data converters**, or create them inline during integration setup — both approaches produce identical results. To change the converter after the integration is created, open the integration and edit the **Uplink data converter** or **Downlink data converter** field.
</Aside>

## Uplink data converter

The uplink converter decodes raw payloads from external devices or network servers and maps them to ThingsBoard's internal format: device name, device type, telemetry values, and attributes.

### Generic uplink converter

A generic converter works with any integration type. To create one:

<Aside type="tip">
Use <DocLink product={props.product} path="user-guide/tbel">TBEL</DocLink> (ThingsBoard Expression Language) for converter scripts — it executes significantly faster than JavaScript inside ThingsBoard.
</Aside>

<Steps>
1. Go to **Integration center &#8702; Data converters**.
2. Click **+ Add data converter &#8702; Create new converter**.
3. The **Converter type** is set to **Uplink** by default. Select the **Integration type** from the dropdown (e.g. MQTT, HTTP, ChirpStack) or leave it as **All** to apply the converter across all integration types.
4. Enter a **Name**. Optionally configure debug output via the **Failures** button.
5. In **Main decoding configuration**, write or paste your decoder script. Use the **TBEL** / **JS** selector to switch languages.
6. Click **Test decoder function** to validate the script against a sample payload before saving.
7. Optionally expand **Advanced decoding parameters** and add keys to the **Update only keys list** — values for those keys are written to the database only when they change between messages.
8. Click **Add**.
</Steps>

### Typed uplink converter

Starting from **ThingsBoard 4.0**, certain integrations support a typed uplink converter — a structured alternative to writing a decoder script manually. Instead of coding the full payload parser, you select the entity type, define the name pattern, and specify which payload fields map to telemetry and which to attributes. A decoder function is auto-generated based on the integration type and can be reviewed or replaced.

Supported integrations: <DocLink product={props.product} path="user-guide/integrations/chirpstack">ChirpStack</DocLink>, <DocLink product={props.product} path="TODO">Loriot</DocLink>, <DocLink product={props.product} path="TODO">The Things Stack Community</DocLink>, <DocLink product={props.product} path="TODO">The Things Stack Industries</DocLink>, ThingPark, and ThingPark Enterprise.

<Aside type="note">Converters created before ThingsBoard 4.0 continue to work without changes.</Aside>

To create a typed uplink converter:

<Steps>
1. In the **Add data converter** dialog, select a supported **Integration type** (e.g. Loriot, ChirpStack). 
2. The **Uplink data converter** section will show a **Create new** / **Library** tab selector — choose **Create new**.
3. Enter a **Name**. Optionally configure debug output via the **Failures** button.
4. In **Main decoding configuration**, select the **Entity type** (**Device** or **Asset**) and enter the entity name pattern. Use `$field` references to resolve values from the incoming message (e.g. `Device $eui`). Available field names come from the integration-specific uplink payload — for example, Loriot provides `eui`, `dr`, `fPort`; ChirpStack provides `devEui`, `fPort`, `dr`. Refer to the integration-specific guide for the full list.
5. The decoder function is pre-generated for the selected integration type — review it or replace it with a custom script. Click **Test payload decoder** to validate it against a sample payload.
6. Expand **Advanced decoding parameters** to configure optional fields:
   - **Device profile name**, **Device label**, **Customer name**, **Device group name** — all support `$field` patterns (same field names as the entity name pattern above).
   - **Telemetry** / **Attributes** — add the payload keys to extract into each category. Keys absent in the incoming message are silently ignored.
   - **Update only keys list** — keys listed here are written to the database only when their value changes between messages.
7. Click **Add**.
</Steps>

**Payload** — the input message from the device. Each integration type pre-fills a sample. The `payload` variable is available in the decoder script; its type depends on the selected content type:
- **JSON**
- **TEXT**                                                                                               
- **Binary (Base64)** — automatically decoded to a byte array in the script; no manual base64 decoding needed.

Binary payloads are decoded from Base64 automatically — no manual decoding needed. Use TBEL built-in helpers (`parseBytesToInt`, `parseBytesToFloat`, `decodeToString`, etc.) to extract values from the byte array.

**Metadata** — a key-value map of integration-level fields, accessible via `metadata`. Custom metadata parameters can be defined per integration in its settings (e.g. `deviceType`).

**Converter output** — the fully assembled message ThingsBoard produces from the decoder result. The top-level fields depend on the converter type:

- **Generic converter**: the decoder function must return an object containing `deviceName` and `deviceType` (or `assetName` and `assetType` for assets). Optional: `customerName`, `groupName` — ThingsBoard auto-creates the customer or group and assigns the entity.
- **Typed converter**: the decoder function returns only `{ attributes, telemetry }`. ThingsBoard adds `entityType`, `name`, and `profile` from the UI-configured entity type and name pattern.

The **Converter output** tab in the test dialog shows the final assembled message with all fields combined.

      }
    },

## Downlink data converter

The downlink converter transforms a Rule Engine message into the format expected by the external integration.

<Aside type="note">A downlink converter is optional. You only need one if the integration sends outgoing messages (RPCs, attribute updates, commands). Receive-only integrations can skip it.</Aside>

To create a downlink converter:

<Steps>
1. Go to **Integration center &#8702; Data converters**.
2. Click **+ Add data converter &#8702; Create new converter**.

4. Select the **Integration type** or leave **All**.
5. Enter a **Name** and optionally configure debug output via the **Failures** button.
6. In **Main encoding configuration**, write your encoder script.
7. Click **Add**.
</Steps>

The encoder function signature:

```js
function encoder(msg, metadata, msgType, integrationMetadata);
```

| Parameter | Description |
|---|---|
| `msg` | JSON message payload from the Rule Engine |
| `metadata` | Key-value pairs with additional message data |
| `msgType` | Rule Engine message type (e.g. `ATTRIBUTES_UPDATED`, `POST_TELEMETRY_REQUEST`) |
| `integrationMetadata` | Key-value map with integration-specific fields configured in integration details |

### Converter output

The encoder must return a JSON object:

```json
{
  "contentType": "JSON",
  "data": "{\"tempFreq\":60,\"firmwareVersion\":\"1.2.3\"}",
  "metadata": {
    "topic": "temp-sensor/sensorA/upload"
  }
}
```

| Field | Description |
|---|---|
| `contentType` | `JSON`, `TEXT`, or `BINARY` (Base64 string) |
| `data` | Encoded data string matching the content type |
| `metadata` | Key-value pairs — e.g. MQTT topic, HTTP headers |

### Triggering a downlink

To send a downlink from the Rule Engine, add an **Integration Downlink** action node to your rule chain and configure it to use the target integration. The node forwards any Rule Engine message to the integration's downlink converter.

### Synchronous vs asynchronous downlinks

Most integrations (MQTT, AWS IoT, etc.) push downlinks asynchronously — each Rule Engine message is sent to the external broker immediately.

Some integrations (SigFox, generic HTTP) can only push downlinks **synchronously** in reply to an uplink request. In this case, the last downlink message is queued until the next uplink arrives for that device.

## Converter import and export

Converters can be exported as JSON and imported into any ThingsBoard instance — useful for sharing custom decoders between environments, tenants, or team members.

- **Export**: on the **Data converters** list, click the export icon on a converter row. Alternatively, open the converter details panel and click **Export converter** in the panel header. Save the downloaded JSON file.
- **Import**: click **+ Add data converter &#8702; Import converter**, then drag and drop the JSON file or click **Browse file** to select it, and click **Import**. All converter settings are restored — name, type, integration type, script, and advanced parameters.

## Managing data converters

All converters are listed in **Integration center &#8702; Data converters**. From the list you can:

- **Edit**: click a converter name to open it, make changes, and click **Apply changes**.
- **Delete**: click the delete icon on a row, or select multiple converters and use bulk delete.

A converter is referenced by ID. If the same converter is assigned to multiple integrations, any change to the converter (script, advanced parameters) immediately affects all integrations using it.

## Debug mode

Debug mode captures all raw input/output events for a converter or integration — full payload, metadata, decoder input and output — which is useful during development and troubleshooting. Because debug data is written to the database, it should be disabled in production.

### Enabling debug mode

Debug mode is controlled individually per converter and per integration via the **Failures** button in their settings forms:

- **Failures** (default) — only failure events are captured.
- **Active debug** — when debug is enabled for a time window, the button shows the remaining duration (e.g. **1 hour**, **15 min**). Clicking it allows you to extend, shorten, or disable the window.

To enable debug for a converter: open the converter, click the **Failures** button next to the converter name, and select the desired duration.
To enable debug for an integration: open the integration settings and use the same control.

Starting from **ThingsBoard 3.9**, debug events are stored for only the first **15 minutes** after a converter or integration is created or re-enabled — after that, the mode reverts to **Failures** automatically. The duration can be changed at any time.

### Integration events

Each integration has an **Events** tab that records every processed message — the primary surface for debugging uplink and downlink flows without enabling full debug mode.

Events are grouped by type:

| Event type | Description |
|---|---|
| **Uplink** | Each message received and processed by the integration — raw payload, converter output, and the resulting device data |
| **Downlink** | Each outgoing message sent to the external system |
| **Error** | Failed messages with the full error details and stack trace |
| **Debug** | Detailed trace events, only captured while debug mode is active |

To view events: go to **Integration center &#8702; Integrations**, click an integration name, and open the **Events** tab.

## Deployment options

ThingsBoard Integration has two deployment options: embedded and remote. See details and architecture diagrams below.

### Embedded integrations

Embedded integrations run inside the main ThingsBoard server process (monolith deployment).

| Pros | Cons |
|---|---|
| Simple setup — just a few clicks in the UI | Consumes resources from the main ThingsBoard process |
| Minimal message delivery latency | Low isolation from core platform |
| | Cannot reach local MQTT brokers / OPC-UA servers when ThingsBoard runs in the cloud |

### Remote integrations

Remote integrations run as a separate process, typically deployed close to the data source (e.g. a local MQTT broker or OPC-UA server that has no external IP). The remote integration pulls data and streams it to the cloud-hosted ThingsBoard instance when internet is available.

| Pros | Cons |
|---|---|
| Connects to servers in a local network | Requires installing a separate package |
| Isolates integration from the main ThingsBoard process | |
| Buffers data locally when internet is unavailable | |

## Integrations vs IoT Gateway

| | Platform Integrations | <DocLink product={props.product} path="TODO">IoT Gateway</DocLink> |
|---|---|---|
| **Designed for** | Server-to-server communication | Local network deployments |
| **Scale** | High throughput, cluster-ready | Up to ~1,000 devices |
| **Custom decoders** | Modify converter scripts in real time via UI | Requires connector configuration update and gateway restart |

Both systems serve different use cases and complement each other.
