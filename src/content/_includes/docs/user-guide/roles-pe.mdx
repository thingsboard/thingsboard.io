A **Role** in ThingsBoard Professional Edition defines a set of permissions that determine what operations users can perform on platform resources.

Roles do not directly assign permissions to users. Instead, permissions are granted through **user groups** and linked using a **Group Permission Entity (GPE)**.

A role defines **what actions are allowed**.  
User groups define **who receives them**.

## Access control model

In ThingsBoard PE, access is granted through **Role assignments to User Groups**.

A role defines:
- **Resource type** (e.g., Device, Dashboard, Customer, Alarm)
- **Allowed operations** (e.g., Read, Create, Write, Delete, RPC Call)

Users do not receive permissions directly. Instead:

```
User → User Group → Role → (Optional) Entity Group
```

Depending on the role type:
- **Generic role** — applies recursively within a Tenant or Customer scope.
- **Group role** — applies only to a specific Entity Group.

**Permission scope**

Permissions may be:
- Scope-wide (Tenant / Customer level)
- Restricted to specific entity groups
- Combined across multiple roles (additive model)

If a user belongs to multiple user groups, permissions are aggregated.

**Enforcement**

All permissions are enforced at the **API and service layer**.  
Every secured operation is validated before execution.

Access is denied by default unless explicitly granted by an assigned role.

This model ensures consistent, predictable, and secure access control across the platform.

## Role types

ThingsBoard PE supports two role types:

| Role type | Scope model                            | Use case                      |
| --------- | -------------------------------------- | ----------------------------- |
| Generic   | Recursive within Tenant/Customer scope | Broad administrative access   |
| Group     | Specific entity group only             | Segmented and isolated access |

**When to use:**
- Use **Generic roles** for hierarchical, scope-wide access.
- Use **Group roles** for precise access to specific entity groups.

### Generic role

A **Generic role** defines a set of permissions that applies recursively to all entities within a selected scope: **Tenant**, **Customer**, or **Sub-customer** (including all descendants).

A Generic role is assigned to a **user group** via a **Group Permission Entity (GPE)**.

The GPE defines:
- **User group** — who receives the permissions
- **Scope** — Tenant or Customer level
- **Role** — the set of permissions

**Key characteristics**
- Scope depends on the assignment level (Tenant or Customer).
- Does not require entity groups.
- Applies to all entities within the defined scope.
- Supports hierarchical customer structures.

**When to use**
- Defining broad permission models.
- Granting tenant-wide administrative access.
- Implementing hierarchical customer-level access.
- Creating read-only analytical roles.
- Defining organization-wide access templates.

#### Creating a generic role

<Steps>
  1. Navigate to **Security &#8702; Roles**.
  2. Click **+ Add role**.
  3. Fill in the **Name** — unique role name
  4. **Role type** — select **Generic**
  5. Configure **Permissions**: **Resource** and **Operations**  
  (At least one permission entry must be specified).
  6. Click **Add**.
</Steps>

You can find a description of all available resource types <DocLink product={props.product} path='user-guide/roles/#permissions-table/' target="_blank">here</DocLink>.

#### Assigning a generic role

To apply a Generic role:

<Steps>
1. Open **Users &#8702; Groups** (Tenant level)  
or  
Open **Customers &#8702; Manage customer users &#8702; Groups** (Customer level).
2. Open group details.
3. Navigate to **Roles** tab.
4. Click **Add**.
5. Select:  
  &#8226;&#8194;**Role type**: *Generic*  
  &#8226;&#8194;Choose the created role
6. Click **Add**.
</Steps>

The role now applies recursively within the group’s scope.

### Group role

A **Group role** defines permissions for a specific **user group** over a specific **entity group**.

Unlike Generic roles, which apply recursively within a scope, Group roles restrict access strictly to explicitly selected entity groups.

Assignment is implemented via a **Group Permission Entity (GPE)** that links:
- User Group
- Entity Group
- Group Role (permissions)

This model enables precise, group-level access control without extending permissions beyond the targeted entities.

**Key characteristics**
- Requires an entity group.
- Applies only to selected entities.
- Enables strong segmentation and isolation.
- Suitable for controlled access within the same tenant.

**When to use**
- Restricting access to specific device groups.
- Implementing organizational segmentation (building, department, project, region).
- Supporting multiple teams managing different resource subsets.
- Enforcing fine-grained isolation within a shared tenant.

#### Creating a group role

<Steps>
  1. Navigate to **Security &#8702; Roles**.
  2. Click **+ Add role**.
  3. Fill in the **Name** — unique role name
  4. **Role type** — select **Group**
  5. Under **Permissions**, specify required **operations**.  
  (At least one permission entry must be specified).
  6. Click **Add**.
</Steps>

The Group role is now available for assignment to entity groups.

#### Assigning a group role

<Steps>
1. Navigate to the relevant entity type (e.g., **Devices &#8702; Groups**).
2. Open the target entity group details.
3. Go to the **Permissions** tab.
4. Click **Add**.
5. Select:  
  &#8226;&#8194;The created Group role  
  &#8226;&#8194;Owner  
  &#8226;&#8194;Target user group
6. Click **Add**.
</Steps>

The role now applies only to that entity group.

## Examples

### Example: Generic role scope

**Overview**

Demonstrates how Generic role scope changes depending on assignment level.

**Scenario**

**Users**
- Bob - member of Tenant Admins group (Tenant level).
- Alice - member of Customer Admins group (Customer level).

**Devices**
- Device A1 — owned by Tenant A
- Device B1 — owned by Customer B

<ImageGallery images={[
  {
    src: '/src/assets/images/role/generic-role-2.svg',
  },
]} />

**Objective**
- Grant **Bob** full access to all entities within **Tenant A**, including entities of **all customers and sub-customers**.
- Grant **Alice** full access only within **Customer B and its sub-customers**.

##### Step 1. Create the generic role

Create a role with:
- **Role type:** *Generic*
- **Permissions:**
  - **Resource:** *All*
  - **Operations:** *All*

The role is now ready for assignment.

##### Step 2 — Assign generic role at tenant level (Bob)

<Steps>
1. Navigate to the **Users &#8702; Groups**.
3. Open **Tenant Admins** group details.
4. Open the **Roles** tab.
5. Click **Add**.
6. Select:  
  &#8226;&#8194;**Role type:** *Generic*  
  &#8226;&#8194;Choose the created role
7. Click **Add**.
</Steps>

Bob can perform any operation on all entities that belong to **Tenant A**, including entities under Customer A, Customer B, and their sub-customers.

##### Step 3 — Assign generic role at customer level (Alice)

<Steps>
1. Go to **Customers**.
2. Click **Manage customer users** for Customer B.
3. Navigate to the Groups tab. 
3. Open **Customer Admins** group details.
5. Open the **Roles** tab.
6. Click **Add**.
7. Select:  
  &#8226;&#8194;**Role type:** *Generic*  
  &#8226;&#8194;Choose the same role
8. Click **Add**.
</Steps>

Alice can perform any operation only on entities that belong to **Customer B** and its sub-customers.

##### Access verification

- Sign in as the Tenant Administrator Bob. Bob sees *Device A1* and *Device B1*.
- Then sign in as the Customer User Alice. Alice sees *Device B1* only.

##### Result

- Both users have access to *Device B1*.
- Only Bob has access to *Device A1* because his Generic role is assigned at the **Tenant** level.

Demonstrates segmented access using Group roles.

**Scenario**

**User groups**

  &#8226;&#8194;**User group:** *Building A Admins*

##### Step 3 — Assign group role to "Building B" device group

Repeat the same steps for **Building B**:

<Steps>

  3. Click **+** (**Add**).
  4. Select:  
  &#8226;&#8194;The same **Group role**  
  &#8226;&#8194;**Owner**  
  &#8226;&#8194;**User group:** *Building B Admins*
  5. Click **Add**.
</Steps>

Permission is assigned.

##### Access verification

Login as **Alice** → She sees only:
- Device group **Building A**
- **Device A1**

Login as **Bob** → He sees only:
- Device group **Building B**
- **Device B1**

##### Result

Users cannot access devices outside their assigned entity group.

### Example: Smart buildings — separate user groups per facility

**Overview**

This example demonstrates how to implement structured access control for a smart building solution using **Generic** and **Group** roles.

The solution manages multiple commercial buildings with different user types:
- Supervisors (global monitoring)
- Facility Managers (building-level administration)
- End Users (read-only building access)

The goal is to ensure:
- Cross-building read-only visibility for supervisors
- Full management rights per facility
- Strict isolation between buildings
- Read-only, limited UI access for end users

**Scenario**

**Entities**
- Multiple buildings (modeled as Customers)
- Devices (HVAC, electricity meters, sensors)
- Dashboards
- User groups

**User types**
- Supervisors
- Facility Managers
- End Users

**Objective**
- Supervisors: Read-only access to all buildings + ability to manage their own dashboards.
- Facility Managers: Full administrative control within their building.
- End Users: Read-only access to dashboards within their building only.

#### Supervisors configuration

##### Step 1. Create dashboard group

<Steps>
1. Navigate to **Dashboards &#8702; Groups**.
2. Click **Add entity group**.
3. Create group: **Supervisor Dashboards**.
</Steps>

##### Step 2. Create roles

###### Step 2.1 Generic role: "All Entities Read-only"

Create a role:
<Steps>
1. Navigate to **Security &#8702; Roles**
2. Click **Add Role**.
3. **Name:** *All Entities Read-only*  
3. **Role type:** *Generic*
4. **Permissions:**  
  &#8226;&#8194;**Resource:** *All*  
  &#8226;&#8194;**Operations:** *Read*, *Read Attributes*, *Read Telemetry*.
6. Click **Add**.
</Steps>

Purpose: Read-only access to all entities.

###### Step 2.1 Group role: "Entity Group Administrator"

Create another role:
- **Name:** *Entity Group Administrator*
- **Role type**: *Group*
- **Permissions:**
  - **Operations**: *All*
- **Save** the role.

Purpose: Full control over specific dashboard group.

##### Step 3. Create supervisors user group

<Steps>
1. Navigate to **Users &#8702; Groups** 
2. Click **Add entity group**.
3. Create group: **Supervisors**.
4. Open group details &#8702; **Roles** tab.
5. Assign:  
  &#8226;&#8194;**1. Generic role:** *All Entities Read-only*.  
  &#8226;&#8194;**2. Group role:** *Entity Group Administrator* for:  
  &#8194;&#8194;&#8226;&#8194;**Owner:** *Tenant*  
  &#8194;&#8194;&#8226;&#8194;**Type:** *Dashboard*  
  &#8194;&#8194;&#8226;&#8194;**Entity group:** *Supervisor Dashboards*  
6. Click **Add**.
</Steps>

##### Result

Supervisors:
- Can view all entities across all buildings.
- Can manage dashboards only within Supervisor Dashboards.
- Cannot modify other system entities.  

#### Facility manager configuration

Each building is modeled as a separate Customer.

##### Step 1. Create customer

<Steps>
1. Navigate to **Customers**
2. Click **Add Customer**.
3. **Title**: *Building A*.
4. Click **Add**.  
</Steps>

##### Step 2. Add facility manager

Create a user - facility manager:
<Steps>
1. Click **Manage customer users** for *Building A*.
2. Use **default group**: *Customer Administrators*.
3. Click **Add user**
4. Enter **email:** *janesmith@thingsboard.io*
5. Click **Add**.
6. Copy and save the *User activation link*.
7. Click **OK**.  
</Steps>

**Result**

Facility Manager:
- Can provision devices.
- Manage dashboards.
- Configure thresholds.
- Manage users within that building.
- Has no access to other buildings.

#### End users configuration

##### Step 1. Create dashboard

Logged in as Facility Manager:

<Steps>
1. Create dashboard: *End User Dashboard*.
2. Add required widgets.
3. Click **Save**.
</Steps>

##### Step 2. Create read-only user

<Steps>
1. Navigate to **Users &#8702; Customer Users**
2. Click **Add**.
3. Add end user (e.g., bob@thingsboard.io).
4. Edit user:  
  &#8226;&#8194;Set **Default dashboard** to *End User Dashboard*  
  &#8226;&#8194;Enable **Always fullscreen**  
</Steps>

#### Verification

##### Supervisors
- Can view telemetry from all buildings.
- Can edit dashboards only in Supervisor Dashboards group.
- Cannot modify devices.

##### Facility Manager (Building A)
- Can manage devices and dashboards for Building A.
- Cannot access other buildings.

##### End User (Building A)
- Sees only assigned dashboard.
- Dashboard opens in full screen.
- No access to admin panel.
- Read-only browsing of data.

#### Result

This configuration provides:
- Hierarchical access control.
- Cross-building monitoring for supervisors.
- Per-building administration.
- Strict isolation between facilities.
- Secure read-only access for end users.

The solution combines:
- **Generic roles** for scope-wide visibility.
- **Group roles** for controlled dashboard management.
- **Customer hierarchy** for facility isolation.
