ThingsBoard Agent executes every application action remotely: **restart**, **update**, **upgrade**, and **delete**. Each action runs on a single <DocLink product={props.product} path='user-guide/agents/applications'>application</DocLink> or fleet-wide as a <DocLink product={props.product} path='user-guide/agents/bulk-actions'>bulk action</DocLink>. Actions that change an application follow the step sequence defined by the application <DocLink product={props.product} path='user-guide/agents/application-profiles#templates'>template</DocLink>, support volume backups, and roll back automatically when a step fails.

## Restart an application

A **restart** re-runs the application's start steps, restarting the containers in dependency order; the existing data and configuration are preserved. Run it with the **Restart** action on the <DocLink product={props.product} path='user-guide/agents/applications#manage-an-application'>application</DocLink>, or fleet-wide with a <DocLink product={props.product} path='user-guide/agents/bulk-actions'>bulk restart</DocLink>.

## Update an application

An **update** applies a changed Docker Compose configuration without moving the application to a new version: the agent recreates the project's containers with the new definition. An update never runs the ThingsBoard database upgrade scripts — the schema migration that carries Edge or Gateway data to a new product version — so to move the application to a new Edge or Gateway version, use an upgrade. That is unrelated to the [PostgreSQL major version migration](#postgresql-major-version-migration), which the agent still performs automatically during an update. Run it with the **Update** action on the <DocLink product={props.product} path='user-guide/agents/applications#manage-an-application'>application</DocLink>, or fleet-wide with a <DocLink product={props.product} path='user-guide/agents/bulk-actions'>bulk update</DocLink>.

For an application with an assigned profile, the Compose configuration is managed by the profile and is read-only in the update dialog: to change it, edit the profile itself with the **Update profile** shortcut. By default, the update re-fetches the profile's configuration for the application's current template version and re-applies the credential values managed by the related entity; a profile that moved to a newer template version is never applied — that requires an upgrade. Select **Skip refetch profile's configuration** to keep the current Compose untouched and apply only the credentials: use it for credential rotation or a plain image re-pull.

## Upgrade an application

An **upgrade** moves the application to a new template version, like Edge 4.2 to Edge 4.3: it is the only action that runs the ThingsBoard database upgrade scripts and advances the application's template version. When the assigned <DocLink product={props.product} path='user-guide/agents/application-profiles'>application profile</DocLink> moves to a newer template version than the application, ThingsBoard marks the application with **Upgrade available** and enables the **Upgrade** action.

<Steps>
  <ol>
    <li>
      Open the application and click **Upgrade**, on the details page or with the row action in the **Applications** table. The **Upgrade Application** wizard opens. If the assigned profile is still on the application's current template version, the wizard offers an **Upgrade Profile** step first.
    </li>
    <li>
      On the **Review & Customize** step, select the volumes to back up before the upgrade and choose whether the images are re-pulled. There is no Docker Compose editor here: the upgrade applies the profile's configuration and injects the credentials of the related entity.
    </li>
    <li>
      On the **Save Application** step, check that the summary matches what you intend and click **Upgrade**.
    </li>
    <li>
      Follow every upgrade step in the **Event progress** dialog: it opens automatically, and you can reopen it later from the **Events** tab.
    </li>
  </ol>
</Steps>

<Aside type="tip">
Back up the volumes that hold your application data. Backups allow automatic rollback if the upgrade fails. After a successful upgrade, the agent keeps the latest backup of each volume and removes older ones.
</Aside>

<Aside type="caution" title="Update won't apply a new template version">
When the profile is ahead, the application details show the note **Profile is on template version 4.3.1.1EDGEPE. Update won't apply it — use Upgrade**. ThingsBoard blocks moving to the new version through **Update**: the ThingsBoard database upgrade scripts run only during an upgrade, and the application's template version would stay stale, which breaks the following upgrade cycles. Use **Update** only when you don't want an upgrade but need to re-fetch the images: the application keeps its current Compose configuration, and only the credential values are re-applied.
</Aside>

## Delete an application

**Delete** stops and removes the application's containers and networks from the host. The confirmation dialog lists the application volumes: they stay on the host with all their data unless you select **Also remove volumes**. Run it with the **Delete** action on the application, or fleet-wide with a <DocLink product={props.product} path='user-guide/agents/bulk-actions'>bulk delete</DocLink>.

<Aside type="danger">
Volume removal is label-based, not configuration-based: it permanently destroys **every** volume that belongs to the project — the volumes listed in the dialog, volumes left behind by earlier configurations, and the retained upgrade backups. External volumes and bind-mounted host directories are not touched.
</Aside>

## Automatic rollback

Before an upgrade or update starts, the agent snapshots the current state of the application. If any step fails:

1. The agent restores the backed-up volumes.
2. The agent recreates the containers from the snapshot, returning the application to its previous version.
3. The event is marked as failed with the error reported by the failing step.

Rollback is idempotent: if the agent restarts mid-rollback, it resumes without repeating completed work.

## PostgreSQL major version migration

A PostgreSQL data directory is incompatible across major versions. When an update or upgrade moves a PostgreSQL service of any application to a new major version, the agent migrates the database automatically: it detects the version change from the data volume, backs the volume up, dumps the database with the old version's image, and restores it with the new one. The migration is crash-resumable and rolls back with the rest of the operation on failure. It covers services that run the official `postgres` images.

The agent refuses to migrate and fails the operation with an actionable error when the change is a downgrade or when the database data directory is bind-mounted from the host instead of a named volume.

## Fleet-wide actions

Every action runs fleet-wide as a <DocLink product={props.product} path='user-guide/agents/bulk-actions'>bulk action</DocLink>: one bulk restart, update, upgrade, or delete targets every application that shares an application profile across many agents. Assign the application profile to several <DocLink product={props.product} path='user-guide/agents/agent-profiles'>agent profiles</DocLink> to stage an upgrade rollout: upgrade the staging fleet first, verify the result and adjust the configuration, then upgrade production.
