Tuya Integration connects ThingsBoard to the <a href="https://iot.tuya.com/" target="_blank" rel="noopener noreferrer nofollow">**Tuya IoT Platform**</a> (Tuya Cloud). It subscribes to the Tuya **Message Service** and receives status reports from devices added in the **Smart Life** or **Tuya Smart** app. An **uplink data converter** turns each report into telemetry and attributes. ThingsBoard can also send **downlink** commands to the devices through the Tuya OpenAPI.

Use Tuya Integration when:
- Your devices are Tuya-based and already connected to Tuya Cloud through the Smart Life or Tuya Smart app.
- You want to monitor them in ThingsBoard dashboards and process their data in the Rule Engine.
- You need to control them from ThingsBoard, for example switch a smart plug on or off.

This guide uses a Tuya **Smart Plug**. A <a href="https://developer.tuya.com/en/docs/iot/manage-virtual-devices?id=Ka4725tiyfhg0" target="_blank" rel="noopener noreferrer nofollow"><strong>virtual Tuya device</strong></a> works for testing too.

## Architecture

1. **Receive data.** The device reports its status to Tuya Cloud over Wi-Fi. The integration subscribes to the Message Service (an Apache Pulsar queue) with your cloud project credentials and receives each status report.
2. **Decode the payload.** The integration decrypts the report and passes it to the uplink converter, which returns the device name, telemetry, and attributes.
3. **Process the message.** ThingsBoard processes the converted data through the Rule Engine. If **Allow create devices or assets** is enabled, ThingsBoard creates the device on its first report.
4. **Send downlink data (optional).** The Rule Engine passes an RPC message to the integration. The downlink converter encodes it as a Tuya command, and the integration sends it to the Tuya OpenAPI, which delivers it to the device.

### Configure Messaging Rules

A **messaging rule** defines which messages Tuya pushes. Tuya keeps separate rules and subscriptions for two environments:

| Tuya environment | Devices | Integration **Environment** |
|------------------|---------|-----------------------------|
| **Production** | Real (physical) devices. | **PROD** |
| **Test** | Only devices you add as test devices, for example virtual devices. | **TEST** |

The rule must be enabled in the environment where your device reports, and the integration must use the same environment. Otherwise the integration connects, but no uplinks arrive.

<Steps>
1. In the cloud project, open **Message Service &#8702; Messaging Rules**.
2. Select **Production Environment** for a real device, or **Test Environment** for a test device.
3. Turn on the rule. While it is off, the tab shows *"The rules for the production environment are disabled, so all messages will not be pushed"*.
4. Click **Modify Messaging Rules**, make sure **BizCode** includes **`statusReport` (Status Report)**, and save. Optionally add `online` and `offline`.
5. Open **Subscription Management**, select the same environment, and check that the subscription `<Access ID>-sub` has **Status** = **Good**.
</Steps>

## Set Up Tuya Integration

Create the uplink converter, assign it to a new Tuya integration, and trigger a status report from the device.

### Create the Uplink Data Converter

The uplink converter receives each status report as JSON, resolves the device by its Tuya ID, and returns its telemetry. Tuya Integration uses the **Generic** converter: you write the decoder in TBEL or JavaScript. For converter types and the full decoder reference, see <DocLink product={props.product} path="user-guide/integrations/uplink-data-converter/#converter-types" target="_blank">Uplink data converter</DocLink>.

<Steps>
1. Go to **Integrations &#8702; Data converters** and click **+ Add data converter &#8702; Create new converter**.
2. **Converter type** — keep **Uplink**.
3. **Integration type** — select **Tuya**.
4. **Name** — enter a name, for example `Tuya Uplink Converter`.
5. **Main decoding configuration** — the editor opens with the generic default decoder. Replace it with the decoder below. It reads the `code`–`value` pairs from the `status` array and scales the smart plug readings: `cur_voltage` and `cur_power` ÷ 10, `cur_current` ÷ 100. The editor opens in TBEL; use the **TBEL / JS** toggle to switch to JavaScript.
   <Aside type="tip" title="TBEL">
     Use <DocLink product={props.product} path="user-guide/tbel" target="_blank">TBEL</DocLink> for converter scripts — it runs much faster than JavaScript inside ThingsBoard.
   </Aside>
   <Tabs>
     <TabItem label="TBEL (Recommended)">
       ```js maxLines=15 collapsible
       /** Decoder **/

       // Parse the incoming payload (byte array) into a JSON object.
       // decodeToJson is a built-in TBEL helper — no need to declare it.
       var data = decodeToJson(payload);
       // Also accept the integration event format { metadata, data },
       // for example when you test with a payload copied from the Events tab.
       if (data.?data != null) {
         data = data.data;
       }

       // Resolve the device name.
       // Try bizData.devId first (present in some Tuya message types);
       // fall back to devId otherwise. The .? operator safely returns null
       // if an intermediate field is missing (won't throw an error).
       var deviceName = data.?bizData.?devId != null ? data.?bizData.?devId : data.?devId;

       // Fixed device type — used to create the Device Profile in ThingsBoard.
       var deviceType = 'Tuya device';

       // Array that will hold the telemetry (key-value pairs).
       var telemetry = [];

       // Tuya's main data arrives in the status array. Make sure it exists.
       if (data.status != null) {
         // Iterate over each element of the status array.
         for (var i = 0; i < data.status.length; i++) {
           var res = {};                       // temp object for a single data point
           var code = data.status[i].code;     // parameter name, e.g. "cur_voltage"
           var value = data.status[i].value;   // raw value from the device

           // Tuya sends some values as integers without a decimal point.
           // Divide voltage and power by 10 to get real units (V, W).
           if (code == "cur_voltage" || code == "cur_power") {
             value = data.status[i].value / 10;
           // Divide current by 100 (to get A).
           } else if (code == "cur_current") {
             value = data.status[i].value / 100;
           }
           res[code] = value;   // build a pair, e.g. { "cur_voltage": 231 }
           telemetry.push(res);  // add it to the telemetry array
         }
       } else {
         // If there is no status array, return the payload as-is (fallback).
         telemetry = data;
       }

       // Build the result in the format ThingsBoard expects.
       var result = {
         deviceName: deviceName,   // device is created/matched by this name
         deviceType: deviceType,   // device profile
         attributes: {},           // attributes (empty here)
         telemetry: telemetry      // time-series data
       };

       /** Helper functions 'decodeToString' and 'decodeToJson' are already built-in **/

       return result;
       ```
     </TabItem>
     <TabItem label="JavaScript">
       ```js maxLines=15 collapsible
       /** Decoder **/

       // In JS the helpers are NOT built-in, so we declare them ourselves.
       // Convert a byte array into a string.
       function decodeToString(payload) {
         return String.fromCharCode.apply(String, payload);
       }

       // Convert a byte array into JSON: first to a string, then parse it.
       function decodeToJson(payload) {
         var str = decodeToString(payload);
         var data = JSON.parse(str);
         return data;
       }

       // Parse the incoming payload into a JSON object.
       var data = decodeToJson(payload);
       // Also accept the integration event format { metadata, data },
       // for example when you test with a payload copied from the Events tab.
       if (data.data) {
         data = data.data;
       }

       // Device name: use bizData.devId if present, otherwise devId.
       // JS has no .? operator, so we check existence with && .
       var deviceName = (data.bizData && data.bizData.devId) ? data.bizData.devId : data.devId;

       // Fixed device type (profile).
       var deviceType = 'Tuya device';

       // Array for telemetry.
       var telemetry = [];

       // Tuya data lives in the status array.
       if (data.status != null) {
         for (var i = 0; i < data.status.length; i++) {
           var res = {};                       // a single data point
           var code = data.status[i].code;     // parameter name
           var value = data.status[i].value;   // raw value

           // Unit scaling for the Smart Plug.
           if (code == "cur_voltage" || code == "cur_power") {
             value = data.status[i].value / 10;   // voltage/power ÷10
           } else if (code == "cur_current") {
             value = data.status[i].value / 100;  // current ÷100
           }

           res[code] = value;    // e.g. { "cur_power": 15 }
           telemetry.push(res);   // add to the array
         }
       } else {
         telemetry = data;  // fallback if status is missing
       }

       // Result for ThingsBoard.
       var result = {
         deviceName: deviceName,
         deviceType: deviceType,
         attributes: {},
         telemetry: telemetry
       };

       return result;
       ```
     </TabItem>
   </Tabs>

   **To adapt:**
   - **Other data points** — add or change the `code` branches. Codes without a branch are stored as received.
   - **Other scaling** — change the divisors. For example, some models report `add_ele` (energy, kWh) that needs ÷ 100 or ÷ 1000.
   - **Friendly key names** — map codes explicitly, for example `cur_voltage` to `voltage`.
   - **Device timestamp** — each `status` entry carries `t` (ms). Return `{ ts: data.status[i].t, values: res }` instead of `res` to store it instead of the server time.
   - **Device properties** — add them to `attributes`, for example `productKey: data.productKey`.
6. Click **Test decoder function** and check the result (see **[Test the Decoder](#test-the-decoder)**).
7. Click **Add**.
</Steps>

<Aside type="caution" title="Keep the Tuya device ID as the device name">
  The integration sends downlink commands to the Tuya device whose ID equals the ThingsBoard device name. Keep `deviceName` exactly the Tuya `devId`, with no prefix or spaces. A space causes `Illegal character in path`; any other change targets the wrong device. For a readable name, set the device **Label** in ThingsBoard.
</Aside>

<h4>Decoder Inputs</h4>

The decoder signature is `function decoder(payload, metadata): object | object[]`.

| Variable | Type | Content |
|----------|------|---------|
| `payload` | byte array | The decrypted status report (JSON). Parse it with `decodeToJson(payload)`. |
| `metadata` | `{[key: string]: string}` | Message Service envelope: `topic`, `t` (send time, ms), `pv` (protocol version), `protocol`, and `sign`. Also `integrationName` and the key–value pairs from the integration's **Metadata** field. |

Status report fields:

| Field | Content |
|-------|---------|
| `devId` | Tuya device ID, for example `bfac3c40adca459c9chaar`. |
| `productKey` | Product key of the device model, for example `iq9hwd2bjsdgqiby`. |
| `dataId` | Unique ID of the report. |
| `status` | Data points. Each entry has `code`, `value`, and `t` (ms). An entry can also carry a numeric alias key, for example `"1": true`; the decoder ignores it. |

The integration's **Events** tab shows each message as `{ "metadata": {...}, "data": {...} }`. The decoder receives only `data` as `payload`.

<Aside type="note">
  Data point codes (`switch_1`, `cur_power`, `cur_voltage`, …) and their scaling depend on the device model. To see the codes your device reports, open **Devices**, select the device in the Tuya IoT Platform, and go to **Device Debugging**.
</Aside>

### Create the Integration

<Steps>
1. Go to **Integrations &#8702; Integrations** and click **+ Add integration**.
2. **Basic settings:**
   - **Integration type** — select **Tuya**.
   - **Name** — enter a name, for example `Tuya integration`.
   - **Enable integration** and **Allow create devices or assets** — keep both on, so the device is created on its first report.
   - Click **Next**.
3. **Uplink data converter:**
   - Click **Select existing** and choose `Tuya Uplink Converter`.
   - Alternatively, click **Create new** to write a decoder here.
   - Click **Next**.
4. **Downlink data converter:**
   - Click **Skip**. Add a downlink converter later if you need to **[send commands to devices](#configure-downlink)**.
5. **Connection:**
   - **Region** — select the data center of your cloud project.
   - **Environment** — select **PROD** for a real device or **TEST** for a test device.
   - **Access Id** and **Access Key** — paste the **Access ID/Client ID** and **Access Secret/Client Secret** from the **[cloud project](#create-a-cloud-project)**.
   - See **[Connection Settings](#connection-settings)** for details.
6. Click **Add**.
</Steps>

#### Connection Settings

| Parameter | Description |
|-----------|-------------|
| **Region** | Data center of the cloud project: **China** (default), **United States** (Western America), **Europe** (Central Europe), or **India**. Selects the Message Service and OpenAPI endpoints, for example `mqe.tuyaeu.com` and `openapi.tuyaeu.com` for **Europe**. |
| **Environment** | **PROD** (default) or **TEST**. **PROD** reads the production topic `<Access Id>/out/event`; **TEST** reads `<Access Id>/out/event-test`. Must match the environment of the **[messaging rule](#configure-messaging-rules)**. |
| **Access Id** | **Access ID/Client ID** of the cloud project. The integration subscribes as `<Access Id>-sub`. |
| **Access Key** | **Access Secret/Client Secret** of the cloud project. Signs OpenAPI requests and decrypts messages. Keep it secret. |
| **Execute remotely** | Runs the integration as a separate process outside the ThingsBoard cluster. ThingsBoard generates an **Integration key** and **Integration secret** for it. See <DocLink product={props.product} path="user-guide/integrations/remote" target="_blank">Remote Integration</DocLink>. |
| **Description** | In **Advanced settings**. Free-text description. |
| **Metadata** | In **Advanced settings**. Key–value pairs added to the `metadata` of every message from this integration. |

If the connection fails, the integration retries every 60 seconds and logs a **CONNECT** event with the error on its **Events** tab.

### Send a Test Uplink

### Verify the Result

- **Converter events** — open `Tuya Uplink Converter` in **Integrations &#8702; Data converters** and click the **Events** tab. **In** shows the report, **Out** shows the decoded result, and **Metadata** shows the Message Service envelope.

## Configure Downlink

ThingsBoard sends a command to the device when the Rule Engine routes an RPC request to the integration — for example, when a dashboard switch is toggled. The integration calls the Tuya OpenAPI of the selected region:

1. It takes the Tuya device ID from `deviceId` in the encoder's output `metadata`, or from `deviceName` if `deviceId` is not set.
2. It sends `data` to `POST /v1.0/iot-03/devices/{deviceId}/commands` as `{ "commands": [...] }`.

The encoder's `data` must be one of:

| `data` | Sent to Tuya |
|--------|--------------|
| An object with `code` and `value`, for example `{"code": "switch_1", "value": true}` | `{"commands": [{"code": "switch_1", "value": true}]}` |
| An array of such objects | `{"commands": [...]}` with every command |
| An object with `method` set to a query name: `getStatus`, `getFunctions`, `getSpecification`, `getLogs`, `getReportLogs`, or `getCategory` | A `GET` request to the matching OpenAPI endpoint. The response goes to the uplink converter as `payload`, with `msgType` = `DownlinkResponse` and `deviceId` in `metadata`. |

Any other `data`, including `{"commands": [...]}`, fails with *"Downlink message format is not correct, downlink message should contain one of the following: code field, service RPC method, commands array!"*.

The downlink converter turns a <DocLink product={props.product} path="user-guide/rule-engine" target="_blank">Rule Engine</DocLink> message into a Tuya command. For the full encoder reference, see <DocLink product={props.product} path="user-guide/integrations/downlink-data-converter" target="_blank">Downlink data converter</DocLink>.

### Create and Assign the Downlink Converter

The encoder below uses the RPC method as the Tuya command `code` and the RPC params as its `value`. It converts `"true"` and `"false"` to booleans, because RPC params arrive as strings. It sets `deviceId` to the device name, which is the Tuya `devId`.

<Steps>
1. Open the integration in **Integrations &#8702; Integrations** and click **Toggle edit mode** (pencil icon).
2. In the **Downlink data converter** field, click **Create new**. The **Downlink** converter type and **Tuya** integration type are preselected.
3. Enter a name, for example `Tuya Downlink Converter`.
4. In **Main encoding configuration**, replace the default encoder with the encoder below.
   <Tabs>
     <TabItem label="TBEL (Recommended)">
       ```js maxLines=20 collapsible
       /** Encoder **/

       // The command object we will send to the Tuya device.
       var command = {};

       // msg.method — the RPC method name from ThingsBoard. Becomes the Tuya
       // command code, e.g. "switch_1", "bright_value", etc.
       command["code"] = msg.method;

       // msg.params — the command value.
       // If it is the string "true"/"false", convert it to a real boolean
       // (needed for switches, e.g. turning the plug on/off).
       if (msg.params == "false" || msg.params == "true") {
         command["value"] = Boolean.valueOf(msg.params);
       } else {
       // Otherwise pass it as-is (number, string, e.g. brightness level).
         command["value"] = msg.params;
       }

       // Build the result for the integration.
       var result = {
         contentType: "JSON",                  // command body is JSON
         data: JSON.stringify(command),        // serialize { code, value } to a string
         metadata: {
           deviceId: metadata.deviceName     // which device to send the command to
         }
       };

       return result;
       ```
     </TabItem>
     <TabItem label="JavaScript">
       ```js maxLines=20 collapsible
       /** Encoder **/

       // Build the command object.
       const command = {
         // Tuya command code = RPC method name from ThingsBoard.
         code: msg.method,
         // Command value:
         // if msg.params is "true"/"false", convert it to a boolean (true/false),
         // otherwise keep the value as-is.
         value:
           msg.params === "false" || msg.params === "true"
             ? msg.params === "true"
             : msg.params
       };

       // Result to send through the integration.
       const result = {
         contentType: "JSON",                // body is JSON
         data: JSON.stringify(command),      // serialize { code, value }
         metadata: {
           deviceId: metadata.deviceName   // target device
         }
       };

       return result;
       ```
     </TabItem>
   </Tabs>
5. To record downlink events, click the debug icon next to the name, select **All messages**, and click **Apply**.
6. Click **Add**, then **Apply changes**.
</Steps>

<Aside type="note">
  The command `code` must be a **writable** data point of your device. Some plugs use `switch` instead of `switch_1`. Check the writable codes in **Device Debugging** in the Tuya IoT Platform.
</Aside>

## Troubleshooting

| Symptom | Cause | Fix |
|---------|-------|-----|
| **CONNECT** event with status **FAILURE** | Wrong **Access Id**, **Access Key**, or **Region**. | Copy the credentials from the project **Overview** page again. Select the **Region** that matches the project data center. |
| Integration connects, but no uplinks arrive | The messaging rule is off, or enabled in the other environment. | Enable the rule with `statusReport` in the environment that matches **Environment**. See **[Configure Messaging Rules](#configure-messaging-rules)**. |
| Same, with the rule enabled | The device is not linked to the cloud project. | Link the app account. See **[Link Your Tuya App Account](#link-your-tuya-app-account)**. |
| Subscription **Status** is not **Good** | The messaging rule was disabled or changed. | Enable the rule for the matching environment and check the subscription again. |
| Device not created | **Allow create devices or assets** is off, or `deviceName` is empty. | Turn the option on. Check **Out** in the converter events for `deviceName`. |
| Only `switch_1` arrives | The plug has no load. | Connect a load and wait for the next report. |
| Downlink fails with *"Downlink message format is not correct…"* | `data` has neither `code`, a query `method`, nor an array of commands. | Check **Out** in the downlink converter events. Make sure the RPC method reaches `msg.method`. |
| Downlink fails with *"Device identifier not found in metadata"* | The encoder's output `metadata` has neither `deviceId` nor `deviceName`. | Set `deviceId` in the encoder's `metadata`. |
| Downlink fails with `Illegal character in path` | The device name is not the raw Tuya `devId`. | Rename the device to its `devId`. Use **Label** for a readable name. |
| Downlink fails with *"Tuya integration response error code…"* | Tuya Cloud rejected the command, for example the `code` is not writable. | Check the writable codes in **Device Debugging** in the Tuya IoT Platform. |
| No downlink event | The rule chain does not reach the **integration downlink** node. | Connect the node with the **RPC Request to Device** relation. |

To read debug events, open the integration or converter, click **Events**, and select an event: **In** is the received data, **Out** is the converter result, and **Error** holds the error text.
