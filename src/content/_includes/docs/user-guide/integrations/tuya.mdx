Tuya Integration connects ThingsBoard to the <a href="https://iot.tuya.com/" target="_blank" rel="noopener noreferrer nofollow">**Tuya IoT Platform**</a> (Tuya Cloud). It subscribes to the Tuya **Message Service** and receives status reports from devices added in the **Smart Life** or **Tuya Smart** app. An **uplink data converter** turns each report into telemetry and attributes. ThingsBoard can also send **downlink** commands to the devices through the Tuya OpenAPI.

Use Tuya Integration when:
- Your devices are Tuya-based and already connected to Tuya Cloud through the Smart Life or Tuya Smart app.
- You want to monitor them in ThingsBoard dashboards and process their data in the Rule Engine.
- You need to control them from ThingsBoard, for example switch a smart plug on or off.

This guide uses a Tuya **Smart Plug**. A <a href="https://developer.tuya.com/en/docs/iot/manage-virtual-devices?id=Ka4725tiyfhg0" target="_blank" rel="noopener noreferrer nofollow"><strong>virtual Tuya device</strong></a> works for testing too.

## Architecture

1. **Receive data.** The device reports its status to Tuya Cloud over Wi-Fi. The integration subscribes to the Message Service (an Apache Pulsar queue) with your cloud project credentials and receives each status report.
2. **Decode the payload.** The integration decrypts the report and passes it to the uplink converter, which returns the device name, telemetry, and attributes.
3. **Process the message.** ThingsBoard processes the converted data through the Rule Engine. If **Allow create devices or assets** is enabled, ThingsBoard creates the device on its first report.
4. **Send downlink data (optional).** The Rule Engine passes an RPC message to the integration. The downlink converter encodes it as a Tuya command, and the integration sends it to the Tuya OpenAPI, which delivers it to the device.

### Configure Messaging Rules

A **messaging rule** defines which messages Tuya pushes. Tuya keeps separate rules and subscriptions for two environments:

| Tuya environment | Devices | Integration **Environment** |
|------------------|---------|-----------------------------|
| **Production** | Real (physical) devices. | **PROD** |
| **Test** | Only devices you add as test devices, for example virtual devices. | **TEST** |

The rule must be enabled in the environment where your device reports, and the integration must use the same environment. Otherwise the integration connects, but no uplinks arrive.

<Steps>
1. In the cloud project, open **Message Service &#8702; Messaging Rules** and select **Production Environment** for a real device, or **Test Environment** for a test device.
2. If the tab shows *"No messaging rules apply to the production environment, no messages will be pushed"*, click **Create Messaging Rules**, then **Add Message Filtering Rule**. If a rule already exists, click **Modify Messaging Rules**.
3. Set the rule to **BizCode (Message Type)** **In** **`statusReport` (Status Report)**. Optionally add **`online`** and **`offline`**: the decoder in this guide stores them as the `online` attribute. Click **Release Rule**, then **OK**.
4. Turn on the rule and confirm with **OK**. The tab then shows *"The rules for the production environment are in effect … The corresponding message topic is: clientId/out/event"*. While the rule is off, it shows *"The rules for the production environment are disabled, so all messages will not be pushed"*.
5. Open **Subscription Management**, select the same environment, and check that the subscription `<Access ID>-sub` has **Status** = **Good**. **Consumers** shows `1` once the integration is connected.
</Steps>

## Set Up Tuya Integration

Create the uplink converter, assign it to a new Tuya integration, and trigger a status report from the device.

### Create the Uplink Data Converter

The uplink converter receives each status report as JSON, resolves the device by its Tuya ID, and returns its telemetry. Tuya Integration uses the **Generic** converter: you write the decoder in TBEL or JavaScript. For converter types and the full decoder reference, see <DocLink product={props.product} path="user-guide/integrations/uplink-data-converter/#converter-types" target="_blank">Uplink data converter</DocLink>.

<Steps>
1. Go to **Integrations &#8702; Data converters** and click **+ Add data converter &#8702; Create new converter**.
2. **Converter type** — keep **Uplink**.
3. **Integration type** — select **Tuya**.
4. **Name** — enter a name, for example `Tuya Uplink Converter`.
5. **Main decoding configuration** — the editor opens with the default Tuya decoder, which is the decoder below. Keep it, or write your own. It reads the `code`–`value` pairs from the `status` array and scales the smart plug readings: `cur_voltage` (V) and `cur_power` (W) ÷ 10, `cur_current` (reported in mA) ÷ 1000 to get A. Each value keeps the device time `t` of its report. It stores `online` and `offline` messages as the `online` attribute and skips other messages, so they do not create or update a device. If the message has no Tuya device ID, it stops with the error `Tuya message has no devId`. The editor opens in TBEL; use the **TBEL / JS** toggle to switch to JavaScript.
   <Aside type="tip" title="TBEL">
     Use <DocLink product={props.product} path="user-guide/tbel" target="_blank">TBEL</DocLink> for converter scripts — it runs much faster than JavaScript inside ThingsBoard.
   </Aside>
   <Tabs>
     <TabItem label="TBEL (Recommended)">
       ```js maxLines=15 collapsible
       /** Decoder **/

       // Tuya Message Service pushes each device report as JSON.
       // This example handles status reports (statusReport) and online/offline messages
       // of a Tuya smart plug. Other messages are skipped.

       // Parse the incoming payload (byte array) into a JSON object.
       var data = decodeToJson(payload);

       // Use the Tuya device ID as the device name.
       // Keep it unchanged: the downlink sends commands to the Tuya device with this ID.
       var deviceName = data.devId;
       if (deviceName == null || deviceName.trim().isEmpty()) {
           raiseError("Tuya message has no devId");
       }

       // Fixed device type, used as the device profile name.
       var deviceType = "Tuya device";

       if (data.status != null) {
           // Status report: each status entry is a data point with code, value and time t (ms).
           var telemetry = [];
           for (var i = 0; i < data.status.length; i++) {
               var code = data.status[i].code;
               var value = data.status[i].value;

               // The smart plug reports integers: voltage (V) and power (W) multiplied by 10,
               // current in mA. Convert them to V, W and A.
               if (code == "cur_voltage" || code == "cur_power") {
                   value = value / 10;
               } else if (code == "cur_current") {
                   value = value / 1000;
               }

               var values = {};
               values[code] = value;
               // Store the value with the device time, or with the server time if t is missing.
               if (data.status[i].t != null) {
                   telemetry.push({ts: data.status[i].t, values: values});
               } else {
                   telemetry.push(values);
               }
           }
           return {
               deviceName: deviceName,
               deviceType: deviceType,
               attributes: {},
               telemetry: telemetry
           };
       }

       if (data.bizCode == "online" || data.bizCode == "offline") {
           // Online/offline message: store the connection state as an attribute.
           var noTelemetry = [];
           return {
               deviceName: deviceName,
               deviceType: deviceType,
               attributes: {online: data.bizCode == "online"},
               telemetry: noTelemetry
           };
       }

       // Skip other messages, for example nameUpdate or delete: an empty result creates or updates no device.
       return [];

       /** Helper functions 'decodeToString' and 'decodeToJson' are already built-in **/
       ```
     </TabItem>

       /** Decoder **/

       // Tuya Message Service pushes each device report as JSON.
       // This example handles status reports (statusReport) and online/offline messages
       // of a Tuya smart plug. Other messages are skipped.

       // Parse the incoming payload (byte array) into a JSON object.
       var data = decodeToJson(payload);

       // Use the Tuya device ID as the device name.
       // Keep it unchanged: the downlink sends commands to the Tuya device with this ID.
       var deviceName = data.devId;
       if (typeof deviceName !== "string" || !deviceName.trim()) {

           var telemetry = [];

               var code = data.status[i].code;

           };
       }

           // Online/offline message: store the connection state as an attribute.
           return {
               deviceName: deviceName,
               deviceType: deviceType,
               attributes: {online: data.bizCode === "online"},
               telemetry: []
           };
       }

       // Skip other messages, for example nameUpdate or delete: an empty result creates or updates no device.
       return [];

       /** Helper functions **/

       function decodeToString(payload) {
           return String.fromCharCode.apply(String, payload);
       }

       function decodeToJson(payload) {
           var str = decodeToString(payload);
           var data = JSON.parse(str);
           return data;
       }

   **To adapt:**
   - **Other data points** — add or change the `code` branches. Codes without a branch are stored as received.
   - **Other scaling** — change the divisors. For example, some models report `add_ele` (energy, kWh) that needs ÷ 100 or ÷ 1000.
   - **Friendly key names** — map codes explicitly, for example `cur_voltage` to `voltage`.
   - **Server time** — to store values with the time ThingsBoard receives them instead of the device time `t`, push `values` instead of `{ts: data.status[i].t, values: values}`.
   - **Device properties** — add them to `attributes`, for example `productKey: data.productKey` in the `attributes` of the status report result.
   - **Device settings** — after it reconnects, the plug reports its full state, including settings such as `child_lock`, `light_mode`, `relay_status`, and `countdown_1`. Store them in `attributes` instead of `telemetry` if you do not need their history.
6. Click **Test decoder function** and check the result (see **[Test the Decoder](#test-the-decoder)**).
7. Click **Add**.
</Steps>

<Aside type="caution" title="Keep the Tuya device ID as the device name">
  The integration sends downlink commands to the Tuya device whose ID equals the ThingsBoard device name. Keep `deviceName` exactly the Tuya `devId`, with no prefix or spaces. A space causes `Illegal character in path`; any other change targets the wrong device. For a readable name, set the device **Label** in ThingsBoard.
</Aside>

<h4>Decoder Inputs</h4>

The decoder signature is `function decoder(payload, metadata): object | object[]`.

| Variable | Type | Content |
|----------|------|---------|
| `payload` | byte array | The decrypted status report (JSON). Parse it with `decodeToJson(payload)`. |
| `metadata` | `{[key: string]: string}` | Message Service envelope: `topic`, `t` (send time, ms), `pv` (protocol version), `protocol`, and `sign`. Also `integrationName` and the key–value pairs from the integration's **Metadata** field. |

Status report fields:

| Field | Content |
|-------|---------|
| `devId` | Tuya device ID, for example `bfac3c40adca459c9chaar`. |
| `productKey` | Product key of the device model, for example `iq9hwd2bjsdgqiby`. |
| `dataId` | Unique ID of the report. |
| `status` | Data points. Each entry has `code`, `value`, and `t` (ms). An entry also carries the data point number with the value as a string, for example `"1": "false"` for `switch_1` or `"20": "2072"` for `cur_voltage`; the decoder ignores it. |

The integration's **Events** tab shows each message as `{ "metadata": {...}, "data": {...} }`. The decoder receives only `data` as `payload`. To test the decoder with a message from **Events**, paste only the `data` object as the payload.

<Aside type="note">
  Data point codes (`switch_1`, `cur_power`, `cur_voltage`, …) and their scaling depend on the device model. To see the codes your device reports, open **Devices**, select the device in the Tuya IoT Platform, and go to **Device Debugging**.
</Aside>

<h4 id="test-the-decoder">Test the Decoder</h4>

Click **Test decoder function** below the editor. The default payload of a Tuya converter is this status report, with **Payload content type** set to **JSON**. If the payload differs, paste the report. Click **Test**:

```json
{
  "dataId": "000657E477596B12C80347616A03002A",
  "devId": "bfac3c40adca459c9chaar",
  "productKey": "iq9hwd2bjsdgqiby",
  "status": [
    { "code": "cur_voltage", "t": 1785490000000, "value": 2086 },
    { "code": "cur_power", "t": 1785490000000, "value": 142 },
    { "code": "cur_current", "t": 1785490000000, "value": 63 }
  ]
}
```

The **Output** panel shows:

```json
{
  "deviceName": "bfac3c40adca459c9chaar",
  "deviceType": "Tuya device",
  "attributes": {},
  "telemetry": [
    { "ts": 1785490000000, "values": { "cur_voltage": 208.6 } },
    { "ts": 1785490000000, "values": { "cur_power": 14.2 } },
    { "ts": 1785490000000, "values": { "cur_current": 0.063 } }

```

Check that `deviceName` equals the `devId` and that `telemetry` holds the scaled values with the report time `ts`. If the output shows an error, fix the decoder and test again. An empty result `[]` means the decoder skipped the message: it has no `status` and is not `online` or `offline`.

<Aside type="note">
  `cur_voltage`, `cur_power`, and `cur_current` are reported only while a load draws current. If only `switch_1` arrives, connect a load and wait for the next report.
</Aside>

### Create the Integration

<Steps>
1. Go to **Integrations &#8702; Integrations** and click **+ Add integration**.
2. **Basic settings:**
   - **Integration type** — select **Tuya**.
   - **Name** — enter a name, for example `Tuya integration`.
   - **Enable integration** and **Allow create devices or assets** — keep both on, so the device is created on its first report.
   - Click **Next**.
3. **Uplink data converter:**

## Configure Downlink

ThingsBoard sends a command to the device when the Rule Engine routes an RPC request to the integration — for example, when a dashboard switch is toggled. The integration calls the Tuya OpenAPI of the selected region:

1. It takes the Tuya device ID from `deviceId` in the encoder's output `metadata`, or from `deviceName` if `deviceId` is not set.
2. It sends `data` to `POST /v1.0/iot-03/devices/{deviceId}/commands` as `{ "commands": [...] }`.

The encoder's `data` must be one of:

| `data` | Sent to Tuya |
|--------|--------------|
| An object with `code` and `value`, for example `{"code": "switch_1", "value": true}` | `{"commands": [{"code": "switch_1", "value": true}]}` |
| An array of such objects | `{"commands": [...]}` with every command |
| An object with `method` set to a query name: `getStatus`, `getFunctions`, `getSpecification`, `getLogs`, `getReportLogs`, or `getCategory` | A `GET` request to the matching OpenAPI endpoint. The response goes to the uplink converter as `payload`, with `msgType` = `DownlinkResponse` and `deviceId` in `metadata`. |

Any other `data`, including `{"commands": [...]}`, fails with *"Downlink message format is not correct, downlink message should contain one of the following: code field, service RPC method, commands array!"*.

The encoder in this guide sends commands only. To send a query, return `data` with `method`, for example `{"method": "getStatus"}`, from your own encoder, and handle the response in the uplink converter: the response has no `devId` (the device ID is in `metadata.deviceId`), so the decoder in this guide stops with an error.

The downlink converter turns a <DocLink product={props.product} path="user-guide/rule-engine" target="_blank">Rule Engine</DocLink> message into a Tuya command. For the full encoder reference, see <DocLink product={props.product} path="user-guide/integrations/downlink-data-converter" target="_blank">Downlink data converter</DocLink>.

### Create and Assign the Downlink Converter

The encoder below uses the RPC method as the Tuya command `code` and the RPC params as its `value`. ThingsBoard passes RPC params as JSON text, for example `true` from the **Round switch** as `"true"`, so the encoder parses the text back into a boolean, number, string, or object. It sets `deviceId` to the device name, which is the Tuya `devId`. It stops with an error if the device name is missing, if the message is not an RPC request, or if the RPC has no method or params; see **[Troubleshooting](#troubleshooting)**.

<Steps>
1. Open the integration in **Integrations &#8702; Integrations** and click **Toggle edit mode** (pencil icon).
2. In the **Downlink data converter** field, click **Create new**. The **Downlink** converter type and **Tuya** integration type are preselected.
3. Enter a name, for example `Tuya Downlink Converter`.
4. **Main encoding configuration** — the editor opens with the default Tuya encoder, which is the encoder below. Keep it, or write your own. The editor opens in TBEL; use the **TBEL / JS** toggle to switch to JavaScript.
   <Tabs>
     <TabItem label="TBEL (Recommended)">
       ```js maxLines=20 collapsible
       // Encode downlink data from incoming Rule Engine message

       // msg - JSON message payload downlink message json
       // msgType - type of message, for ex. 'ATTRIBUTES_UPDATED', 'POST_TELEMETRY_REQUEST', etc.
       // metadata - list of key-value pairs with additional data about the message
       // integrationMetadata - list of key-value pairs with additional data defined in Integration executing this converter

       /** Encoder **/

       // Send an RPC request to the Tuya device as a Device Control command:
       // the RPC method becomes the command code, the RPC params become its value.
       // For example, method "switch_1" with params true turns a smart plug on.

       // The device name is the Tuya device ID. Reject the message if it is missing or empty.
       var deviceId = metadata.deviceName != null ? metadata.deviceName.trim() : null;
       if (deviceId == null || deviceId.isEmpty()) {
           raiseError("Message metadata has no deviceName");
       }

       // Only RPC requests are sent as commands. Reject other messages, for example attribute updates.
       if (msgType != "RPC_CALL_FROM_SERVER_TO_DEVICE") {
           raiseError("Message is not an RPC request");
       }
       if (msg.method == null || msg.method.trim().isEmpty()) {
           raiseError("RPC request has no method");
       }

       // ThingsBoard passes RPC params as JSON text, for example true as "true", 500 as "500"
       // and "colour" as "\"colour\"". Parse JSON text into a boolean, number, string or object.
       // Keep other text, for example colour typed without quotes, as it is.
       var value = msg.params;
       if (value instanceof String) {
           var text = value.trim();
           if (text == "true" || text == "false" || text == "null"
                   || text.matches("-?(0|[1-9][0-9]*)(\\.[0-9]+)?([eE][+-]?[0-9]+)?")
                   || text.startsWith("\"") || text.startsWith("{") || text.startsWith("[")) {
               value = JSON.parse(text);
           }
       }
       if (value == null) {
           raiseError("RPC request has no params");
       }

       var command = {
           code: msg.method,
           value: value
       };

       var result = {
           // The Tuya Device Control API expects a JSON body.
           contentType: "JSON",

           // One command: { "code": ..., "value": ... }.
           data: JSON.stringify(command),

           // The integration sends the command to the Tuya device with this ID.
           metadata: {
               deviceId: deviceId
           }
       };

       return result;
       ```
     </TabItem>
     <TabItem label="JavaScript">
       ```js maxLines=20 collapsible
       // Encode downlink data from incoming Rule Engine message

       // msg - JSON message payload downlink message json
       // msgType - type of message, for ex. 'ATTRIBUTES_UPDATED', 'POST_TELEMETRY_REQUEST', etc.
       // metadata - list of key-value pairs with additional data about the message
       // integrationMetadata - list of key-value pairs with additional data defined in Integration executing this converter

       /** Encoder **/

       // Send an RPC request to the Tuya device as a Device Control command:
       // the RPC method becomes the command code, the RPC params become its value.
       // For example, method "switch_1" with params true turns a smart plug on.

       // The device name is the Tuya device ID. Reject the message if it is missing or empty.
       var deviceId = typeof metadata.deviceName === "string" ? metadata.deviceName.trim() : "";
       if (!deviceId) {
           throw new Error("Message metadata has no deviceName");
       }

       // Only RPC requests are sent as commands. Reject other messages, for example attribute updates.
       if (msgType !== "RPC_CALL_FROM_SERVER_TO_DEVICE") {
           throw new Error("Message is not an RPC request");
       }
       if (typeof msg.method !== "string" || !msg.method.trim()) {
           throw new Error("RPC request has no method");
       }

       // ThingsBoard passes RPC params as JSON text, for example true as "true", 500 as "500"
       // and "colour" as "\"colour\"". Parse JSON text into a boolean, number, string or object.
       // Keep other text, for example colour typed without quotes, as it is.
       var value = msg.params;
       if (typeof value === "string") {
           var text = value.trim();
           if (text === "true" || text === "false" || text === "null"
                   || /^-?(0|[1-9][0-9]*)(\.[0-9]+)?([eE][+-]?[0-9]+)?$/.test(text)
                   || text.charAt(0) === "\"" || text.charAt(0) === "{" || text.charAt(0) === "[") {
               value = JSON.parse(text);
           }
       }
       if (value === undefined || value === null) {
           throw new Error("RPC request has no params");
       }

       var command = {
           code: msg.method,
           value: value
       };

       var result = {
           // The Tuya Device Control API expects a JSON body.
           contentType: "JSON",

           // One command: { "code": ..., "value": ... }.
           data: JSON.stringify(command),

           // The integration sends the command to the Tuya device with this ID.
           metadata: {
               deviceId: deviceId
           }
       };

       return result;
       ```
     </TabItem>
   </Tabs>
5. Click **Test encoder function**. The defaults are the RPC message `{"method":"switch_1","params":"true"}` with **Message type** `RPC_CALL_FROM_SERVER_TO_DEVICE`, for the device `bfac3c40adca459c9chaar` of type `Tuya device`. Click **Test** and check the output: `data` is `{"code":"switch_1","value":true}` and `metadata.deviceId` is `bfac3c40adca459c9chaar`.
6. To record downlink events, click the debug icon next to the name, select **All messages**, and click **Apply**.
7. Click **Add**, then **Apply changes**.

## Troubleshooting

| Symptom | Cause | Fix |
|---------|-------|-----|
| **CONNECT** event with status **FAILURE** | Wrong **Access Id**, **Access Key**, or **Region**. | Copy the credentials from the project **Overview** page again. Select the **Region** that matches the project data center. |
| Integration connects, but no uplinks arrive | The messaging rule is off, or enabled in the other environment. | Enable the rule with `statusReport` in the environment that matches **Environment**. See **[Configure Messaging Rules](#configure-messaging-rules)**. |
| Same, with the rule enabled | The device is not linked to the cloud project. | Link the app account. See **[Link Your Tuya App Account](#link-your-tuya-app-account)**. |
| Subscription **Status** is not **Good** | The messaging rule was disabled or changed. | Enable the rule for the matching environment and check the subscription again. |
| Device not created | **Allow create devices or assets** is off, or the decoder skipped the message. | Turn the option on. Check **Out** in the converter events: `[]` means the message has no `status` and is not `online` or `offline`. |
| Only `switch_1` arrives | The plug has no load. | Connect a load and wait for the next report. |
| **Downlink** event with status **FAILURE** and *"Please contact system administrator"* | The integration shows this text instead of the error. The causes are in the rows below. On a self-hosted installation, set `HTTP_LOG_CONTROLLER_ERROR_STACK_TRACE=true` and restart ThingsBoard: the event then shows the full error. A remote integration (**Execute remotely**) or a separate integration executor always shows the full error. | Check the causes below. To see the error returned by Tuya Cloud, send the same command in the Tuya IoT Platform: **Cloud &#8702; API Explorer**, **IoT Core**, **Device Control(Standard Instruction Set) &#8702; Send commands**, with the device ID and the encoder's `data` in `commands`. The response shows the Tuya code and message. |
| Same, the full error has Tuya code `28841002`, *"IoT Core service subscription has expired."* | The **IoT Core** subscription has expired. Status reports keep arriving, because the Message Service does not depend on it. | Renew IoT Core in **Cloud &#8702; Cloud Services**. |
| Same, the full error is *"Downlink message format is not correct…"* | `data` has neither `code`, a query `method`, nor an array of commands. | Check **Out** in the downlink converter events. Make sure the RPC method reaches `msg.method`. |
| Same, the full error is *"Device identifier not found in metadata"* | The encoder's output `metadata` has neither `deviceId` nor `deviceName`. | Set `deviceId` in the encoder's `metadata`. |
| Same, the full error has `Illegal character in path` | The device name is not the raw Tuya `devId`. | Rename the device to its `devId`. Use **Label** for a readable name. |
| Same, the full error is *"Tuya integration response error code…"* | Tuya Cloud rejected the command, for example the `code` is not writable. | Check the writable codes in **Device Debugging** in the Tuya IoT Platform. |
| Uplink fails with `Tuya message has no devId` | The message has no `devId`, for example a query response. | Check **In** in the uplink converter events. Handle this message type in your own decoder. |
| Downlink converter event with the error `Message metadata has no deviceName` | The RPC message has no `deviceName` in its metadata. | Send the RPC to the device, so the message carries the device name. |
| Downlink converter event with the error `Message is not an RPC request` | A message that is not an RPC request, for example an attribute update, reached the **integration downlink** node. | Connect the node with the **RPC Request to Device** relation only. |
| Downlink converter event with the error `RPC request has no method` or `RPC request has no params` | The RPC has an empty method, or no value. | Set the RPC method (the Tuya command code, for example `switch_1`) and the value in the widget or the RPC request. |
| No downlink event | The rule chain does not reach the **integration downlink** node. | Connect the node with the **RPC Request to Device** relation. |

To read debug events, open the integration or converter, click **Events**, and select an event: **In** is the received data, **Out** is the converter result, and **Error** holds the error text.
