ChirpStack Integration receives device data from <a href="https://www.chirpstack.io/" target="_blank" rel="noopener noreferrer nofollow"><strong>ChirpStack</strong></a>, the open-source LoRaWAN Network Server, through an **HTTP** integration of a ChirpStack application. An **uplink data converter** extracts the device payload and the LoRaWAN details from each message and turns them into telemetry and attributes. For downlink, ThingsBoard adds commands to the device queue through the ChirpStack REST API.

Use ChirpStack Integration when:
- Your LoRaWAN devices are registered in ChirpStack, and you want their data in ThingsBoard without registering each device by hand.
- You need to send commands from ThingsBoard to those devices, for example when a shared attribute changes.

## Architecture

<ImageGallery images={[
  {
    src: '/src/assets/images/user-guide/integrations/chirpstack-integration-architecture.svg',

For downlink, an attribute update or RPC command goes through the downlink converter, which returns the data with the DevEUI and fPort, and the integration enqueues it through the ChirpStack REST API with the application server URL and API token; ChirpStack sends it to the device in its next receive window',
    caption: 'ChirpStack integration architecture. ChirpStack posts device events to the integration endpoint. Downlinks go right away to the ChirpStack device queue, and a Class A device gets them after its next uplink.',
  },
]} />

1. **Receive data.** The device sends an uplink through a LoRaWAN gateway to ChirpStack. The HTTP integration of the ChirpStack application sends the uplink event as an HTTP request with a JSON body to the integration endpoint.
2. **Unwrap the event.** The uplink converter extracts the device payload from the event, and the device EUI, frame counter, port, radio details, and other fields as metadata.
3. **Decode the payload.** The decoder turns the payload into telemetry and attributes. The converter adds the LoRaWAN details that you select, and builds the device name from the EUI. If **Allow create devices or assets** is on, ThingsBoard creates the device on its first message.
4. **Send a command (optional).** The Rule Engine passes a message to the integration. The downlink converter encodes it, and ThingsBoard sends it right away to `POST {Application server URL}/api/devices/{DevEUI}/queue`. ChirpStack keeps it in the device queue and delivers it in the next receive window of the device: for a Class A device, after its next uplink.

## Prepare ChirpStack

In ChirpStack, devices belong to an **application**, and the application's integrations forward the device events. Here you start ChirpStack if you do not have a server yet, and create the application. The HTTP integration comes later: it needs the integration endpoint, so you add it **[after creating the integration](#add-the-http-integration-in-chirpstack)**.

### Start ChirpStack

Skip this step if you already have a ChirpStack server. The <a href="https://github.com/chirpstack/chirpstack-docker" target="_blank" rel="noopener noreferrer nofollow"><strong>chirpstack-docker</strong></a> repository runs ChirpStack with Docker Compose.

<Steps>
1. Install Docker and Docker Compose. See the <a href="https://docs.docker.com/get-docker/" target="_blank" rel="noopener noreferrer nofollow"><strong>Docker installation guide</strong></a>.
2. Clone the repository:

   ```bash
   git clone https://github.com/chirpstack/chirpstack-docker.git
   cd chirpstack-docker
   ```

3. Both gateway bridges in this setup use the EU868 region. To use another region, change the topic prefix as described in the `README.md` of the repository.
   <Aside type="caution" title="ThingsBoard on the same host">
     The setup publishes the ChirpStack UI on port `8080` and the MQTT broker on port `1883`. ThingsBoard uses the same ports by default. To run both on one host, in `docker-compose.yml` change the `chirpstack` port mapping to `"8081:8080"` and remove the `ports` of the `mosquitto` service. Then open the ChirpStack UI on port `8081`.
   </Aside>

4. Start ChirpStack:

   ```bash
   docker compose up
   ```

   On the first run, the logs can show errors while the database initializes. This is expected.

5. Point your gateway to the host. The ChirpStack Gateway Bridge accepts Semtech UDP Packet Forwarder traffic on UDP port `1700`, and LoRa Basics Station connections on port `3001`.
6. Open `http://localhost:8080` (or `http://localhost:8081` if you changed the port) and sign in with the username `admin` and the password `admin`. If ChirpStack runs on another host, replace `localhost` with its address. The REST API that ThingsBoard uses for downlink listens on port `8090`.
</Steps>

## Set Up ChirpStack Integration

Create the uplink converter and the integration, then point a ChirpStack HTTP integration at the integration endpoint.

### Create the Uplink Data Converter

ChirpStack Integration uses the **Typed** uplink converter. It unwraps the ChirpStack event before your decoder runs: the decoder gets only the device payload as a byte array, and the event fields arrive as `metadata`. The device name, profile, label, and the LoRaWAN details to store are set in the converter form. The script can override them. ThingsBoard selects this converter for the **ChirpStack** integration type, and you cannot change it later. See <DocLink product={props.product} path="user-guide/integrations/uplink-data-converter/#typed-uplink-converter" target="_blank">Typed uplink converter</DocLink>.

If your device model is in the catalog, you can take a ready-made decoder instead. See **[Use a Library Converter](#use-a-library-converter)**.

<Steps>
1. Go to **Integrations &#8702; Data converters** and click **+ Add data converter &#8702; Create new converter**.
2. **Converter type** — keep **Uplink**.
3. **Integration type** — select **ChirpStack**.
4. Keep **Create new** selected and enter a **Name**, for example `ChirpStack Uplink Converter`.
5. **Main decoding configuration:**
   - **Entity type** — keep **Device**.

       ```js maxLines=15 collapsible
           // Initialize the output object with empty attributes and telemetry for clarity.
           var result = { attributes: {}, telemetry: {}};

           // Extract the timestamp from metadata (represented in milliseconds).
           var timestamp = metadata.ts; // ts is the timestamp parsed from the incoming message's time, or returns the current time if it cannot be parsed.

               // payloadFormat is 'JSON' when ChirpStack sends a pre-decoded JSON payload
               // (the uplink contains an "object" field produced by a codec/payload formatter).
               // All fields from the decoded object are put directly into telemetry.
               var decoded = decodeToJson(input);

               return result;
       ```

       ```js maxLines=15 collapsible
        * Converts a slice of bytes from an array into an integer (big-endian).
        *
        * @param {number[]} input - The array of bytes.
        * @param {number} offset - The starting index.
        * @param {number} length - The number of bytes to convert.
        * @returns {number} - The resulting integer.
        */

         var result = 0;
       ```

   The decoder has two paths, chosen by `metadata.payloadFormat`:

   | `payloadFormat` | When | `payload` holds | The decoder |
   |-----------------|------|-----------------|-------------|
   | `BINARY` | No codec on the ChirpStack device profile | The bytes of the Base64 `data` field | Reads the example layout below |
   | `JSON` | A codec on the ChirpStack device profile decoded the payload | The `object` field as JSON text | Stores every field of `object` as telemetry |

   The example layout of the `BINARY` path:

   | Bytes | Expression | Result |
   |-------|------------|--------|
   | 0–3 | `parseBytesToInt(input, 0, 4)` | Attribute `sn` |
   | 4 | `parseBytesToInt(input, 4, 1)` | Telemetry `battery` |
   | 5–6 | `parseBytesToInt(input, 5, 2) / 100.0` | Telemetry `temperature` |
   | 7 | `parseBytesToInt(input, 7, 1)` | Telemetry `saturation` |

   **To adapt:**
   - **Payload layout** — change the offsets, lengths, and keys in `decodePayload` to match the payload format of your device. If a ChirpStack codec already decodes the payload, the `JSON` path needs no changes.
   - **Device identity** — set `result.name`, `result.profile`, `result.customer`, or `result.group` in the script to override the form fields, as the commented lines show.
6. **Advanced decoding parameters** — keep the defaults:
   - **Device profile name** — `$deviceProfileName`, the ChirpStack device profile name. ThingsBoard assigns the device profile with this name and creates it if it does not exist.
   - **Device label** — `$deviceName`, the device name in ChirpStack.
   - **Customer name** and **Device group name** — empty. Set them to assign new devices to a customer or add them to a group.
   - **Telemetry** — `fCnt`, `data`, `decoded`, `latitude`, `longitude`, `rssi`, `snr`, `channel`, `altitude`.
   - **Attributes** — `eui`, `devAddr`, `fPort`, `tenantId`, `tenantName`, `applicationId`, `applicationName`, `adr`, `dr`, `frequency`, `bandwidth`, `spreadingFactor`, `codeRate`.
   - **Update only keys list** — the same keys as **Attributes**. These keys are stored only when their value changes.

   The **Telemetry** and **Attributes** lists do not filter the decoder output. They add the listed keys from the event metadata to the telemetry and attributes that the decoder returns. A key that the event does not carry is skipped. Downlink in this guide needs the `eui` and `fPort` attributes, so keep them in the list.
7. Click **Test payload decoder** and check the result (see **[Test the Decoder](#test-the-decoder)**).
8. Click **Add**.
</Steps>

<h4 id="decoder-inputs">Decoder Inputs</h4>

| Variable | Type | Content |
|----------|------|---------|
| `payload` | byte array | The device payload: the decoded Base64 `data` field, or the `object` field as JSON text when a ChirpStack codec decoded the payload. Empty if the event carries neither. |
| `metadata` | `{[key: string]: any}` | The fields extracted from the ChirpStack event, listed below, plus `integrationName` and the key–value pairs from the integration's **Metadata** field. A **Metadata** key with the same name as an extracted field replaces it. |

| Key | Source in the event | Example |
|-----|---------------------|---------|
| `eui` | `deviceInfo.devEui` | `24e124538b223213` |
| `deviceName`, `deviceProfileName`, `deviceProfileId` | `deviceInfo` | `chirpstack sensor 001`, `chirpstack-sensor` |
| `tenantId`, `tenantName`, `applicationId`, `applicationName`, `tags` | `deviceInfo` | `ChirpStack`, `Sample Application` |

| `ts`, `timeTs` | `time` in Unix milliseconds. If `time` is missing or cannot be parsed, `ts` is the current time. | `1792507372653` |
| `payloadFormat` | `JSON` if the event has `object`, otherwise `BINARY` | `BINARY` |

<h4 id="use-a-library-converter">Use a Library Converter</h4>

The <DocLink product={props.product} path="user-guide/integrations/uplink-data-converter/#converters-library" target="_blank">Converters library</DocLink> holds ready-made converters for devices from vendors such as Milesight, Elsys, Decentlab, and Bosch. They are maintained in the <a href="https://github.com/thingsboard/data-converters" target="_blank" rel="noopener noreferrer"><strong>data-converters</strong></a> repository.

<Steps>
1. In the **Add data converter** dialog, select **Uplink** and the **ChirpStack** integration type, then switch from **Create new** to **Library**.
2. **Vendor** — select the manufacturer, for example **Milesight**.
3. **Model** — select the device model, for example **AM102L: 2-in-1 Environment Sensor**.
4. **Name** is filled in as `ChirpStack Uplink Converter for <Vendor> <Model>`, for example `ChirpStack Uplink Converter for Milesight AM102L`. Change it if needed.
5. Review the decoder and the **Advanced decoding parameters**, and click **Add**. The **TBEL / JS** toggle is locked to the language of the entry.
</Steps>

A library converter can work differently from the converter above. Some entries, such as Milesight AM102L, are written as Generic converters: the function is `decoder(payload, metadata)`, `payload` is the whole ChirpStack event, and the decoder reads the device name and the payload from it, for example `var data = decodeToJson(payload);` and `data.deviceInfo.deviceName`. Such a converter shows only the **Update only keys list** under **Advanced decoding parameters**. Its test button is **Test decoder function**, and the test dialog takes the whole event as a **Json** payload. The AM102L entry names devices `AM102L <ChirpStack device name>` and adds `rssi`, `snr`, `channel`, `rfChain`, and `fCnt` to the telemetry only if the integration **Metadata** has `includeGatewayInfo` = `true`. Check the decoder of the entry you select before you rely on the device name or keys described in this guide.

## Configure Downlink

ThingsBoard sends each downlink right away as a ChirpStack REST API call. Nothing is queued in ThingsBoard: if the call fails, ThingsBoard records an error and drops the command. ChirpStack adds an accepted downlink to the device queue and sends it in the next receive window of the device: for a Class A device, after its next uplink.

For each downlink, the integration sends `POST {Application server URL}/api/devices/{DevEUI}/queue` with the API key as a `Bearer` token and this body:

```json
{
  "queueItem": {
    "confirmed": false,
    "data": "eyJ0ZW1wZXJhdHVyZVVwbG9hZEZyZXF1ZW5jeSI6NjB9",
    "fPort": 84
  }
}
```

`DevEUI`, `fPort`, and `confirmed` come from the `metadata` of the encoder result, and `data` from its `data`. With **Use API for ChirpStack 4+** off, the body key is `deviceQueueItem`. For the full encoder reference, see <DocLink product={props.product} path="user-guide/integrations/downlink-data-converter" target="_blank">Downlink data converter</DocLink>.

Encoder used in this guide. It sends the message as compact JSON text, for example `{"temperatureUploadFrequency":60}`, encoded in Base64 as ChirpStack expects. It reads the device EUI and port from the `cs_eui` and `cs_fPort` metadata keys, which the rule chain adds from the device's client attributes.

<Tabs>
<TabItem label="TBEL (Recommended)">

```js
/** Encoder **/

// Device EUI and LoRaWAN port. The rule chain adds the eui and fPort
// client attributes to the metadata as cs_eui and cs_fPort.
var devEui = metadata['cs_eui'];
var fPort = metadata['cs_fPort'];

return {
    // TEXT passes the Base64 string to ChirpStack unchanged.
    contentType: "TEXT",
    // ChirpStack expects the device payload as a Base64 string.
    data: btoa(JSON.stringify(msg)),
    metadata: {
        // Required. The device to send the downlink to.
        DevEUI: devEui,
        // Required. An integer from 1 to 223 that your device listens on.
        fPort: fPort,
        // Optional. "true" asks the device to acknowledge the downlink.
        confirmed: "false"
    }
};
```

```json
{
  "contentType": "TEXT",
  "data": "eyJ0ZW1wZXJhdHVyZVVwbG9hZEZyZXF1ZW5jeSI6NjB9",
  "metadata": {
    "DevEUI": "24e124538b223213",
    "fPort": "84",
    "confirmed": "false"
  }
}
```

The integration reads these fields from the encoder result:

| Field | Required | Description |
|-------|----------|-------------|
| `data` | Yes | The device payload as a Base64 string. The integration sends it to ChirpStack as is. |
| `contentType` | Yes | Use `TEXT` or `JSON`. |
| `metadata.DevEUI` | Yes | Device EUI. Without it, the downlink fails with `DevEUI is missing in the downlink metadata!`. |
| `metadata.fPort` | Yes | LoRaWAN port, as an integer or a numeric string. Without it, the downlink fails with `FPort is missing in the downlink metadata!`. |
| `metadata.confirmed` | No | `true` or `false`. Any other value fails the downlink. |

The encoder sends the whole message. A LoRaWAN downlink carries from about 50 to about 220 bytes, depending on the region and data rate. To send a compact binary command instead, build a byte array, encode it with `bytesToBase64()` in TBEL, and return it as `data`. To send several downlinks from one message, return an array of results.

## Troubleshooting

| Symptom | Cause | Fix |
|---------|-------|-----|
| No events on the integration **Events** tab | The HTTP integration in ChirpStack is missing or has a wrong URL, ChirpStack cannot reach ThingsBoard, or the integration is disabled. Or debug mode is off: it records events for 15 minutes after you turn it on. | Check the **Integrations** tab of the ChirpStack application. Copy the **HTTP endpoint URL** again. Turn on **Enable integration**. Turn debug mode on again. |
| No events on the integration **Events** tab, and the ChirpStack log shows `Posting event failed` | **Event endpoint URL(s)** points to an address at which ChirpStack does not reach ThingsBoard, for example `localhost` when ChirpStack runs in Docker. | Use an address that ChirpStack can reach, such as the host address of the Docker network. Check the log again after the next uplink. |
| Downlink stays on the **Queue** tab after the next uplink | ChirpStack first sends pending MAC commands to the device, for example right after activation. | Wait for the next uplinks. The downlink is sent once the device has answered the MAC commands. |
| No events on the integration **Events** tab, and the ChirpStack log shows `Posting event failed` with `415` | **Payload encoding** in ChirpStack is **Protobuf**. The integration accepts only JSON. | Set it to **JSON**. |
| `URL must be in the public network.` under **Base URL** | On ThingsBoard Cloud, **Base URL** must be a public address. | Keep the default **Base URL**. To send data from a private network, use a <DocLink product={props.product} path="user-guide/integrations/remote" target="_blank">Remote Integration</DocLink>. |
| Uplink events with status **ERROR** | The decoder failed, for example because the payload is shorter than the byte layout expects. | Check the **Error** column in the converter events and fix the decoder. |
| Device not created | **Allow create devices or assets** is off. | Turn it on in the integration's **Basic settings**. |
| Telemetry key `decoded` with a JSON object | A ChirpStack codec decoded the payload. The decoder stores its fields as telemetry, and the default **Telemetry** list adds the whole object as `decoded`. | Remove `decoded` from **Telemetry** if you do not need it. |
| No downlink events at all | The rule chain does not route attribute updates, or the device was not created by this integration, so **check relation presence** returns **False**. | Check the **Attributes Updated** and **True** relations in the Root Rule Chain. |
| Message stops at `Get EUI and port` with **Failure** | The device has no `eui` or `fPort` client attribute. | Keep `eui` and `fPort` in the converter's **Attributes** list, and send an uplink to store them. |
| `DevEUI is missing in the downlink metadata!` or `FPort is missing in the downlink metadata!` | The encoder does not set `metadata.DevEUI` or `metadata.fPort`. The generic default encoder sets neither. | Use the encoder from this guide. |
| `ChirpStack rejected downlink (401 ...)` | The API key is wrong or was deleted, or no device with this DevEUI exists in the ChirpStack tenant of the key. | Check the key in **Application server API Token**, or create a new one. Register the device in ChirpStack. |
| `ChirpStack rejected downlink (400 ...)`, for example `invalid value for bytes field data` | `data` is not a Base64 string, or the body format does not match the ChirpStack version. | Return `data` as a Base64 string, as the encoder in this guide does. Turn **Use API for ChirpStack 4+** on for ChirpStack v4 and off for v3. |
| `I/O error on POST request for "..."`, for example `Connection refused` | ThingsBoard cannot reach the **Application server URL**. | Check the address and port. If ChirpStack is in a private network, use a <DocLink product={props.product} path="user-guide/integrations/remote" target="_blank">Remote Integration</DocLink>. |

To read debug events, open the integration or converter, click **Events**, and select an event: **In** is the received data, **Out** is the converter result, and **Error** holds the error text.
