TCP Integration lets devices send data to ThingsBoard over raw TCP connections. The integration runs a TCP server and splits the incoming byte stream into messages. An **uplink data converter** transforms each message into device or asset data, including telemetry and attributes. ThingsBoard can also send a **downlink** message back over the device's open connection.

Use TCP Integration when:
- Devices use a custom text or binary protocol over raw TCP.
- Device firmware already connects to a configurable host and port.
- Devices keep a long-lived connection and must receive commands over it.

<Aside type="note">
  TCP Integration always runs as a <DocLink product={props.product} path="user-guide/integrations/remote/" target="_blank">remote integration</DocLink>: a separate process outside the ThingsBoard cluster that listens on the TCP port and forwards data to ThingsBoard.
</Aside>

## Architecture

1. **Receive data.** A device opens a TCP connection to the remote integration and sends data. The handler (**Text**, **JSON**, or **Binary**) splits the byte stream into separate messages.
2. **Decode the payload.** The uplink converter identifies the device or asset in each message and extracts attributes and telemetry.
3. **Process the message.** ThingsBoard processes the converted data through the Rule Engine. If **Allow create devices or assets** is enabled, ThingsBoard can create an entity that does not exist yet.
4. **Send downlink data (optional).** The downlink converter encodes the Rule Engine message, and the integration writes it to the device's open connection, followed by `\n`. If the device is not connected, the downlink waits for its next uplink.

## Prerequisites

- Access to {props.product !== Products.PAAS && props.product !== Products.PAAS_EU && <><DocLink product={Products.PE} path="installation/" target="_blank">ThingsBoard</DocLink> or </>}<a href="/installations/?product=thingsboard-cloud" target="_blank"><strong>ThingsBoard Cloud</strong></a> with integrations enabled for your tenant.
- Permission to create integrations and data converters.
- A host for the remote integration. Devices must reach it on the TCP port (default `10560`), and it needs outbound access to ThingsBoard's gRPC port `9090`.
- The payload format and framing your devices use.
- `nc` (netcat) to send test data.

## Set Up TCP Integration

Create the uplink converter, assign it to a new TCP integration, start the remote integration, and send a test message.

<h4 id="sample-payloads">Sample Payloads</h4>

This guide uses device **SN-002**, which sends temperature and humidity in one of three formats. Pick one format and use the matching decoder, handler, and test command throughout.

<Tabs>
<TabItem label="Text">
Comma-separated records, one per line:

```
SN-002,default,temperature,25.7\nSN-002,default,humidity,69
```
</TabItem>
<TabItem label="JSON">
```json
{
  "deviceName": "SN-002",
  "deviceType": "default",
  "temperature": 25.7,
  "humidity": 69
}
```
</TabItem>
<TabItem label="Binary">
A 25-byte message with a 1-byte length field:

```
\x30\x30\x30\x30\x11\x53\x4e\x2d\x30\x30\x32\x64\x65\x66\x61\x75\x6c\x74\x32\x35\x2e\x37\x00\x00\x00
```

| Bytes | Hex | Value |
|-------|-----|-------|
| 0–3 | `\x30\x30\x30\x30` | Header, stripped by the handler |
| 4 | `\x11` | Length field: 17 bytes of payload follow |
| 5–10 | `\x53\x4e\x2d\x30\x30\x32` | Device name: `SN-002` |
| 11–17 | `\x64\x65\x66\x61\x75\x6c\x74` | Device type: `default` |
| 18–21 | `\x32\x35\x2e\x37` | Temperature: `25.7` |
| 22–24 | `\x00\x00\x00` | Padding, outside the frame |

This message needs these **[Binary handler](#handler-configuration)** settings:

| Parameter | Value |
|-----------|-------|
| **Max Frame Length (in bytes)** | `128` |
| **Length Field Offset** | `4` |
| **Length Field Length** | `1` |
| **Length Adjustment** | `0` |
| **Number of first bytes to strip out from the decoded frame** | `5` |
| **Byte Order of the length field** | Little Endian |
</TabItem>
</Tabs>

### Create the Uplink Data Converter

The uplink converter reads one framed message and maps it to ThingsBoard entities and data. TCP Integration uses the **Generic** converter: you write the decoder in TBEL or JavaScript. For converter types and the full decoder reference, see <DocLink product={props.product} path="user-guide/integrations/uplink-data-converter/#converter-types" target="_blank">Uplink data converter</DocLink>.

<Steps>
1. Go to **Integrations &#8702; Data converters** and click **+ Add data converter &#8702; Create new converter**.
2. **Converter type** — keep **Uplink**.
3. **Integration type** — select **TCP**.
4. **Name** — enter a name, for example `TCP Uplink Converter`.
5. **Main decoding configuration** — the editor is pre-filled with the default decoder template for JSON payloads. Replace it with the decoder for your payload format below and, if needed, adapt the field names to your device. The editor opens in TBEL; use the **TBEL / JS** toggle to switch to JavaScript.
   <Aside type="tip" title="TBEL">
     Use <DocLink product={props.product} path="user-guide/tbel" target="_blank">TBEL</DocLink> for converter scripts — it runs much faster than JavaScript inside ThingsBoard.
   </Aside>
   <Tabs>
   <TabItem label="Text">
   <Tabs>
   <TabItem label="TBEL (Recommended)">
   ```js maxLines=20 collapsible
   /** Decoder **/

   // decode payload to string
   var strArray = decodeToString(payload);
   var payloadArray = strArray.replaceAll("\"", "").replaceAll("\\n", "").split(',');

   var telemetryPayload = {};
   for (var i = 2; i < payloadArray.length; i = i + 2) {
       var telemetryKey = payloadArray[i];
       var telemetryValue = parseFloat(payloadArray[i + 1]);
       telemetryPayload[telemetryKey] = telemetryValue;
   }

   // Result object with device attributes/telemetry data
   var result = {
       deviceName: payloadArray[0],
       deviceType: payloadArray[1],
       telemetry: telemetryPayload,
       attributes: {}
   };

   /** Helper functions 'decodeToString' and 'decodeToJson' are already built-in **/

   return result;
   ```
   </TabItem>
   <TabItem label="JavaScript">
   ```js maxLines=25 collapsible
   /** Decoder **/

   // decode payload to string
   var strArray = decodeToString(payload);
   var payloadArray = strArray.replace(/"/g, "").replace(/\s/g, "").split(',');

   var telemetryPayload = {};
   for (var i = 2; i < payloadArray.length; i = i + 2) {
       var telemetryKey = payloadArray[i];
       var telemetryValue = parseFloat(payloadArray[i + 1]);
       telemetryPayload[telemetryKey] = telemetryValue;
   }

   // Result object with device attributes/telemetry data
   var result = {
       deviceName: payloadArray[0],
       deviceType: payloadArray[1],
       telemetry: telemetryPayload,
       attributes: {}
   };

   /** Helper functions **/

   function decodeToString(payload) {
       return String.fromCharCode.apply(String, payload);
   }

   return result;
   ```
   </TabItem>
   </Tabs>

   Each call receives one record. Position 0 is the device name, position 1 the device type, then telemetry key–value pairs.

   **To adapt:**

   - **Another delimiter** — replace `split(',')`, for example with `split(';')`.
   - **Name or type at another position** — change the `payloadArray[0]` and `payloadArray[1]` indexes.
   - **Fixed telemetry keys** — replace the loop with explicit assignments: `telemetryPayload['temperature'] = parseFloat(payloadArray[2]);`.
   - **Attributes instead of telemetry** — move the fields to `attributes`.

   </TabItem>

       return String.fromCharCode.apply(String, payload);

   </TabItem>

   The decoder parses the message as a JSON object and maps its fields directly.

   **To adapt:**

   - **Other field names** — replace `data.deviceName` and `data.deviceType`, for example with `data.id` and `data.model`.
   - **More telemetry** — add fields, for example `pressure: data.pressure`.
   - **Device properties** — move them to `attributes`, for example `firmware: data.fw`.

   ```js maxLines=30 collapsible

   // decode payload to string
   var payloadStr = decodeToString(payload);

   var deviceName = payloadStr.substring(0, 6);
   var deviceType = payloadStr.substring(6, 13);

   var result = {
      deviceName: deviceName,

   **To adapt:**

   - **Another byte layout** — change the `substring(start, end)` offsets.
   - **Another header size** — change **Number of first bytes to strip out from the decoded frame** in the handler.
   - **Integers stored as raw bytes** — use `parseBytesToInt(payload, offset, length, bigEndian)`, for example `temperature: parseBytesToInt(payload, 13, 2, true) / 100.0`.

<h4>Decoder Inputs</h4>

The decoder signature is `function decoder(payload, metadata): object | object[]`.

| Variable | Type | Content |
|----------|------|---------|
| `payload` | byte array | One message as framed by the **[handler](#handler-configuration)**: without the delimiter if **Strip delimiter** is on (Text), or without the stripped header bytes (Binary). |
| `metadata` | `{[key: string]: string}` | `integrationName` and the key–value pairs from the integration's **Metadata** field. |

Built-in helpers:

| Function | Result |
|----------|--------|
| `decodeToString(payload)` | Converts the bytes to a UTF-8 string. |
| `decodeToJson(payload)` | Parses the bytes as JSON and returns an object. |

For more parsing patterns, see <DocLink product={props.product} path="user-guide/integrations/uplink-data-converter/#common-scripting-patterns" target="_blank">Common scripting patterns</DocLink>.

<h4 id="test-the-decoder">Test the Decoder</h4>

```

### Create the Integration

<Steps>
1. Go to **Integrations &#8702; Integrations** and click **+ Add integration**.
2. **Basic settings:**
   - **Integration type** — select **TCP**.
   - **Name** — enter a name, for example `TCP integration`.
   - **Enable integration** and **Allow create devices or assets** — keep both on, so the device is created on its first uplink.
   - Click **Next**.
3. **Uplink data converter:**
   - Click **Select existing** and choose `TCP Uplink Converter`.
   - Alternatively, click **Create new** to write a decoder here.
   - Click **Next**.
4. **Downlink data converter:**
   - Click **Skip**. Add a downlink converter later if you need to **[send commands to the device](#configure-downlink)**.
5. **Connection:**
   - **Port** — keep `10560` or enter your own.
   - **Handler Type** — select the handler that matches your payload format. See **[Handler Configuration](#handler-configuration)**.
   - Copy the **Integration key** and **Integration secret**. You need them to **[run the remote integration](#install-and-run-the-remote-integration)**.
   - Leave the other parameters at their defaults. See **[Connection Settings](#connection-settings)** for details.
6. Click **Add**.
</Steps>

#### Connection Settings

| Parameter | Description |
|-----------|-------------|
| **Port** | TCP port the remote integration listens on. Default: `10560`. Must be free on the remote host. If the port is busy, the integration retries binding every 5 seconds. |
| **Max number of pending connects on the socket** | Queue length for connections not yet accepted. Default: `128`. Raise it for many simultaneous connections. |
| **Size of the buffer for inbound socket (in KB)** | Socket receive buffer. Default: `64`. |
| **Size of the buffer for outbound socket (in KB)** | Socket send buffer. Default: `64`. |
| **Enable sending of keep-alive messages on connection-oriented sockets** | Sends TCP keep-alive probes to detect dead connections. Off by default. Turn it on for long-lived connections that can drop silently. |
| **Forces a socket to send the data without buffering (disable Nagle's buffering algorithm)** | Sends each write immediately instead of batching small packets. On by default. |
| **Cache Size** / **Cache time to live in minutes** | Limits of the cache that maps devices to sender addresses for downlinks. Defaults: `1000` entries and `1440` minutes (24 hours). |
| **Execute remotely** | Always on for TCP. Shows the **Integration key** and **Integration secret** for the remote process. See <DocLink product={props.product} path="user-guide/integrations/remote" target="_blank">Remote Integration</DocLink>. |
| **Metadata** | In **Advanced settings**. Key–value pairs added to the `metadata` of every message from this integration. |

#### Handler Configuration

TCP has no message boundaries, so the handler defines how the byte stream is split into messages. Select it in **Handler Type** (default: **Binary**).

<Tabs>
<TabItem label="Binary">

Reads a length field from each message header and cuts the frame to that length.

| Parameter | Description |
|-----------|-------------|
| **Max Frame Length (in bytes)** | Largest allowed frame. Default: `128`. |
| **Length Field Offset** | Position of the length field from the start of the frame, in bytes. Default: `0`. |
| **Length Field Length** | Size of the length field: `1`, `2`, `3`, `4`, or `8` bytes. Default: `2`. |
| **Length Adjustment (the compensation value to add to the value of the length field)** | Added to the length field value to get the number of bytes that follow it. Range: `0`–`8`. Default: `0`. |
| **Number of first bytes to strip out from the decoded frame** | Bytes removed from the start of the frame before the converter runs, typically the header. Default: `0`. |
| **Byte Order of the length field** | **Little Endian** (default) or **Big Endian**. |
| **Thrown exception soon as the decoder notices the length of the frame will exceed max size** | Raises the error as soon as the length field exceeds **Max Frame Length**, instead of after the whole frame arrives. Off by default. |

</TabItem>
<TabItem label="Text">

Splits the stream at a delimiter. For CSV, plain-text lines, or text-encoded JSON.

| Parameter | Description |
|-----------|-------------|
| **Max Frame Length (in bytes)** | Largest allowed message. Longer messages raise an error. Default: `128`. |
| **Strip delimiter** | Removes the delimiter before the converter runs. On by default. |
| **Message separator type** | **System line separator** (`\n` or `\r\n`), **Nul delimiter** (`\0`), or **Custom separator** (any string, entered in **Separator**). Default: **System line separator**. |

</TabItem>
<TabItem label="JSON">

Reads the stream until a complete JSON object or array arrives and passes it to the converter. No delimiter or settings needed.

</TabItem>
</Tabs>

## Configure Downlink

ThingsBoard sends a downlink over the open connection on which the device sent its last uplink, and appends `\n` to every downlink payload. If that connection is closed, the downlink is held and sent right after the device's next uplink. The device must therefore keep the connection open to receive commands immediately.

<Aside type="note">
  The integration links a device to a connection only while a downlink converter is assigned. After you add the converter, the device must send an uplink before ThingsBoard can reach it.
</Aside>

The downlink converter turns a <DocLink product={props.product} path="user-guide/rule-engine" target="_blank">Rule Engine</DocLink> message into the bytes sent to the device. For the full encoder reference, see <DocLink product={props.product} path="user-guide/integrations/downlink-data-converter" target="_blank">Downlink data converter</DocLink>.

### Create and Assign the Downlink Converter

<Steps>
1. Open the integration in **Integrations &#8702; Integrations** and click **Toggle edit mode** (pencil icon).
2. In the **Downlink data converter** field, click **Create new**. The **Downlink** converter type and **TCP** integration type are preselected.
3. Enter a name, for example `TCP Downlink Converter`.
4. **Main encoding configuration** opens with a default encoder. Use the encoder shown below or your own.
5. To record downlink events, click the debug icon next to the name, select **All messages**, and click **Apply**.
6. Click **Add**, then **Apply changes**.
</Steps>

Encoder used in this guide:

```js
/** Encoder **/

// Encode downlink data from the incoming Rule Engine message.
// msg: JSON message payload.
// msgType: message type, e.g. 'ATTRIBUTES_UPDATED', 'POST_TELEMETRY_REQUEST', etc.
// metadata: key-value pairs containing additional message data.
// integrationMetadata: key-value pairs configured in the integration.

var result = {
    // Specify the response body format: JSON, TEXT, or BINARY.
    contentType: "JSON",

    // Serialize the incoming message and use it as the TCP payload.
    data: JSON.stringify(msg),

    // Add optional metadata when required by the integration.
    metadata: {}
};

return result;
```

## Troubleshooting

| Symptom | Cause | Fix |
|---------|-------|-----|
| Device not created | `deviceName` is empty or undefined. | Check **Out** in the converter events. Make sure the decoder extracts `deviceName`. |
| Converter error | The decoder threw an exception. | Open the converter's **Events** tab and check **Error**. Test the decoder with a sample payload. |
| Messages split or merged wrongly | The handler does not match the device framing. | Match the **Handler Configuration** to the protocol. Capture the raw TCP bytes to check the framing. |
| Messages dropped with a frame-length error | A message is longer than **Max Frame Length**. | Raise **Max Frame Length (in bytes)**. |
| Remote integration does not connect to ThingsBoard | Wrong host, port, key, or secret. | Check `host`, `port`, `routingKey`, and `secret` in `tb-remote-integration.yml`. Make sure gRPC port `9090` is reachable. |
| Port already in use | Another process holds the port. | Free the port or pick another one. The integration retries binding every 5 seconds. |
| Downlink not received | The connection closed after the uplink, or no uplink arrived after the downlink converter was added. | Keep the connection open (`-w60` or a persistent client) and send an uplink first. Check the Root Rule Chain wiring. |
| Wrong timestamp | The device sends `ts` in seconds. | Convert it: `ts: data.ts * 1000`. |
| Telemetry not saved | The decoder returns `{}`, `[]`, or empty `telemetry`. | Make sure `telemetry` holds at least one key. |

To read debug events, open the integration or converter, click **Events**, and select an event: **In** is the received data, **Out** is the converter result, and **Error** holds the error text.
