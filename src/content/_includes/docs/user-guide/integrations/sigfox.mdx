SigFox Integration receives device messages from the <a href="https://www.sigfox.com/" target="_blank" rel="noopener noreferrer nofollow"><strong>Sigfox Backend</strong></a> through a custom HTTP callback. An **uplink data converter** transforms each message into device data, including telemetry and attributes. For downlink, ThingsBoard returns the queued command in the HTTP response to the callback, and the Sigfox Backend sends it to the device.

Use SigFox Integration when:
- Your devices transmit over the Sigfox network and their messages reach the Sigfox Backend.
- You need to send short configuration commands (up to 8 bytes) back to devices that request a downlink.

1. **Transmit an uplink.** The device sends a message over the Sigfox network to the Sigfox Backend.
2. **Forward the message.** A custom callback on the device type sends the message as an HTTP `POST` with a JSON body to the integration endpoint. The body holds the Sigfox variables you choose, such as `device`, `time`, and `data`.
3. **Decode the payload.** The uplink converter maps the Sigfox device ID to the device name and decodes the hex `data` into telemetry and attributes. If **Allow create devices or assets** is on, ThingsBoard creates the device on its first message.
4. **Return downlink data (optional).** If a downlink is queued for the device, ThingsBoard encodes it and returns it in the response to the same callback request. ThingsBoard cannot open a connection to the Sigfox Backend on its own.

## Prepare Sigfox

Callbacks and downlink settings belong to the **device type**, not to a single device. Every device of that type uses them.

### Find the Device Type

<Steps>
1. Log in to the Sigfox Backend and open **Device**.
2. Open your device and note its **Id**, for example `1CB0F1`. The callback sends it as `{device}`, and this guide uses it in the ThingsBoard device name.
3. Note the device type the device belongs to, for example `thermostats`. You create the callback on this device type.
</Steps>

### Payload Format Used in This Guide

This guide uses a CO₂ sensor that sends a 7-byte payload. The Sigfox Backend passes it to the callback as a hex string in `{data}`, for example `2502af2102462a`:

| Bytes | Field | Decoding |
|-------|-------|----------|
| 0 | Flags and firmware version | Bit 0: auto calibration (`on`/`off`). Bit 1: zero point adjusted. Bit 2: transmit power (`full`/`low`). Bit 3: power control (`on`/`off`). Bits 4–7: firmware version. |
| 1–2 | Temperature | Value / 10 − 40, in °C. |
| 3 | Humidity | Value, in %. |
| 4–5 | CO₂ | Value, in ppm. |
| 6 | CO₂ baseline | Value × 10, in ppm. `0` means 400 ppm. |

The default SigFox decoder reads this layout. Replace the decoding with your device's layout from its datasheet.

| Variable | Type | Content |

| `payload` | byte array | The callback body, as compact JSON. |

### Create the Integration

<Steps>
1. Go to **Integrations &#8702; Integrations** and click **+ Add integration**.
2. **Basic settings:**
   - **Integration type** — select **SigFox**.

   - Click **Skip**. Add a downlink converter later if you need to **[send commands to the device](#configure-downlink)**.

   - Copy the **HTTP endpoint URL**. You need it for the Sigfox callback.
   - Leave the other parameters at their defaults. See **[Connection Settings](#connection-settings)** for details.
6. Click **Add**.
</Steps>

#### Connection Settings

| Parameter | Default | Description |
|-----------|---------|-------------|
| **Base URL** | Address of the current ThingsBoard server | Used to build the endpoint URL. Must be a public address. Example: `https://thingsboard.cloud`. |
| **HTTP endpoint URL** | — | Read-only. Format: `{Base URL}/api/v1/integrations/sigfox/{integrationKey}`, where `integrationKey` is a UUID assigned at creation. Accepts JSON bodies only. |
| **Enable security (Headers filter)** | Off | Accepts only requests that carry the configured headers. See **[Secure the Endpoint with Header Filters](#secure-the-endpoint-with-header-filters)**. |
| **Execute remotely** | Off | Runs the integration as a separate process outside the ThingsBoard cluster. ThingsBoard generates an **Integration key** and **Integration secret** for it. The Sigfox Backend needs a public endpoint, so the standard setup keeps this off. See <DocLink product={props.product} path="user-guide/integrations/remote" target="_blank">Remote Integration</DocLink>. |
| **Replace response status from 'No-Content' to 'OK'** | Off | In **Advanced settings**. Has no effect on SigFox Integration: without a downlink, the endpoint always returns `204`. |
| **Description** | — | In **Advanced settings**. Free-text description. |
| **Metadata** | — | In **Advanced settings**. Key–value pairs added to the `metadata` of every message from this integration. The key `SigFoxDeviceIdAttributeName` has a special meaning: see **[How the Integration Responds](#how-the-integration-responds)**. |

#### How the Integration Responds

The integration answers each callback request with one of these statuses:

| Status | When |
|--------|------|
| `200 OK` | A downlink is queued for the device. The body is `{"<Sigfox device ID>":{"downlinkData":"<data>"}}` with `Content-Type: application/json`. |
| `204 No Content` | No downlink is queued, or the decoder returned an empty result. |
| `400 Bad Request` | The decoder failed, or it returned data for more than one device. In the second case, the data is saved anyway. |
| `403 Forbidden` | **Enable security** is on, and a required header is missing or has another value. The decoder does not run. |
| `500 Internal Server Error` | No enabled integration has this `integrationKey`. Or processing failed after decoding, for example because the body has no `device` field; in that case, the data is saved anyway. |

The integration reads the Sigfox device ID for the response from the body field `device`, or `Device` if `device` is missing. To read it from another field, add the key `SigFoxDeviceIdAttributeName` to the integration's **Metadata** with that field's name as the value. Every request must carry this field, even if you do not use downlink.

### Create the Sigfox Callback

<Steps>
1. In the Sigfox Backend, open **Device type** and select the device type of your device.
2. Open **Callbacks** and click **New**.
3. Select **Custom callback**.
4. Set the callback fields:
   - **Type** — `DATA`, and `BIDIR` if you plan to use downlink, or `UPLINK` for uplink only.

   - **Use HTTP Method** — `POST`.

   - **Content type** — `application/json`.
   - **Body** — the JSON below.

  "time": "{time}",
  "data": "{data}",

## Secure the Endpoint with Header Filters

Anyone who knows the endpoint URL can send data to it. A header filter rejects every request that does not carry the required headers with the exact values, and returns `403 Forbidden` before the converter runs. The Sigfox Backend shows the failed call in the callback status of the message.

<Steps>
1. In ThingsBoard, open the integration and click **Toggle edit mode** (pencil icon).
2. Turn on **Enable security (Headers filter)**.
3. Click **Add** and enter a **Header** and **Value**, for example `x-api-key` and a secret value. The header name is not case-sensitive. A request must carry every header in the list. The value match is exact and case-sensitive.
4. Click **Apply changes**.
5. In the Sigfox Backend, edit the callback and add the same header and value under **Headers**. Click **Ok**.
</Steps>

## Configure Downlink

Sigfox downlinks are not pushed. ThingsBoard queues the downlink for the device and returns it in the response to the next callback request for that device:

- The queue holds one downlink per device. A newer Rule Engine message replaces the queued one.
- ThingsBoard sends the queued downlink in response to any callback request it receives for the device, then removes it from the queue. The Sigfox Backend delivers it only if the device requested a downlink in that message.
- The device firmware decides when to request a downlink. ThingsBoard cannot trigger one.
- A Sigfox downlink carries exactly 8 bytes, written as 16 hex characters.

The downlink converter turns a <DocLink product={props.product} path="user-guide/rule-engine" target="_blank">Rule Engine</DocLink> message into the downlink payload. For the full encoder reference, see <DocLink product={props.product} path="user-guide/integrations/downlink-data-converter" target="_blank">Downlink data converter</DocLink>.

<Steps>

3. Open **Callbacks**. Check that the callback has the subtype `BIDIR`.

Encoder used in this guide. It sends the value of the shared attribute `downlink`:

<Tabs>
  <TabItem label="TBEL (Recommended)">
    ```js maxLines=15 collapsible
    /** Encoder **/

    // Sigfox downlink: 8 bytes as 16 hexadecimal characters.
    // msg.downlink holds the value of the shared attribute "downlink".
    var result = [];

    if (msg.downlink != null) {
        var payload = "" + msg.downlink;

        // A value saved as a number loses its leading zeros. Restore them.
        while (payload.length() < 16) {
            payload = "0" + payload;
        }

        if (payload.length() > 16) {
            raiseError("Sigfox downlink payload must not exceed 16 hexadecimal characters.");
        }

        result = {
            contentType: "TEXT",
            data: payload,
            metadata: {}
        };
    }

    // An empty array sends no downlink, for example for other attribute updates.
    return result;
    ```
  </TabItem>
  <TabItem label="JavaScript">
    ```js maxLines=15 collapsible
    /** Encoder **/

    // Sigfox downlink: 8 bytes as 16 hexadecimal characters.
    // msg.downlink holds the value of the shared attribute "downlink".
    var result = [];

    if (msg.downlink != null) {
        var payload = String(msg.downlink);

        // A value saved as a number loses its leading zeros. Restore them.
        while (payload.length < 16) {
            payload = "0" + payload;
        }

        if (payload.length > 16) {
            throw new Error("Sigfox downlink payload must not exceed 16 hexadecimal characters.");
        }

        result = {
            contentType: "TEXT",
            data: payload,
            metadata: {}
        };
    }

    // An empty array sends no downlink, for example for other attribute updates.
    return result;
    ```
  </TabItem>
</Tabs>

The integration reads these fields from the encoder result:

| Field | Description |
|-------|-------------|
| `data` | Required. Sent unchanged as `downlinkData`. Must be 16 hex characters for the Sigfox Backend to accept it. |
| `contentType` | Required. Use `TEXT`. `JSON` also sends `data` unchanged. `BINARY` decodes `data` from Base64 first, which breaks a hex string. |
| `metadata` | Not used by SigFox Integration. The response always uses the Sigfox device ID from the callback body. |

The encoder must return exactly one result. An empty array, or more than one result, sends no downlink: the endpoint returns `204` and the queued message is dropped.

To test the encoder, click **Test encoder function**, replace the message with `{"downlink": "0000780001900000"}`, and click **Test**. **Output** shows `data` = `0000780001900000`.

**To adapt:**
- **Another attribute** — replace `msg.downlink` with your attribute key, for example `msg.config`.
- **Payload built from several values** — build the hex string in the encoder, for example from `msg.interval` and `msg.mode`, and pad each field to its byte length.
- **Fixed-length payload of another size** — keep the result at 16 hex characters. Fill unused bytes with `0`.

### Configure the Root Rule Chain

Route shared attribute updates to the integration.

<Steps>
1. Go to **Data processing &#8702; Rule chains** and open the **Root Rule Chain**.
2. From the **Action** section, drag an **integration downlink** node onto the canvas.
3. Enter a **Name** (for example, `Downlink to SigFox integration`), select your SigFox integration, and click **Add**.
4. Connect the **message type switch** node to the **integration downlink** node with the **Attributes Updated** relation.
5. Click **Apply changes**.
</Steps>

<Aside type="caution">
  Do not add the **Post attributes** relation. The integration posts the decoded attributes on every uplink. Each post would replace the queued downlink with a message that has no `downlink` key, so the downlink would never be sent.
</Aside>

### Test Downlink

Add a shared attribute to queue a downlink, then send an uplink to receive it.

<Steps>
1. Go to **Devices & assets &#8702; Devices**, select `Sigfox-1CB0F1`, and open the **Attributes** tab.
2. Select **Shared attributes** and click **+**.
3. Set **Key** to `downlink`, **Type** to **String**, **Value** to `0000780001900000`, and click **Add**. ThingsBoard queues the downlink.
4. Send the **[test uplink](#send-a-test-uplink)** again, or wait for the device to send an uplink that requests a downlink.
</Steps>

In this guide's sensor, the payload `0000780001900000` sets a 2-hour reporting interval:

| Bytes | Meaning |
|-------|---------|
| `00` | Byte 0 — transmit power mode 1 off. |
| `00 78` | Bytes 1–2 — reporting interval, `0x0078` = 120 minutes. |
| `01 90` | Bytes 3–4 — CO₂ baseline calibration, `0x0190` = 400 ppm. |
| `00 00 00` | Bytes 5–7 — not used. |

The command format is device-specific. Take it from your device's datasheet.

## Troubleshooting

| Symptom | Cause | Fix |
|---------|-------|-----|
| The callback fails, and the integration has no events | Wrong **Url pattern**, ThingsBoard is unreachable, or the request is not JSON. | Copy the **HTTP endpoint URL** again. Check that ThingsBoard is reachable from the internet. Set **Content type** to `application/json` and check the body syntax. |
| Callback returns `500`, and the integration has no new events | Wrong integration key in the URL, or the integration is disabled. | Copy the **HTTP endpoint URL** from the integration again, and check that the integration is enabled. |
| Callback returns `403` | **Enable security** is on, and the callback does not send the header with the exact value. | Add the header to the callback's **Headers**, and check that its value matches the integration's, including case. |
| Callback returns `500`, error `Incoming message should contain either 'device' or 'Device' field!` | The callback body has no `device` field. | Add `"device": "{device}"` to the body, or set `SigFoxDeviceIdAttributeName` in the integration's **Metadata**. |
| Callback returns `400` | The decoder failed, for example because `data` is missing. | Check the **Error** column in the converter events. Make sure the body has the fields the decoder reads. |
| Device named `Sigfox-null` or `Sigfox-undefined` | The body has no `device` field, or the field name differs. | Use the **[callback body](#create-the-sigfox-callback)** from this guide. Variable names are case-sensitive. |
| Telemetry values look wrong | The decoder does not match the device's byte layout. | Check the layout in the datasheet and adjust the `substring` ranges and scaling. |
| Callback returns `204` although a downlink is queued | No downlink converter is assigned, the encoder returned an empty array, or the queued message was replaced by another attribute update. | Assign the converter. Set the `downlink` attribute again, and check that only the **Attributes Updated** relation leads to the **integration downlink** node. |
| ThingsBoard returned the downlink, but the device did not get it | The device did not request a downlink in that message, **Downlink mode** is not `CALLBACK`, or the callback is not the active downlink callback. | Set **Downlink mode** to `CALLBACK`, use subtype `BIDIR`, and fill the circle in the **Downlink** column. Set the attribute again, then let the device send an uplink that requests a downlink. |
| The Sigfox Backend rejects the downlink | `downlinkData` is not 16 hex characters. | Return exactly 8 bytes as hex from the encoder. |

To read debug events, open the integration or converter, click **Events**, and select an event: **In** is the received data, **Out** is the converter result, and **Error** holds the error text.
