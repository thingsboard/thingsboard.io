CoAP Integration lets devices that use the **[Constrained Application Protocol (CoAP)](https://tools.ietf.org/html/rfc7252)** send data to ThingsBoard through a dedicated CoAP endpoint. CoAP is a lightweight UDP-based request/response protocol for low-power, low-bandwidth hardware. An **uplink data converter** transforms each incoming request into device or asset data, including telemetry and attributes. The integration is uplink-only: it does not send downlink messages to devices.

Use CoAP Integration when:
- Devices use CoAP (RFC 7252): constrained MCUs, NB-IoT modules, or similar hardware.
- Firmware lacks the memory or power budget for HTTP or MQTT.
- The network is lossy or UDP-only.
- The device firmware sends a payload format you cannot change.

<Aside type="note">
  To connect devices that send data in the ThingsBoard format, use the <DocLink product={props.product} path="reference/coap-api/getting-connected/" target="_blank">CoAP Device API</DocLink> instead — no integration needed.
</Aside>

1. **Receive data.** A device sends a CoAP `POST` or `PUT` request to the integration endpoint — port `5683` for plain CoAP, `5684` for DTLS. Confirmable (CON) and non-confirmable (NON) requests are both accepted.
2. **Decode the payload.** The uplink converter identifies the device or asset and extracts attributes and telemetry.
3. **Process the message.** ThingsBoard processes the converted data through the Rule Engine. If **Allow create devices or assets** is enabled, ThingsBoard can create an entity that does not exist yet.
4. **Respond.** ThingsBoard answers `2.01 Created` on success or `4.00 Bad Request` if processing fails. The response carries no data: CoAP Integration does not support downlink.

## Set Up CoAP Integration

Create the uplink converter, assign it to a new CoAP integration, and send a test request.

### Create the Uplink Data Converter

The uplink converter receives the CoAP request body as a byte array, resolves the target device, and returns its telemetry and attributes. CoAP Integration uses the **Generic** converter: you write the decoder in TBEL or JavaScript. For converter types and the full decoder reference, see <DocLink product={props.product} path="user-guide/integrations/uplink-data-converter/#converter-types" target="_blank">Uplink data converter</DocLink>.

<h4>Decoder Inputs</h4>

The decoder signature is `function decoder(payload, metadata): object | object[]`.

| Variable | Type | Content |
|----------|------|---------|
| `payload` | byte array | The CoAP request body. |
| `metadata` | `{[key: string]: string}` | `integrationName`, the key–value pairs from the integration's **Metadata** field, and the CoAP options below. |

CoAP options added to `metadata` when present in the request:

| Key | Value |
|-----|-------|
| `Option:content-format` | Numeric Content-Format code, for example `50` for `application/json`, `0` for `text/plain`, `42` for `application/octet-stream`. |
| `Option:uri` | Request URI path and query, for example `/i/{integrationKey}/extra?x=1`. |
| `Option:location-path` | Location-Path option values, comma-separated. |
| `Option:location-query` | Location-Query option values, comma-separated. |

The Content-Format also sets how debug events display the payload: JSON (codes `50`, `110`, `11543`), text (`0`, `41`, `46`, `11542`), or binary (any other code, or none).

Built-in helpers:

| Function | Result |
|----------|--------|
| `decodeToJson(payload)` | Parses the bytes as JSON and returns an object. |
| `decodeToString(payload)` | Converts the bytes to a string. |
| `parseBytesToInt(payload, offset, length, bigEndian)` | TBEL only. Reads an integer from raw bytes. |

For field renaming, nested values, and other patterns, see <DocLink product={props.product} path="user-guide/integrations/uplink-data-converter/#common-scripting-patterns" target="_blank">Common scripting patterns</DocLink>.

## Troubleshooting

| Symptom | Cause | Fix |
|---------|-------|-----|
| No response or timeout | Wrong endpoint URL, or the UDP port is blocked. | Copy the **CoAP endpoint URL** again. Open UDP port `5683` (or `5684` for DTLS). |
| `4.04 Not Found` | Wrong integration key in the URI, or the integration is disabled. | Copy the endpoint URL from the integration again. |
| `4.05 Method Not Allowed` | The device sent `GET` or `DELETE`. | Use `POST` or `PUT`. |
| `4.00 Bad Request` | The decoder threw an error or the payload is malformed. | Check the converter's **Events** tab for the error. |
| `4.00 Bad Request` for every request; the converter receives nothing | The request protocol does not match **Security mode**: a DTLS request to a **NO SECURE** integration, or a plain CoAP request to a **DTLS** integration. | Send to the endpoint that matches the mode: `coap://` (port `5683`) for **NO SECURE**, `coaps://` (port `5684`) for **DTLS**. To accept both, set **Security mode** to **MIXED**. |
| Integration fails to save: `CoAP server doesn't have DTLS Endpoint enabled!` | DTLS or MIXED mode is selected, but the server has DTLS off. | **[Enable DTLS](#enable-dtls)** on the server, or use **NO SECURE**. |
| DTLS handshake fails | Client and server certificates or cipher suites do not match. | Check the key store and client credentials against the <DocLink product={props.product} path="reference/coap-api/getting-connected/#coap-over-dtls--server-configuration" target="_blank"><strong>DTLS server configuration</strong></DocLink>. |
| `4.00 Bad Request`; the events show `Device name is missing. Provide deviceName in the payload.` | The converter uses the default template, and the payload has no `deviceName`, or it is empty. | Add `deviceName` to the payload, or adapt the decoder to read the name from another field. |
| `4.00 Bad Request`; the events show `Payload is not a JSON object` | The device sends text or binary data, and the converter uses the default template, which decodes JSON only. The error also shows the request's Content-Format. | Replace the decoder with the **Text payload** or **Binary payload** example from **[Create the Uplink Data Converter](#create-the-uplink-data-converter)**. |
| `4.00 Bad Request`; the events show an error about `deviceName` or `assetName`, for example `Either 'deviceName' or 'assetName' should be present in the converter output!` | A custom decoder returned no `deviceName` (for example `{}`) or an empty one. | Check **In** and **Error** in the converter events. Make sure the payload has the field the decoder reads. |
| Telemetry not saved, no error | The decoder returns `[]` or empty `telemetry`. | Make sure `telemetry` holds at least one key. |
| Wrong timestamp | The device sends `ts` in seconds. | Convert it: `ts: data.ts * 1000`. |

To read debug events, open the integration or converter, click **Events**, and select an event: **In** is the received data, **Out** is the converter result, and **Error** holds the error text.
