AWS Kinesis Integration connects ThingsBoard to <a href="https://aws.amazon.com/kinesis/data-streams/" target="_blank" rel="noopener noreferrer"><strong>Amazon Kinesis Data Streams</strong></a>. ThingsBoard reads every shard of a stream with the Kinesis Client Library (KCL). An **uplink data converter** transforms each record into device or asset data, including telemetry and attributes. ThingsBoard can also write **downlink** records to a Kinesis stream.

Use AWS Kinesis Integration when:
- Devices, AWS IoT rules, or backend services already write data to a Kinesis data stream.
- One stream carries data for many devices: the converter resolves each device from the record.
- You need to send commands or events back to AWS through a stream.

## Architecture

1. **Receive data.** A producer writes a record to the stream. The integration reads each shard and stores its read position (checkpoint) in an Amazon DynamoDB table.
2. **Decode the payload.** The uplink converter receives the record data and its partition key, identifies the device or asset, and extracts attributes and telemetry.
3. **Process the message.** ThingsBoard processes the converted data through the Rule Engine. If **Allow create devices or assets** is enabled, ThingsBoard creates an entity that does not exist yet.
4. **Send downlink data (optional).** The Rule Engine passes a message to the integration. The downlink converter encodes it and names the target stream and partition key. The integration writes the record with the Kinesis Producer Library (KPL).

## Prepare AWS Kinesis

Create two streams and an IAM user whose access key the integration uses.

### Create the Streams

This guide uses the stream `my-thingsboard` for uplink and `tb-test-downlink` for downlink. Create both in the same Region:

```bash
aws kinesis create-stream --stream-name my-thingsboard --shard-count 1
aws kinesis create-stream --stream-name tb-test-downlink --shard-count 1
```

Wait until both streams are active. The command returns when `StreamStatus` is `ACTIVE`:

```bash
aws kinesis wait stream-exists --stream-name my-thingsboard
aws kinesis wait stream-exists --stream-name tb-test-downlink
```

### Create IAM Credentials

Besides Kinesis, the integration uses Amazon DynamoDB and Amazon CloudWatch. KCL creates three DynamoDB tables named after the **Application name** of the integration (by default, the stream name): a lease table with checkpoints, `<name>-CoordinatorState`, and `<name>-WorkerMetricStats`. KCL and KPL also publish metrics to CloudWatch.

<Steps>
1. In the AWS console, open **IAM &#8702; Users** and click **Create user**. Enter a name, for example `thingsboard-kinesis`, and complete the wizard.
2. Open the user, go to the **Permissions** tab, and click **Add permissions &#8702; Create inline policy**.
3. Select **JSON**, paste the policy below, replace `REGION` and `ACCOUNT_ID`, and save it.
4. Open the **Security credentials** tab and click **Create access key**. Select a use case, for example **Application running outside AWS**, and click **Create access key**.
5. Copy the **Access key** and **Secret access key**. AWS shows the secret only once.
</Steps>

## Set Up AWS Kinesis Integration

Create the uplink converter, assign it to a new AWS Kinesis integration, and write a test record.

### Create the Uplink Data Converter

The uplink converter receives the data of each record as a byte array, resolves the target device, and returns its telemetry. AWS Kinesis Integration uses the **Generic** converter: you write the decoder in TBEL or JavaScript. For converter types and the full decoder reference, see <DocLink product={props.product} path="user-guide/integrations/uplink-data-converter/#converter-types" target="_blank">Uplink data converter</DocLink>.

This guide uses a producer that writes records like this:

```json
{
  "devName": "kitchen_thermostat",
  "devType": "thermostat",
  "temperature": 22
}
```

<Steps>
1. Go to **Integrations &#8702; Data converters** and click **+ Add data converter &#8702; Create new converter**.
2. **Converter type** — keep **Uplink**.
3. **Integration type** — select **AWS Kinesis**.
4. **Name** — enter a name, for example `AWS Kinesis Uplink Converter`.
5. **Main decoding configuration** — the editor opens with the generic decoder template. Replace it with the decoder below. It maps `devName` to the device name, `devType` to the device type, and `temperature` to telemetry. The editor opens in TBEL; use the **TBEL / JS** toggle to switch to JavaScript.
   <Aside type="tip" title="TBEL">
     Use <DocLink product={props.product} path="user-guide/tbel" target="_blank">TBEL</DocLink> for converter scripts — it runs much faster than JavaScript inside ThingsBoard.
   </Aside>
   <Tabs>
     <TabItem label="TBEL (Recommended)">
       ```js
       var data = decodeToJson(payload);
       var deviceName = data.devName;
       var deviceType = data.devType;

       var result = {
           deviceName: deviceName,
           deviceType: deviceType,
           telemetry: {
               temperature: data.temperature
           }
       };

       return result;
       ```
     </TabItem>
     <TabItem label="JavaScript">
       ```js maxLines=15 collapsible
       var data = decodeToJson(payload);
       var deviceName = data.devName;
       var deviceType = data.devType;

       var result = {
           deviceName: deviceName,
           deviceType: deviceType,
           telemetry: {
               temperature: data.temperature
           }
       };

       function decodeToString(payload) {
           return String.fromCharCode.apply(String, payload);
       }

       function decodeToJson(payload) {
           var str = decodeToString(payload);
           var data = JSON.parse(str);
           return data;
       }

       return result;
       ```
     </TabItem>
   </Tabs>

   **To adapt:**

   - **Other field names** — replace `data.devName`, `data.devType`, and `data.temperature` with the fields of your records.
   - **Other telemetry** — add keys to `telemetry`, for example `humidity: data.humidity`.
   - **Device properties** — add an `attributes` object next to `telemetry`, for example `attributes: { model: data.model }`.
   - **Device name from the partition key** — if producers use the device ID as the partition key, use `metadata.partitionKey`.
6. Click **Test decoder function** and check the result (see **[Test the Decoder](#test-the-decoder)**).
7. Click **Add**.
</Steps>

To skip copying the code, click **+ Add data converter &#8702; Import converter** instead and import a file with the same decoder: <a href="/resources/docs/integrations/aws-kinesis/aws_kinesis_tbel_uplink_converter.json" download="aws_kinesis_tbel_uplink_converter.json"><strong>TBEL</strong></a> or <a href="/resources/docs/integrations/aws-kinesis/aws_kinesis_javascript_uplink_converter.json" download="aws_kinesis_javascript_uplink_converter.json"><strong>JavaScript</strong></a>.

<h4>Decoder Inputs</h4>

The decoder signature is `function decoder(payload, metadata): object | object[]`.

| Variable | Type | Content |
|----------|------|---------|
| `payload` | byte array | The record data, exactly as the producer wrote it. The AWS CLI and SDKs Base64-encode data only in transit; the decoder receives the original bytes. |
| `metadata` | `{[key: string]: string}` | `partitionKey` and `sequenceNumber` of the record. Also `integrationName` and the key–value pairs from the integration's **Metadata** field. |

For field renaming, nested values, and non-JSON payloads, see <DocLink product={props.product} path="user-guide/integrations/uplink-data-converter/#common-scripting-patterns" target="_blank">Common scripting patterns</DocLink>.

<h4 id="test-the-decoder">Test the Decoder</h4>

Click **Test decoder function** below the editor. Set **Payload content type** to **JSON**, paste the sample record, and click **Test**. The **Output** panel shows:

```json
{
  "deviceName": "kitchen_thermostat",
  "deviceType": "thermostat",
  "telemetry": {
    "temperature": 22
  }
}
```

### Create the Integration

<Steps>
1. Go to **Integrations &#8702; Integrations** and click **+ Add integration**.
2. **Basic settings:**
   - **Integration type** — select **AWS Kinesis**.
   - **Name** — enter a name, for example `AWS Kinesis integration`.
   - **Enable integration** and **Allow create devices or assets** — keep both on, so the device is created on its first record.
   - Click **Next**.
3. **Uplink data converter:**
   - Click **Select existing** and choose `AWS Kinesis Uplink Converter`.
   - Alternatively, click **Create new** to write a decoder here.
   - Click **Next**.
4. **Downlink data converter:**
   - Click **Skip**. Add a downlink converter later if you need to **[write records to a stream](#configure-downlink)**.
5. **Connection:**
   - **Stream name** — `my-thingsboard`.
   - **Region** — the Region of the stream, for example `eu-west-1`.
   - **Initial position in stream** — select **Latest**.
   - **Access Key Id** and **Secret Access Key** — paste the access key of the IAM user.
   - Leave the other parameters at their defaults. See **[Connection Settings](#connection-settings)** for details.
6. Click **Add**.
</Steps>

#### Connection Settings

| Parameter | Description |
|-----------|-------------|
| **Stream name** | Stream the integration reads. Required. |
| **Region** | AWS Region code of the stream, for example `us-east-1`. Required. The DynamoDB tables, CloudWatch metrics, and downlink stream use the same Region. |
| **Initial position in stream** | Where to start reading a shard that has no checkpoint yet. Required. **Latest** reads only records written after the integration starts. **Trim horizon** reads from the oldest record still retained in the stream. **At timestamp** is not supported: the integration fails to start with `Invalid InitialPosition: AT_TIMESTAMP`. |
| **Use credentials from the Amazon EC2 Instance Metadata Service** | Takes credentials from the IAM role of the EC2 instance that runs ThingsBoard or the remote integration. Hides **Access Key Id** and **Secret Access Key**. Off by default. |
| **Access Key Id** and **Secret Access Key** | Access key of the IAM user. Required unless the previous option is on. |
| **Use Consumers with Enhanced Fan-Out** | Reads through an <a href="https://docs.aws.amazon.com/streams/latest/dev/enhanced-consumers.html" target="_blank" rel="noopener noreferrer"><strong>enhanced fan-out</strong></a> consumer with dedicated read throughput, at extra AWS cost. Off by default, so the integration polls the shards. Turning it on hides **Max records** and **Request timeout in seconds**. |
| **Max records** | Polling only. Maximum number of records per `GetRecords` request, 1–10000. Default: `10000`. |
| **Request timeout in seconds** | Polling only. Timeout of a `GetRecords` request. Default: `30`. |
| **Execute remotely** | Runs the integration as a separate process outside the ThingsBoard cluster. ThingsBoard generates an **Integration key** and **Integration secret** for it. See <DocLink product={props.product} path="user-guide/integrations/remote" target="_blank">Remote Integration</DocLink>. |

**Advanced settings**

| Parameter | Default | Description |
|-----------|---------|-------------|
| **Application name** | Stream name | KCL application name. It names the DynamoDB tables that keep the checkpoints. Integrations with the same name share these tables and split the shards between them; use different names for integrations that must each read every record. |
| **Description** | — | Free-text description. |
| **Metadata** | — | Key–value pairs added to the `metadata` of every message from this integration. |

<Aside type="note">
  **Initial position in stream** applies only while the application has no checkpoints. Once the integration has run, it resumes from the stored checkpoints, and changing the position has no effect. To read a stream again from the start, set a new **Application name** and select **Trim horizon**.
</Aside>

## Test Uplink

Write a record to the stream, then confirm that ThingsBoard decoded it and created the device.

<Aside type="note">
  Turn on **Debug** mode with **All messages** for the integration and the uplink converter before you write the record. Without it, the **Events** tabs stay empty.
</Aside>

### Send a Test Uplink

Run <a href="https://docs.aws.amazon.com/cli/latest/reference/kinesis/put-record.html" target="_blank" rel="noopener noreferrer"><strong>`aws kinesis put-record`</strong></a>. The `--cli-binary-format raw-in-base64-out` option makes AWS CLI version 2 send `--data` as plain text:

```bash
aws kinesis put-record \
  --stream-name my-thingsboard \
  --partition-key kitchen_thermostat \
  --cli-binary-format raw-in-base64-out \
  --data '{"devName":"kitchen_thermostat","devType":"thermostat","temperature":22}'
```

With **Latest**, the integration skips records written before it started reading. Write the record after the integration is created.

### Verify the Result

- **Integration events** — go to **Integrations &#8702; Integrations**, open the integration, and click the **Events** tab. The uplink appears with status **OK**. Click <code>&#8901;&#8901;&#8901;</code> in the **Message** column to see the shard ID, sequence number, partition key, and payload.
- **Converter events** — open `AWS Kinesis Uplink Converter` in **Integrations &#8702; Data converters** and click the **Events** tab. **In** shows the record data, **Out** shows the decoded result, and **Metadata** shows the partition key, sequence number, and integration name.
- **Device** — go to **Devices & assets &#8702; Devices**. The integration has created **kitchen_thermostat** with type **thermostat**. Open it and confirm `temperature` = `22` on the **Latest telemetry** tab.

## Configure Downlink

ThingsBoard writes a downlink record when the Rule Engine routes a message to the integration — for example, after a shared attribute update. The target stream and partition key come from `streamName` and `partitionKey` in the downlink converter's output `metadata`. The stream must be in the integration's **Region**.

The downlink converter turns a <DocLink product={props.product} path="user-guide/rule-engine" target="_blank">Rule Engine</DocLink> message into a Kinesis record. For the full encoder reference, see <DocLink product={props.product} path="user-guide/integrations/downlink-data-converter" target="_blank">Downlink data converter</DocLink>.

### Create and Assign the Downlink Converter

The encoder returns:

| Field | Required | Description |
|-------|----------|-------------|
| `contentType` | Yes | `JSON`, `TEXT`, or `BINARY` (a Base64-encoded string). |
| `data` | Yes | Record data. |
| `metadata.streamName` | Yes | Target stream. |
| `metadata.partitionKey` | Yes | Partition key. Records with the same key go to the same shard, in order. |

<Steps>
1. Open the integration in **Integrations &#8702; Integrations** and click **Toggle edit mode** (pencil icon).
2. In the **Downlink data converter** field, click **Create new**. The **Downlink** converter type and **AWS Kinesis** integration type are preselected.
3. Enter a name, for example `AWS Kinesis Downlink Converter`.
4. In **Main encoding configuration**, replace the default encoder with the one below.
5. To record downlink events, click the debug icon next to the name, select **All messages**, and click **Apply**.
6. Click **Add**, then **Apply changes**.
</Steps>

Encoder used in this guide (TBEL and JavaScript):

```js
var data = {
    devName: 'kitchen_thermostat',
    version: msg.version
};

var result = {
    contentType: 'JSON',
    data: JSON.stringify(data),
    metadata: {
        streamName: 'tb-test-downlink',
        partitionKey: '123'
    }
};

return result;
```

The same encoder is available for import: <a href="/resources/docs/integrations/aws-kinesis/aws_kinesis_tbel_downlink_converter.json" download="aws_kinesis_tbel_downlink_converter.json"><strong>TBEL</strong></a> or <a href="/resources/docs/integrations/aws-kinesis/aws_kinesis_javascript_downlink_converter.json" download="aws_kinesis_javascript_downlink_converter.json"><strong>JavaScript</strong></a>. Import it in **Integrations &#8702; Data converters**, then select it in the integration's **Downlink data converter** field.

**To adapt:**

- **Device name** — replace `'kitchen_thermostat'` with `metadata.deviceName` to address the device that triggered the message. Add an **originator fields** node before the **integration downlink** node if the message metadata has no `deviceName`.
- **Partition key** — use a per-device value, for example the device name, to keep each device's records in order.
- **Other stream** — change `streamName`. The IAM policy must allow `kinesis:PutRecords` on that stream.
- **Other payload** — forward other attributes or RPC parameters instead of `msg.version`.

### Configure the Root Rule Chain

<Steps>
1. Go to **Data processing &#8702; Rule chains** and open the **Root Rule Chain**.
2. From the **Action** section, drag an **integration downlink** node onto the canvas.
3. Enter a **Name** (for example, `Downlink to AWS Kinesis`), select your AWS Kinesis integration, and click **Add**.
4. Connect the **message type switch** node to the **integration downlink** node with the **Attributes Updated** relation.
5. Click **Apply changes**.
</Steps>

### Test Downlink

<Steps>
1. Go to **Devices & assets &#8702; Devices**, open `kitchen_thermostat`, and select the **Attributes** tab.
2. Select **Shared attributes** and click **+**.
3. Set **Key** to `version`, **Type** to **String**, **Value** to `v.0.11`, and click **Add**. ThingsBoard writes the downlink record.
</Steps>

### Verify the Downlink

- **ThingsBoard** — the integration's **Events** tab shows a **Downlink** event with the stream name, partition key, and payload.
- **AWS** — read the downlink stream. Get a shard iterator:

  ```bash
  aws kinesis get-shard-iterator \
    --stream-name tb-test-downlink \
    --shard-id shardId-000000000000 \
    --shard-iterator-type TRIM_HORIZON
  ```

  Pass the returned `ShardIterator` to `get-records`:

  ```bash
  aws kinesis get-records --shard-iterator <ShardIterator>
  ```

  The response contains the record, with `Data` Base64-encoded:

  ```json
  {
    "Records": [
      {
        "SequenceNumber": "49599912710236940383450082324919185009278025474345271298",
        "ApproximateArrivalTimestamp": "2026-10-15T10:30:12.270000+00:00",
        "Data": "eyJkZXZOYW1lIjoia2l0Y2hlbl90aGVybW9zdGF0IiwidmVyc2lvbiI6InYuMC4xMSJ9",
        "PartitionKey": "123"
      }
    ],
    "MillisBehindLatest": 0
  }
  ```

  Decode `Data` to get the payload `{"devName":"kitchen_thermostat","version":"v.0.11"}`:

  ```bash
  echo 'eyJkZXZOYW1lIjoia2l0Y2hlbl90aGVybW9zdGF0IiwidmVyc2lvbiI6InYuMC4xMSJ9' | base64 --decode
  ```

<Aside type="note">
  The KPL aggregates records written within a short interval into one Kinesis record. KCL-based consumers split them automatically; a consumer that reads with `GetRecords` directly must deaggregate them with the <a href="https://docs.aws.amazon.com/streams/latest/dev/kinesis-kpl-consumer-deaggregation.html" target="_blank" rel="noopener noreferrer"><strong>KCL deaggregation</strong></a> modules.
</Aside>

## Troubleshooting

| Symptom | Cause | Fix |
|---------|-------|-----|
| No uplinks and no errors | The stream name or **Region** is wrong, or the record was written before the integration started with **Latest**. | Check **Stream name** and **Region**. Write a new record. |
| Integration does not start, `Invalid InitialPosition: AT_TIMESTAMP` | **At timestamp** is selected. | Select **Latest** or **Trim horizon**. |
| `AccessDeniedException` in the logs or events | The IAM policy lacks a Kinesis, DynamoDB, or CloudWatch action. | Compare the policy with **[Create IAM Credentials](#create-iam-credentials)**. Check the table names when you use a custom **Application name**. |
| Old records are not read after switching to **Trim horizon** | Checkpoints from the earlier run already exist. | Set a new **Application name**. |
| Only some records arrive | Another integration or KCL application with the same **Application name** reads the stream and takes some shards. | Give each integration its own **Application name**. |
| Records processed twice after a restart | The integration saves checkpoints on a graceful stop. After an unexpected stop, it resumes from the last saved checkpoint. | Deduplicate in the Rule Engine where it matters, for example by `sequenceNumber`. |
| Decoder error | The record data is not valid JSON. | Open the converter's **Events** tab and check **In**. Adapt the decoder to the producer's format. |
| Device not created | `deviceName` is empty or undefined. | Check **Out** in the converter events. |
| Downlink fails with stream `${streamName}` | The encoder's output `metadata` has no `streamName`, so the placeholder is not replaced. Same for `partitionKey`. | Set both keys in the encoder's `metadata`. |
| Downlink not written | The rule chain does not reach the **integration downlink** node, or the IAM policy denies `kinesis:PutRecords` on the target stream. | Check the **Attributes Updated** relation and the policy. |

To read debug events, open the integration or converter, click **Events**, and select an event: **In** is the received data, **Out** is the converter result, and **Error** holds the error text.
