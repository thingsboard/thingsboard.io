AWS IoT Integration connects ThingsBoard to <a href="https://aws.amazon.com/iot/" target="_blank" rel="noopener noreferrer"><strong>AWS IoT Core</strong></a>, the managed MQTT broker of AWS. ThingsBoard connects as an MQTT client over mutual TLS and subscribes to the topics you configure. An **uplink data converter** transforms each message into device or asset data, including telemetry and attributes. ThingsBoard can also publish **downlink** messages to AWS IoT Core for devices to consume.

Use AWS IoT Integration when:
- Devices already publish to AWS IoT Core and you want their data in ThingsBoard without changing the firmware.
- One subscription must serve many devices: the converter resolves each device from the topic or the payload.
- You need to send commands to devices through AWS IoT Core.

<Aside type="note">
  To read AWS IoT data from a queue or a stream instead, route it with an <a href="https://docs.aws.amazon.com/iot/latest/developerguide/iot-rules.html" target="_blank" rel="noopener noreferrer"><strong>AWS IoT rule</strong></a> and use the <DocLink product={props.product} path="user-guide/integrations/aws-sqs" target="_blank">AWS SQS</DocLink> or <DocLink product={props.product} path="user-guide/integrations/aws-kinesis" target="_blank">AWS Kinesis</DocLink> integration.
</Aside>

1. **Receive data.** A device publishes a message to AWS IoT Core. The integration is subscribed to that topic and receives the message.
2. **Decode the payload.** The uplink converter uses the payload and topic to identify the device or asset and extract attributes and telemetry.
3. **Process the message.** ThingsBoard processes the converted data through the Rule Engine. If **Allow create devices or assets** is enabled, ThingsBoard creates an entity that does not exist yet.
4. **Send downlink data (optional).** The Rule Engine passes a message to the integration. The downlink converter encodes it, and the integration publishes it to AWS IoT Core on the downlink topic.

## Configure AWS IoT

In the <a href="https://console.aws.amazon.com/iot" target="_blank" rel="noopener noreferrer"><strong>AWS IoT console</strong></a>, create a policy, a thing with a certificate, and copy the device data endpoint. ThingsBoard authenticates with the certificate and its private key, and verifies AWS IoT Core with the Amazon Root CA certificate.

### Create a Policy

A policy lists the AWS IoT actions (`Connect`, `Publish`, `Subscribe`, `Receive`) that the certificate may perform. See <a href="https://docs.aws.amazon.com/iot/latest/developerguide/iot-policies.html" target="_blank" rel="noopener noreferrer"><strong>AWS IoT Core policies</strong></a>.

<Steps>
1. Go to **Manage &#8702; Security &#8702; Policies** and click **Create policy**.
2. Enter a **Policy name**, for example `thingsboard-integration-policy`, and click **JSON** to switch the **Policy document** from **Builder** to the JSON editor.
3. Paste the policy below. Replace `YOUR_REGION` and `YOUR_AWS_ID` with your AWS Region code and account ID, for example `eu-north-1` and `111122223333`. The Region menu in the top-right corner of the console shows the Region name (for example, **Europe (Stockholm)**); open it to see the code next to the name. The account ID is in the account menu next to it.
4. Click **Create**.
</Steps>

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Action": ["iot:Publish", "iot:Receive"],
      "Resource": ["arn:aws:iot:YOUR_REGION:YOUR_AWS_ID:topic/*"]
    },
    {
      "Effect": "Allow",
      "Action": ["iot:Subscribe"],
      "Resource": ["arn:aws:iot:YOUR_REGION:YOUR_AWS_ID:topicfilter/*"]
    },
    {
      "Effect": "Allow",
      "Action": ["iot:Connect"],
      "Resource": ["arn:aws:iot:YOUR_REGION:YOUR_AWS_ID:client/*"]
    }
  ]
}
```

<Aside type="tip">
  The policy above allows all topics. In production, limit it to a dedicated namespace: replace `topic/*` with `topic/tb/aws/iot/*` and `topicfilter/*` with `topicfilter/tb/aws/iot/*`. This namespace covers both the device data topics (`tb/aws/iot/telemetry/...`) and the command topics (`tb/aws/iot/commands/...`).
</Aside>

<Steps>

2. Select **Create single thing** and click **Next**.
3. Enter a **Thing name**, for example `thingsboard-integration`. Leave the **Additional configurations** and **Device Shadow** sections at their defaults, and click **Next**.

5. Select the policy you created and click **Create thing**.
6. In the **Download certificates and keys** window, click **Download all**, or download at least these three files:

## Set Up AWS IoT Integration

Create the uplink converter, assign it to a new AWS IoT integration, and publish a test message.

### Create the Uplink Data Converter

The uplink converter receives each MQTT message as a byte array plus its topic, resolves the target device, and returns its telemetry and attributes. AWS IoT Integration uses the **Generic** converter: you write the decoder in TBEL or JavaScript. For converter types and the full decoder reference, see <DocLink product={props.product} path="user-guide/integrations/uplink-data-converter/#converter-types" target="_blank">Uplink data converter</DocLink>.

This guide uses a thermostat that publishes its readings to `tb/aws/iot/telemetry/thermostat/Thermostat-01`:

```json
{
  "ts": 1791901200000,
  "temperature": 25.3,
  "humidity": 62.8,
  "battery": 78.5,
  "fwVersion": "1.4.2",
  "location": {
    "latitude": 37.7749,
    "longitude": -122.4194
  }
}
```

`ts` is the measurement time in milliseconds. Replace it with the current time, or remove it: without `ts`, ThingsBoard uses the time the message arrives.

Devices publish their data under `tb/aws/iot/telemetry/` and receive commands under `tb/aws/iot/commands/`. Keep the two namespaces separate: the integration subscribes only to the data topics, so it does not receive its own downlink messages back as uplinks.

The topic structure `tb/aws/iot/telemetry/{deviceType}/{deviceName}` is a convention of this guide, not an AWS IoT requirement. If your devices publish to other topics, adapt the decoder and the topic filter. The decoder has no fallback values: a message whose topic has no device type or device name is rejected, and no device is created.

<Steps>
1. Go to **Integrations &#8702; Data converters** and click **+ Add data converter &#8702; Create new converter**.
2. **Converter type** — keep **Uplink**.
3. **Integration type** — select **AWS IoT**.
4. **Name** — enter a name, for example `AWS IoT Uplink Converter`.
5. **Main decoding configuration** — the editor opens with the default AWS IoT template, which already takes the device name and type from the topic. Replace it with the decoder below. The decoder takes the device name and type from the last two topic segments (`.../{deviceType}/{deviceName}`), stores `fwVersion` and the `location` coordinates as attributes and `temperature`, `humidity`, and `battery` as telemetry, and uses the device timestamp `ts` if the payload has one. If the topic is missing or its last two segments are empty, the decoder stops with an error. The editor opens in TBEL; use the **TBEL / JS** toggle to switch to JavaScript.
   <Aside type="tip" title="TBEL">
     Use <DocLink product={props.product} path="user-guide/tbel" target="_blank">TBEL</DocLink> for converter scripts — it runs much faster than JavaScript inside ThingsBoard.
   </Aside>
   <Tabs>
     <TabItem label="TBEL (Recommended)">
       ```js maxLines=15 collapsible
       /** Decoder **/

       // ThingsBoard passes the MQTT topic of each AWS IoT message in metadata.topic.
       // This example uses the last two topic segments to identify the device:
       //
       //   tb/aws/iot/telemetry/thermostat/Thermostat-01
       //                        ^^^^^^^^^^ ^^^^^^^^^^^^^
       //                        type       name

       // Get the MQTT topic and reject messages if it is missing or empty.
       var topic = metadata.topic;
       if (topic == null || topic.trim().isEmpty()) {
           raiseError("MQTT topic is missing or empty");
       }

       // Split the topic into segments, preserving empty trailing segments.
       var topicParts = topic.split("/", -1);
       var n = topicParts.length;

       // Reject topics without valid device type and device name segments.
       if (n < 2 || topicParts[n - 1].trim().isEmpty() || topicParts[n - 2].trim().isEmpty()) {
           raiseError("MQTT topic must contain device type and device name: " + topic);
       }

       // Extract the device name and type from the last two topic segments, without surrounding spaces.
       var deviceName = topicParts[n - 1].trim();
       var deviceType = topicParts[n - 2].trim();

       // Decode the incoming payload to a JSON object.
       var data = decodeToJson(payload);

       // Use the device timestamp if provided; otherwise, use the current server time.
       var ts = data.ts != null ? data.ts : Date.now();

       // Map device properties to ThingsBoard attributes.
       var attributes = {
           fwVersion: data.fwVersion
       };

       // Add location attributes if available.
       if (data.location != null) {
           attributes.latitude = data.location.latitude;
           attributes.longitude = data.location.longitude;
       }

       // Map device measurements to ThingsBoard telemetry.
       var telemetry = {
           temperature: data.temperature,
           humidity: data.humidity,
           battery: data.battery
       };

       // Return the converted uplink message.
       return {
           deviceName: deviceName,
           deviceType: deviceType,
           attributes: attributes,
           telemetry: {
               ts: ts,
               values: telemetry
           }
       };
       ```
     </TabItem>
     <TabItem label="JavaScript">
       ```js maxLines=15 collapsible
       /** Decoder **/

       // ThingsBoard passes the MQTT topic of each AWS IoT message in metadata.topic.
       // This example uses the last two topic segments to identify the device:
       //
       //   tb/aws/iot/telemetry/thermostat/Thermostat-01
       //                        ^^^^^^^^^^ ^^^^^^^^^^^^^
       //                        type       name

       // Get the MQTT topic and reject messages if it is missing or empty.
       var topic = metadata.topic;
       if (typeof topic !== "string" || !topic.trim()) {
           throw new Error("MQTT topic is missing or empty");
       }

       // Split the topic into segments; empty segments are kept.
       var topicParts = topic.split("/");
       var n = topicParts.length;

       // Reject topics without valid device type and device name segments.
       if (n < 2 || !topicParts[n - 1].trim() || !topicParts[n - 2].trim()) {
           throw new Error("MQTT topic must contain device type and device name: " + topic);
       }

       // Extract the device name and type from the last two topic segments, without surrounding spaces.
       var deviceName = topicParts[n - 1].trim();
       var deviceType = topicParts[n - 2].trim();

       // Decode the incoming payload to a JSON object.
       var data = decodeToJson(payload);

       // Use the device timestamp if provided; otherwise, use the current server time.
       var ts = data.ts != null ? data.ts : Date.now();

       // Map device properties to ThingsBoard attributes.
       var attributes = {
           fwVersion: data.fwVersion
       };

       // Add location attributes if available.
       if (data.location != null) {
           attributes.latitude = data.location.latitude;
           attributes.longitude = data.location.longitude;
       }

       // Map device measurements to ThingsBoard telemetry.
       var telemetry = {
           temperature: data.temperature,
           humidity: data.humidity,
           battery: data.battery
       };

       // Build the converted uplink message.
       var result = {
           deviceName: deviceName,
           deviceType: deviceType,
           attributes: attributes,
           telemetry: {
               ts: ts,
               values: telemetry
           }
       };

       /** Helper functions **/

       // Convert the byte array to a string.
       function decodeToString(payload) {
           return String.fromCharCode.apply(String, payload);
       }

       // Convert the byte array to a JSON object.
       function decodeToJson(payload) {
           return JSON.parse(decodeToString(payload));
       }

       // Return the converted uplink message.
       return result;
       ```
     </TabItem>
   </Tabs>

   **To adapt:**

   - **Other topic structure** — change the indexes in `topicParts[n - 1]` and `topicParts[n - 2]`, and change the topic filter to match. With the filter `tb/aws/iot/telemetry/+/+`, only topics with exactly two levels after `tb/aws/iot/telemetry/` reach the decoder. With `tb/aws/iot/telemetry/#`, a topic such as `tb/aws/iot/telemetry/Thermostat-01` would also reach it, and the decoder would take `telemetry` as the device type.
   - **Device name in the payload** — use a payload field instead, for example `data.deviceId`.
   - **Other telemetry** — add keys to `telemetry`, for example `pressure: data.pressure`.
   - **Other device properties** — add them to `attributes`, for example `serialNumber: data.serialNumber`.
   - **Update-only keys** — in **Advanced decoding parameters**, the **Update only keys list** of a new AWS IoT converter already contains `fwVersion`, `latitude`, and `longitude`: these keys are stored only when their value changes. Add other keys that rarely change, or remove keys that you want to store with every message.
6. Click **Test decoder function** and check the result (see **[Test the Decoder](#test-the-decoder)**).
7. Click **Add**.
</Steps>

<h4>Decoder Inputs</h4>

The decoder signature is `function decoder(payload, metadata): object | object[]`.

| Variable | Type | Content |
|----------|------|---------|
| `payload` | byte array | The MQTT message body. |
| `metadata` | `{[key: string]: string}` | `topic` — the topic the message arrived on, for example `tb/aws/iot/telemetry/thermostat/Thermostat-01`. Also `integrationName` and the key–value pairs from the integration's **Metadata** field. |

With a wildcard topic filter, `topic` holds the actual topic of the message, not the filter.

For field renaming, nested values, and non-JSON payloads, see <DocLink product={props.product} path="user-guide/integrations/uplink-data-converter/#common-scripting-patterns" target="_blank">Common scripting patterns</DocLink>.

#### Connection Settings

ThingsBoard always connects to AWS IoT Core on port `8883` over TLS, with a clean session.

| Parameter | Description |
|-----------|-------------|
| **AWS IoT Endpoint** | Device data endpoint, in the form `{prefix}-ats.iot.{region}.amazonaws.com`: a host name only, without `https://` or a port. Required. |
| **Credentials** | Certificate files for mutual TLS. See **[Credentials](#credentials)**. |
| **Topic filters** | One or more subscriptions, each with a **Topic** and **QoS**. Default: `#` with QoS `0`. Click **Add topic filter** to add more. See **[Topic Filters](#topic-filters)**. |
| **Execute remotely** | Runs the integration as a separate process outside the ThingsBoard cluster. ThingsBoard generates an **Integration key** and **Integration secret** for it. See <DocLink product={props.product} path="user-guide/integrations/remote" target="_blank">Remote Integration</DocLink>. |

**Advanced settings**

| Parameter | Default | Description |
|-----------|---------|-------------|
| **Protocol version** | MQTT 3.1.1 | `MQTT 3.1`, `MQTT 3.1.1`, or `MQTT 5.0`. AWS IoT Core supports 3.1.1 and 5.0. |
| **Client ID** | empty | Empty: an ID is generated. A custom ID must be unique and at most 128 characters long — AWS IoT Core disconnects a client when another one connects with the same ID. |
| **Max bytes in message** | `32368` | Maximum size of an incoming message, in bytes (1–256,000,000). A bigger message is dropped, and the integration **Events** tab shows an uplink with status **ERROR**. AWS IoT Core itself limits messages to 128 KB.<ShowFor product={props.product} show={[Products.PE]}> The converter script has its own input limit: `TBEL_MAX_TOTAL_ARGS_SIZE` (default 100,000) or `JS_MAX_TOTAL_ARGS_SIZE` (default 150,000) in `thingsboard.yml`. In tests, TBEL decoders failed from about 80 KB and JavaScript decoders from about 95 KB.</ShowFor> |
| **Connection timeout (sec)** | `10` | Time to wait for AWS IoT Core to accept the connection (1–200). |
| **Downlink topic pattern** | `${topic}` | Topic for downlink messages. Each `${key}` is replaced with the value of `key` from the downlink converter's output `metadata`. |
| **Description** | — | Free-text description. |
| **Metadata** | — | Key–value pairs added to the `metadata` of every message from this integration. |

#### Credentials

AWS IoT Integration supports only certificate (PEM) credentials. Upload each file (**Browse file**) or take it from <DocLink product={props.product} path="user-guide/security/secrets-storage" target="_blank">Secrets storage</DocLink>.

| Field | File |
|-------|------|
| **CA certificate file** | `AmazonRootCA1.pem`. Verifies AWS IoT Core. |
| **Certificate file** | Device certificate, `*.pem.crt`. |
| **Private key file** | Private key, `*-private.pem.key`. |
| **Private key password** | Only for an encrypted key. Keys generated by AWS are not encrypted; leave it empty. |

The certificate must be **Active** and have the policy attached. See <a href="https://docs.aws.amazon.com/iot/latest/developerguide/x509-client-certs.html" target="_blank" rel="noopener noreferrer"><strong>X.509 client certificates</strong></a>.

#### Topic Filters

The integration subscribes to all topic filters when it connects. Subscribe to a dedicated namespace rather than `#`, so the integration receives only ThingsBoard traffic. Do not include the downlink topics in the filters: with `tb/aws/iot/#`, the integration would also receive its own commands from `tb/aws/iot/commands/...` and process them as uplinks.

ThingsBoard checks the filters when you save the integration: `#` must be the last level, and `+` must take a whole level.

| Wildcard | Matches | Example filter | Matching topics |
|----------|---------|----------------|-----------------|
| `+` | Exactly one level | `tb/aws/iot/telemetry/+/+` | `tb/aws/iot/telemetry/thermostat/Thermostat-01`, `tb/aws/iot/telemetry/meter/Meter-01` |
| `#` | All remaining levels, any number; must be last | `tb/aws/iot/telemetry/#` | The topics above, and also `tb/aws/iot/telemetry/Thermostat-01` and `tb/aws/iot/telemetry/site-1/thermostat/Thermostat-01` |

This guide uses `tb/aws/iot/telemetry/+/+`: the integration receives only topics with a device type and a device name, in the structure the decoder expects. Messages on topics with fewer or more levels are not delivered to ThingsBoard and do not appear in the integration **Events**.

| QoS | Name | Delivery |
|-----|------|----------|
| `0` | At most once | No acknowledgment. A message may be lost. |
| `1` | At least once | Acknowledged. A message may arrive twice. |

AWS IoT Core does not support QoS 2, so the integration does not offer it. If a subscription fails, for example because the policy denies `iot:Subscribe` for the filter, the integration shows an error status with the reason. See <a href="https://docs.aws.amazon.com/iot/latest/developerguide/topics.html" target="_blank" rel="noopener noreferrer"><strong>MQTT topics</strong></a>.

## Test Uplink

## Configure Downlink

ThingsBoard publishes downlinks to AWS IoT Core when the Rule Engine routes a message to the integration — for example, after a shared attribute update. Downlinks are always published with QoS 1. The topic comes from the **Downlink topic pattern**: with the default `${topic}`, it is the `topic` value in the downlink converter's output `metadata`. If a placeholder of the pattern has no value in the output `metadata`, or the topic contains `+` or `#`, the downlink is not published and the integration **Events** tab shows a `Downlink` event with status **ERROR**.

The downlink converter turns a <DocLink product={props.product} path="user-guide/rule-engine" target="_blank">Rule Engine</DocLink> message into an MQTT payload. For the full encoder reference, see <DocLink product={props.product} path="user-guide/integrations/downlink-data-converter" target="_blank">Downlink data converter</DocLink>.

### Create and Assign the Downlink Converter

The encoder returns:

- `contentType` — `JSON`, `TEXT`, or `BINARY`.
- `data` — the payload to publish.
- `metadata` — values for the **Downlink topic pattern** placeholders, for example `topic`. Use a topic outside the subscribed data topics, for example `tb/aws/iot/commands/{deviceName}`.

For RPC commands, `msg.method` and `msg.params` are available. `msg.params` is a string — use `parseFloat(msg.params)` or `JSON.parse(msg.params)` to get a number or an object.

<Steps>
1. Open the integration in **Integrations &#8702; Integrations** and click **Toggle edit mode** (pencil icon).
2. In the **Downlink data converter** field, click **Create new**. The **Downlink** converter type and **AWS IoT** integration type are preselected.
3. Enter a name, for example `AWS IoT Downlink Converter`.
4. **Main encoding configuration** — the editor opens with the default AWS IoT encoder, which is the encoder below. Keep it, or write your own. The editor opens in TBEL; use the **TBEL / JS** toggle to switch to JavaScript.
5. To record downlink events, click the debug icon next to the name, select **All messages**, and click **Apply**.
6. Click **Add**, then **Apply changes**.
</Steps>

Encoder used in this guide:

<Tabs>
<TabItem label="TBEL (Recommended)">

```js
/** Encoder **/
// Publish the ThingsBoard message as JSON to the device command topic.
// metadata.topic is read by the integration when Downlink topic pattern is ${topic}.

// Get the device name without surrounding spaces and reject the message if it is missing or empty.
// The rule chain adds deviceName to the metadata, for example with an originator fields node.
var deviceName = metadata.deviceName != null ? metadata.deviceName.trim() : null;
if (deviceName == null || deviceName.isEmpty()) {
    raiseError("Message metadata has no deviceName");
}

var result = {
    // Specify the downlink payload format: JSON, TEXT, or BINARY.
    contentType: "JSON",

    // Serialize the incoming message and use it as the MQTT payload.
    data: JSON.stringify(msg),

    // Build a per-device command topic in the same namespace as the uplink.
    metadata: {
        topic: "tb/aws/iot/commands/" + deviceName
    }
};

return result;
```

</TabItem>
<TabItem label="JavaScript">

```js
/** Encoder **/
// Publish the ThingsBoard message as JSON to the device command topic.
// metadata.topic is read by the integration when Downlink topic pattern is ${topic}.

// Get the device name without surrounding spaces and reject the message if it is missing or empty.
// The rule chain adds deviceName to the metadata, for example with an originator fields node.
var deviceName = typeof metadata.deviceName === "string" ? metadata.deviceName.trim() : "";
if (!deviceName) {
    throw new Error("Message metadata has no deviceName");
}

var result = {
    // Specify the downlink payload format: JSON, TEXT, or BINARY.
    contentType: "JSON",

    // Serialize the incoming message and use it as the MQTT payload.
    data: JSON.stringify(msg),

    // Build a per-device command topic in the same namespace as the uplink.
    metadata: {
        topic: "tb/aws/iot/commands/" + deviceName
    }
};

return result;
```

</TabItem>
</Tabs>

**To adapt:**

- **Other payload** — build the object the device expects instead of `msg`, for example `{ "interval": msg.temperatureUploadFrequency }`.
- **Non-JSON payload** — set `contentType` to `TEXT` for a plain string, or `BINARY` with a Base64-encoded string.
- **Other message types** — branch on `msgType` to handle other <DocLink product={props.product} path="reference/rule-engine/message-types" target="_blank">Rule Engine message types</DocLink>.
- **Device name check** — the encoder stops with the error `Message metadata has no deviceName` if the message has no `deviceName` in its metadata, so a command is never published to `tb/aws/iot/commands/null`. The rule chain adds `deviceName` with an **originator fields** node; see **[Configure the Root Rule Chain](#configure-the-root-rule-chain)**.

### Configure the Root Rule Chain

The encoder builds the topic from `deviceName`, so the rule chain first adds the device name to the message metadata.

<Steps>
1. Go to **Data processing &#8702; Rule chains** and open the **Root Rule Chain**.
2. From the **Enrichment** section, drag an **originator fields** node onto the canvas.
3. Enter a **Name** (for example, `Retrieve device name`) and map the source fields:
   - **Name &#8702; deviceName**
   - **Add mapped originator fields to &#8702; Metadata**
   - Click **Add**.
4. Connect the **message type switch** node to the **originator fields** node with the **Attributes Updated** relation.
5. From the **Action** section, drag an **integration downlink** node onto the canvas.
6. Enter a **Name** (for example, `Downlink to AWS IoT integration`), select your AWS IoT integration, and click **Add**.
7. Connect the **originator fields** node to the **integration downlink** node with the **Success** relation.
8. Click **Apply changes**.
</Steps>

## Troubleshooting

| Symptom | Cause | Fix |
|---------|-------|-----|
| Integration status: unknown host | Wrong **AWS IoT Endpoint**. | Copy the endpoint again from **Connect &#8702; Domain configurations** (row **iot:Data-ATS**). Enter the host name only, without `https://` or a port. |
| Integration status: the server certificate is not trusted | Wrong **CA certificate file**. | Upload `AmazonRootCA1.pem` (Amazon Root CA 1, RSA). |
| Integration status: the certificate and the private key do not match, or the key cannot be read | The certificate and private key belong to different things, or the key file is damaged. | Upload the certificate and key downloaded for the same thing. |
| Integration status: connection refused (not authorized) | The certificate is inactive or has no policy, or the policy denies `iot:Connect`. | In the AWS IoT console, check that the certificate is **Active** and that the policy is attached and allows `iot:Connect`. |
| Integration status: connection timeout, on a self-hosted server | Outbound port `8883` is blocked. | Open TCP `8883` to AWS IoT Core, or use a <DocLink product={props.product} path="user-guide/integrations/remote" target="_blank">Remote Integration</DocLink>. |
| Integration status: the connection is lost and restored again and again | Another client uses the same **Client ID**. | Clear **Client ID** to get a generated one, or make it unique. |
| Integration status: subscription failed | The policy denies `iot:Subscribe` or `iot:Receive` for the topic filter. | Check the policy resources: `topicfilter/...` for `iot:Subscribe`, `topic/...` for `iot:Receive`. |
| No messages received, status is Active | No topic filter matches the published topic, for example the topic has fewer or more levels than the filter. | Check the topic filters. `tb/aws/iot/telemetry/+/+` matches `tb/aws/iot/telemetry/thermostat/Thermostat-01`, but not `tb/aws/iot/telemetry/Thermostat-01` or `tb/aws/iot/telemetry/site-1/thermostat/Thermostat-01`. |
| Uplinks of the integration's own commands | The topic filters include the downlink topics, for example `tb/aws/iot/#` with commands in `tb/aws/iot/commands/...`. | Use separate namespaces for data and commands, for example `tb/aws/iot/telemetry/+/+` for the filter. |
| Decoder error, no device created | The topic has no device type or device name (for example, it ends with `/`), the test has no `topic` row, or the payload is not JSON. | Open the converter's **Events** tab and read the **Error** column. To see the decoder's error message, run the same payload and topic in **Test decoder function**. Publish to `tb/aws/iot/telemetry/{deviceType}/{deviceName}`. |
| Device not created | `deviceName` is empty or undefined. | Check **Out** in the converter events. |
| Uplink event with status ERROR: message too large | The message exceeds **Max bytes in message** (default 32,368 bytes). | Raise **Max bytes in message** in **Advanced settings**, or send smaller messages.<ShowFor product={props.product} show={[Products.PE]}> For messages above about 80 KB, also raise `TBEL_MAX_TOTAL_ARGS_SIZE` or `JS_MAX_TOTAL_ARGS_SIZE` in `thingsboard.yml`.</ShowFor> |
| Downlink not received | The rule chain does not reach the **integration downlink** node, or the topic differs from the subscription. | Check the Root Rule Chain wiring and the topic in the integration's **Events**. Check that the policy allows `iot:Publish` on that topic. |
| Downlink event with status ERROR: unresolved placeholder | The downlink converter output `metadata` has no value for a placeholder of **Downlink topic pattern**, for example `topic`. | Return `metadata.topic` from the encoder, or change the pattern. |
| Downlink event with status ERROR: `Message metadata has no deviceName` | The message metadata has no `deviceName`, so the encoder does not publish the command. | Add the **originator fields** node before the **integration downlink** node. |

To read debug events, open the integration or converter, click **Events**, and select an event: **In** is the received data, **Out** is the converter result, and **Error** holds the error text.
