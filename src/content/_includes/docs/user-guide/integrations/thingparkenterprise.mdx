ThingPark Enterprise Integration receives LoRaWAN uplinks from <a href="https://www.actility.com/thingpark-enterprise/" target="_blank" rel="noopener noreferrer"><strong>Actility ThingPark Enterprise</strong></a> (TPE), the private LoRaWAN network server of Actility. TPE sends each uplink as an HTTP request to the integration endpoint. An **uplink data converter** transforms it into device data, including telemetry and attributes. For downlink, ThingsBoard sends commands to the device through the TPE DX API.

Use ThingPark Enterprise Integration when:
- Your LoRaWAN devices are registered in your own ThingPark Enterprise instance.
- You need to send commands from ThingsBoard to those devices, for example when a shared attribute changes.

If your devices are on the Actility ThingPark Wireless network instead, use <DocLink product={props.product} path="user-guide/integrations/thingpark" target="_blank">ThingPark Integration</DocLink>.

1. **Receive data.** The device sends an uplink through a LoRaWAN gateway to ThingPark Enterprise. TPE sends it to the integration endpoint as an HTTP request with a `DevEUI_uplink` JSON body. The query string carries the `AS_ID`, `LrnDevEui`, `LrnFPort`, `Time`, and `Token` parameters.
2. **Check the request.** The `AS_ID` parameter must match the **AS ID** of the integration, and the body must hold `DevEUI_uplink` with `DevEUI` and `FPort`. Otherwise, the integration rejects the request with `403 Forbidden`.
3. **Decode the payload.** The uplink converter unwraps the TPE message, decodes the device payload, and returns telemetry and attributes. If **Allow create devices or assets** is on, ThingsBoard creates the device on its first uplink.
4. **Send a command (optional).** The Rule Engine passes a message to the integration. The downlink converter encodes it, and ThingsBoard sends it right away through the TPE DX API, with an OAuth access token.

- Access to {props.product !== Products.PAAS && props.product !== Products.PAAS_EU && <><DocLink product={Products.PE} path="installation/" target="_blank">ThingsBoard</DocLink> or </>}<a href="/installations/?product=thingsboard-cloud" target="_blank"><strong>ThingsBoard Cloud</strong></a> with integrations enabled for your tenant. The ThingsBoard endpoint must be reachable from your ThingPark Enterprise instance, because TPE calls it.
- Permission to create integrations and data converters, and to edit rule chains for downlink.
- A ThingPark Enterprise instance with at least one LoRaWAN device registered and joined to the network, and an account that can create applications.
- For downlink: credentials that the TPE DX API accepts, and the address of the DX API of your instance.

## Prepare ThingPark Enterprise

TPE sends uplinks only to an **HTTP application** that the device is assigned to. The application needs the integration endpoint URL, so you create it **[after creating the integration](#create-the-http-application)**. Prepare the credentials first.

### Choose the AS ID and AS Key

The **AS ID** and **AS Key** identify ThingsBoard as the application server of the TPE application. You enter the same pair in TPE and in ThingsBoard:

| Credential | Format | Example |
|------------|--------|---------|
| **AS ID** | 16 hexadecimal characters (8 bytes) | `A8360F9312345789` |
| **AS Key** | 32 hexadecimal characters (16 bytes) | `0122456789ABCDEF0122456789ABCDEF` |

Take the values from an existing TPE application, or generate new ones with any hex string generator.

TPE adds the AS ID to every uplink as the `AS_ID` query parameter, and the integration compares it with its own **AS ID**. ThingsBoard sends the AS ID and AS Key back to TPE in every downlink request.

### Get DX API Credentials

Skip this step if you only need uplinks. To send downlinks, the integration calls the TPE DX API. It needs:

- **DX API address** — the base address of the DX API of your TPE instance. The integration appends the API paths to it, for example `/admin/latest/api/oauth/token`.
- **Client ID** and **Client Secret** — the credentials that the DX API accepts for an OAuth `client_credentials` token request, usually the login and password of a TPE user with API access.

## Set Up ThingPark Enterprise Integration

Create the uplink converter and the integration, then create the TPE application that sends uplinks to the integration endpoint.

### Create the Uplink Data Converter

ThingPark Enterprise Integration uses the **Typed** uplink converter. ThingsBoard selects it automatically for this integration type, and you cannot change it later. The converter first unwraps the TPE message: it takes the device payload from `payload_hex` and puts the network fields, such as `eui`, `fPort`, `rssi`, and `snr`, into the metadata. The decoder then decodes only the device payload. For details, see <DocLink product={props.product} path="user-guide/integrations/uplink-data-converter/#typed-uplink-converter" target="_blank">Typed uplink converter</DocLink>.

To use a ready-made decoder for your device model instead, see **[Use a Library Converter](#use-a-library-converter)**.

<Steps>
1. Go to **Integrations &#8702; Data converters** and click **+ Add data converter &#8702; Create new converter**.
2. **Converter type** — keep **Uplink**.
3. **Integration type** — select **ThingParkEnterprise**.
4. Keep **Create new** selected.
5. **Name** — enter a name, for example `ThingPark Enterprise Uplink Converter`.
6. **Main decoding configuration:**
   - **Entity type** — keep **Device**.
   - **Device name** — keep `Device $eui`. ThingsBoard replaces `$eui` with the `DevEUI` of the uplink, for example `Device 0018B20000000123`. Any key from **[Decoder Inputs](#decoder-inputs)** works as a `$key` placeholder.
   - The decoder editor opens in TBEL with a default decoder for a sample 8-byte payload: a 4-byte serial number, then battery, temperature, and saturation. Replace it with your device's decoding logic, or keep it to follow this guide. The decoder below is a shorter version of the default one. For JavaScript, use the **TBEL / JS** toggle and the **JavaScript** tab.
   <Aside type="tip" title="TBEL">
     Use <DocLink product={props.product} path="user-guide/tbel" target="_blank">TBEL</DocLink> for converter scripts — it runs much faster than JavaScript inside ThingsBoard.
   </Aside>
   <Tabs>
     <TabItem label="TBEL (Recommended)">
       ```js
       // payload — the device payload bytes from payload_hex.
       // metadata — integration metadata plus the keys unwrapped from the TPE message.
       return {
           attributes: {
               // Serial number: bytes 0–3.
               sn: parseBytesToInt(payload, 0, 4)
           },
           telemetry: {
               // Time of the uplink, parsed from the Time field of the message.
               ts: metadata.ts,
               values: {
                   battery: parseBytesToInt(payload, 4, 1),
                   temperature: parseBytesToInt(payload, 5, 2) / 100.0,
                   saturation: parseBytesToInt(payload, 7, 1)
               }
           }
       };
       ```
     </TabItem>
     <TabItem label="JavaScript">
       ```js
       // payload — the device payload bytes from payload_hex.
       // metadata — integration metadata plus the keys unwrapped from the TPE message.
       return {
           attributes: {
               // Serial number: bytes 0–3.
               sn: parseBytesToInt(payload, 0, 4)
           },
           telemetry: {
               // Time of the uplink, parsed from the Time field of the message.
               ts: metadata.ts,
               values: {
                   battery: parseBytesToInt(payload, 4, 1),
                   temperature: parseBytesToInt(payload, 5, 2) / 100.0,
                   saturation: parseBytesToInt(payload, 7, 1)
               }
           }
       };

       // Big-endian integer from length bytes at offset.
       function parseBytesToInt(input, offset, length) {
           var result = 0;
           for (var i = offset; i < offset + length; i++) {
               result = (result << 8) | (input[i] & 0xFF);
           }
           return result;
       }
       ```
     </TabItem>
   </Tabs>

   **To adapt:**
   - **Payload layout** — change the byte offsets, lengths, and scaling to match the payload specification of your device.
   - **Device identity** — to override the values of **Main decoding configuration** and **Advanced decoding parameters**, add `name`, `type` (`DEVICE` or `ASSET`), `profile`, `label`, `customer`, or `group` to the result, for example `name: 'Sensor ' + metadata.eui`.
   - **Network fields** — read any key from **[Decoder Inputs](#decoder-inputs)**, for example `metadata.rssi`, or list it in **Advanced decoding parameters** to store it without code.
7. **Advanced decoding parameters** — ThingsBoard pre-fills them for ThingPark Enterprise:
   - **Device profile name**, **Device label**, **Customer name**, and **Device group name** — empty. Without a profile name, the device gets the `default` profile. These fields accept `$key` placeholders too.
   - **Telemetry** — `fCnt`, `data`, `rssi`, `snr`, `channel`, and `decoded`. **Attributes** — `eui`, `fPort`, `adr`, `spreadingFactor`, `bandwidth`, `devAddr`, `frequency`, and `class`. ThingsBoard adds these metadata keys to the decoder output, if the uplink has them. A key that the decoder already returns keeps the decoder value. The lists add keys: they do not filter the decoder output.
   - **Update only keys list** — the same keys as **Attributes**. ThingsBoard stores these keys only when their value changes.
8. Click **Test payload decoder** and check the result (see **[Test the Decoder](#test-the-decoder)**).
9. Click **Add**.
</Steps>

<h4 id="decoder-inputs">Decoder Inputs</h4>

| Variable | Type | Content |
|----------|------|---------|
| `payload` | byte array | The device payload: the bytes of `payload_hex`. If the TPE message has a decoded `payload` object, the decoder gets that object as JSON bytes instead. |
| `metadata` | `{[key: string]: any}` | The keys unwrapped from `DevEUI_uplink` (see the table below), `ts` and `timeTs` (the `Time` field in Unix milliseconds), `payloadFormat` (`BINARY` or `JSON`), and the integration metadata: `integrationName`, the `AS_ID`, `LrnDevEui`, and `LrnFPort` query parameters, and the pairs from the integration's **Metadata** field. A key of the integration metadata replaces an unwrapped key with the same name. |

TPE sends an uplink like this one:

```json
{
  "DevEUI_uplink": {
    "Time": "2026-10-22T10:30:00.000+00:00",
    "DevEUI": "0018B20000000123",
    "FPort": 1,
    "FCntUp": 42,
    "ADRbit": 1,
    "MType": 4,
    "FCntDn": 5,
    "payload_hex": "0000162e5a0a2b41",
    "mic_hex": "a1b2c3d4",
    "Lrcid": "00000065",
    "LrrRSSI": -85.0,
    "LrrSNR": 7.25,
    "SpFact": 7,
    "SubBand": "G0",
    "Channel": "LC1",
    "Lrrid": "FF0000C8",
    "Late": 0,
    "LrrLAT": 48.8566,
    "LrrLON": 2.3522,
    "CustomerID": "100000507",
    "DevAddr": "04A1B2C3",
    "Frequency": 868.1
  }
}
```

The converter unwraps these fields into metadata keys:

| Metadata key | TPE field | Example |
|--------------|-----------|---------|
| `time` | `Time` | `2026-10-22T10:30:00.000+00:00` |
| `eui` | `DevEUI` | `0018B20000000123` |
| `fPort` | `FPort` | `1` |
| `fCnt` | `FCntUp` | `42` |
| `fCntDn` | `FCntDn` | `5` |
| `adr` | `ADRbit` | `1` |
| `mType` | `MType` | `4` |
| `data` | `payload_hex` | `0000162e5a0a2b41` |
| `micHex` | `mic_hex` | `a1b2c3d4` |
| `rssi`, `snr` | `LrrRSSI`, `LrrSNR` | `-85.0`, `7.25` |
| `spreadingFactor` | `SpFact` | `7` |
| `bandwidth` | `SubBand` | `G0` |
| `channel` | `Channel` | `LC1` |
| `lrcid`, `lrrId` | `Lrcid`, `Lrrid` | `00000065`, `FF0000C8` |
| `late` | `Late` | `0` |
| `latitude`, `longitude` | `LrrLAT`, `LrrLON` | `48.8566`, `2.3522` |
| `customerId` | `CustomerID` | `100000507` |
| `devAddr` | `DevAddr` | `04A1B2C3` |
| `frequency` | `Frequency` | `868.1` |
| `decoded` | `payload` | The decoded payload object, if TPE decodes the device payload. |

The converter also unwraps less common fields when TPE sends them, for example `LostUplinksAS` as `lostUplinksAs`, `LrrESP` as `esp`, `DevLrrCnt` as `devLrrCnt`, `TxPower` as `txPower`, and `CustomerData` as `customerData`.

The sample `payload_hex` holds the serial number `0x0000162E` (5678), battery `0x5A` (90), temperature `0x0A2B` (2603, or 26.03 after scaling), and saturation `0x41` (65).

</Steps>

| Parameter | Default | Description |
|-----------|---------|-------------|

| **Client Id** and **Client Secret** | — | DX API credentials. ThingsBoard exchanges them for an access token. Shown when **Enable security for automatic token updates** is on. |
| **Maximum time difference (seconds)** | `60` | Not used by this integration type: ThingParkEnterprise integration does not check the `Time` parameter. |
| **Execute remotely** | Off | Runs the integration as a separate process outside the ThingsBoard cluster. ThingsBoard generates an **Integration key** and **Integration secret** for it. See <DocLink product={props.product} path="user-guide/integrations/remote" target="_blank">Remote Integration</DocLink>. |
| **Replace response status from 'No-Content' to 'OK'** | Off | In **Advanced settings**. No effect for this integration type: it always answers `200 OK` to an accepted request. |

The default is a ThingPark Wireless address: replace it with the DX API address of your TPE instance. See **[Configure Downlink](#configure-downlink)**. |
| **Description** | — | In **Advanced settings**. Free-text description. |
| **Metadata** | — | In **Advanced settings**. Key–value pairs added to the `metadata` of every message from this integration. |

The integration answers `200 OK` when the request passes the check, `403 Forbidden` when it does not, `400 Bad Request` on a converter script error, and `500 Internal Server Error` on other processing errors.

## Configure Downlink

ThingsBoard sends each downlink right away through the TPE DX API. Nothing is queued in ThingsBoard: if a call fails, ThingsBoard records an error and drops the command.

For each downlink, the integration:

1. Gets an access token with `POST {Downlink URL}/admin/latest/api/oauth/token?grant_type=client_credentials&client_id={Client Id}&client_secret={Client Secret}`, and reuses it until it expires.
2. Finds the device with `GET {Downlink URL}/core/latest/api/devices`: it takes the `ref` of the device whose `EUI` equals the `DevEUI` from the encoder.
3. Sends the payload with `POST {Downlink URL}/core/latest/api/devices/{ref}/downlinkMessages`, with the token as a `Bearer` token and this body:

   ```json
   {
     "payloadHex": "<payload from the encoder>",
     "targetPorts": "<1 to 15>",
     "securityParams": {
       "asId": "<AS ID>",
       "creationTime": "<current time>",
       "asKey": "<AS Key>"
     }
   }
   ```

The integration sets `targetPorts` itself: it counts from 1 to 15 and starts again, one step per downlink. The encoder cannot set the LoRaWAN port.

The downlink converter turns a Rule Engine message into the payload. For the full encoder reference, see <DocLink product={props.product} path="user-guide/integrations/downlink-data-converter" target="_blank">Downlink data converter</DocLink>.

### Create and Assign the Downlink Converter

<Steps>
1. Open the integration in **Integrations &#8702; Integrations** and click **Toggle edit mode** (pencil icon).

Encoder used in this guide. It sends the value of the `downlinkHex` shared attribute as the payload, and ignores messages without it. The rule chain adds the device EUI to the metadata as `cs_eui`.

<Tabs>
<TabItem label="TBEL (Recommended)">

```js
/** Encoder **/

// Device EUI. The rule chain adds the client attribute "eui" to the metadata as cs_eui.
var eui = metadata.cs_eui;

// Payload as a hex string, for example "0102". Nothing to send without it.
var payloadHex = msg.downlinkHex;
if (eui == null || payloadHex == null) {
    return [];
}

return {
    contentType: "JSON",
    // The integration reads DevEUI and payload from data.
    data: JSON.stringify({
        DevEUI: eui,
        payload: payloadHex
    }),
    // The integration checks that metadata has DevEUI.
    metadata: {
        DevEUI: eui
    }
};
```

</TabItem>

```js
}

return {
    contentType: "JSON",
    // The integration reads DevEUI and payload from data.
    data: JSON.stringify({
        DevEUI: eui,
        payload: payloadHex
    }),
    // The integration checks that metadata has DevEUI.
    metadata: {
        DevEUI: eui
    }
};
```

</TabItem>
</Tabs>

To check the encoder, click **Test encoder function**. Replace the **Message** with `{"downlinkHex": "0102"}`, add `cs_eui` = `0018B20000000123` to **Metadata**, and click **Test**. The **Output** panel shows:

```json
{
  "contentType": "JSON",
  "data": "{\"DevEUI\":\"0018B20000000123\",\"payload\":\"0102\"}",
  "metadata": {
    "DevEUI": "0018B20000000123"
  }
}
```

Without `downlinkHex` in the message, the output is `[]`, and nothing is sent.

The integration reads these fields from the encoder result:

| Field | Required | Description |
|-------|----------|-------------|
| `data` | Yes | A JSON object as a string. The integration reads its fields, listed below. |
| `data.DevEUI` | Yes | The device EUI. It must equal the `EUI` of the device in TPE exactly, including letter case. |
| `data.payload` | Yes | The payload as a hex string. Sent as `payloadHex`. |
| `metadata.DevEUI` | Yes | Must be present. Without it, the downlink fails with `DevEUI is missing in the downlink metadata!`. |
| `data.urlSuffixToken`, `data.urlSuffixGetDevices`, `data.urlPrefix`, `data.urlSuffix` | No | Override the API paths, if your TPE version uses others. Defaults: `/admin/latest/api/oauth/token`, `/core/latest/api/devices`, `/core/latest/api/devices/`, and `/downlinkMessages`. |
| `data.firstParamToken` | No | Overrides the `grant_type` of the token request. Default: `client_credentials`. |

### Configure the Root Rule Chain

The encoder needs the device EUI. The uplink converter stores it as the `eui` client attribute. Add it to the metadata with an **originator attributes** node, then pass the message to the integration.

<Steps>
1. Go to **Data processing &#8702; Rule chains** and open the **Root Rule Chain**.
2. From the **Enrichment** section, drag an **originator attributes** node onto the canvas:
   - **Name** — for example `Add EUI`.
   - **Client attributes** — `eui`. The node adds it to the metadata as `cs_eui`.
   - **Add originator attributes to** — keep **Metadata**.
   - Click **Add**.
3. From the **Action** section, drag an **integration downlink** node onto the canvas:
   - **Name** — for example `Downlink to ThingPark Enterprise`.
   - **Integration** — select `ThingParkEnterprise integration`.
   - Click **Add**.
4. Connect the **message type switch** node to `Add EUI` with the **Attributes Updated** relation.
5. Connect `Add EUI` to `Downlink to ThingPark Enterprise` with the **Success** relation.
6. Click **Apply changes**.
</Steps>

### Test Downlink

<Steps>
1. Go to **Devices & assets &#8702; Devices** and open the device created in **[Test Uplink](#test-uplink)**.
2. On the **Attributes** tab, select **Shared attributes** and click **+**.
3. Enter **Key** `downlinkHex`, keep the **String** type, enter **Value** `0102`, and click **Add**.
</Steps>

### Verify the Downlink

- **Converter events** — open `ThingPark Enterprise Downlink Converter` in **Integrations &#8702; Data converters** and click the **Events** tab. **In** shows the message `{"downlinkHex": "0102"}` with `cs_eui` in its metadata. **Out** shows the `data` with `DevEUI` and `payload`.
- **Integration events** — open the integration's **Events** tab. **Downlink: ATTRIBUTES_UPDATED** appears for the message from the Rule Engine, and an event of type **Downlink** with status **OK** for each successful DX API call. A failed call appears with status **ERROR** and the error text.
- **TPE** — open the **Wireless Logger** in ThingPark Enterprise. The downlink to the device shows that TPE received it. TPE sends it in the next receive window of the device.

## Troubleshooting

| Symptom | Cause | Fix |
|---------|-------|-----|
| No events on the integration **Events** tab | The device is not assigned to the HTTP application, the URL in the application is wrong, ThingsBoard is not reachable from TPE, or the integration is disabled. Or debug mode is off: it records events for 15 minutes after you turn it on. | Check **Associated Application** of the device. Copy the **HTTP endpoint URL** again. Turn on **Enable integration**. Turn debug mode on again. |
| Uplink events with status **FORBIDDEN**, and no converter events | The `AS_ID` query parameter is missing or does not match the **AS ID** of the integration. Or the body has no `DevEUI_uplink`, or no `DevEUI` or `FPort` in it. | Enter the same AS ID in the TPE application and the integration. Check the body on the **Events** tab. |
| `415 Unsupported Media Type` | The request has no `Content-Type: application/json` header. | Set **Content-type** to `application/json` in the TPE application. |
| Uplink events with status **ERROR** | The decoder failed. | Check the **Error** column in the converter events and fix the decoder. |
| Events of type **Downlink_Sent** with status **ERROR** | TPE reports a sent downlink with a `DevEUI_downlink_Sent` message. The integration accepts it once a downlink converter is assigned, but the uplink converter reads only `DevEUI_uplink`. | No data is lost: the downlink was already sent. |
| Device not created | **Allow create devices or assets** is off. | Open the integration, click **Toggle edit mode** (pencil icon), turn the option on, and click **Apply changes**. |
| Wrong telemetry values | The byte offsets or scaling do not match the device payload. | Compare `data` in the **Converter output** with the payload specification of your device. |
| No downlink and no error | No downlink converter is assigned, the rule chain does not route attribute updates, or the encoder returned `[]` because the message had no `downlinkHex` or the metadata had no `cs_eui`. | Assign the converter and check the **Attributes Updated** relation and the `Add EUI` node. Check **Out** in the downlink converter events. |
| `DevEUI is missing in the downlink metadata!` | The encoder result has no `metadata.DevEUI`. | Use the encoder from this guide. |
| Downlink **ERROR** with `Bad request, 401 UNAUTHORIZED` or `Bad request, httpHeaders == null` | A DX API call failed. The integration reports every failed call with this text, whatever the real cause: a wrong **Downlink URL** or API path, wrong **Client Id** or **Client Secret**, **Enable security for automatic token updates** off, or a request that the DX API rejected. | Set **Downlink URL** to the DX API address of your TPE instance, turn the option on, and check the credentials. For the real response, check the ThingsBoard log. |
| Downlink **ERROR** with `No value present` | The device list from TPE has no device whose `EUI` equals `data.DevEUI`. | Check that the device exists in TPE, and that the EUI matches, including letter case. |

To read debug events, open the integration or converter, click **Events**, and select an event: **In** is the received data, **Out** is the converter result, and **Error** holds the error text.
