Azure Service Bus Integration receives messages from a topic subscription in <a href="https://learn.microsoft.com/en-us/azure/service-bus-messaging/service-bus-messaging-overview" target="_blank" rel="noopener noreferrer"><strong>Azure Service Bus</strong></a>. An **uplink data converter** transforms each message into device or asset data, including telemetry and attributes. ThingsBoard can also publish **downlink** messages to a separate Service Bus topic.

Use Azure Service Bus Integration when:
- Your applications or IoT platforms already publish device data to a Service Bus topic.
- Several consumers must read the same data: each topic subscription receives its own copy of every message.
- Backend services must receive commands or data from ThingsBoard through a Service Bus topic.

## Architecture

<ImageGallery images={[
  { src: '/src/assets/images/user-guide/integrations/azure-service-bus/azure-service-bus-overview.png', alt: 'Azure Service Bus integration architecture showing uplink messages flowing from a Service Bus topic subscription to ThingsBoard and downlink messages flowing from ThingsBoard to a Service Bus topic', caption: 'Azure Service Bus integration architecture. Messages are received from a topic subscription, converted by the uplink data converter, and forwarded to the ThingsBoard Core Service. Downlinks are published to a separate topic.' },
]} />

1. **Receive data.** A producer sends a message to the uplink topic. The integration receives it from its subscription on that topic.
2. **Decode the payload.** The uplink converter identifies the target device or asset from the payload and extracts attributes and telemetry.
3. **Process the message.** ThingsBoard processes the converted data through the Rule Engine. If **Allow create devices or assets** is enabled, ThingsBoard can create an entity that does not exist yet.
4. **Send downlink data (optional).** The Rule Engine passes a message to the integration. The downlink converter encodes it, and the integration publishes it to the downlink topic.

## Set Up Azure Service Bus Integration

Create the uplink converter, assign it to a new Azure Service Bus integration, and send a test message.

### Create the Uplink Data Converter

The uplink converter receives each message body as a byte array, finds the target device, and returns its telemetry and attributes. For converter types and the full decoder reference, see <DocLink product={props.product} path="user-guide/integrations/uplink-data-converter/#converter-types" target="_blank">Uplink data converter</DocLink>.

<Steps>
1. Go to **Integrations &#8702; Data converters** and click **+ Add data converter &#8702; Create new converter**.
2. **Converter type** — keep **Uplink**.
3. **Integration type** — select **Azure Service Bus**.
4. **Name** — enter a name, for example `Azure Service Bus Uplink Converter`.
5. **Main decoding configuration** — the editor opens with the default Azure Service Bus template, which is the decoder below. Keep it, or adapt it to your payload. The editor opens in TBEL; use the **TBEL / JS** toggle to switch to JavaScript.
   <Aside type="tip" title="TBEL">
     Use <DocLink product={props.product} path="user-guide/tbel" target="_blank">TBEL</DocLink> for converter scripts — it runs much faster than JavaScript inside ThingsBoard.
   </Aside>
   <Tabs>
     <TabItem label="TBEL (Recommended)">
       ```js maxLines=15 collapsible
       /** Decoder **/

       // Decode the incoming payload to a JSON object.
       var data = decodeToJson(payload);

       // The device name comes from deviceId in the payload.
       // Otherwise, it comes from the custom message property deviceId (sysProp:deviceId).
       // Reject the message if neither is present.
       var deviceName = data.deviceId != null ? data.deviceId.toString().trim() : "";
       var propertyId = metadata["sysProp:deviceId"];
       if (deviceName.isEmpty() && propertyId != null) {
           deviceName = propertyId.trim();
       }
       if (deviceName.isEmpty()) {
           raiseError("Payload has no deviceId and the message has no deviceId property");
       }
       // The device profile comes from deviceType. If it is missing or empty, the "default" profile is used.
       var deviceType = data.deviceType != null ? data.deviceType.toString().trim() : "";
       if (deviceType.isEmpty()) {
           deviceType = "default";
       }

       // Use the timestamp if provided; otherwise, use the current server time.
       // An invalid timestamp rejects the message.
       var ts = data.timestamp != null && !data.timestamp.toString().trim().isEmpty() ? new Date(data.timestamp).getTime() : Date.now();

       // Static device properties become attributes.
       var attributes = {};
       if (data.location != null) {
           attributes.latitude = data.location.latitude;
           attributes.longitude = data.location.longitude;
           attributes.altitude = data.location.altitude;
       }
       if (data.metadata != null) {
           attributes.version = data.metadata.version;
           attributes.manufacturer = data.metadata.manufacturer;
       }

       // All other top-level fields (temperature, pressure, status, humidity, ...) become telemetry as they are.
       var handled = ["deviceId", "deviceType", "timestamp", "location", "metadata", "vibration", "alarms"];
       var telemetry = {};
       foreach (key : data.keySet()) {
           if (!handled.contains(key)) {
               telemetry[key] = data[key];
           }
       }
       if (data.alarms != null) {
           telemetry.receivedAlarms = data.alarms;
       }
       if (data.vibration != null) {
           telemetry.vibrationX = data.vibration.x;
           telemetry.vibrationY = data.vibration.y;
           telemetry.vibrationZ = data.vibration.z;
       }
       if (data.metadata != null) {
           telemetry.batteryLevel = data.metadata.batteryLevel;
           telemetry.batteryStatus = data.metadata.batteryStatus;
       }

       // Return the converted uplink message.
       return {
           deviceName: deviceName,
           deviceType: deviceType,
           attributes: attributes,
           telemetry: {
               ts: ts,
               values: telemetry
           }
       };
       ```
     </TabItem>
     <TabItem label="JavaScript">
       ```js maxLines=15 collapsible
       /** Decoder **/

       // Decode the incoming payload to a JSON object.
       var data = decodeToJson(payload);

       // The device name comes from deviceId in the payload.
       // Otherwise, it comes from the custom message property deviceId (sysProp:deviceId).
       // Reject the message if neither is present.
       var deviceName = data.deviceId != null ? String(data.deviceId).trim() : "";
       var propertyId = metadata["sysProp:deviceId"];
       if (!deviceName && propertyId) {
           deviceName = String(propertyId).trim();
       }
       if (!deviceName) {
           throw new Error("Payload has no deviceId and the message has no deviceId property");
       }
       // The device profile comes from deviceType. If it is missing or empty, the "default" profile is used.
       var deviceType = data.deviceType != null ? String(data.deviceType).trim() : "";
       if (!deviceType) {
           deviceType = "default";
       }

       // Use the timestamp if provided; otherwise, use the current server time.
       // An invalid timestamp rejects the message.
       var ts = data.timestamp != null && String(data.timestamp).trim() !== "" ? new Date(data.timestamp).getTime() : Date.now();
       if (isNaN(ts)) {
           throw new Error("Invalid timestamp: " + data.timestamp);
       }

       // Static device properties become attributes.
       var attributes = {};
       if (data.location != null) {
           attributes.latitude = data.location.latitude;
           attributes.longitude = data.location.longitude;
           attributes.altitude = data.location.altitude;
       }
       if (data.metadata != null) {
           attributes.version = data.metadata.version;
           attributes.manufacturer = data.metadata.manufacturer;
       }

       // All other top-level fields (temperature, pressure, status, humidity, ...) become telemetry as they are.
       var handled = ["deviceId", "deviceType", "timestamp", "location", "metadata", "vibration", "alarms"];
       var telemetry = {};
       for (var key in data) {
           if (handled.indexOf(key) < 0) {
               telemetry[key] = data[key];
           }
       }
       if (data.alarms != null) {
           telemetry.receivedAlarms = data.alarms;
       }
       if (data.vibration != null) {
           telemetry.vibrationX = data.vibration.x;
           telemetry.vibrationY = data.vibration.y;
           telemetry.vibrationZ = data.vibration.z;
       }
       if (data.metadata != null) {
           telemetry.batteryLevel = data.metadata.batteryLevel;
           telemetry.batteryStatus = data.metadata.batteryStatus;
       }

       var result = {
           deviceName: deviceName,
           deviceType: deviceType,
           attributes: attributes,
           telemetry: {
               ts: ts,
               values: telemetry
           }
       };

       /** Helper functions **/

       // Convert the byte array to a string.
       function decodeToString(payload) {
           return String.fromCharCode.apply(String, payload);
       }

       // Convert the byte array to a JSON object.
       function decodeToJson(payload) {
           return JSON.parse(decodeToString(payload));
       }

       // Return the converted uplink message.
       return result;
       ```
     </TabItem>
   </Tabs>

   The decoder:
   - takes the device name from `deviceId` in the payload, or from the custom message property `deviceId`, and rejects the message if both are missing;
   - takes the device profile from `deviceType`, or uses `default`;
   - uses `timestamp` as the time of the data, or the server time if the payload has no `timestamp`;
   - stores `location` and `metadata.version` / `metadata.manufacturer` as attributes, and all other fields as telemetry.

   **To adapt:**
   - **Device name in another field** — replace `data.deviceId`, for example with `data.serialNumber`.
   - **Fields that are not telemetry** — add them to `handled`, then map them yourself.
   - **Update-only keys** — for Azure Service Bus, ThingsBoard pre-fills the **Update only keys list** in **Advanced decoding parameters** with `manufacturer`, `receivedAlarms`, `status`, `batteryLevel`, `batteryStatus`, and `version`. These keys are stored only when their value changes. Edit the list to match your keys.
6. Click **Test decoder function** and check the result (see **[Test the Decoder](#test-the-decoder)**).
7. Click **Add**.
</Steps>

<h4>Decoder Inputs</h4>

The decoder signature is `function decoder(payload, metadata): object | object[]`.

| Variable | Type | Content |
|----------|------|---------|
| `payload` | byte array | The message body. |
| `metadata` | `{[key: string]: string}` | `integrationName`, the key–value pairs from the integration's **Metadata** field, and each custom property of the message as `sysProp:<name>`, for example `sysProp:site`. Broker properties such as **Label/Subject** or **Message ID** are not passed. |

Built-in helpers:

| Function | Result |
|----------|--------|
| `decodeToJson(payload)` | Parses the bytes as JSON and returns an object. |
| `decodeToString(payload)` | Converts the bytes to a UTF-8 string. |

For field renaming, nested values, and non-JSON payloads, see <DocLink product={props.product} path="user-guide/integrations/uplink-data-converter/#common-scripting-patterns" target="_blank">Common scripting patterns</DocLink>.

Click **Test decoder function** below the editor. **Payload** already holds a sample message, the same one that you send in **[Test Uplink](#test-uplink)**, and **Metadata** holds `integrationName`:

```json
{"deviceId": "sb-sensor-01", "temperature": 24.6, "humidity": 51}
```

Click **Test**. The **Output** panel shows:

```json
{
  "deviceName": "sb-sensor-01",
  "deviceType": "default",
  "attributes": {},
  "telemetry": {
    "ts": 1795099761202,
    "values": {
      "temperature": 24.6,
      "humidity": 51
    }
  }
}
```

The payload has no `timestamp`, so `ts` is the time of the test, in milliseconds, and differs in your output. `humidity` is not mapped in the decoder; it becomes telemetry as it is, like every other top-level field.

Check that `deviceName` is set and `telemetry` holds the expected keys. If the output is empty or shows an error, fix the decoder and test again.

   - **Name** — keep the default `Azure Service Bus integration` or enter your own.

5. **Connection:**
   - **Connection string** — paste the **Primary connection string** of `tb-listen`.
   - **Topic name** — enter `tb-uplink`.
   - **Subscription name** — enter `thingsboard`.
   - See **[Connection Settings](#connection-settings)** for details.
6. Click **Add**.
</Steps>

## Configure Downlink

ThingsBoard publishes a downlink when the Rule Engine routes a message to the integration — for example, after a shared attribute update. The integration sends it to the **Downlink topic name**. Every subscription on that topic receives a copy, and your backend reads it from its subscription.

Each downlink message carries:
- **Body** — the encoder's `data`.
- **contentType** — the encoder's `contentType`: `JSON`, `TEXT`, or `BINARY`.
- **to** — the encoder's `metadata.deviceId`.
- **Custom properties** — every key of the encoder's `metadata`.

The downlink converter turns a <DocLink product={props.product} path="user-guide/rule-engine" target="_blank">Rule Engine</DocLink> message into the published message. For the full encoder reference, see <DocLink product={props.product} path="user-guide/integrations/downlink-data-converter" target="_blank">Downlink data converter</DocLink>.

### Create the Downlink Topic

A message sent to a topic without subscriptions is discarded, so the downlink topic needs a subscription for its consumer before ThingsBoard publishes to it.

<Steps>
1. In the namespace, go to **Entities &#8702; Topics**, click **+ Topic**, enter `tb-downlink`, and click **Create**.
2. Open `tb-downlink`, go to **Entities &#8702; Subscriptions**, click **+ Subscription**, enter `device-commands`, keep **Max delivery count** `10`, and click **Create**. Your backend reads the downlinks from this subscription.
3. Go to **Settings &#8702; Shared access policies**, click **+ Add**, enter `tb-send`, select **Send**, and click **Create**.
4. Open `tb-send` and copy the **Primary connection string**.
</Steps>

```json
{
  "contentType": "JSON",
  "data": "{\"temperatureUploadFrequency\":60}",
  "metadata": {
    "deviceId": "sb-sensor-01"
  }
}
```

**To adapt:**
- **Another envelope** — build `data` in the structure your consumer expects, for example `{ "device": deviceId, "config": msg }`.
- **Routing properties** — add keys to `metadata`, for example `type: "config"`. Subscription filter rules on the downlink topic can route on these custom properties.
- **Other message types** — branch on `msgType`, for example to handle `RPC_CALL_FROM_SERVER_TO_DEVICE` with `msg.method` and `msg.params`. See <DocLink product={props.product} path="reference/rule-engine/message-types" target="_blank">Rule Engine message types</DocLink>.

### Configure the Root Rule Chain

The encoder reads `deviceName` from the message metadata, so the rule chain first adds the device name.

<Steps>
1. Go to **Data processing &#8702; Rule chains** and open the **Root Rule Chain**.
2. From the **Enrichment** section, drag an **originator fields** node onto the canvas.
3. Enter a **Name**, for example `Add device name`, and map the source fields:
   - **Name &#8702; deviceName**
   - **Add mapped originator fields to &#8702; Metadata**
   - Click **Add**.
4. Connect the **message type switch** node to the **originator fields** node with the **Attributes Updated** relation.
5. From the **Action** section, drag an **integration downlink** node onto the canvas.
6. Enter a **Name**, for example `Downlink to Azure Service Bus`, select `Azure Service Bus integration`, and click **Add**.
7. Connect the **originator fields** node to the **integration downlink** node with the **Success** relation.
8. Click **Apply changes**.
</Steps>

### Test Downlink

<Steps>
1. Go to **Devices & assets &#8702; Devices**, select **sb-sensor-01**, and open the **Attributes** tab.
2. Select **Shared attributes** and click **+**.
3. Set **Key** to `temperatureUploadFrequency`, **Type** to **Integer**, **Value** to `60`, and click **Add**. ThingsBoard publishes the downlink.
</Steps>

### Verify the Downlink

- **Integration events** — the integration's **Events** tab shows a **Downlink** event with `deviceId` `sb-sensor-01`, `payload` `{"temperatureUploadFrequency":60}`, and `properties`.
- **Service Bus Explorer** — open `tb-downlink`, click **Service Bus Explorer**, select the subscription `device-commands`, and click **Peek from start**. Select the message: **Message Body** shows `{"temperatureUploadFrequency":60}`; **Message Properties** shows **contentType** `JSON`, **to** `sb-sensor-01`, and the custom property `deviceId` `sb-sensor-01`.

## Troubleshooting

| Symptom | Cause | Fix |
|---------|-------|-----|
| **Check connection** shows *Connection established.*, but no uplinks arrive | **Check connection** does not connect to Service Bus. The namespace, topic, subscription, or key is wrong, or the policy lacks **Listen**. | Compare the names with the Azure portal. Copy the connection string again from a policy with **Listen**. |
| Uplinks stop, the integration shows no errors | The key of the policy was regenerated, or the topic or subscription was deleted. ThingsBoard writes the error only to the server log, for example `401 InvalidSignature`. The messages stay in the subscription. | Copy the new connection string to the integration and click **Apply changes**. The waiting messages arrive. |
| Same, from a private network | Outbound port `5671` is blocked. | Open TCP `5671` to `*.servicebus.windows.net`, or use a <DocLink product={props.product} path="user-guide/integrations/remote" target="_blank">Remote Integration</DocLink>. |
| Messages go to another consumer | Another application reads the same subscription. | Create a dedicated subscription for ThingsBoard. |
| Topics are not available | The namespace is on the Basic tier. | Use the Standard or Premium tier. |
| Uplink event with status **ERROR** | The converter failed on the message. The message is removed from the subscription and lost. | Check **Error** in the converter events, fix the decoder, and send the message again. |
| Device not created | `deviceName` is empty, or **Allow create devices or assets** is off. | Check **Out** in the converter events and the integration settings. |
| **Downlink: ATTRIBUTES_UPDATED** is **OK**, but no **Downlink** event and nothing in the downlink subscription | The encoder does not set `metadata.deviceId`, so the integration skips the message. | Check **Out** in the downlink converter events for `deviceId`. Use the encoder from this guide. |
| No downlink events at all | The rule chain does not reach the **integration downlink** node. | Check the Root Rule Chain wiring. |
| **Downlink** event is **OK**, nothing in the downlink subscription | The downlink topic had no subscription when the message arrived, or a subscription filter rejected it. | Create the subscription before you trigger the downlink. Check its filter rules. |

To read debug events, open the integration or converter, click **Events**, and select an event: **In** is the received data, **Out** is the converter result, and **Error** holds the error text.
