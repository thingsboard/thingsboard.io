Azure Service Bus Integration receives messages from a topic subscription in <a href="https://learn.microsoft.com/en-us/azure/service-bus-messaging/service-bus-messaging-overview" target="_blank" rel="noopener noreferrer"><strong>Azure Service Bus</strong></a>. An **uplink data converter** transforms each message into device or asset data, including telemetry and attributes. ThingsBoard can also publish **downlink** messages to a separate Service Bus topic.

Use Azure Service Bus Integration when:
- Your applications or IoT platforms already publish device data to a Service Bus topic.
- Several consumers must read the same data: each topic subscription receives its own copy of every message.
- Backend services must receive commands or data from ThingsBoard through a Service Bus topic.

## Architecture

<ImageGallery images={[
  { src: '/src/assets/images/user-guide/integrations/azure-service-bus/azure-service-bus-overview.png', alt: 'Azure Service Bus integration architecture showing uplink messages flowing from a Service Bus topic subscription to ThingsBoard and downlink messages flowing from ThingsBoard to a Service Bus topic', caption: 'Azure Service Bus integration architecture. Messages are received from a topic subscription, converted by the uplink data converter, and forwarded to the ThingsBoard Core Service. Downlinks are published to a separate topic.' },
]} />

1. **Receive data.** A producer sends a message to the uplink topic. The integration receives it from its subscription on that topic.
2. **Decode the payload.** The uplink converter identifies the target device or asset from the payload and extracts attributes and telemetry.
3. **Process the message.** ThingsBoard processes the converted data through the Rule Engine. If **Allow create devices or assets** is enabled, ThingsBoard can create an entity that does not exist yet.
4. **Send downlink data (optional).** The Rule Engine passes a message to the integration. The downlink converter encodes it, and the integration publishes it to the downlink topic.

## Configure Azure Service Bus

Create a namespace, the uplink and downlink topics with their subscriptions, and copy the connection string. For details, see <a href="https://learn.microsoft.com/en-us/azure/service-bus-messaging/service-bus-quickstart-topics-subscriptions-portal" target="_blank" rel="noopener noreferrer"><strong>Create Service Bus topics and subscriptions</strong></a>.

### Create a Namespace

<Steps>
1. In the <a href="https://portal.azure.com" target="_blank" rel="noopener noreferrer"><strong>Azure portal</strong></a>, click **+ Create a resource**, search for **Service Bus**, and click **Create**.
2. On the **Basics** tab, select or create a **Resource group**, enter a globally unique **Namespace name**, and choose a **Location**.
3. Set **Pricing tier** to **Standard** or **Premium**. The Basic tier does not support topics.
4. Click **Review + create**, then **Create**.
5. When the deployment finishes, click **Go to resource**.
</Steps>

### Create Topics and Subscriptions

The integration reads from a topic subscription, not from a queue. Downlinks go to a second topic. A message sent to a topic without subscriptions is discarded, so the downlink topic also needs a subscription for its consumer.

<Steps>
1. In the namespace, go to **Entities &#8702; Topics** and click **+ Topic**.
2. Enter the name `uplinktopic` and click **Create**.
3. Open `uplinktopic`, click **+ Subscription**, enter `S1`, and click **Create**. ThingsBoard reads from this subscription.
4. Repeat steps 1–3 for the downlink: a topic `downlinktopic` with a subscription `S2`. Skip this if you do not need downlink.
</Steps>

Each subscription keeps its own copy of every topic message. Give ThingsBoard a subscription that no other application reads.

### Copy the Connection String

<Steps>
1. In the namespace, go to **Settings &#8702; Shared access policies**.
2. Click **+ Add**, enter a **Policy name**, for example `thingsboard`, select **Send** and **Listen**, and click **Create**. **Listen** is needed for uplink, **Send** for downlink.
3. Open the policy and copy the **Primary Connection String**. It has the form `Endpoint=sb://<namespace>.servicebus.windows.net/;SharedAccessKeyName=thingsboard;SharedAccessKey=<key>`.
</Steps>

For a quick test, the default `RootManageSharedAccessKey` policy also works, but it grants full control of the namespace.

<Aside type="caution">
  The connection string grants access to the namespace. Store it in <DocLink product={props.product} path="user-guide/security/secrets-storage" target="_blank">Secret storage</DocLink> rather than in shared configuration.
</Aside>

You now have the values for the integration:

| Value | Example | Source |
|-------|---------|--------|
| **Connection string** | `Endpoint=sb://…;SharedAccessKeyName=thingsboard;SharedAccessKey=…` | Policy details page |
| **Topic name** | `uplinktopic` | Uplink topic |
| **Subscription name** | `S1` | Subscription on the uplink topic |
| **Downlink topic name** | `downlinktopic` | Downlink topic. Needed only for downlink. |

## Set Up Azure Service Bus Integration

Create the uplink converter, assign it to a new Azure Service Bus integration, and send a test message.

### Create the Uplink Data Converter

The uplink converter receives each message body as a byte array, resolves the target device, and returns its telemetry and attributes. Azure Service Bus Integration uses the **Generic** converter: you write the decoder in TBEL or JavaScript. For converter types and the full decoder reference, see <DocLink product={props.product} path="user-guide/integrations/uplink-data-converter/#converter-types" target="_blank">Uplink data converter</DocLink>.

This guide uses the sample payload that ThingsBoard provides for Azure Service Bus converters, with a recent `timestamp`:

```json
{
  "deviceId": "8F4A2C6D",
  "deviceType": "Packing machine",
  "temperature": 25.5,
  "pressure": 1013.25,
  "vibration": {
    "x": 0.02,
    "y": 0.03,
    "z": 0.015
  },
  "location": {
    "latitude": 37.7749,
    "longitude": -122.4194,
    "altitude": 10
  },
  "timestamp": "2026-10-14T10:30:00Z",
  "status": "ALARM",
  "alarms": [
    {
      "type": "temperature",
      "severity": "high",
      "message": "Temperature exceeds threshold."
    },
    {
      "type": "vibration",
      "severity": "critical",
      "message": "Excessive vibration detected."
    }
  ],
  "metadata": {
    "version": 1,
    "batteryLevel": 100,
    "batteryStatus": "Charging",
    "manufacturer": "Example corporation"
  }
}
```

<Steps>
1. Go to **Integrations &#8702; Data converters** and click **+ Add data converter &#8702; Create new converter**.
2. **Converter type** — keep **Uplink**.
3. **Integration type** — select **Azure Service Bus**.
4. **Name** — enter a name, for example `Azure Service Bus Uplink Converter`.
5. **Main decoding configuration** — the editor opens with the default Azure Service Bus template. Replace it with the decoder below. The decoder maps measurements and state to telemetry and static device properties to attributes. It also reads `timestamp`, `location`, and `vibration` when the payload carries them. The editor opens in TBEL; use the **TBEL / JS** toggle to switch to JavaScript.
   <Aside type="tip" title="TBEL">
     Use <DocLink product={props.product} path="user-guide/tbel" target="_blank">TBEL</DocLink> for converter scripts — it runs much faster than JavaScript inside ThingsBoard.
   </Aside>
   <Tabs>
     <TabItem label="TBEL (Recommended)">
       ```js maxLines=15 collapsible

       var deviceName = data.deviceId != null ? data.deviceId : "Device A";
       var deviceType = data.deviceType != null ? data.deviceType : "default";

       // ISO 8601 timestamp; fall back to server time.
       var ts = data.timestamp != null ? new Date(data.timestamp).getTime() : Date.now();

       // Static device properties become attributes.
       var attributes = {};
       if (data.location != null) {
           attributes.latitude = data.location.latitude;
           attributes.longitude = data.location.longitude;
           attributes.altitude = data.location.altitude;
       }
       if (data.metadata != null) {
           attributes.version = data.metadata.version;
           attributes.manufacturer = data.metadata.manufacturer;
       }

       // Measurements and state become telemetry.
       var telemetry = {
           temperature: data.temperature,
           pressure: data.pressure,
           status: data.status,
           receivedAlarms: data.alarms
       };
       if (data.vibration != null) {
           telemetry.vibrationX = data.vibration.x;
           telemetry.vibrationY = data.vibration.y;
           telemetry.vibrationZ = data.vibration.z;
       }
       if (data.metadata != null) {
           telemetry.batteryLevel = data.metadata.batteryLevel;
           telemetry.batteryStatus = data.metadata.batteryStatus;
       }

       return {
           deviceName: deviceName,
           deviceType: deviceType,
           attributes: attributes,
           telemetry: {
               ts: ts,
               values: telemetry
           }
       };
       ```
     </TabItem>

   **To adapt:**
   - **Device name in another field** — replace `data.deviceId`, for example with `data.serialNumber`.
   - **Device name in a message property** — if the producer sets a custom property, for example `deviceId`, read it with `metadata["sysProp:deviceId"]`.
   - **Optional fields** — remove the `location`, `vibration`, `status`, or `alarms` mappings your devices never send.
   - **Other telemetry** — add keys to `telemetry`, for example `humidity: data.humidity`.
   - **Other device properties** — add them to `attributes`, for example `model: data.model`.
   - **Update-only keys** — for Azure Service Bus, ThingsBoard pre-fills the **Update only keys list** in **Advanced decoding parameters** with `manufacturer`, `receivedAlarms`, `status`, `batteryLevel`, `batteryStatus`, and `version`. These keys are stored only when their value changes. Edit the list to match your keys.
6. Click **Test decoder function** and check the result (see **[Test the Decoder](#test-the-decoder)**).
7. Click **Add**.

<h4>Decoder Inputs</h4>

The decoder signature is `function decoder(payload, metadata): object | object[]`.

| Variable | Type | Content |
|----------|------|---------|
| `payload` | byte array | The message body. |
| `metadata` | `{[key: string]: string}` | Each custom (application) property of the message as `sysProp:<name>`. Also `integrationName` and the key–value pairs from the integration's **Metadata** field. Broker properties such as `MessageId` or `ContentType` are not passed. |

Built-in helpers:

| Function | Result |
|----------|--------|
| `decodeToJson(payload)` | Parses the bytes as JSON and returns an object. |
| `decodeToString(payload)` | Converts the bytes to a UTF-8 string. |
| `toFlatMap(obj, excludeKeys, flatNested)` | TBEL only. Returns a flat key–value map of `obj`, skipping `excludeKeys`. With `flatNested` set to `true`, nested objects become dot-separated keys. |

For field renaming, nested values, and non-JSON payloads, see <DocLink product={props.product} path="user-guide/integrations/uplink-data-converter/#common-scripting-patterns" target="_blank">Common scripting patterns</DocLink>.

### Create the Integration

<Steps>
1. Go to **Integrations &#8702; Integrations** and click **+ Add integration**.
2. **Basic settings:**
   - **Integration type** — select **Azure Service Bus**.
   - **Name** — keep the default or enter your own.
   - **Enable integration** and **Allow create devices or assets** — keep both on, so the device is created on its first uplink.
   - Click **Next**.
3. **Uplink data converter:**
   - Click **Select existing** and choose `Azure Service Bus Uplink Converter`.
   - Alternatively, click **Create new** to write a decoder here.
   - Click **Next**.
4. **Downlink data converter:**
   - Click **Skip**. Add a downlink converter later if you need to **[publish to Service Bus](#configure-downlink)**.
5. **Connection:**
   - **Connection string** — paste the **Primary Connection String**.
   - **Topic name** — enter `uplinktopic`.
   - **Subscription name** — enter `S1`.
   - See **[Connection Settings](#connection-settings)** for details.
6. Click **Add**.
</Steps>

#### Connection Settings

| Parameter | Description |
|-----------|-------------|
| **Connection string** | Namespace connection string of a policy with **Listen** permission. Required. |
| **Topic name** | Topic the integration receives from. Required. |
| **Subscription name** | Subscription on that topic. Required. |
| **Execute remotely** | Runs the integration as a separate process outside the ThingsBoard cluster, for example in a network with access to Azure. ThingsBoard generates an **Integration key** and **Integration secret** for it. See <DocLink product={props.product} path="user-guide/integrations/remote" target="_blank">Remote Integration</DocLink>. |

**Advanced settings**

| Parameter | Description |
|-----------|-------------|
| **Downlink connection string** | Connection string of a policy with **Send** permission on the namespace of the downlink topic. It can be the same namespace and string as for uplink. Required when a downlink converter is assigned. |
| **Downlink topic name** | Topic the integration publishes downlinks to. Required when a downlink converter is assigned. |
| **Description** | Free-text description. |
| **Metadata** | Key–value pairs added to the `metadata` of every message from this integration. |

**Check connection** validates only the format of the connection string. It does not connect to the topic, so wrong names or keys show up as missing uplinks.

The integration removes each message from the subscription after processing it, including messages the converter fails to decode. Check **Error** events in the converter to catch them.

## Configure Downlink

ThingsBoard publishes a downlink when the Rule Engine routes a message to the integration — for example, after a shared attribute update. The integration sends it to the **Downlink topic name**. Every subscription on that topic receives a copy, and your backend reads it from its subscription.

Each downlink message carries:
- **Body** — the encoder's `data`.
- **Content type** — the encoder's `contentType`: `JSON`, `TEXT`, or `BINARY`.
- **To** — the encoder's `metadata.deviceId`. Consumers can filter or route on it.
- **Custom properties** — every key of the encoder's `metadata`.

The downlink converter turns a <DocLink product={props.product} path="user-guide/rule-engine" target="_blank">Rule Engine</DocLink> message into the published message. For the full encoder reference, see <DocLink product={props.product} path="user-guide/integrations/downlink-data-converter" target="_blank">Downlink data converter</DocLink>.

### Create and Assign the Downlink Converter

The encoder must set `metadata.deviceId`. Without it, the integration skips the message.

<Steps>
1. Open the integration in **Integrations &#8702; Integrations** and click **Toggle edit mode** (pencil icon).
2. In the **Downlink data converter** field, click **Create new**. The **Downlink** converter type and **Azure Service Bus** integration type are preselected.
3. Enter a name, for example `Azure Service Bus Downlink Converter`.
4. In **Main encoding configuration**, replace the default encoder with the one below.
5. To record downlink events, click the debug icon next to the name, select **All messages**, and click **Apply**.
6. Click **Add**.
7. In **Advanced settings**, fill in:
   - **Downlink connection string** — the connection string of a policy with **Send** permission. With the `thingsboard` policy, paste the same string as for uplink.
   - **Downlink topic name** — enter `downlinktopic`.
8. Click **Apply changes**.
</Steps>

Encoder used in this guide (TBEL and JavaScript):

```js maxLines=15 collapsible
/** Encoder **/

// Publish the Rule Engine message as the message body.
var result = {
  // Payload content type: JSON, TEXT, or BINARY (Base64).
  contentType: 'JSON',
  data: JSON.stringify(msg),
  metadata: {
    // Required. Becomes the message's To property
    // and the custom property deviceId.
    deviceId: metadata.deviceName
  }
};

return result;
```

To check the encoder, click **Test encoder function**. **Message type** is already `ATTRIBUTES_UPDATED`. Set **Message** to `{"temperatureUploadFrequency":60}` and **deviceName** in **Metadata** to `8F4A2C6D`, if they differ, then click **Test**. The **Output** shows:

```json
{
  "contentType": "JSON",
  "data": "{\"temperatureUploadFrequency\":60}",
  "metadata": {
    "deviceId": "8F4A2C6D"
  }
}
```

**To adapt:**
- **Another envelope** — build `data` in the structure your consumer expects, for example `{ "device": metadata.deviceName, "config": msg }`.
- **Routing properties** — add keys to `metadata`, for example `type: 'config'`. Subscription filter rules on the downlink topic can route on these custom properties.
- **Other message types** — branch on `msgType`, for example to handle `RPC_CALL_FROM_SERVER_TO_DEVICE` with `msg.method` and `msg.params`. See <DocLink product={props.product} path="reference/rule-engine/message-types" target="_blank">Rule Engine message types</DocLink>.

### Configure the Root Rule Chain

The encoder reads `deviceName` from the message metadata, so the rule chain first adds the device name.

<Steps>

3. Enter a **Name** (for example, `Retrieve device name`) and map the source fields:
   - **Name &#8702; deviceName**
   - **Add mapped originator fields to &#8702; Metadata**
   - Click **Add**.
4. Connect the **message type switch** node to the **originator fields** node with the **Attributes Updated** relation.
5. From the **Action** section, drag an **integration downlink** node onto the canvas.
6. Enter a **Name** (for example, `Downlink to Azure Service Bus`), select your Azure Service Bus integration, and click **Add**.
7. Connect the **originator fields** node to the **integration downlink** node with the **Success** relation.
8. Click **Apply changes**.
</Steps>

## Troubleshooting

| Symptom | Cause | Fix |
|---------|-------|-----|
| **Check connection** passes, but no uplinks arrive | **Check connection** does not connect to Service Bus. The namespace, topic, subscription, or key is wrong, or the policy lacks **Listen**. | Compare the names with the Azure portal. Copy the connection string again from a policy with **Listen**. |
| Same, from a private network | Outbound port `5671` is blocked. | Open TCP `5671` to `*.servicebus.windows.net`, or use a <DocLink product={props.product} path="user-guide/integrations/remote" target="_blank">Remote Integration</DocLink>. |
| Messages go to another consumer | Another application reads the same subscription. | Create a dedicated subscription for ThingsBoard. |
| Topics are not available | The namespace is on the Basic tier. | Upgrade the namespace to Standard or Premium. |
| Device not created | `deviceName` is empty, or **Allow create devices or assets** is off. | Check **Out** in the converter events and the integration settings. |
| Message lost after a converter error | The integration removes every processed message, even when decoding fails. | Check **Error** events in the converter, fix the decoder, and resend the message. |
| Downlink event with an error | Wrong **Downlink connection string** or **Downlink topic name**, or the policy lacks **Send**. | Compare the topic name with the Azure portal. Use a policy with **Send**. |
| No downlink is sent | The rule chain does not reach the **integration downlink** node, or the encoder does not set `metadata.deviceId`. | Check the Root Rule Chain wiring. Check **Out** in the downlink converter events for `deviceId`. |
| Downlink sent, nothing in the downlink subscription | The downlink topic had no subscription when the message arrived, or a subscription filter rejected it. | Create the subscription before you trigger the downlink. Check its filter rules. |

To read debug events, open the integration or converter, click **Events**, and select an event: **In** is the received data, **Out** is the converter result, and **Error** holds the error text.
