Azure IoT Hub Integration connects ThingsBoard to <a href="https://azure.microsoft.com/en-us/products/iot-hub" target="_blank" rel="noopener noreferrer">**Azure IoT Hub**</a> over MQTT as one registered device. It receives the cloud-to-device messages addressed to that device, and an **uplink data converter** transforms each message into device or asset data, including telemetry and attributes. ThingsBoard can also publish **downlink** messages to the hub as that device.

Use Azure IoT Hub Integration when:
- A backend application sends data to ThingsBoard as cloud-to-device messages through Azure IoT Hub.
- One hub connection must deliver data for many ThingsBoard devices: the converter sets the target device for each message.
- An Azure-side consumer must receive ThingsBoard data from the hub's built-in events endpoint.

<Aside type="note">
  To read the telemetry that a fleet of Azure IoT Hub devices already sends, use the <DocLink product={props.product} path="user-guide/integrations/azure-event-hub" target="_blank">Azure Event Hub Integration</DocLink> instead. It reads the hub's Event Hub-compatible endpoint, and its downlink sends cloud-to-device messages to any device in the hub.
</Aside>

1. **Receive data.** A backend application, the Azure portal, or the Azure CLI sends a cloud-to-device message to the integration's device identity. The integration is subscribed to `devices/{deviceId}/messages/devicebound/#` and receives it.
2. **Decode the payload.** The uplink converter identifies the target device or asset from the payload and extracts attributes and telemetry.
3. **Process the message.** ThingsBoard processes the converted data through the Rule Engine. If **Allow create devices or assets** is enabled, ThingsBoard can create an entity that does not exist yet.
4. **Send downlink data (optional).** The Rule Engine passes a message to the integration. The downlink converter encodes it, and the integration publishes it to `devices/{deviceId}/messages/events/` as a device-to-cloud message.

<Aside type="caution">
  IoT Hub allows one active connection per device identity. Register a dedicated device for the integration, for example `tb-bridge-01`. If physical hardware connects with the same Device ID, the two connections drop each other.
</Aside>

## Configure Azure IoT Hub

Create the hub and the device identity in the Azure portal.

### Create an IoT Hub

<Steps>
1. In the <a href="https://portal.azure.com" target="_blank" rel="noopener noreferrer"><strong>Azure portal</strong></a>, click **+ Create a resource**, search for **IoT Hub**, and click **Create**.
2. On the **Basics** tab, select or create a **Resource group**, enter a globally unique **IoT hub name** (for example, `tb-iot-hub`), and choose a **Region**.
3. Adjust the **Networking** and **Management** tabs if your environment requires it, then click **Review + create** and **Create**.
4. When the deployment finishes, click **Go to resource**.
5. On the **Overview** page, copy the **Hostname**, for example `tb-iot-hub.azure-devices.net`.
</Steps>

For tiers and limits, see <a href="https://learn.microsoft.com/en-us/azure/iot-hub/create-hub?tabs=portal" target="_blank" rel="noopener noreferrer"><strong>Create an IoT hub</strong></a>.

### Register a Device

<Steps>
1. In the hub, go to **Device management &#8702; Devices** and click **+ Add device**.
2. Enter a **Device ID**, for example `tb-bridge-01`.
3. Keep **Authentication type** set to **Symmetric key** and **Auto-generate keys** selected.
4. Click **Save**.
5. Open the device and copy its **Primary key**.
</Steps>

<Aside type="caution">
  The primary key grants full access to this device identity. Store it in <DocLink product={props.product} path="user-guide/security/secrets-storage" target="_blank">Secret storage</DocLink> rather than in shared configuration.
</Aside>

To authenticate with X.509 certificates instead, see <a href="https://learn.microsoft.com/en-us/azure/iot-hub/create-connect-device?tabs=portal" target="_blank" rel="noopener noreferrer"><strong>Create and manage device identities</strong></a> and **[Credentials](#credentials)**.

You now have the values for the integration:

| Value | Example | Source |
|-------|---------|--------|
| **Hostname** | `tb-iot-hub.azure-devices.net` | Hub **Overview** page |
| **Device ID** | `tb-bridge-01` | Device you registered |
| **SAS Key** | Primary key | Device details page |

## Set Up Azure IoT Hub Integration

Create the uplink converter, assign it to a new Azure IoT Hub integration, and send a test message.

### Create the Uplink Data Converter

Azure IoT Hub Integration uses the **Generic** converter: you write the decoder in TBEL or JavaScript. For converter types and the full decoder reference, see <DocLink product={props.product} path="user-guide/integrations/uplink-data-converter/#converter-types" target="_blank">Uplink data converter</DocLink>.

<h4>Decoder Inputs</h4>

The decoder signature is `function decoder(payload, metadata): object | object[]`.

| Variable | Type | Content |
|----------|------|---------|
| `payload` | byte array | The message body. |
| `metadata` | `{[key: string]: string}` | `topic` — the topic the message arrived on: `devices/{deviceId}/messages/devicebound/` followed by the message's property bag. Also `integrationName` and the key–value pairs from the integration's **Metadata** field. |

Built-in helpers:

| Function | Result |
|----------|--------|
| `decodeToJson(payload)` | Parses the bytes as JSON and returns an object. |
| `decodeToString(payload)` | Converts the bytes to a UTF-8 string. |
| `toFlatMap(obj, excludeKeys, flatNested)` | TBEL only. Returns a flat key–value map of `obj`, skipping `excludeKeys`. With `flatNested` set to `true`, nested objects become dot-separated keys. |

For field renaming, nested values, and non-JSON payloads, see <DocLink product={props.product} path="user-guide/integrations/uplink-data-converter/#common-scripting-patterns" target="_blank">Common scripting patterns</DocLink>.

#### Connection Settings

| Parameter | Description |
|-----------|-------------|
| **Hostname** | Hub hostname, `{hub-name}.azure-devices.net`. Find it on the hub's **Overview** page. |
| **Device ID** | The device identity the integration connects as. It is also the MQTT client ID. |
| **Credentials** | **Shared Access Signature** (default) or **PEM**. See **[Credentials](#credentials)**. |
| **Topic filters** | Subscriptions, each with a **Topic** and **QoS** (`0` or `1`; IoT Hub does not support QoS 2). Default: `#` with QoS `0`. Use `devices/{deviceId}/messages/devicebound/#` — IoT Hub delivers cloud-to-device messages only on this topic. The `#` is required because the hub appends a property bag to the topic. |
| **Execute remotely** | Runs the integration as a separate process outside the ThingsBoard cluster, for example in a network with access to Azure. ThingsBoard generates an **Integration key** and **Integration secret** for it. See <DocLink product={props.product} path="user-guide/integrations/remote" target="_blank">Remote Integration</DocLink>. |

**Advanced settings**

| Parameter | Default | Description |
|-----------|---------|-------------|
| **Protocol version** | MQTT 3.1.1 | The only version available. |
| **Max bytes in message** | `32368` | Maximum size of an incoming message, in bytes (1–256,000,000). |
| **Description** | — | Free-text description. |
| **Metadata** | — | Key–value pairs added to the `metadata` of every message from this integration. |

The integration always connects over TLS on port `8883` with a clean session. It does not offer **Check connection**: check the integration status after you add it.

#### Credentials

| Type | Fields |
|------|--------|
| **Shared Access Signature** | **SAS Key** — the device's primary or secondary key. ThingsBoard builds a SAS token from it on each connection, valid for one year. **CA certificate file** — optional; see below. |
| **PEM** | X.509 authentication. **Certificate file** — the device certificate registered in the hub. **Private key file** — the key for that certificate. **Private key password** — only for an encrypted key. **CA certificate file** — optional; see below. |

Without a **CA certificate file**, the integration verifies the hub with the DigiCert Global Root G2 certificate, which Azure IoT Hub uses. Upload your own CA bundle only if your environment requires it. For X.509 device registration, see <a href="https://learn.microsoft.com/en-us/azure/iot-hub/authenticate-authorize-x509" target="_blank" rel="noopener noreferrer"><strong>Authenticate identities with X.509 certificates</strong></a>.

## Configure Downlink

ThingsBoard publishes downlinks to the hub when the Rule Engine routes a message to the integration — for example, after a shared attribute update. Downlinks are published with QoS 1 as device-to-cloud messages from the integration's Device ID. They reach the hub's built-in events endpoint, where an Azure-side consumer reads them.

The topic comes from the `topic` value in the downlink converter's output `metadata`. The integration has no fixed downlink topic, so the encoder must set `topic` to `devices/{deviceId}/messages/events/`, with the integration's Device ID. IoT Hub closes the connection when a device publishes to any other topic. To identify the ThingsBoard device, put its name in the payload.

The downlink converter turns a <DocLink product={props.product} path="user-guide/rule-engine" target="_blank">Rule Engine</DocLink> message into the published payload. For the full encoder reference, see <DocLink product={props.product} path="user-guide/integrations/downlink-data-converter" target="_blank">Downlink data converter</DocLink>.

### Create and Assign the Downlink Converter

The encoder returns:

- `contentType` — `JSON`, `TEXT`, or `BINARY`.
- `data` — the payload to publish.
- `metadata` — `topic`, the topic to publish to.

For RPC commands, `msg.method` and `msg.params` are available.

<Steps>
1. Open the integration in **Integrations &#8702; Integrations** and click **Toggle edit mode** (pencil icon).
2. In the **Downlink data converter** field, click **Create new**. The **Downlink** converter type and **Azure IoT Hub** integration type are preselected.
3. Enter a name, for example `Azure IoT Hub Downlink Converter`.
4. In **Main encoding configuration**, replace the default encoder with the one below. Replace `tb-bridge-01` with your Device ID.
5. To record downlink events, click the debug icon next to the name, select **All messages**, and click **Apply**.
6. Click **Add**, then **Apply changes**.
</Steps>

Encoder used in this guide (TBEL and JavaScript):

```js maxLines=15 collapsible
/** Encoder **/

// Prepare the downlink payload.
var data = {
  deviceName: metadata.deviceName,
  ts: Date.now()
};

// Map Rule Engine messages to commands.
if (msgType == 'RPC_CALL_FROM_SERVER_TO_DEVICE') {
  // RPC request.
  data.method = msg.method;
  data.params = msg.params;
  data.requestId = metadata.requestId;
} else if (msgType == 'ATTRIBUTES_UPDATED' || msgType == 'POST_ATTRIBUTES_REQUEST') {
  // Shared attribute update.
  data.method = 'setSharedAttributes';
  data.params = msg;
} else {
  // Other message types.
  data.method = 'data';
  data.params = msg;
}

// Return the encoded downlink payload.
var result = {
  // Payload content type: JSON, TEXT, or BINARY (Base64).
  contentType: 'JSON',
  data: JSON.stringify(data),
  metadata: {
    // Azure IoT Hub device-to-cloud MQTT topic.
    topic: 'devices/tb-bridge-01/messages/events/'
  }
};

return result;
```

To check the encoder, click **Test encoder function**. **Message type** is already `ATTRIBUTES_UPDATED`. Set **Message** to `{"temperatureUploadFrequency":60}` and **deviceName** in **Metadata** to `8F4A2C6D`, if they differ, then click **Test**. The **Output** shows:

```json
{
  "contentType": "JSON",
  "data": "{\"deviceName\":\"8F4A2C6D\",\"ts\":1755422164000,\"method\":\"setSharedAttributes\",\"params\":{\"temperatureUploadFrequency\":60}}",
  "metadata": {
    "topic": "devices/tb-bridge-01/messages/events/"
  }
}
```

**To adapt:**
- **Another envelope** — build `data` in the structure your Azure-side consumer expects.
- **Payload as is** — use `data: JSON.stringify(msg)` and drop the branches.
- **Message properties** — append a URL-encoded property bag to the topic, for example `devices/tb-bridge-01/messages/events/source=thingsboard`. IoT Hub routing queries can filter on these properties.
- **Other message types** — add branches for other <DocLink product={props.product} path="reference/rule-engine/message-types" target="_blank">Rule Engine message types</DocLink>.

### Configure the Root Rule Chain

The encoder puts `deviceName` in the payload, so the rule chain first adds the device name to the message metadata.

<Steps>
1. Go to **Data processing &#8702; Rule chains** and open the **Root Rule Chain**.
2. From the **Enrichment** section, drag an **originator fields** node onto the canvas.
3. Enter a **Name** (for example, `Retrieve device name`) and map the source fields:
   - **Name &#8702; deviceName**
   - **Add mapped originator fields to &#8702; Metadata**
   - Click **Add**.
4. Connect the **message type switch** node to the **originator fields** node with the **Attributes Updated** relation.
5. From the **Action** section, drag an **integration downlink** node onto the canvas.
6. Enter a **Name** (for example, `Downlink to Azure IoT Hub`), select your Azure IoT Hub integration, and click **Add**.
7. Connect the **originator fields** node to the **integration downlink** node with the **Success** relation.
8. Click **Apply changes**.
</Steps>

### Test Downlink

IoT Hub does not keep a viewable history of device-to-cloud messages, so start monitoring before you trigger the downlink.

<Steps>
1. Start the event monitor:

   ```bash
   az iot hub monitor-events --hub-name tb-iot-hub --device-id tb-bridge-01
   ```

2. Go to **Devices & assets &#8702; Devices**, select **8F4A2C6D**, and open the **Attributes** tab.
3. Select **Shared attributes** and click **+**.
4. Set **Key** to `temperatureUploadFrequency`, **Type** to **Integer**, **Value** to `60`, and click **Add**. ThingsBoard publishes the downlink.
</Steps>

## Troubleshooting

| Symptom | Cause | Fix |
|---------|-------|-----|
| Integration is not connected | Wrong **Hostname**. | Copy it from the hub's **Overview** page: `{hub-name}.azure-devices.net`. |
| Same, after authentication | Wrong **Device ID** or **SAS Key**. | Compare both with the device details in the Azure portal. Regenerate the key if unsure. |
| Same, from a private network | Outbound port `8883` is blocked. | Open TCP `8883` to `*.azure-devices.net`, or use a <DocLink product={props.product} path="user-guide/integrations/remote" target="_blank">Remote Integration</DocLink>. |
| Connection keeps dropping | Another client uses the same Device ID. | Register a dedicated device identity for the integration. |
| Connection drops after each downlink | The encoder's `topic` is not `devices/{deviceId}/messages/events/`. | Set `metadata.topic` in the encoder to that topic, with the integration's Device ID. |
| No messages received | The topic filter does not match. | Use `devices/{deviceId}/messages/devicebound/#`, ending in `#`. |
| Device telemetry never arrives | Devices send device-to-cloud messages, which this integration does not receive. | Use the <DocLink product={props.product} path="user-guide/integrations/azure-event-hub" target="_blank">Azure Event Hub Integration</DocLink>. |
| Device not created | `deviceName` is empty, or **Allow create devices or assets** is off. | Check **Out** in the converter events and the integration settings. |
| Large messages dropped | The message exceeds **Max bytes in message**. | Raise the limit in **Advanced settings**. IoT Hub limits cloud-to-device messages to 64 KB. |
| Downlink produces no event | The rule chain does not reach the **integration downlink** node. | Check the Root Rule Chain wiring and turn on debug mode for its nodes. |
| Downlink sent, nothing in the monitor | The monitor started after the downlink. | Start `az iot hub monitor-events` first, then trigger the downlink. |

To read debug events, open the integration or converter, click **Events**, and select an event: **In** is the received data, **Out** is the converter result, and **Error** holds the error text.
