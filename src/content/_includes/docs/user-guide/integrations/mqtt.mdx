MQTT Integration allows connecting to external MQTT brokers, subscribing to data streams from those brokers, and converting any type of payload from your devices to ThingsBoard message format. Its typical use is whenever your devices are already connected to an external MQTT broker or any other IoT platform or connectivity provider with an MQTT-based back-end.

<DocImage src="/src/assets/images/user-guide/integrations/mqtt-integration.svg" alt="MQTT Integration architecture diagram — MQTT broker forwards messages to ThingsBoard MQTT Integration which decodes them via uplink converter and pushes telemetry/attributes to ThingsBoard; downlink messages flow in the opposite direction through the downlink converter" />

ThingsBoard MQTT Integration acts as an MQTT client. It subscribes to topics and converts the data into telemetry and attribute updates. In case of a downlink message, MQTT Integration converts it to the device-suitable format and pushes it to the external MQTT broker.

<Aside type="caution">
The MQTT broker should be either co-located with the ThingsBoard instance or deployed in the cloud with a valid DNS name or static IP address. A ThingsBoard instance running in the cloud cannot connect to an MQTT broker deployed in a local area network.
</Aside>

### ThingsBoard setup

Before setting up an MQTT Integration, you need to create uplink and downlink converters.

The uplink converter is a script for parsing and transforming the data received by MQTT Integration.

The downlink converter parses and transforms the data sent from ThingsBoard to the format consumed by existing device(s).

#### Uplink Converter

The purpose of the decoder function is to parse the incoming data and metadata to a format that ThingsBoard can consume.
`deviceName` and `deviceType` are required, while `attributes` and `telemetry` are optional.
`Attributes` and `telemetry` are flat key-value objects. Nested objects are not supported.

To create an uplink converter go to **Integrations center → Data converters** and click the **"+"** button.
Name it "**MQTT Uplink Converter**" and select type **Uplink**. Enable **Debug mode** for now.

<Aside type="note">
  **Debug mode**

  Enabling debug mode lets you track events, states, and potential errors related to converter execution.
  Debug mode can quickly increase disk usage because all debug events are stored in the database.
  Starting from **ThingsBoard 3.9**, the platform stores the full set of debug events only during the first **15 minutes** after the converter is created; afterward, only error events are retained.
</Aside>

<Aside type="tip">Use **TBEL** (ThingsBoard Expression Language) for converter scripts — it executes significantly faster than plain JavaScript inside ThingsBoard.</Aside>

Now copy and paste the following script to the **Decoder function** section:

<Tabs>
<TabItem label="TBEL (Recommended)">

```js  maxLines=15 collapsible
/** Decoder **/

// decode payload to string
var payloadStr = decodeToString(payload);
var data = JSON.parse(payloadStr);

var deviceName = metadata.topic.split("/")[3];
// decode payload to JSON
var deviceType = 'sensor';

// Result object with device attributes/telemetry data
var result = {
    deviceName: deviceName,
    deviceType: deviceType,
    attributes: {
        integrationName: metadata['integrationName'],
    },
    telemetry: {
        temperature: data.value,
    }
};

/** Helper functions 'decodeToString' and 'decodeToJson' are already built-in **/

return result;
```

    return String.fromCharCode.apply(String, payload);

    // convert payload to string.

#### Downlink Converter

The Downlink converter transforms outgoing RPC messages and then the Integration sends them to the external MQTT broker.

<Aside type="note">
Even if you won't send downlink RPC, you still need to create a dummy Downlink converter.
</Aside>

Create another converter with the name "**MQTT Downlink Converter**" and type **Downlink**. Leave the default script and click **Add**.

<Tabs>
<TabItem label="TBEL (Recommended)">

```js maxLines=15 collapsible
// Encode downlink data from incoming Rule Engine message

// msg - JSON message payload downlink message json
// msgType - type of message, for ex. 'ATTRIBUTES_UPDATED', 'POST_TELEMETRY_REQUEST', etc.
// metadata - list of key-value pairs with additional data about the message
// integrationMetadata - list of key-value pairs with additional data defined in Integration executing this converter

/** Encoder **/

var data = {};

// Process data from incoming message and metadata

data.tempFreq = msg.temperatureUploadFrequency;
data.humFreq = msg.humidityUploadFrequency;

data.devSerialNumber = metadata['ss_serialNumber'];

// Result object with encoded downlink payload
var result = {

    // downlink data content type: JSON, TEXT or BINARY (base64 format)
    contentType: "JSON",

    // downlink data
    data: JSON.stringify(data),

    // Optional metadata object presented in key/value format
    metadata: {
        topic: metadata['deviceType']+'/'+metadata['deviceName']+'/upload'
    }

};

return result;
```

#### MQTT Integration Setup

<Steps>
1. Go to **Integrations center → Integrations** and click the **"+"** icon to add a new integration. Name it "**MQTT Integration**" and select type **MQTT**.
2. Add the recently created **uplink** and **downlink** converters.
3. Specify **Host**: `broker.hivemq.com` and **Port**: `1883` on the connection step.
4. Add a **topic filter**:

   ```shell
   tb/mqtt-integration-tutorial/sensors/+/temperature
   ```

   You can also select an MQTT **QoS** level. We use MQTT QoS level 0 (At most once) by default.
5. Go to **Advanced settings**. Uncheck the **Clean session** parameter — many brokers do not support sticky sessions and will silently close the connection if this option is enabled.
6. Leave the **Downlink topic pattern** at its default value, meaning the Integration will use `metadata.topic` as the downlink topic.
7. Optionally click **Check connection** to verify connectivity. Click **Add** to create the integration.
</Steps>

### MQTT retransmission mechanism

The MQTT Integration uses ThingsBoard's internal MQTT client.

ThingsBoard's internal MQTT client includes a retransmission mechanism designed to improve reliability for message types that require acknowledgment.
This mechanism applies specifically to the following MQTT message types:
- **PUBLISH** (only for QoS 1 or 2)
- **SUBSCRIBE**
- **UNSUBSCRIBE**
- **PUBREL** (only for QoS 2)

When one of these messages is sent, the client waits for an acknowledgment within a configurable delay period.
If no acknowledgment is received, the message is retransmitted. The delay between retransmissions follows an **exponential backoff** strategy, starting from an initial delay and doubling with each attempt.
A **jitter factor** introduces random variance into the delay to help prevent synchronized retries.

For example, if the retransmission configuration is set to **three attempts**, with an **initial delay of 5,000 ms** and a **jitter factor of 0.15**, the retransmission attempts would be scheduled at approximately **5,000 ms**, **10,000 ms**, and **20,000 ms**, each adjusted by ±15% jitter.
If no acknowledgment is received after the final attempt, the system waits through the next scheduled delay — based on exponential backoff with jitter — before finally considering the message **undeliverable and dropping it**.
