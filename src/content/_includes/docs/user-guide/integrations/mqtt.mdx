MQTT Integration connects ThingsBoard to an external MQTT broker as a client. It subscribes to the topics you configure, and an **uplink data converter** transforms each message into device or asset data, including telemetry and attributes. ThingsBoard can also publish **downlink** messages to the broker for devices to consume.

Use MQTT Integration when:
- Devices already publish to an existing broker (Mosquitto, HiveMQ, EMQX, and others) and you want their data in ThingsBoard without changing the firmware.
- The device name or type is encoded in the topic path rather than in the payload.
- Devices send a custom payload format that must be converted before ThingsBoard processes it.
- You need to send commands to devices through the same broker.

<Aside type="note">
  To connect devices directly to ThingsBoard and send data in the ThingsBoard format, use the <DocLink product={props.product} path="reference/mqtt-api/" target="_blank">MQTT Device API</DocLink> instead — no external broker or integration needed.
</Aside>

1. **Receive data.** A device publishes a message to the broker. The integration is subscribed to that topic and receives the message.
2. **Decode the payload.** The uplink converter uses the payload and topic to identify the device or asset and extract attributes and telemetry.
3. **Process the message.** ThingsBoard processes the converted data through the Rule Engine. If **Allow create devices or assets** is enabled, ThingsBoard can create an entity that does not exist yet.
4. **Send downlink data (optional).** The Rule Engine passes a message to the integration. The downlink converter encodes it, and the integration publishes it to the broker on the downlink topic.

<Aside type="note">
The broker must be reachable from the ThingsBoard server. ThingsBoard Cloud cannot connect to a broker inside a private network. In that case, use a <DocLink product={props.product} path="user-guide/integrations/remote">Remote Integration</DocLink>.
</Aside>

       ```js maxLines=15 collapsible
       // If neither is provided, the current time is used.
       ```

       ```js maxLines=15 collapsible
               if (typeof value === 'object' && value !== null && !Array.isArray(value)) {

               }
       ```

<h4>Decoder Inputs</h4>

The decoder signature is `function decoder(payload, metadata): object | object[]`.

| Variable | Type | Content |
|----------|------|---------|
| `payload` | byte array | The MQTT message body. |
| `metadata` | `{[key: string]: string}` | `topic` — the topic the message arrived on, for example `tb/devices/thermostat/Thermostat-01/telemetry`. Also `integrationName` and the key–value pairs from the integration's **Metadata** field. |

With a wildcard topic filter, `topic` holds the actual topic of the message, not the filter. Split it with `metadata['topic'].split('/')` to read a device name or type from the path.

Built-in helpers:

| Function | Result |
|----------|--------|
| `decodeToJson(payload)` | Parses the bytes as JSON and returns an object. |
| `decodeToString(payload)` | Converts the bytes to a UTF-8 string. |
| `toFlatMap(obj, excludeKeys, flatNested)` | TBEL only. Returns a flat key–value map of `obj`, skipping `excludeKeys`. With `flatNested` set to `true`, nested objects become dot-separated keys. Add the result with `putAll(...)`. The JavaScript template defines its own `toFlatMap(obj, result, excludeList)`, which writes into `result`. |

<Aside type="note">
  A nested object in `telemetry` or `attributes` is saved as a single JSON value. To store each nested field as its own key, flatten the object with `toFlatMap` or extract the fields explicitly.
</Aside>

For field renaming, nested values, and non-JSON payloads, see <DocLink product={props.product} path="user-guide/integrations/uplink-data-converter/#common-scripting-patterns" target="_blank">Common scripting patterns</DocLink> and the **[converter examples](#converter-examples-by-payload-type)** below.

<h4 id="device-name-and-type">Device Name and Type</h4>

The default decoder resolves the device in this order:

| Value | Source |
|-------|--------|
| `deviceName` | `deviceName` in the payload. Otherwise, the topic, if it has a supported format. |
| `deviceType` | `deviceType` in the payload. Otherwise, the topic, if it has a supported format. Otherwise, `default`. |

Supported topic formats:

- `tb/devices/{deviceType}/{deviceName}`, optionally followed by `/telemetry`
- `tb/sensors/{deviceType}/{deviceName}`, optionally followed by `/telemetry`

If neither the payload nor the topic provides the device name, the decoder fails with `Device name is missing. Provide deviceName in the payload or use a supported MQTT topic format.`

If your devices publish to other topics, change `topicPrefixes` at the start of the decoder, for example to `["factory/devices"]`. Each prefix must have exactly two topic levels: the decoder reads `{prefix}/{deviceType}/{deviceName}`, optionally followed by `/telemetry`.

#### Topic Filters

The integration subscribes to all topic filters when it connects.

| Wildcard | Matches | Example filter | Matching topics |
|----------|---------|----------------|-----------------|
| `+` | One level | `tb/devices/+/+/telemetry` | `tb/devices/thermostat/Thermostat-01/telemetry`, `tb/devices/meter/Meter-02/telemetry` |
| `#` | All remaining levels; must be last | `v1/devices/me/#` | `v1/devices/me/telemetry`, `v1/devices/me/attributes/request/1` |

| QoS | Name | Delivery |
|-----|------|----------|
| `0` | At most once | No acknowledgment. A message may be lost. |
| `1` | At least once | Acknowledged. A message may arrive twice. |
| `2` | Exactly once | Delivered once. Highest overhead. |

## Message Retransmission

ThingsBoard resends unacknowledged MQTT packets — PUBLISH (QoS 1 and 2), SUBSCRIBE, UNSUBSCRIBE, and PUBREL — with exponential backoff. The delay doubles after each attempt, and a jitter factor adds random variance so that clients do not retry in sync.

**Example:** 3 attempts, 5,000 ms initial delay, jitter factor 0.15 → retries at about 5,000 ms, 10,000 ms, and 20,000 ms (±15% each). After the last attempt, the packet is dropped.

## Configure Downlink

ThingsBoard publishes downlinks to the broker when the Rule Engine routes a message to the integration — for example, after a shared attribute update. Downlinks are always published with QoS 1. The topic comes from the **Downlink topic pattern**: with the default `${topic}`, it is the `topic` value in the downlink converter's output `metadata`.

The downlink converter turns a <DocLink product={props.product} path="user-guide/rule-engine" target="_blank">Rule Engine</DocLink> message into an MQTT payload. For the full encoder reference, see <DocLink product={props.product} path="user-guide/integrations/downlink-data-converter" target="_blank">Downlink data converter</DocLink>.

### Create and Assign the Downlink Converter

The encoder returns:

- `contentType` — `JSON`, `TEXT`, or `BINARY`.
- `data` — the payload to publish.
- `metadata` — values for the **Downlink topic pattern** placeholders, for example `topic`.

For RPC commands, `msg.method` and `msg.params` are available. `msg.params` is a string — use `parseFloat(msg.params)` or `JSON.parse(msg.params)` to get a number or an object.

<Steps>
1. Open the integration in **Integrations &#8702; Integrations** and click **Toggle edit mode** (pencil icon).
2. In the **Downlink data converter** field, click **Create new**. The **Downlink** converter type and **MQTT** integration type are preselected.
3. Enter a name, for example `MQTT Downlink Converter`.
4. In **Main encoding configuration**, use the default encoder or write your own.
5. Click **Test encoder function** and check the result (see **[Test the Encoder](#test-the-encoder)**).
6. To record downlink events, click **Disabled** next to the name, select **All messages**, and click **Apply**.
7. Click **Add**, then **Apply changes**.
</Steps>

The default encoder publishes the message as JSON to `tb/devices/{deviceType}/{deviceName}/commands`. If `deviceName` or `deviceType` is missing or contains `/`, `+`, or `#`, it raises an error and the downlink is not sent.

```js
/** Encoder **/

// Publish the ThingsBoard message as JSON to the device commands topic:
// tb/devices/{deviceType}/{deviceName}/commands
// Requires deviceName and deviceType in the message metadata,
// e.g. added by the "Originator fields" rule node (name -> deviceName, type -> deviceType).
// metadata.topic is read by the integration when Downlink topic pattern is ${topic}.
var deviceName = metadata['deviceName'];
var deviceType = metadata['deviceType'];

// Reject values that are missing or contain MQTT topic separators/wildcards ('/', '+', '#'):
// such a topic would be invalid and the command would not be delivered.
if (!isValidTopicLevel(deviceName) || !isValidTopicLevel(deviceType)) {
  var errorMessage = "Invalid MQTT downlink topic: deviceName '" + deviceName + "' and deviceType '" + deviceType +
      "' must be present and must not contain '/', '+' or '#'.";
  raiseError(errorMessage);
}

var result = {
  contentType: "JSON",
  data: JSON.stringify(msg),
  metadata: {
    topic: 'tb/devices/' + deviceType + '/' + deviceName + '/commands'
  }
};

function isValidTopicLevel(value) {
  return value != null && value.toString().trim() != '' &&
      value.indexOf('/') < 0 && value.indexOf('+') < 0 && value.indexOf('#') < 0;
}

return result;
```

### Configure the Root Rule Chain

The encoder builds the topic from `deviceName` and `deviceType`, so the rule chain first adds these values to the message metadata.

<Steps>
1. Go to **Data processing &#8702; Rule chains** and open the **Root Rule Chain**.
2. From the **Enrichment** section, drag an **originator fields** node onto the canvas.
3. Enter a **Name** (for example, `Retrieve device name`) and map the source fields:
   - **Name &#8702; deviceName**
   - **Profile name &#8702; deviceType**
   - **Add mapped originator fields to &#8702; Metadata**
   - Click **Add**.
4. Connect the **message type switch** node to the **originator fields** node with the **Attributes Updated** relation.
5. From the **Action** section, drag an **integration downlink** node onto the canvas.
6. Enter a **Name** (for example, `Downlink to MQTT integration`), select your MQTT integration, and click **Add**.
7. Connect the **originator fields** node to the **integration downlink** node with the **Success** relation.
8. Click **Apply changes**.
</Steps>

### Test Downlink

Subscribe to the downlink topic, then update a shared attribute to trigger a downlink.

<Steps>

   ```shell
   mosquitto_sub -h demo.tbmq.io -p 1883 -t "tb/devices/thermostat/Thermostat-01/commands" -u "demo" -P "demo"
   ```

2. Go to **Devices & assets &#8702; Devices**, select your device, and open the **Attributes** tab.
3. Select **Shared attributes** and click **+**.

## Converter Examples by Payload Type

Ready-made decoders for common payload shapes. Each example lists the input, the decoder, and the output.

<h4>Device Name and Type in the Payload</h4>

Use when every message carries `deviceName` and `deviceType`.

**Input payload (any topic):**

```json
{
  "deviceName": "Thermometer",
  "deviceType": "thermostat",
  "model": "SN-001",
  "temperature": 33
}
```

**Decoder:**

```js
/** Decoder **/
 
var data = decodeToJson(payload);
 
var deviceName = data.deviceName;
var deviceType = data.deviceType;
 
var result = {
   deviceName: deviceName,
   deviceType: deviceType,
   attributes: {
       model: data.model,
       integrationName: metadata['integrationName'],
   },
   telemetry: {
       temperature: data.temperature
   }
};
 
/** Helper function 'decodeToJson' is already built-in **/
 
return result;
```

**Field mapping:**

| JSON field | Output field | Type | Notes |
|------------|--------------|------|-------|
| `deviceName` | `deviceName` | — | Device identifier; creates the device on first uplink |
| `deviceType` | `deviceType` | — | Device profile name |
| `model` | `model` | attribute | |
| `temperature` | `temperature` | telemetry | |

**Output:**

```json
{
  "deviceName": "Thermometer",
  "deviceType": "thermostat",
  "attributes": {
    "model": "SN-001",
    "integrationName": "MQTT integration"
  },
  "telemetry": {
    "temperature": 33
  }
}
```

**To adapt:**

- **Device name in another field** — replace `data.deviceName` with that field.
- **One profile for all devices** — replace `data.deviceType` with a string, for example `'thermostat'`.
- **Rename a field** — write `outputName: data.sourceField`.
- **More telemetry** — extend the `telemetry` object.

<h4>Device Name from the Topic</h4>

Use when devices send readings only and put their identity in the topic path.

**Topic structure:** `tb/mqtt-integration-tutorial/sensors/{deviceName}`, for example `tb/mqtt-integration-tutorial/sensors/Thermometer-01`.

**Input payload:**

```json
{
  "temperature": 25.1
}
```

**Decoder:**

<Tabs>
  <TabItem label="TBEL (Recommended)">
  ```js
  /** Decoder **/
   
  // decode payload to string
  var payloadStr = decodeToString(payload);
  var data = JSON.parse(payloadStr);
   
  // Topic: tb/mqtt-integration-tutorial/sensors/{deviceName}
  // Index:  0             1                2         3
  var deviceName = metadata.topic.split("/")[3];
  var deviceType = 'sensor'; // hardcoded device profile
   
  // Result object with device attributes/telemetry data
  var result = {
    deviceName: deviceName,
    deviceType: deviceType,
    attributes: {
      integrationName: metadata['integrationName'],
    },
    telemetry: {
      temperature: data.temperature,
    }
  };
   
  /** Helper functions 'decodeToString' and 'decodeToJson' are already built-in **/
   
  return result;
  ```
  </TabItem>
  <TabItem label="JavaScript">
  ```js
  /** Decoder **/

  // decode payload to string
  var payloadStr = decodeToString(payload);
  var data = JSON.parse(payloadStr);

  // Topic: tb/mqtt-integration-tutorial/sensors/{deviceName}
  // Index:  0             1                2         3
  var deviceName = metadata.topic.split("/")[3];
  var deviceType = 'sensor'; // hardcoded device profile

  // Result object with device attributes/telemetry data
  var result = {
    deviceName: deviceName,
    deviceType: deviceType,
    attributes: {
      integrationName: metadata['integrationName'],
    },
    telemetry: {
      temperature: data.temperature,
    }
  };

  /** Helper functions **/

  function decodeToString(payload) {
    return String.fromCharCode.apply(String, payload);
  }

  function decodeToJson(payload) {
    // convert payload to string.
    var str = decodeToString(payload);

    // parse string to JSON
    var data = JSON.parse(str);
    return data;
  }

  return result;
  ```
  </TabItem>
</Tabs>

**Field mapping:**

| Source | Output field | Type | Notes |
|--------|--------------|------|-------|
| `metadata.topic.split("/")[3]` | `deviceName` | — | Fourth topic segment (0-indexed: 3) |
| `'sensor'` | `deviceType` | — | Fixed profile |
| `data.temperature` | `temperature` | telemetry | |
| `metadata['integrationName']` | `integrationName` | attribute | |

**Output** for `{"temperature": 25.1}` on `tb/mqtt-integration-tutorial/sensors/Thermometer-01`:

```json
{
  "deviceName": "Thermometer-01",
  "deviceType": "sensor",
  "attributes": {
    "integrationName": "MQTT integration"
  },
  "telemetry": {
    "temperature": 25.1
  }
}
```

**To adapt:**

- **Another topic depth** — change the index in `split("/")[3]`.
- **Device type from the topic** — replace `'sensor'` with another segment, for example `metadata.topic.split("/")[2]`.
- **Device name in the payload** — replace the topic segment with a payload field, for example `data.deviceId`.
- **Wildcard filter** — with `tb/mqtt-integration-tutorial/sensors/+`, `metadata.topic` holds the real topic, so the same `split` works.

<h4>Nested JSON Flattened with toFlatMap</h4>

Use when the payload is nested and every remaining field should become telemetry. `toFlatMap` produces dot-separated keys (`sensors.co2`) and skips the keys in `excludeKeys`.

**Input payload:**

```json
{
  "deviceName": "air-monitor-X",
  "deviceType": "air-quality",
  "meta": { "source": "cloud" },
  "sensors": {
    "co2": 412,
    "pm25": 8.2,
    "voc": 0.3
  },
  "location": {
    "lat": 50.45,
    "lon": 30.52
  },
  "ts": 1700000000000
}
```

**Decoder:**

```js
/** Decoder **/
 
var data = decodeToJson(payload);
 
// Fields to exclude from telemetry — used as device identity, attributes, or timestamp
var excludeKeys = ['deviceName', 'deviceType', 'ts', 'meta', 'location'];
 
// Flatten all remaining fields into telemetry (nested objects become dot-separated keys)
var telemetry = {};
telemetry.putAll(toFlatMap(data, excludeKeys, true));

// Use the device timestamp (ms) if present, otherwise the current time
var ts = data.ts != null ? data.ts : Date.now();
 
var result = {
    deviceName: data.deviceName,
    deviceType: data.deviceType,
    attributes: {
        latitude:        data.location.lat,
        longitude:       data.location.lon,
        source:          data.meta.source,
        integrationName: metadata['integrationName']
    },
    telemetry: {
        ts:     ts,
        values: telemetry
    }
};
 
/** Helper functions 'decodeToString', 'decodeToJson' and 'toFlatMap' are already built-in **/
 
return result;
```

**Field mapping:**

| JSON field | Output field | Type | Notes |
|------------|--------------|------|-------|
| `deviceName` | `deviceName` | — | Excluded from telemetry |
| `deviceType` | `deviceType` | — | Excluded from telemetry |
| `location.lat` | `latitude` | attribute | Extracted explicitly |
| `location.lon` | `longitude` | attribute | Extracted explicitly |
| `meta.source` | `source` | attribute | Extracted explicitly |
| `sensors.co2` | `sensors.co2` | telemetry | Mapped by `toFlatMap` |
| `sensors.pm25` | `sensors.pm25` | telemetry | Mapped by `toFlatMap` |
| `sensors.voc` | `sensors.voc` | telemetry | Mapped by `toFlatMap` |
| `ts` | `ts` | — | Timestamp, ms; excluded from telemetry |

**Output:**

```json
{
  "deviceName": "air-monitor-X",
  "deviceType": "air-quality",
  "attributes": {
    "latitude": 50.45,
    "longitude": 30.52,
    "source": "cloud",
    "integrationName": "MQTT integration"
  },
  "telemetry": {
    "ts": 1700000000000,
    "values": {
      "sensors.co2": 412,
      "sensors.pm25": 8.2,
      "sensors.voc": 0.3
    }
  }
}
```

**To adapt:**

- **Other top-level fields to skip** — add them to `excludeKeys`.
- **Rename a flattened key** — extract the field explicitly and add its parent to `excludeKeys` so it is not duplicated.
- **No timestamp** — use `ts: Date.now()`.
- **Timestamp in seconds** — use `ts: data.ts * 1000`.

<h4>Delimited Text Payload</h4>

Use when the device sends text instead of JSON. `decodeToString` converts the bytes to a string, and `split` separates the fields.

**Input payload:**

```
sensor-001;23.5;60;87
```

**Decoder:**

```js
/** Decoder **/
 
// Decode bytes to a UTF-8 string and split by delimiter
var raw   = decodeToString(payload);
var parts = raw.trim().split(';');
 
// parts[0] = device name
// parts[1] = temperature
// parts[2] = humidity
// parts[3] = battery
 
var result = {
    deviceName: parts[0],
    deviceType: 'csv-sensor',
    attributes: {
        integrationName: metadata['integrationName'],
        topic: metadata['topic']
    },
    telemetry: {
        ts: Date.now(),
        values: {
            temperature: parseFloat(parts[1]),
            humidity:    parseFloat(parts[2]),
            battery:     parseInt(parts[3])
        }
    }
};
 
/** Helper function 'decodeToString' is already built-in **/
 
return result;
```

**Field mapping:**

| Position | Output field | Type | Notes |
|----------|--------------|------|-------|
| `parts[0]` | `deviceName` | — | Device identifier |
| `'csv-sensor'` | `deviceType` | — | Fixed profile |
| `parts[1]` | `temperature` | telemetry | Float |
| `parts[2]` | `humidity` | telemetry | Float |
| `parts[3]` | `battery` | telemetry | Integer |

**Output:**

```json
{
  "deviceName": "sensor-001",
  "deviceType": "csv-sensor",
  "attributes": {
    "integrationName": "MQTT integration",
    "topic": "tb/sensors/csv/sensor-001"
  },
  "telemetry": {
    "ts": 1780299924174,
    "values": {
      "temperature": 23.5,
      "humidity": 60.0,
      "battery": 87
    }
  }
}
```

**To adapt:**

- **Another delimiter** — replace `';'`, for example with `','` or `'|'`.
- **Device name from the topic** — replace `parts[0]` with `metadata['topic'].split('/').pop()`.
- **Timestamp in the string** — parse it into `ts` and convert seconds to milliseconds.
- **Fewer or more fields** — edit the `values` object and the index comments.

## Troubleshooting

| Symptom | Cause | Fix |
|---------|-------|-----|
| **Check connection** fails or the integration is disconnected | Wrong host or port, or a firewall blocks the connection. | Check the host, port, and firewall rules. |
| Same, after authentication | Wrong credentials or credentials type. | Check the username and password or the certificate files. Match the credentials type to the broker. |
| Same, with TLS | **Enable SSL** does not match the broker. | Match **Enable SSL** and the port to the broker (`1883` plain, `8883` TLS). |
| `Usage of local network host ... is not allowed` | ThingsBoard Cloud cannot connect to a private-network host. | Use a public broker address or a <DocLink product={props.product} path="user-guide/integrations/remote" target="_blank">Remote Integration</DocLink>. |
| No messages received | No topic filter matches the published topic. | Check the topic filters and wildcard syntax. |
| Device not created, the converter event has an error | The payload has no `deviceName`, and the topic does not match a format that the default decoder supports. The decoder fails with `Device name is missing. Provide deviceName in the payload or use a supported MQTT topic format.` | Add `deviceName` to the payload, publish to `tb/devices/{deviceType}/{deviceName}/telemetry`, or change `topicPrefixes` in the decoder to match your topics. |
| Telemetry not saved | The decoder returns `{}`, `[]`, or empty `values`. | Make sure `values` holds at least one key. |
| Decoder error | The TBEL or JavaScript code throws an exception. | Open the converter's **Events** tab and read the **Error** column. |
| Wrong timestamp | The device sends `ts` in seconds. | Convert it: `ts: data.ts * 1000`. |
| Duplicate messages after reconnect | QoS 1 or 2 with **Clean session** off. | Turn on **Clean session**. |
| Connection keeps dropping | Another client uses the same **Client ID**. | Clear **Client ID** to get a generated one, or make it unique. |
| Downlink not received | The rule chain does not reach the **integration downlink** node, or the topic differs from the subscription. | Check the Root Rule Chain wiring and the topic in the downlink converter's **Events**. |
| Downlink not sent, the downlink converter event has an error | The message metadata has no `deviceName` or `deviceType`, or a value contains `/`, `+`, or `#`. The encoder fails with `Invalid MQTT downlink topic: deviceName '...' and deviceType '...' must be present and must not contain '/', '+' or '#'.` | Map **Name &#8702; deviceName** and **Profile name &#8702; deviceType** in the **originator fields** node of the Root Rule Chain, or rename the device or device profile. |

To read debug events, open the integration or converter, click **Events**, and select an event: **In** is the received data, **Out** is the converter result, and **Error** holds the error text.
