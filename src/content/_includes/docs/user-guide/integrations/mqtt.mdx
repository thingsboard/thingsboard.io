MQTT Integration connects ThingsBoard to an external MQTT broker: it subscribes to topics, decodes device payloads via an uplink converter, and pushes telemetry and attributes to the platform. In the reverse direction, it encodes Rule Engine messages via a downlink converter and publishes them back to the broker.

<DocImage src="/src/assets/images/user-guide/integrations/mqtt-integration.svg" alt="MQTT Integration architecture diagram — MQTT broker forwards messages to ThingsBoard MQTT Integration which decodes them via uplink converter and pushes telemetry/attributes to ThingsBoard; downlink messages flow in the opposite direction through the downlink converter" />

<Aside type="caution">
The MQTT broker must be reachable from the ThingsBoard server — either co-located, cloud-hosted with a public DNS name, or exposed via a static IP. A ThingsBoard Cloud instance cannot connect to a broker running inside a private local network. Use a <DocLink product={props.product} path="user-guide/integrations/remote">Remote Integration</DocLink> for LAN deployments.
</Aside>

## How MQTT Integration works

MQTT Integration, uplink/downlink converters, and the Rule Engine have distinct roles:

| Component | Responsibility |
|---|---|
| **MQTT Integration** | Maintains the MQTT client connection, subscribes to topic filters, and routes raw messages to the uplink converter |
| **Uplink converter** | Transforms the broker payload into the ThingsBoard internal format (device name, type, telemetry, attributes) |
| **Rule Engine** | Processes ThingsBoard messages — stores data, triggers alarms, generates downlinks |
| **Downlink converter** | Transforms a Rule Engine message back into a broker-ready payload (content type, data, target topic) |

**Topic filter vs downlink topic pattern:**
- **Topic filter** — MQTT topics the integration *subscribes* to for uplink messages (supports wildcards: `+`, `#`).
- **Downlink topic pattern** — MQTT topic the integration *publishes* to for downlink messages. The default `${topic}` means the integration reads the target topic from `metadata.topic` produced by the downlink converter. You can also hardcode a topic here.

### Uplink Converter

The uplink converter decodes the incoming MQTT payload and maps it to the ThingsBoard data model. The decoder function must return `deviceName` and `deviceType`; `attributes` and `telemetry` are optional. Both are flat key-value objects — nested objects are not supported.

<Steps>
1. Go to **Integration center → Data converters** and click **+ Add data converter → Create new converter**.
2. Name it "**MQTT Uplink Converter**" and select type **Uplink**. Enable **Debug mode**.
3. Paste the decoder script below and click **Add**.
</Steps>

<Aside type="note">
  **Debug mode** captures all raw input/output events. Starting from ThingsBoard 3.9, the full set of debug events is stored only during the first 15 minutes; afterward, only error events are retained. Disable debug mode in production to avoid excessive disk usage.
</Aside>

<Aside type="tip">Use **TBEL** (ThingsBoard Expression Language) for converter scripts — it executes significantly faster than plain JavaScript inside ThingsBoard.</Aside>

### Downlink Converter

The downlink converter transforms a Rule Engine message into the payload published to the MQTT broker.

The encoder function must return an object with:
- `contentType` — `JSON`, `TEXT`, or `BINARY` (Base64 string)
- `data` — the payload string to publish
- `metadata` — key-value pairs; `metadata.topic` sets the publish topic when the downlink topic pattern is `${topic}`

<Aside type="note">
A downlink converter is required only when the integration sends messages to devices (RPCs, attribute updates). If you only ingest data into ThingsBoard, you can skip it.
</Aside>

<Steps>
1. Go to **Integration center → Data converters** and click **+ Add data converter → Create new converter**.
2. Name it "**MQTT Downlink Converter**" and select type **Downlink**. Leave the default script and click **Add**.
3. Open the **MQTT Integration** and assign this downlink converter.
</Steps>

<Tabs>
<TabItem label="TBEL (Recommended)">

```js maxLines=15 collapsible
// Encode downlink data from incoming Rule Engine message

// msg - JSON message payload downlink message json
// msgType - type of message, for ex. 'ATTRIBUTES_UPDATED', 'POST_TELEMETRY_REQUEST', etc.
// metadata - list of key-value pairs with additional data about the message
// integrationMetadata - list of key-value pairs with additional data defined in Integration executing this converter

/** Encoder **/

var data = {};

// Process data from incoming message and metadata

data.tempFreq = msg.temperatureUploadFrequency;
data.humFreq = msg.humidityUploadFrequency;

data.devSerialNumber = metadata['ss_serialNumber'];

// Result object with encoded downlink payload
var result = {

    // downlink data content type: JSON, TEXT or BINARY (base64 format)
    contentType: "JSON",

    // downlink data
    data: JSON.stringify(data),

    // Optional metadata object presented in key/value format
    metadata: {
        topic: metadata['deviceType']+'/'+metadata['deviceName']+'/upload'
    }

};

return result;
```

## MQTT retransmission mechanism

ThingsBoard's internal MQTT client retransmits unacknowledged messages for reliability. The mechanism applies to:
- **PUBLISH** (QoS 1 or 2 only)
- **SUBSCRIBE**
- **UNSUBSCRIBE**
- **PUBREL** (QoS 2 only)

After sending, the client waits for an acknowledgment within a configurable delay. If none arrives, the message is retransmitted using **exponential backoff** — the delay doubles with each attempt. A **jitter factor** adds random variance to prevent synchronized retries.

For example: three attempts, initial delay 5,000 ms, jitter factor 0.15 → retransmission attempts at approximately **5,000 ms**, **10,000 ms**, and **20,000 ms** (each ±15%). If no acknowledgment is received after the final attempt, the message is dropped.

## Troubleshooting

**Integration cannot connect to the broker**
- Verify the host and port are correct and the broker is reachable from the ThingsBoard server.
- ThingsBoard Cloud instances cannot connect to brokers on private networks — use a <DocLink product={props.product} path="user-guide/integrations/remote">Remote Integration</DocLink> instead.
- Uncheck **Clean session** in Advanced settings if the broker drops the connection unexpectedly.

**No messages received**
- Check that the topic filter exactly matches the published topic pattern, including wildcard levels.
- Use the integration **Events** tab to verify whether messages arrive and how the converter processes them.

**Downlink not delivered to device**
- Verify that `metadata.topic` is set in the downlink converter output.
- Confirm the **Integration Downlink** node is connected to the **Message Type Switch** node via the **RPC Request to Device** relation.
- Check that the **MQTT Integration** has a downlink converter assigned.

**Debug mode causes high disk usage**
- Disable debug mode in production. Active debug stores all events to the database. Switch back to **Failures** mode once setup is complete.
