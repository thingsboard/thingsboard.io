**OPC-UA** (Open Platform Communications Unified Architecture, IEC 62541) is a platform-independent industrial M2M protocol for reliable, secure data exchange in automation and IoT systems. The ThingsBoard **OPC-UA Integration** connects to an OPC-UA server, subscribes to the device nodes you configure, decodes their values with an <DocLink product={props.product} path="user-guide/integrations/uplink-data-converter">uplink converter</DocLink>, and pushes the resulting telemetry and attributes into the platform. In the reverse direction it can encode Rule Engine messages with a <DocLink product={props.product} path="user-guide/integrations/downlink-data-converter">downlink converter</DocLink> and deliver them to OPC-UA nodes as write operations or method calls.

Use this integration whenever your data lives on an OPC-UA server — a PLC, SCADA gateway, historian, or any OPC-UA-capable device — and you want ThingsBoard to collect that data, create devices for it, and optionally control it.

**Data flow:** the OPC-UA server exposes nodes &#8702; the integration subscribes to the nodes matched by your mapping &#8702; node values are packed into a message and passed to the uplink converter &#8702; the converter returns a device name, telemetry, and attributes &#8702; ThingsBoard stores the telemetry and creates or updates the matching device.

In this guide the OPC-UA server is the **public Prosys OPC UA demo server** (`opc.tcp://uademo.prosysopc.com:53530/OPCUA/SimulationServer`) — a free, internet-hosted instance of the <a href="https://www.prosysopc.com/products/opc-ua-simulation-server/" target="_blank"><strong>Prosys OPC UA Simulation Server</strong></a>. It is always running, exposes a ready-to-use address space with continuously changing simulated values, and requires no installation, so you can follow the example on any operating system without setting up a server.

<Aside type="caution">
  The Prosys demo server is a shared, best-effort service intended for learning and testing only. Availability is not guaranteed, it accepts **unsecured (`None`) connections only**, and its data is shared with everyone. Do not use it for production or for anything sensitive. For a private or hardened setup, run your own <a href="https://www.prosysopc.com/products/opc-ua-simulation-server/" target="_blank">Prosys OPC UA Simulation Server</a> locally and substitute its address.
</Aside>

## The Public Prosys Demo Server

You do not install anything — the server is already running on the internet. Everything the integration needs is summarized here.

- **Endpoint** — `opc.tcp://uademo.prosysopc.com:53530/OPCUA/SimulationServer`, which splits into **Host** `uademo.prosysopc.com`, **Port** `53530`, and **Endpoint path** `/OPCUA/SimulationServer`.
- **Security** — `None` only. The public server does not allow `Sign` or `Sign&Encrypt`; use a self-hosted server if you need a secure connection.
- **Authentication** — `Anonymous`; no username or password.
- **Simulation** — always on. Values change continuously on the server side; there is nothing to start or stop.

**Example nodes.** The server exposes the standard Prosys Simulation Server address space. This guide reads the sample device **MyDevice**:

- Full path (FQN): `Objects.MyObjects.MyDevice`
- **MyLevel** — a `Double` variable holding a simulated level measurement that changes continuously (read as telemetry).
- **MySwitch** — a `Boolean` variable (read as an attribute).
- **MyMethod** — a callable sample method.

The **Simulation** folder on the same server also contains additional ready-made changing signals that you can add later as extra subscription tags.

## Create OPC-UA Uplink Data Converter

The uplink converter decodes the raw OPC-UA message and maps it to the ThingsBoard data model (device identity, telemetry, and attributes). It receives:

- `payload` — a JSON object keyed by your subscription-tag **Keys**, e.g. `{"level": "42.17", "switchState": "true"}` (values arrive as strings).
- `metadata` — node metadata: `opcUaNode_name`, `opcUaNode_namespaceIndex`, `opcUaNode_identifier`, `opcUaNode_fqn`, and `integrationName`.
**Sample input**

```json
{
  "payload": {
    "level": "42.17",
    "switchState": "true"
  },
  "metadata": {
    "opcUaNode_name": "MyDevice",
    "opcUaNode_namespaceIndex": "3",
    "opcUaNode_identifier": "MyDevice",
    "opcUaNode_fqn": "Objects.MyObjects.MyDevice",
    "integrationName": "OPC-UA integration"
  }
}
```

<Aside type="tip" title="TBEL">
  We recommend <DocLink product={props.product} path="user-guide/tbel">TBEL</DocLink> for converter scripts — it executes much more efficiently than JavaScript inside ThingsBoard.
</Aside>

The quickest path is inline in the integration wizard: on the **Uplink data converter** step (shown bottom), keep **Create new** and paste the decoder below into the **Main decoding configuration** editor, leaving the language toggle on **TBEL**. To create it as a reusable converter instead:

  4. Paste the decoder function below into the editor.

#### Connection settings

<h5>Host</h5>

Hostname or IP address of the OPC-UA server.

<h5>Port</h5>

Port number of the OPC-UA server. Default: `49320`.

<h5>Endpoint</h5>

Optional path suffix appended to the server address when constructing the OPC-UA connection URL. Use this when the server exposes a specific endpoint path, for example `/OPCUA/SimulationServer`. Leave blank if the server listens on the root path (most common for demo servers).

<h5>Security</h5>

Message security policy for the OPC-UA session:

- `None` — no encryption or signing (suitable for local/trusted networks)
- `Basic128Rsa15` — 128-bit symmetric encryption, RSA-15 key exchange
- `Basic256` — 256-bit symmetric encryption
- `Basic256Sha256` — 256-bit symmetric encryption with SHA-256 signing (recommended for production)

When any security policy other than `None` is selected, you must provide a client certificate and private key so the server can verify the ThingsBoard client's identity.

<h5>Identity</h5>

Authentication method used when establishing the OPC-UA session:

- `Anonymous` — no credentials required; the server must have anonymous logon enabled
- `Username` — additional **Username** and **Password** fields appear; authenticate with a server-side account

<h5>Mapping type</h5>

Determines how ThingsBoard identifies device nodes on the OPC-UA server:

- `Fully Qualified Name` — matches nodes by their full browsed path (e.g. `Objects.BuildingAutomation.AirConditioner_1`)
- `ID` — matches nodes by namespace index and node identifier

<h5>Device Node Pattern</h5>

Regular expression applied to OPC-UA node names or IDs to identify which nodes represent devices. Only nodes matching this pattern are subscribed to. Example: `Channel1\.Device\d+$`.

<h5>Namespace</h5>

OPC-UA namespace index used to scope node identifiers. Only visible when **Mapping type** is set to `ID`.

<h5>Subscription tags</h5>

Defines which child node values ThingsBoard reads from each matched device node. Each entry has:

- **Key** — the field name used in the ThingsBoard message payload (e.g. `temperature`)
- **Path** — relative path of the child node under the matched device node (e.g. `Temperature`)
- **Required** — when checked, a missing or unreadable value for this tag prevents the message from being processed; leave unchecked for optional tags

<h5>Execute remotely</h5>

When enabled, ThingsBoard generates an **Integration key** and **Integration secret** that allow the integration to run as a separate <DocLink product={props.product} path="user-guide/integrations">Remote Integration</DocLink> process outside the ThingsBoard cluster. This is the recommended approach when the OPC-UA server is only reachable from a local or isolated network that has no direct path to ThingsBoard.

<h5>Advanced settings</h5>

- **Application name** — OPC-UA client application name sent to the server during session establishment (informational)
- **Application uri** — OPC-UA client application URI; must be globally unique per the OPC-UA specification
- **Scan period in seconds** — how frequently ThingsBoard polls the OPC-UA server for updated node values. Default: `10`
- **Timeout in milliseconds** — connection and request timeout. Default: `5000`
- **Description** — optional text description for the integration
- **Metadata** — key-value pairs injected into every uplink message as `integrationMetadata` in converter scripts

## Configure Downlink

Downlink lets ThingsBoard write back to the server. The Rule Engine turns an RPC (or shared-attribute update) into a message, routes it through an **Integration Downlink** rule node to the downlink converter, and the converter encodes it into OPC-UA write operations or method calls.

<Aside type="caution">
  The public demo server is shared and read-oriented — writes affect every user and may be rejected or reset. **Test downlink only against your own self-hosted Prosys server**, where you can safely write to `MySwitch` and watch it change. Point the integration's **Host** at your local server for this part.
</Aside>
The encoder must return an object with:

- `contentType` — `JSON`.
- `data` — a JSON string with two optional arrays:
  - `writeValues` — `{nodeId, value}` pairs. NodeId format: `ns=<namespaceIndex>;<type>=<identifier>`, where `<type>` is `s` (string), `i` (numeric), `g` (GUID), or `b` (byte string).
  - `callMethods` — `{objectId, methodId, args}` objects.
- `metadata` — must be an empty object `{}` for OPC-UA.

The converter below reacts to an RPC named `setSwitch` carrying a boolean parameter and writes it to the device's **MySwitch** node.

Read the exact NodeId of **MySwitch** by browsing the server with the <a href="https://www.prosysopc.com/products/opc-ua-browser/" target="_blank"><strong>Prosys OPC UA Browser</strong></a> rather than assuming a namespace index. For the complete encoder reference and testing tools see <DocLink product={props.product} path="user-guide/integrations/downlink-data-converter" target="_blank">Downlink data converter</DocLink>.

For a method call instead of a write (e.g. `MyMethod`), leave `writeValues` empty and push to `callMethods` a `{ objectId, methodId, args }` object, reading both NodeIds from the server. See <DocLink product={props.product} path="user-guide/integrations/downlink-data-converter" target="_blank">Downlink data converter</DocLink> for the full encoder reference.

    ```js maxLines=25 collapsible
    // Downlink encoder: RPC 'setSwitch' -> OPC-UA write to MySwitch.
    // Trigger example: { "method": "setSwitch", "params": true }
    var data = { 
      writeValues: [], 
      callMethods: [] 
    };
    
    if (msgType == 'RPC_CALL_FROM_SERVER_TO_DEVICE' && msg.method == 'setSwitch') {
      // cs_namespaceIndex is the client attribute 'namespaceIndex' pulled into metadata
      // by the 'originator attributes' rule node (cs_ = client-scope prefix).
      // The identifier is just 'MySwitch' on this server — VERIFY yours with the
      // Prosys OPC UA Browser rather than assuming it's prefixed with the device name.
      var nodeId = 'ns=' + metadata['cs_namespaceIndex'] + ';s=MySwitch';
  
      // Normalize the RPC parameter to a real Boolean
      var value = (msg.params == true || msg.params == 'true' || msg.params == 1 || msg.params == '1');
  
      data.writeValues.push({ nodeId: nodeId, value: value });
    }

    var result = {
      contentType: 'JSON',
      data: JSON.stringify(data),
      metadata: {}
    };

    return result;
    ```

### Configure the Root Rule Chain

Configure the Root Rule Chain to forward RPC requests to the OPC-UA integration.

Two rule nodes are needed: an <strong>originator attributes</strong> node that reads the device's <code>namespaceIndex</code> client attribute and injects it into message metadata (the downlink converter reads it as <code>cs_namespaceIndex</code> to build the NodeId), and an <strong>integration downlink</strong> node that sends the message to the integration.

<Steps>
  1. Go to <strong>Rule chains &#8702; Root Rule Chain</strong>.
  2. In the <strong>Enrichment</strong> section of the node library, find the <strong>originator attributes</strong> node and drag it onto the canvas.
  3. Configure the node:
      - <strong>Name</strong> — e.g. <code>Retrieve namespaceIndex</code>.
      - Under <strong>Client attributes</strong>, add <code>namespaceIndex</code>.
      - Set <strong>Add originator attributes to</strong> to <strong>Metadata</strong>.
      - Click <strong>Add</strong>.
  4. In the node panel, search for <strong>integration downlink</strong> and drag it onto the canvas.
  5. Configure the node:
      - <strong>Name</strong> — e.g. <code>Downlink to OPC-UA</code>.
      - Under <strong>Integration</strong> — select <strong>OPC-UA integration</strong>.
      - Click <strong>Add</strong>.
  6. Connect the <strong>message type switch</strong> node to the <strong>originator attributes</strong> node using the <strong>RPC Request to Device</strong> relation.
  7. Connect the <strong>originator attributes</strong> node to the <strong>integration downlink</strong> node using the <strong>Success</strong> relation.
  8. Click <strong>Apply changes</strong>.
</Steps>

### Test Downlink

**Send the RPC.** Trigger a one-way RPC to the **MyDevice** device, for example via the REST API:

```bash
curl -X POST "https://<your-thingsboard-host>/api/rpc/oneway/<DEVICE_ID>" \
-H "Content-Type: application/json" \
-H "X-Authorization: Bearer <JWT_TOKEN>" \
-d '{"method":"setSwitch","params":true}'
```                                                   

### Verify Downlink Converter Events

Go to **Integrations center &#8702; Data converters**, open **OPC-UA Downlink Converter**, and click the **Events** tab.
Click an event row to inspect:
- **In** — the Rule Engine message received by the converter: `msg` contains the RPC `method` and `params`; `metadata.cs_namespaceIndex` and `metadata.deviceName` are injected by the **originator attributes** node.
- **Out** — the encoded output sent to the integration: a JSON `writeValues` array with your NodeId and value.

**Expected result:** the RPC reaches the integration, the downlink converter emits a `writeValues` entry, and **MySwitch** on the server changes to the sent boolean. If you also added a `switchState → MySwitch` subscription tag, the new value flows back into ThingsBoard as an attribute on the next scan.

## Troubleshooting

| Issue | Likely cause | Recommended fix |
|-------|--------------|-----------------|
| Connection refused / timeout | No outbound internet from the integration host, or a firewall blocking port `53530` | Verify the integration host can reach `uademo.prosysopc.com:53530` (e.g. `telnet`/`nc`); allow outbound TCP `53530`; if the ThingsBoard cluster has no internet, enable **Execute remotely** and run from a host that does. |
| Incorrect endpoint URL | Missing or wrong **Endpoint** path | Set **Host** = `uademo.prosysopc.com`, **Port** = `53530`, **Endpoint** = `/OPCUA/SimulationServer` (exact, with leading slash). |
| Incompatible security policy / message security mode | A secure mode was selected | The public demo accepts `None` only — set **Security = None**. For `Sign`/`Sign&Encrypt`, run your own Prosys server. |
| Discovery / endpoint hostname error | The demo server may return an endpoint without a fully qualified domain name | Re-try the connection; keep **Security = None**; if it persists, run a local Prosys server and connect to `opc.tcp://localhost:53530/OPCUA/SimulationServer` instead. |
| Authentication failure | An identity other than Anonymous was selected | Set **Identity = Anonymous**; the public server has no user accounts. |
| Nodes not found / no matching devices | Device Node Pattern does not match any node path | Browse the address space with the Prosys OPC UA Browser; escape dots in the regex (`Objects\.MyObjects\.MyDevice$`); confirm **Mapping type** matches how the pattern is written (FQN vs ID). |
| Device not created | No successful uplink yet, or **Allow create devices** disabled | Check the integration **Events** tab for errors; enable **Allow create devices**; confirm the converter returns a non-empty `deviceName`. |
| Integration receives data but telemetry is missing | Payload keys don't match the converter, or values not assigned to `telemetry` | Ensure subscription-tag **Keys** match the `data.<key>` names in the converter; confirm values are placed under `telemetry` (attributes go under `attributes`). |
| Values do not update | Scan period too long, or connection dropped | Lower the integration **Scan period**; check the **Events** tab for reconnects. The demo server itself updates values continuously. |
