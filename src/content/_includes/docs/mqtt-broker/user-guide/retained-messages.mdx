Retained Messages is an MQTT feature that allows storing the "last known good" message for a particular topic on the broker
and delivering the message to a client whenever the client subscribes to a matching topic.

Key properties of retained messages:

- Only one message can be stored per topic.
- Each new message replaces the previous one.
- A message with an empty payload clears the retained message for that topic.
- Subscribers receive only the last retained message upon subscribing.

## Retained messages usage

Retained messages are useful in scenarios where clients need immediate access to the latest state upon connection, without waiting for the next publish.

**Good use cases:**

- Device status updates (online/offline).
- Sensor readings (temperature, humidity, etc.) where the latest value is always relevant.
- Configuration or command topics where new subscribers need the current value immediately.

**When to avoid:**

- High-frequency data streams where storing every value is not needed.
- Topics carrying transient events that should not be replayed to new subscribers.
- Large payloads that would waste broker memory unnecessarily.

## Publish retained message

To publish a retained message using the Mosquitto CLI client, use the `-r` flag:

```bash
mosquitto_pub -h localhost -t "sensors/temperature" -m "22.5" -r
```

If you are testing against the TBMQ WebSocket endpoint using the built-in `tbmq_websockets_username` credentials:

```bash
mosquitto_pub -h localhost -t "sensors/temperature" -m "22.5" -r -u tbmq_websockets_username
```

## Deleting retained messages

To delete a retained message, publish a message with an empty (zero-byte) payload to the same topic:

```bash
mosquitto_pub -h localhost -t "sensors/temperature" -n -r
```

You can also delete retained messages from the TBMQ UI — either individually or in bulk:

## Clearing empty retained message nodes

TBMQ stores retained messages internally using a trie (prefix tree) data structure, where each topic segment is a node.
When retained messages are deleted, the topic nodes that held them may remain in the trie as empty nodes.
Over time, these empty nodes can accumulate and consume memory unnecessarily.

To clean up empty nodes, use the **"Clear empty retained messages nodes"** button available in the top right corner of the Retained Messages page in the UI.

You can also configure automatic cleanup by setting the following environment variables:

- `MQTT_RETAIN_MSG_TRIE_CLEAR_NODES_CRON` — cron expression for the cleanup scheduler.
- `MQTT_RETAIN_MSG_TRIE_CLEAR_NODES_ZONE` — time zone for the scheduler.
