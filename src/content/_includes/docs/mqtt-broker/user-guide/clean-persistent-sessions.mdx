An MQTT session is core to reliable communication between clients and the broker. Think of it like a hotel room: a persistent session is a booked room where your luggage (subscriptions and queued messages) waits for your return, while a non-persistent session is a walk-in stay — everything is forgotten the moment you leave.

## Persistent Session

A persistent session preserves state after a client disconnects. Requirements for reliable offline message delivery include a fixed Client ID and QoS 1 or QoS 2 subscriptions. The session state stored by the broker includes:

- Session identity (Session + Client ID)
- Subscriptions
- Queued messages (QoS 1 and QoS 2)
- In-flight messages
- QoS 2 messages received but not yet acknowledged
- Will Message and Will Delay Interval
- Session Expiry Interval and expiration timestamp
- Internal delivery state

## Non-Persistent Session

A non-persistent session always starts with a fresh state. No subscriptions or messages are preserved across connections. This minimizes broker overhead and is suitable for clients that do not require offline delivery.

## How the Broker Indicates an Existing Session

The broker communicates session state to the client via the **Session Present** flag in the CONNACK packet:

- `true` — an existing session was resumed
- `false` — a new session was created

## Session Configuration in MQTT v3.x and MQTT v5.0

MQTT v5.0 replaces the single Clean Session flag from v3.x with two separate controls: **Clean Start** and **Session Expiry Interval**. This gives clients finer-grained control over session lifecycle.

The maximum value for Session Expiry Interval is 4,294,967,295 seconds (approximately 136 years).

If the Session Expiry Interval is not specified, it defaults to 0. Clean Start is a boolean flag that controls whether the broker discards any existing session state at the start of a new connection.

### Session Configuration Parameters

```yaml
# Client session expiry settings
client-session-expiry:
  # Cron expression for removing expired client sessions
  cron: "${CLIENT_SESSION_EXPIRY_CRON:0 0 2 * * *}"
  # Zone for the cron expression
  zone: "${CLIENT_SESSION_EXPIRY_ZONE:UTC}"

# Persistent session settings
persistent-session:
  device:
    persisted:
      messages:
        # Maximum number of messages stored per persistent DEVICE client
        limit: "${MQTT_PERSISTENT_SESSION_DEVICE_PERSISTED_MESSAGES_LIMIT:1000}"
        # TTL in seconds for persisted DEVICE messages (0 = no expiry)
        ttl: "${MQTT_PERSISTENT_SESSION_DEVICE_PERSISTED_MESSAGES_TTL:0}"
```

## Message Expiry Interval and Session State

In MQTT 5.0, the **Message Expiry Interval** allows publishers to set a time-to-live for individual messages. The broker starts counting this interval from the moment it receives the message. QoS 1 and QoS 2 messages that are queued for offline delivery may expire before the client reconnects.

Note the distinction between the two expiry concepts: **Session Expiry Interval** governs how long the broker retains the entire session state, while **Message Expiry Interval** governs how long an individual queued message remains valid within that session.

## Demonstrating a Persistent Session

The following steps demonstrate a persistent session using the WebSocket Client. See the <DocLink product={props.product} path="user-guide/ui/websocket-client" /> for details on using the WebSocket Client.

1. In a WebSocket Client connection, enable the persistent session (disable Clean Start), set a Session Expiry Interval greater than zero, and click **Connect**.
2. Add a subscription to the topic `session/persistent` with QoS 1.
3. Click the **Disconnect** button.
4. Switch to another client and publish several messages to the topic `session/persistent`.
5. Switch back to the "Persistent session demo" client and click **Connect**.
6. After a successful connection, the client receives the messages that were published while it was offline.
