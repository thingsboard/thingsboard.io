Shared subscriptions are an MQTT feature that allows multiple clients to share the load of incoming messages on a given topic filter.
Instead of each subscriber receiving every message, messages are distributed across the members of the shared subscription group —
effectively enabling load balancing at the broker level. TBMQ supports shared subscriptions for any MQTT protocol version.

The topic filter format for a shared subscription is:

```
$share/{ShareName}/{TopicFilter}
```

Where `{ShareName}` identifies the subscription group, and `{TopicFilter}` is the MQTT topic filter to subscribe to.

## What are shared subscriptions?

In a standard MQTT subscription, every subscriber that matches a topic receives a copy of each published message.
Shared subscriptions change this behavior: all clients that subscribe using the same `$share/{ShareName}/{TopicFilter}` form a group,
and each message published to `{TopicFilter}` is delivered to exactly one member of that group.

This makes shared subscriptions ideal for building scalable, fault-tolerant MQTT consumers.

## Shared subscription use cases

**Horizontal scaling of message consumers:**
Multiple instances of a consumer application can subscribe to the same shared subscription group.
As the load increases, new instances can be added to the group without any coordination — TBMQ will automatically distribute messages across all active members.

**Handling high message rates:**
A single subscriber may not be able to keep up with a high-throughput topic.
A shared subscription group distributes the message load across multiple subscribers, increasing aggregate processing capacity.

**Balancing resource consumption:**
By distributing messages across consumers, shared subscriptions help balance CPU, memory, and network usage
across a fleet of services.

## Message ordering guarantees

As per the MQTT 5.0 specification, shared subscriptions do **not** guarantee message ordering across the group.
Messages will be distributed to group members, but the order in which different consumers process them is not defined.
If strict ordering is required, a single non-shared subscriber should be used instead.

## Subscribing to shared subscriptions

The following example demonstrates how two subscribers join the same shared subscription group and then receive distributed messages.

**Start two subscribers in separate terminals:**

```bash
mosquitto_sub -h localhost -t '$share/mygroup/sensors/#' -v
```

```bash
mosquitto_sub -h localhost -t '$share/mygroup/sensors/#' -v
```

**Publish several messages:**

```bash
mosquitto_pub -h localhost -t "sensors/temperature" -m "22.5"
mosquitto_pub -h localhost -t "sensors/humidity" -m "60"
mosquitto_pub -h localhost -t "sensors/pressure" -m "1013"
mosquitto_pub -h localhost -t "sensors/temperature" -m "23.1"
```

Each message will be delivered to exactly one of the two subscribers, alternating based on the configured load balancing strategy.

## Shared subscriptions load balancing strategy

TBMQ currently supports the **ROUND_ROBIN** load balancing strategy.
Messages are distributed to group members in a round-robin fashion — each message is sent to the next available subscriber in the rotation.

Additional strategies may be introduced in future releases.

## Shared subscriptions and client type

TBMQ distinguishes between two client types: <DocLink path="user-guide/mqtt-client-type/#device-client" product={props.product}>DEVICE</DocLink> and APPLICATION.
For shared subscriptions, clients of different types are treated as **separate groups**, even if they share the same `ShareName` and `TopicFilter`.

### DEVICE client type

DEVICE clients can use shared subscriptions with both persistent and non-persistent sessions.

**Non-persistent sessions** (Clean Session = true): clients subscribe, receive their share of messages, and no state is retained after disconnect.

**Persistent sessions** (Clean Session = false): when a DEVICE client disconnects, its session is preserved and queued messages accumulate.
Upon reconnection, the client processes the backlog before receiving new messages.

<Aside type="tip">
  Avoid mixing persistent and non-persistent DEVICE clients within the same shared subscription group.
  This can lead to uneven message distribution, where persistent clients accumulate large queues while
  non-persistent clients receive all new messages during the outage period.
</Aside>

### APPLICATION client type

APPLICATION clients have special handling for shared subscriptions.
Before an APPLICATION client can subscribe to a shared subscription, you must create the corresponding
**Application Shared Subscription** entity in TBMQ.

<Aside type="caution">
  If this step is missed, the persistent APPLICATION client will be prevented from subscribing to the shared subscription.
</Aside>

Refer to the <DocLink path="user-guide/ui/shared-subscriptions" product={props.product}>Application Shared Subscriptions</DocLink> guide
for instructions on creating and managing these entities via the UI,
or use the <DocLink path="application-shared-subscription" product={props.product}>REST API</DocLink>.

When an Application Shared Subscription entity is created, TBMQ provisions a dedicated Kafka topic named:

```
tbmq.msg.app.shared.{TopicFilter}
```

If the topic filter contains characters other than alphanumeric characters (and `/`, `+`, `#`), a hash derived from the topic filter is used instead:

```
tbmq.msg.app.shared.{TopicFilterHash}
```

This ensures compatibility with Kafka's topic naming rules.

When a client connects and subscribes to the shared subscription, TBMQ creates a Kafka consumer and adds it to the Consumer Group for that topic. As more clients subscribe, their consumers join the group and share the message load. When a client unsubscribes, its consumer is removed and the group rebalances automatically.

Even if all APPLICATION clients go offline, messages published to the shared subscription continue to be written to Kafka. They are retained and delivered once any client in the group reconnects, ensuring no data is lost.

## Quality of Service (QoS) in shared subscriptions

QoS semantics in shared subscriptions follow the standard MQTT rules, applied per message delivery to the selected group member:

- **QoS 0 (At most once):** The message is delivered to one group member with no acknowledgment. If the member is unavailable, the message is dropped.
- **QoS 1 (At least once):** The message is delivered to one group member and acknowledged. Re-delivery is attempted if the acknowledgment is not received.
- **QoS 2 (Exactly once):** Full four-step handshake is performed between the broker and the selected group member.

The QoS level used for delivery is the minimum of the publisher's QoS and the subscriber's requested QoS, consistent with standard MQTT behavior.
