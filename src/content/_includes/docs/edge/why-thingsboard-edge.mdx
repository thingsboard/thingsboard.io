**ThingsBoard Edge** brings the full IoT platform to the network edge: factories, remote sites, vehicles, and field installations. It runs the complete ThingsBoard platform on-site, processes data at the edge, and syncs with a central ThingsBoard server only when needed. Synchronization is bidirectional: configuration — rule chains, dashboards, device profiles, firmware — flows down from the server to Edge; device telemetry, alarms, and attributes flow up from Edge to the server.

Edge is an add-on to ThingsBoard, not a standalone product. It requires a <DocLink product={props.product === Products.EDGE_PE ? Products.PE : Products.CE} path="why-thingsboard" target="_blank">ThingsBoard server</DocLink> — Cloud, Community Edition, or Professional Edition — to connect to and sync with.

If you need on-site processing, offline operation, or reduced bandwidth costs without sacrificing ThingsBoard's features, Edge is the right choice.

## What Edge provides

Edge runs ThingsBoard locally with:
- Device connectivity via MQTT, CoAP, HTTP, LwM2M, SNMP
- Rule Engine for data processing, filtering, and enrichment
- Local dashboards for operators
- Local alarms and notifications
- Data storage in PostgreSQL or Cassandra
- RPC commands to devices

Configure what syncs to the cloud: all data, filtered data, aggregated summaries, or only alarms and events.

## When to use Edge

### Offline operation

Sites with intermittent connectivity like ships, mines, and remote installations.

Remote industrial sites, moving assets, and developing regions often lack stable internet. Edge continues operating during outages, storing data locally and syncing when connectivity returns. Operators access dashboards and receive alarms regardless of cloud connection.

**Use cases:**
- Oil rigs with satellite uplinks
- Farms in areas with spotty cellular coverage
- Ships and autonomous vehicles
- Remote substations and installations

### Low latency

Time-sensitive operations where cloud round-trip delay causes failures or safety risks.

Cloud round-trips take 50-500 ms depending on location and network quality. Edge processes telemetry and triggers actions locally with sub-second response times.

**Use cases:**
- Factory automation requiring immediate shutdowns
- Autonomous vehicles
- Medical devices needing instant alarms
- Smart building HVAC responding to occupancy changes

### Bandwidth reduction

High-volume sensors where cloud storage is prohibitively expensive.

High-frequency sensors, video streams, and machine data generate massive volumes. Autonomous vehicles produce 5-20 TB per day. Edge filters, aggregates, and compresses data before sending it to the cloud, typically reducing cloud traffic by 80-95% compared to sending all raw data.

**Use cases:**
- Industrial facilities with hundreds of high-frequency sensors
- Video surveillance systems
- Vibration and acoustic monitoring
- Environmental sensor networks

### Data residency

Regulatory or contractual requirements to keep data on-premises.

Edge stores raw telemetry locally and sends only aggregated or anonymized data to the cloud, satisfying GDPR, HIPAA, and similar requirements without sacrificing central analytics.

**Use cases:**
- Healthcare (patient data cannot leave facility)
- Smart homes (privacy-sensitive user behavior)
- Government and defense installations
- Financial institutions

### Distributed architecture

Many remote sites each needing local autonomy, with a unified view at the center.

Connecting hundreds of sites directly to the cloud creates a single point of failure, high bandwidth costs, and no local visibility for on-site operators. With Edge, each site operates independently — local Rule Engine, local dashboards, local alarms — while the cloud receives aggregated data for fleet-wide reporting and management.

**Use cases:**
- Retail chains monitoring equipment across stores
- Utility companies managing distributed substations
- Industrial groups operating multiple factory sites
- Smart city infrastructure across districts

## Community Edition vs Professional Edition

Edge CE is free and open-source. It includes the full Rule Engine, MQTT/HTTP/CoAP/LwM2M device connectivity, local dashboards, alarms, and bidirectional sync. It requires a ThingsBoard CE or Cloud server.

Edge PE adds the capabilities of ThingsBoard PE: role-based access control (RBAC), entity groups, advanced integrations, white-labeling, and the scheduler. It requires a ThingsBoard PE or Cloud server.

As a rule: if your ThingsBoard server is CE, use Edge CE. If your server is PE, use Edge PE — you need matching editions to unlock PE features at the edge.

## Edge vs. IoT Gateway

Both products extend ThingsBoard to the field, but they solve different problems.

The <DocLink product={Products.GW} path="TODO" target="_blank">IoT Gateway</DocLink> is a protocol bridge. It connects legacy and third-party devices — Modbus, OPC-UA, BACnet, BLE, CAN, KNX, and others — to ThingsBoard. It has no local Rule Engine, no local dashboards, and no local alarm processing. It buffers data during connectivity loss but is not designed for offline-first operation.

**ThingsBoard Edge** runs the full ThingsBoard platform locally: Rule Engine, dashboards, alarms, device connectivity, and local storage. It is designed for sites that need to operate independently of the cloud, not for protocol translation.

The two are complementary. A common deployment pattern is: IoT Gateway bridges legacy devices into Edge → Edge processes data locally → Edge syncs to the cloud.

## When not to use Edge

- All devices have stable internet with acceptable latency (50-500 ms).
- Data volumes are low and cloud bandwidth cost is negligible.
- All data can be stored in the cloud without regulatory concerns.
- All devices are at one location with reliable connectivity.
