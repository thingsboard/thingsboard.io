Manage alarms directly in the Edge rule chain using three dedicated rule nodes: **create alarm**, **clear alarm**, and **alarm status filter**. This approach gives you full programmatic control over alarm creation and clearing, based on any telemetry condition, attribute value, or custom script logic, entirely on the Edge without a server connection.

## When to use rule chain alarm nodes

For most threshold alarms, use <DocLink product={props.product === Products.EDGE_PE ? Products.PE : Products.CE} path="user-guide/alarm-rules" target="_blank">alarm rules</DocLink>. They need no rule chain changes, support multiple arguments, dynamic thresholds from attributes, and duration and repeating conditions, and they are evaluated on the Edge. Use the rule nodes instead when the alarm depends on the content of a message in a way the alarm rule arguments cannot express, or when the alarm needs custom details built by a script.

## The pattern

The standard pattern for a threshold alarm in the rule chain:

```
Post telemetry → [Script filter: condition?]
                      ├─ True  → create alarm → Created → (act on new alarm)
                      │                       → Updated → (alarm already exists, skip)
                      └─ False → clear alarm  → Cleared → (act on cleared alarm)
                                              → False   → (no alarm was active, skip)
```

## Example — temperature threshold alarm

This example creates a Critical alarm when `temperature > 35` and clears it when the reading drops to or below 35.

### Step 1 — Open the rule chain

<Steps>
1. On the Edge, go to **Data processing > Rule chains** and open the **Edge Root Rule Chain**.
</Steps>

### Step 2 — Add a Script filter node

<Steps>
1. In the node panel, search for **Script** (under Filter) and drag it onto the canvas.
2. Set the node name to `High Temp?`.
3. Enter the condition:
   ```js
   return msg.temperature !== undefined && msg.temperature > 35;
   ```
4. Click **Add**.
</Steps>

### Step 3 — Add a create alarm node

<Steps>
1. Search for **create alarm** (under Action) and drag it onto the canvas.
2. Configure:
   - **Alarm type:** `High Temperature`
   - **Severity:** *Critical*
   - **Alarm details script** (optional — records the triggering value):
     ```js
     return { temperature: msg.temperature };
     ```
3. Click **Add**.
4. Connect the **True** output of `High Temp?` to this node.
</Steps>

### Step 4 — Add a clear alarm node

<Steps>
1. Search for **clear alarm** (under Action) and drag it onto the canvas.
2. Set **Alarm type** to `High Temperature` (must match exactly).
3. Click **Add**.
4. Connect the **False** output of `High Temp?` to this node.
</Steps>

### Step 5 — Wire the Script filter to the incoming message

<Steps>
1. Find the existing **Message type switch** node in the root rule chain.
2. Connect its **Post telemetry** output to the `High Temp?` Script filter node.
3. Click **Apply changes**.
</Steps>

<Aside type="note">
  If you already have a Script filter or other nodes between Message type switch and Push to cloud, insert the new nodes on that same branch so telemetry still reaches the cloud.
</Aside>

## Output connections

### create alarm

| Connection | When | Message after |
|-----------|------|---------------|
| `Created` | A new alarm was created | Message replaced with alarm object; metadata: `isNewAlarm: true` |
| `Updated` | Alarm of the same type already existed | Message replaced with alarm object; metadata: `isExistingAlarm: true` |
| `Failure` | Script error or invalid severity | Original message unchanged |

### clear alarm

| Connection | When | Message after |
|-----------|------|---------------|
| `Cleared` | Active alarm was found and cleared | Message replaced with alarm object; metadata: `isClearedAlarm: true` |
| `False` | No active alarm existed | Original message unchanged |

## Using the alarm status filter

After a **create alarm** or **clear alarm** node, the message type changes to `ALARM` and the payload contains the full alarm object. Use the **alarm status filter** node to branch on the current alarm status before taking further action (for example, only send a notification on a genuinely new unacknowledged alarm).

Add an **alarm status filter** node after **create alarm**, configure the status set (e.g., `Active Unacknowledged`), and connect:

- `True` → send notification / RPC / push to cloud
- `False` → skip

<Aside type="caution">
  Alarms created or cleared on Edge are not sent to the server automatically. To push them, connect the **Created** and **Updated** outputs of **create alarm** and the **Cleared** output of **clear alarm** to a **push to cloud** node. See <DocLink product={props.product} path="user-guide/manage-alarms#push-alarms-from-edge-to-the-server" target="_blank">Push alarms from Edge to the server</DocLink>.
</Aside>

To apply the same rule chain logic to all Edge instances, configure the rule chain as a <DocLink product={props.product} path='user-guide/rule-chain-templates' target="_blank">rule chain template</DocLink> on the server and assign it to the Edges. An alarm rule created on the server for a device profile does not need a template: it reaches every Edge (4.3.0 and later) automatically.
