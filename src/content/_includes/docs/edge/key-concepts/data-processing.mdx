ThingsBoard Edge runs a full <DocLink product={props.product === Products.EDGE_PE ? Products.PE : Products.CE} path="user-guide/rule-engine" target="_blank">Rule Engine</DocLink> locally. Every message from a connected device passes through the rule engine before it is stored, forwarded, or acted upon — whether the Edge is online or offline.

## How the Rule Engine works

The Edge Rule Engine mirrors the server Rule Engine in architecture and available node types. It uses an actor model: each rule chain and rule node runs as a separate actor, and messages flow between them as immutable objects.

```plaintext
  ┌─────────────────────────────────────────────────┐
  │  Device (MQTT / HTTP / CoAP / etc.)             │
  └──────────────────────┬──────────────────────────┘
                         │
  ┌──────────────────────▼──────────────────────────┐
  │  Transport layer                                │
  │  (validates credentials, parses protocol)       │
  └──────────────────────┬──────────────────────────┘
                         │
  ┌──────────────────────▼──────────────────────────┐
  │  Rule Engine                                    │
  │                                                 │
  │  ┌─────────────┐   ┌──────────────────────┐     │
  │  │ Save to DB  │   │  Generate alarm      │     │
  │  └─────────────┘   └──────────────────────┘     │
  │  ┌─────────────┐   ┌──────────────────────┐     │
  │  │ Push to     │   │  Send RPC to device   │     │
  │  │ server      │   └──────────────────────┘     │
  │  └─────────────┘                                │
  └─────────────────────────────────────────────────┘
```

The same node categories available on the server are available on Edge — filter, enrichment, transformation, action, and external nodes. The key addition is two Edge-specific action nodes: <DocLink product={props.product === Products.EDGE_PE ? Products.PE : Products.CE} path="reference/rule-engine/nodes/action/push-to-cloud" target="_blank">push to cloud</DocLink> and <DocLink product={props.product === Products.EDGE_PE ? Products.PE : Products.CE} path="reference/rule-engine/nodes/action/push-to-edge" target="_blank">push to edge</DocLink>, which control data synchronization with the server. For details on how synchronization works, see <DocLink product={props.product === Products.EDGE_PE ? Products.EDGE_PE : Products.EDGE} path="key-concepts/telemetry-synchronization" target="_blank">Telemetry synchronization</DocLink>.

## Default root rule chain

Edge ships with a preconfigured **Root Rule Chain** that handles the most common scenarios without any additional setup:

- Saves device telemetry and attributes to the local database.
- Generates alarms based on device profile alarm rules.
- Forwards telemetry and attribute updates to the server via the **push to cloud** node.

You can extend the Root Rule Chain by adding nodes before or after existing ones, or replace it entirely with a custom chain. The Root Rule Chain is the entry point for all device messages — every message starts here unless a device is configured to use a different rule chain via its device profile.

## Rule chain templates

A **rule chain template** is a rule chain created on the server specifically for deployment to Edge instances. The template does not run on the server — it runs on the Edge after it is assigned. This lets you design and version processing logic centrally, then deploy it consistently across many Edge instances.

```plaintext
  ┌──────────────────────────────────────┐
  │  Server                              │
  │  Edge management → Rule chain        │
  │  templates                           │
  │                                      │
  │  [ Template A ]  [ Template B ]      │
  └──────────────┬───────────────────────┘
                 │  assign to Edge instance
                 ▼
  ┌──────────────────────────────────────┐
  │  Edge instance                       │
  │                                      │
  │  Rule chains (running locally)       │
  │  [ Template A ]  [ Template B ]      │
  └──────────────────────────────────────┘
```

Starting with Edge 4.0, rule chains can also be created and edited directly on the Edge instance — without going through server templates first. Changes made on Edge propagate back to the server automatically when the connection is available.

## Common processing patterns

These four patterns cover the majority of Edge data processing use cases. They can be combined in a single rule chain.

- **Filter:** Use a script or message type filter node to pass only relevant messages downstream. For example, route only telemetry with a `temperature` key to the push to cloud node and discard the rest. Unmatched messages are still saved locally.
- **Transform:** Use a transformation node to reshape or enrich a message before forwarding it. For example, strip sensitive fields before pushing to the server, or add entity attributes as metadata to a telemetry message.
- **Act:** Use action nodes to respond to device data in real time. For example, when an alarm is created, use an RPC call node to send a command back to the device that triggered it — like switching off a machine or adjusting a setpoint.
- **Route:** Use a switch node or script node to split message traffic by device type, message content, or entity attribute, and send each path to a different downstream chain or output node.

## Offline operation

The Rule Engine continues to process messages when the Edge is disconnected from the server. Devices are processed, alarms are raised, and data is written to the local database without interruption. Events destined for the server accumulate in the cloud event queue and are sent once the connection is restored. For details, see <DocLink product={props.product === Products.EDGE_PE ? Products.EDGE_PE : Products.EDGE} path="key-concepts/telemetry-synchronization" target="_blank">Telemetry synchronization</DocLink>.
