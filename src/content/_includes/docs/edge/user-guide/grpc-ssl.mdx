By default, the gRPC connection between ThingsBoard Edge and the server is unencrypted. Enabling TLS/SSL secures this channel against interception and tampering. Configuration is split into two parts: the server side and the Edge side — both must be completed for the connection to work.

## Server configuration

Choose how SSL termination is handled on the server — either using the built-in certificate mechanism or delegating termination to an external load balancer.

<Tabs defaultTab="builtin" urlParam="server">
  <TabItem label="Built-in" id="builtin">

The built-in mechanism uses self-signed certificates generated with OpenSSL. This approach is suitable for testing but is not recommended for production environments.

Run all certificate generation commands on the ThingsBoard server. Store the generated files in a dedicated directory, for example `/etc/thingsboard/conf/certs/`:

```bash
sudo mkdir -p /etc/thingsboard/conf/certs
cd /etc/thingsboard/conf/certs
```

<Steps>
1. Generate a private key:

   ```bash
   sudo openssl genpkey -algorithm RSA -out privateKey.pem -pkeyopt rsa_keygen_bits:2048
   ```

   This creates a 2048-bit RSA private key stored in `privateKey.pem`.

2. Generate a Certificate Signing Request (CSR):

   ```bash
   sudo openssl req -new -key privateKey.pem -out certRequest.csr
   ```

   Provide your organization name, common name (domain name), and email address when prompted.

3. List the names and IP addresses that Edge uses to reach the server (the value of `CLOUD_RPC_HOST` on the Edge) as subject alternative names. Replace the examples with your values:

   ```bash
   echo "subjectAltName=DNS:tb.example.com,IP:192.168.1.10" | sudo tee san.ext
   ```

   <Aside type="caution">
   Edge checks the server's host name or IP address against the subject alternative names of the certificate, not against the common name. If the certificate has no matching entry, the connection fails with `No subject alternative names present` or a host name mismatch in the Edge log.
   </Aside>

4. Generate a self-signed certificate valid for 365 days:

   ```bash
   sudo openssl x509 -req -in certRequest.csr -signkey privateKey.pem -out certFile.crt -days 365 -extfile san.ext
   ```

   Adjust `-days` to change the validity period. An expired certificate breaks all Edge connections silently — plan for renewal before expiry.

   Give the ThingsBoard service access to the files:

   ```bash
   sudo chown thingsboard:thingsboard privateKey.pem certFile.crt
   ```

5. Enable SSL on the ThingsBoard server. For Ubuntu and CentOS/RHEL installations:

   ```bash
   sudo sh -c 'cat <<EOL >> /etc/thingsboard/conf/thingsboard.conf
   export EDGES_RPC_SSL_ENABLED=true
   export EDGES_RPC_SSL_CERT=/etc/thingsboard/conf/certs/certFile.crt
   export EDGES_RPC_SSL_PRIVATE_KEY=/etc/thingsboard/conf/certs/privateKey.pem
   EOL'
   ```

6. Restart the server to apply the changes:

   ```bash
   sudo systemctl restart thingsboard
   ```

   Check that the server presents the certificate on the gRPC port:

   ```bash
   openssl s_client -connect localhost:7070 </dev/null 2>/dev/null | grep subject=
   ```

   The output shows the subject of your certificate. The server log has no SSL-specific line: it reports only `Edge/Agent RPC server initialized!`.
</Steps>

  </TabItem>
  <TabItem label="Load balancer" id="load-balancer">

The recommended approach for production is to delegate SSL termination to an external load balancer such as HAProxy. This keeps certificate management outside the ThingsBoard process and scales better in clustered deployments.

For Ubuntu and CentOS/RHEL Server, see {(<DocLink product="PE" path="installation/haproxy#step-6-configure-edge-tls-communication-optional">Step 6: Configure Edge TLS communication</DocLink>)} in the HAProxy installation guide.

  </TabItem>
</Tabs>

## Edge configuration

After configuring the server, enable SSL on the Edge side to match.

<Tabs defaultTab="debian" urlParam="installation">
  <TabItem label="Debian-based" id="debian">

<Steps>
1. Enable SSL communication on the Edge:

   ```bash
   sudo sh -c 'cat <<EOL >> /etc/tb-edge/conf/tb-edge.conf
   export CLOUD_RPC_SSL_ENABLED=true
   EOL'
   ```

2. If you are using self-signed certificates, transfer the server's public certificate to the Edge device:

   ```bash
   scp username@server_ip:/etc/thingsboard/conf/certs/certFile.crt /tmp/certFile.crt
   sudo mv /tmp/certFile.crt /etc/tb-edge/conf/certFile.crt
   sudo chmod 644 /etc/tb-edge/conf/certFile.crt
   ```

   Replace `username` and `server_ip` with your server credentials. Then add the certificate path to the Edge configuration:

   ```bash
   sudo sh -c 'cat <<EOL >> /etc/tb-edge/conf/tb-edge.conf
   export CLOUD_RPC_SSL_CERT=/etc/tb-edge/conf/certFile.crt
   EOL'
   ```

3. Restart Edge to apply the changes:

   ```bash
   sudo systemctl restart tb-edge
   ```

4. Verify that Edge connected. In the Edge UI, **Edge > Status** shows **Connected**, and the log has a new `Configuration received` line:

   ```bash
   grep -E "Configuration received|SSLHandshakeException|subject alternative" /var/log/tb-edge/tb-edge.log | tail -5
   ```

   If you see SSL handshake errors, check that the certificate lists the value of `CLOUD_RPC_HOST` as a subject alternative name.
</Steps>

  </TabItem>
  <TabItem label="Docker" id="docker">

<Steps>
1. Copy `certFile.crt` from the server to the Edge device:

   ```bash
   scp username@server_ip:/etc/thingsboard/conf/certs/certFile.crt /path/to/certs/certFile.crt
   ```

   Replace `username`, `server_ip`, and the destination path with your actual values.

2. Open `docker-compose.yml` and add the following to the `environment` block:

   ```yaml
         CLOUD_RPC_SSL_ENABLED: "true"
         CLOUD_RPC_SSL_CERT: "/etc/tb-edge/certs/certFile.crt"
   ```

   Omit `CLOUD_RPC_SSL_CERT` if you are using a CA-signed certificate — it is only required for self-signed certificates.

   Add a volume entry to mount the certificate into the container:

   ```yaml
       volumes:
         - /path/to/certs/certFile.crt:/etc/tb-edge/certs/certFile.crt
   ```

3. Recreate the Edge container to apply the changes (`docker compose restart` does not pick up changes to `docker-compose.yml`):

   ```bash
   docker compose up -d
   ```

4. Verify that Edge connected. In the Edge UI, **Edge > Status** shows **Connected**, and the log has a new `Configuration received` line:

   ```bash
   docker compose logs mytbedge | grep -E "Configuration received|SSLHandshakeException|subject alternative" | tail -5
   ```

   If you see SSL handshake errors, check that the certificate lists the value of `CLOUD_RPC_HOST` as a subject alternative name.
</Steps>

  </TabItem>
</Tabs>
