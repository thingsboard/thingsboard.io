A **ThingsBoard extension** is a small service that adds your own REST API to a tenant. You write it in **Java** or **Python**, package it as a Docker image, and ThingsBoard runs it next to the platform. Clients reach it through ThingsBoard at a fixed path, and every call is checked with the same login your users already have.

Use an extension when the built-in features are not enough — for example:

- **Rule chain callbacks** — react to device telemetry, entity changes, or alarms from a rule chain.
- **Dashboard widget backends** — run custom logic when a user clicks a button on a dashboard.
- **Scheduled jobs** — run a task on a timer that reads or writes ThingsBoard data.
- **Custom integrations** — talk to a third-party system and expose the result as an API.

<Aside type="tip">
The fastest way to build and ship an extension is the <DocLink product={props.product} path='user-guide/cli'>ThingsBoard CLI</DocLink>. See the <DocLink product={props.product} path='reference/extensions/quickstart'>Quickstart</DocLink> for a full Java and Python walkthrough.
</Aside>

## How it works

An extension is a normal web service. It listens on port **8090** (the default) and serves every endpoint under `/api/extension/...`. In the managed mode you do not run or scale it yourself: you give ThingsBoard the image, and ThingsBoard creates the container, keeps it running, and routes traffic to it. (You can also run the container yourself — see [Where extensions run](#where-extensions-run).)

<ImageGallery images={[{ src: '/src/assets/schemas/extension-request-flow.svg', alt: 'ThingsBoard extension request flow: a client calls the ThingsBoard router, the router checks authentication against the ThingsBoard REST API and forwards the request to the extension container', caption: 'A client calls ThingsBoard at /api/ext/{slug}/…. The router checks the caller with the ThingsBoard REST API, strips the prefix, and forwards the request to the extension container. The extension reads and writes platform data with the caller\'s own credential.' }]} />

Three parts work together:

1. **The extension entity.** Each extension is a tenant entity in ThingsBoard, like a device or an asset. It holds the container spec — the image, tag, number of replicas, port, environment variables, and resource size. When you save it, ThingsBoard pulls the image and starts the container. ThingsBoard watches the container and restarts it if it fails.
2. **The router.** Clients never call the container directly. They call ThingsBoard at `{BASE_URL}/api/ext/{slug}/...`. The router removes the `/api/ext/{slug}` prefix and forwards the rest to your service as `/api/extension/...`.
3. **The auth gateway.** Before forwarding, the router asks ThingsBoard whether the caller is allowed, using the caller's `X-Authorization` header. The check passes only when the caller belongs to the tenant that **owns** the extension; anything else is rejected. In the managed mode, your service does not have to check tokens itself.

### The slug

Every extension gets a **slug** — a short, unique name used in its URL. You choose a **slug base** (like `acme-billing`). On ThingsBoard Cloud, ThingsBoard adds a random suffix (for example `acme-billing-9f3a`) so the slug stays unique across all tenants. On a private installation there is no suffix — the slug is the base itself. The slug never changes after the extension is created.

### Calling ThingsBoard back

Your extension often needs to read or write ThingsBoard data. It does this with the **ThingsBoard REST client** for your language — <DocLink product={props.product} path='reference/python-client'>Python</DocLink> (`tb-pe-client`) or <DocLink product={props.product} path='reference/java-client'>Java</DocLink> (`thingsboard-pe-client`); each page shows the exact package for your edition. The client uses the **caller's own credential**, so every call respects that user's tenant and permissions. You do not store an admin password inside the extension.

## Authentication

An incoming request carries an `X-Authorization` header. There are three ways an extension is used:

| Mode | Header | Typical use |
|------|--------|-------------|
| **API key** | `X-Authorization: ApiKey <key>` | Rule chain callbacks |
| **JWT** | `X-Authorization: Bearer <jwt>` | Dashboard widget buttons (the user's session token) |
| **Configured** | *(none — set at startup)* | Scheduled background jobs |

For API key and JWT, the extension acts as the caller. For scheduled jobs there is no caller, so you set a service credential (`TB_AUTH_API_KEY`, or a username and password) as an environment variable.

<Aside type="note">
A few documentation paths skip the gateway check **on purpose**: the API docs shell and the OpenAPI document — `/swagger-ui/...` and `/v3/api-docs/...` for Java, `/docs`, `/redoc`, and `/openapi.json` for Python. This lets a browser open the API documentation without a token. The API shape is visible, but no endpoint can be called without a valid credential.
</Aside>

<Aside type="tip">
API keys were introduced in ThingsBoard 4.3. See the <DocLink product={props.product} path='user-guide/security/api-keys' useTbDocs>API Keys</DocLink> guide.
</Aside>

## Lifecycle

After you deploy an extension, it moves through a few states:

<ImageGallery images={[{ src: '/src/assets/schemas/extension-lifecycle.svg', alt: 'ThingsBoard extension lifecycle states: Provisioning, Active, Updating, Degraded, Stopped, and Failed, with the transitions between them', caption: 'A new deployment starts in Provisioning and becomes Active when all replicas are ready. Deploying a new image moves an Active extension to Updating and back. If some replicas stop being ready, the extension shows Degraded until they recover. Stop scales it to zero; start provisions it again. An error moves the extension to Failed; a new deploy fixes it.' }]} />

- **Provisioning** — ThingsBoard is pulling the image and starting the container.
- **Active** — the container is running and ready to serve requests.
- **Updating** — a new image or spec is rolling out; the replicas that are already ready keep serving.
- **Degraded** — the extension runs, but some replicas are not ready.
- **Stopped** — you stopped it, and ThingsBoard scaled it to zero replicas; the entity stays, but nothing runs.
- **Failed** — the container could not start, or it crashed while running (for example, out of memory or a crash loop); the reason is shown as the last error.

You can **stop**, **start**, and **restart** an extension at any time, and read its logs — from the <DocLink product={props.product} path='user-guide/cli'>CLI</DocLink> or the <DocLink product={props.product} path='reference/extensions/deployment-api'>deployment API</DocLink>. A **Failed** extension keeps its entity and its slug — fix the image or the spec and deploy again. Deploying a new image to a running extension does not stop it: the state shows **Updating** while the new version rolls out. Watch the rollout with the `status` command or endpoint.

## Where extensions run

The same extension image can run in three environments. In the first two, ThingsBoard is **managed** — it runs and scales the container for you. In the third, you run the container yourself.

<ImageGallery images={[{ src: '/src/assets/schemas/extension-deployment-options.svg', alt: 'Three ways to run a ThingsBoard extension: managed on ThingsBoard Cloud (public cloud), managed on your own ThingsBoard PE (private cloud), or self-hosted with Docker Compose', caption: 'In the public and private cloud, ThingsBoard runs and scales the extension container, and you deploy with the CLI or the REST API. In the self-hosted mode, you run the container with Docker Compose and route the traffic to it yourself.' }]} />

| | Public cloud | Private cloud | Self-hosted |
|---|---|---|---|
| **Where** | [ThingsBoard Cloud](/installations/?product=thingsboard-cloud) | Your own ThingsBoard PE | Any host you manage |
| **Who runs the container** | ThingsBoard | ThingsBoard | You |
| **How to deploy** | <DocLink product={props.product} path='reference/extensions/cli-deployment'>CLI</DocLink> or <DocLink product={props.product} path='reference/extensions/deployment-api'>REST API</DocLink> | <DocLink product={props.product} path='reference/extensions/cli-deployment'>CLI</DocLink> or <DocLink product={props.product} path='reference/extensions/deployment-api'>REST API</DocLink> | Docker Compose (`deploy/` folder) |
| **Routing and auth** | Built in | Built in | You set it up |
| **Scaling and restarts** | Automatic | Automatic | Manual |

### Public cloud — ThingsBoard Cloud

ThingsBoard Cloud runs the container on shared cloud infrastructure. This is the fastest way to get an extension online: you push the image and deploy — there is nothing to install or operate.

<ImageGallery images={[{ src: '/src/assets/schemas/extension-mode-public-cloud.svg', alt: 'ThingsBoard extension on the public cloud: a developer pushes the image to a container registry and deploys with the CLI or REST API; ThingsBoard Cloud pulls the image over the internet and runs the extension container', caption: 'You push the image to a registry and send a deploy request. ThingsBoard Cloud pulls the image over the internet, then runs, scales, and restarts the container for you.' }]} />

Points to know:

- The slug always ends with a random suffix (for example `acme-billing-9f3a`), so it is unique across all tenants.
- The image registry must be reachable from the internet. For a private registry, add pull credentials — the registry flags of the <DocLink product={props.product} path='reference/extensions/cli-deployment#private-registry'>CLI</DocLink>, or `registryAuth` in the <DocLink product={props.product} path='reference/extensions/deployment-api'>deployment API</DocLink>.
- CPU and memory are limited by the **resource size** you pick (`tb extension sizes` lists the options).

### Private cloud — your own ThingsBoard PE

A ThingsBoard PE installation (version **4.3.1.3** or later) offers the same managed experience on your own infrastructure. The workflow does not change: the same CLI commands and the same REST API — only your profile points at your own instance instead of `thingsboard.cloud`. One small difference: the slug gets no random suffix here — it is exactly your slug base.

<ImageGallery images={[{ src: '/src/assets/schemas/extension-mode-private-cloud.svg', alt: 'ThingsBoard extension on a private cloud: everything runs inside your network — ThingsBoard PE runs the extension container, the image comes from an internal registry, and the extension reads internal APIs and databases', caption: 'The same deploy workflow, but everything stays inside your network: the image can come from an internal registry, and the extension can reach internal APIs and databases that the public cloud cannot see.' }]} />

Use this mode when your data must stay inside your network, or when the extension needs to reach internal systems that are not visible from the public cloud. The image registry only has to be reachable from your PE installation, so an internal registry works.

One setup step is needed first: on a PE installation, managed extensions are **off by default**. A system administrator turns them on with the `TB_EXTENSIONS_MODE` environment variable (`extensions.mode` in `thingsboard.yml`): `docker-compose` runs each extension as a container on a single Docker host; `private-cloud` runs them in the same Kubernetes cluster as ThingsBoard. While the mode is `disabled`, the `/api/extension` endpoints do not exist, and the CLI reports that the deployment API is not available. ThingsBoard Cloud has the feature enabled already.

### Self-hosted — Docker Compose

You can also run the extension container yourself, next to your ThingsBoard instance (PE or Cloud). The starter project that `tb extension new` creates includes a `deploy/` folder with a ready Docker Compose setup.

<ImageGallery images={[{ src: '/src/assets/schemas/extension-mode-self-hosted.svg', alt: 'Self-hosted ThingsBoard extension with Docker Compose: a reverse proxy on your host routes /api/extension/* to the extension container, and the extension talks to any ThingsBoard instance for authentication and data', caption: 'Your host runs the container with Docker Compose. A reverse proxy routes /api/extension/* to it. The extension still checks callers and reads data through your ThingsBoard instance.' }]} />

In this mode there is no extension entity in ThingsBoard, so nothing is managed for you:

- You start, update, and restart the container yourself.
- You route `/api/extension/*` to the container — for example with a reverse proxy.
- The service still checks callers against your ThingsBoard instance, so authentication keeps working the same way.

Choose this mode for local development, or when you want full control over how and where the container runs. For the details, follow the `deploy/` guide inside the starter project.
