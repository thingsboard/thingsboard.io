<Banner variant="cloud">Available from ThingsBoard PE/Cloud <strong>4.4.1</strong> and later.</Banner>

The fastest way to understand extensions is to watch one run. This page deploys **User Profiles** — a complete, working extension that ships with the <DocLink product={Products.CLI} path='getting-started'>ThingsBoard CLI</DocLink> — with a single command. It takes about five minutes.

You write no code here. You do not need Docker or a container registry: the demo deploys a prebuilt public image, and ThingsBoard pulls it. What you get is a real extension with its own REST API, its own tests, and its own dashboard, running inside your ThingsBoard.

New here? Read the <DocLink product={props.product} path='reference/extensions/overview'>Extensions overview</DocLink> first to see how the pieces fit together.

## The feature you are about to deploy

The extension adds **reusable access templates**. A profile — "Manager", "Technician", "Auditor" — names a whole set of rights. One call gives a user that set: a user group, shared dashboards and devices, roles, and a default start page. One call takes it all back.

ThingsBoard PE already has every RBAC piece, but no template that ties them together. Onboarding one user by hand takes about seven screens. The extension replaces those seven screens with one call.

The same feature ships twice — once in **Java** (Spring Boot) and once in **Python** (FastAPI). Both have the same endpoints, the same behavior, and the same dashboard.

## What you need

| | Needed for |
|---|---|
| **ThingsBoard CLI** (`tb`) | everything — install with `uv tool install thingsboard-cli` |
| **A ThingsBoard PE or Cloud instance** | the target of the deploy — version **4.4.1** or later, with extensions enabled |

The demo needs no Docker and no container registry: ThingsBoard pulls a prebuilt public image. You need both only later, when you build your own version of the example.

On your own PE installation, the feature stays off until a system administrator sets the extensions mode in the server configuration (`extensions.mode`, environment variable `TB_EXTENSIONS_MODE`). While it is `disabled`, the `/api/extension` endpoints do not exist, and the CLI says that extensions are not enabled on the instance. The system administrator also has to prepare the place where the containers run and set up the router in front of them — see <DocLink product={props.product} path='reference/extensions/architecture#what-a-system-administrator-sets-up-first'>What a system administrator sets up first</DocLink>. Without the router the demo deploys, but it stops when it loads the profiles. ThingsBoard Cloud has all of it already.

## Run it

<Steps>

1. **Point a CLI profile at your instance.**

   <HostCode product={props.product} lang="bash" code={`tb config add mytb --url {BASE_URL} --api-key 'tb_XXXX'\ntb config use mytb`} />

   Use an <DocLink product={props.product} path='user-guide/security/api-keys' useTbDocs>API key</DocLink> of a **tenant administrator**. A system administrator key does not work: the `/api/extension` management endpoints need the `TENANT_ADMIN` authority, and the demo needs tenant-admin rights to create the demo entities. Only the name → slug lookup, `GET /api/extension/slug`, also accepts a customer user.

2. **Run the demo.**

   ```bash
   tb demo create
   ```

   Before the first server change it shows a confirmation panel with the target instance and everything it will create. The demo never touches entities it did not create: when a seed name already exists on the instance, the command stops and lists the collisions. The two demo users get one random password, printed when they are activated and again in the final table.

   The options you may need:

   - `--lang python` — the Python version of the demo (Java by default)
   - `--demo-password <pwd>` (or `TB_DEMO_PASSWORD`) with `-y` — a non-interactive run. Without a password it stops, because a random one would have nowhere to be shown
   - `--dir <name>` — another project directory. The solution, and with it the extension, is named after it

   The command writes down every entity it creates, in the `thingsboard.json` of the project. That list is what `tb demo delete` removes again — see [Clean up](#clean-up).

3. **Open what it printed.** The final panel lists the ThingsBoard URL, the demo dashboard URL, the **API docs** link, a `curl` line for the raw OpenAPI specification, the extension slug, the project directory, and the solution directory. Under the panel, a *Demo users* table gives the two logins. Both users get the **same** password. A random one is printed twice — once as soon as the users are activated, and again in that table. Copy it before you close the terminal.

</Steps>

<Aside type="tip">
`tb demo create` deploys into an instance you already have — it does not start one. ThingsBoard pulls a prebuilt public image, so nothing is built on your machine.
</Aside>

### What the command actually did

| Step | Result |
|---|---|
| 1. Unpack | a complete `tb` project in `./user-profiles-demo`, with the demo in `solutions/user-profiles-demo/` — source, tests, Dockerfile, dashboard |
| 2. Preflight | checks that the instance answers and really exposes the extensions API |
| 3. Image | uses the prebuilt public image. ThingsBoard pulls it; nothing is downloaded to your machine |
| 4. Seed | 3 roles, 2 dashboards, 1 dashboard group, 1 device group, 2 devices, 2 tenant users — every name the profiles point at. The demo users keep the tenant-administrator *authority*, but the demo takes them out of the `Tenant Administrators` group, so no group grants them a permission until a profile is assigned. That is why they start with an empty platform, and why this page calls them tenant users with no admin pages |
| 5. Deploy | the **extension entity** plus a running container; waits for `ACTIVE` |
| 6. Profiles | `POST`s the six profile documents **through the router** — the CLI output calls it the gateway — which also proves routing and auth work. The extension stores them in one new tenant asset, `user-profiles` |
| 7. Dashboard | imports the demo dashboard, with the extension name filled in. This is the third dashboard the confirmation panel counted |

<Aside type="note">
**Note the slug.** The run above targets ThingsBoard Cloud, where every slug ends with a random four-character suffix — the extension is *named* `user-profiles-demo`, but its slug is `user-profiles-demo-9f3a`. The suffix is on by default only in `public-cloud` mode, which is what ThingsBoard Cloud runs; on your own PE installation the slug is normally the base itself. Take the real one from the **Extension slug** row of the final panel. The URLs on this page use `$SLUG` for it, and `$KEY` for your tenant API key:

```bash
SLUG=user-profiles-demo-9f3a   # yours is printed by tb demo create
KEY='tb_XXXX'                  # the same key you gave to tb config add
```

Never type a slug into a dashboard or a script — resolve it by name with `GET /api/extension/slug?name=user-profiles-demo`, which is what the demo dashboard does. See <DocLink product={props.product} path='reference/extensions/architecture#the-slug'>The slug</DocLink>.
</Aside>

2. **Look at what it created.** Go to **Customers & users → Users → Groups**. A `Technicians` user group appeared — a normal ThingsBoard group, created by the extension a moment ago:

   <ImageGallery images={[{ src: '/src/assets/images/reference/extensions/user-groups-created.png', alt: 'The User groups page with the Technicians, Auditors and Contractors groups created by the extension, next to the autogenerated Tenant Administrators and Tenant Users groups', caption: 'One group per profile, created by the extension.    Open it: the user is inside.

   <ImageGallery images={[{ src: '/src/assets/images/reference/extensions/technicians-group-members.png', alt: 'The Technicians user group showing John Technician as its only member', caption: 'Group membership is per user. The group\'s permissions are shared by everyone in it.' }]} />

   Its roles carry the permissions the profile describes: the `Dashboard Reader` role on `Ops Dashboards`, and the same role on `Plant Devices`. One role on both groups is not a slip: a profile document has a single `sharingRole`, and it is used for every group the profile shares. `Dashboard Reader` grants only `READ`, `READ_ATTRIBUTES` and `READ_TELEMETRY`, which fits a device group as well. The seeded `Device Operator` role adds write and RPC rights and is used by the `Operator` profile. Nothing here is special to the extension — you could have built it by hand in seven screens.

3. **Log in as that user** (`john.technician@example.com`, password from the *Demo users* table in the summary) in a private window. Before the assign, this account saw an empty platform. Now the menu is short, and under **Dashboards** there is exactly one shared group — `Ops Dashboards`, the one the Technician profile shares. His start page is **Field Operations**, the dashboard the profile card above names:

   <ImageGallery images={[{ src: '/src/assets/images/reference/extensions/technician-user-view.png', alt: 'The ThingsBoard UI as seen by the technician user: a short left menu and a single shared dashboard group named Ops Dashboards', caption: 'What the profile produced, seen from the other side: a short menu and exactly one shared dashboard group. The start page it also set is the Default dashboard of the Technician card above.' }]} />

4. **Assign the same profile to a second user.** The response has an **empty** `createdPermissionIds`: the group and its permissions already exist and are reused, not duplicated.

5. **Unassign.** Click **Unassign** and confirm. The widget sends `DELETE` to the same path it assigned with — the HTTP method is the verb, exactly as in `DELETE /api/alarm/{alarmId}/assign`. That user's next login shows an empty platform again. The `Technicians` group and its permissions stay if anyone else still needs them — only this user's membership and default dashboard were removed.

</Steps>

The widget never sends `?cleanup=true`, so the group survives. To delete it as well, call the endpoint yourself:

<HostCode product={props.product} lang="bash" code={`curl -X DELETE -H "X-Authorization: ApiKey $KEY" \\
  "{BASE_URL}/api/extension/route/$SLUG/userProfile/name/Technician/assign/<userId>?cleanup=true"`} />

The group goes away only when this extension created it and nobody is left in it.

<Aside type="note">
**The owner rule.** Profiles in this example are **tenant-only**. The user group always belongs to the tenant, and ThingsBoard refuses a customer user inside a tenant-owned group, so assign checks the authority first and answers **400** — `user … is a customer user; profiles apply to tenant users only` — before it writes anything. That is also why the users table on the dashboard lists tenant users only.
</Aside>

## Troubleshooting

| Symptom | Cause | Fix |
|---|---|---|
| "ThingsBoard … does not expose the extensions API" | the instance is CE, older than 4.4.1, or `extensions.mode` is `disabled`. The message says which: "Extensions are available from ThingsBoard 4.4.1" or "Extensions are not enabled on this ThingsBoard instance" | upgrade to PE/Cloud 4.4.1 or later, or ask the system administrator to set `TB_EXTENSIONS_MODE` |
| "These entities already exist on the target instance" | the tenant already uses one of the seed names (a role, dashboard, device or user) | rename or remove the listed entities, or use a tenant where the names are free. Entities from an earlier run of the same demo are not a collision: the command finds them by the ids it saved and reuses them |
| `Extension with such name already exists!` | this tenant already has an extension named after the solution, `user-profiles-demo` | undeploy it, or install the demo under another name: `tb demo create --dir user-profiles-demo-2`. `--dir` names the project directory, the solution inside it, and with it the extension |
| `Extension slug 'user-profiles-demo' is already in use!` | on an installation without the random suffix, the slug is the base itself, and the local deployment state was reset while the extension is still deployed | remove the old one first: `tb extension server undeploy user-profiles-demo` |
| `Extension limit reached for this tenant (max N)!` | the tenant already has as many extensions as the tenant profile allows; stopped ones still count | undeploy an extension you no longer need, or ask the system administrator to raise the limit |
| `Extensions CPU limit reached for this tenant: …` or `Extensions memory limit reached for this tenant: …` | the size multiplied by the replicas does not fit the free CPU or memory of the tenant | deploy a smaller `--size`, use fewer `--replicas`, or stop another extension — a stopped extension frees its CPU and memory |
| "No profile could be loaded through the gateway" | nothing routes `/api/extension/route/…` to the extension. On your own PE installation the router is not set up yet | ask the system administrator to set up the router — see <DocLink product={props.product} path='reference/extensions/architecture#what-a-system-administrator-sets-up-first'>What a system administrator sets up first</DocLink>. Then check `tb extension server logs user-profiles-demo`. If the UI and the extension routes are on different origins, pass the one that serves both with `--gw <origin>` |
| The extension is `ACTIVE`, but the first calls fail | in `docker-compose` mode a container with no `HEALTHCHECK` in its image counts as ready as soon as it runs, so the app may still be starting | the demo waits for the gateway before it loads the profiles; in your own scripts, retry the first call |
| `tb demo create` or `tb extension server deploy` says "No such command" | an older CLI is installed | upgrade it: `uv tool install --force thingsboard-cli` |
| Extension containers keep disappearing | two ThingsBoard instances in `docker-compose` extensions mode share one Docker host | run only one such stack per host |
| A `/docs` or `/swagger-ui` link under `/api/extension/route/…` shows 401 | the in-container docs pages need a credential now | open **API docs** on the Extensions page of the ThingsBoard UI instead |

## Complete example: User Profiles

New to extensions? Read the <DocLink product={props.product} path='reference/extensions/development-workflow#your-first-endpoint-hello-world'>hello world</DocLink> first: two endpoints and about 20 lines of code. Then come back here.

What you deployed is a complete example, not a stub. The code ships inside the CLI in two languages. `tb demo create` copies it into your project, and from then on it is yours to read and change.

| Language | Get the code | Where it lands |
|---|---|---|
| Java (Spring Boot) | `tb demo create` | `user-profiles-demo/solutions/user-profiles-demo/extension/` |
| Python (FastAPI) | `tb demo create --lang python` | `user-profiles-demo/solutions/user-profiles-demo/extension/` |

**The scenario.** A profile is a reusable access template. One `assign` call replaces seven manual screens: it creates the user group if it is missing, adds the user, creates the group permissions, shares the dashboard and device groups, and sets the start page. It records what it created, so `unassign` takes exactly that back. Every reference inside a profile is a **name**, never a UUID, so the same profile document works on dev, test, and prod. Everything the extension creates is an ordinary ThingsBoard entity and stays editable in the UI.

**Run it.** `tb demo create` unpacks the project into `./user-profiles-demo/solutions/user-profiles-demo/` — source, tests, `Dockerfile`, dashboard, and the README. Add `--lang python` for the Python version. The tests run without a ThingsBoard: an in-memory stand-in answers the platform REST API.

Run them from the project root. The CLI picks the test runner from the language of the solution — `mvn -B test` for Java, `uv run pytest` for Python — so the command is the same for both:

```bash
cd user-profiles-demo
tb extension test --solution user-profiles-demo
```

Drop `--solution` when you run it from inside `solutions/user-profiles-demo/`.

**Change it and ship your own version.** The unpacked project is yours. Edit the code, then follow the normal release loop — build, run, push, deploy — in the <DocLink product={props.product} path='reference/extensions/development-workflow'>Development workflow</DocLink>. Run those commands from the solution directory, or add `--solution user-profiles-demo` from the project root.

**Import the dashboard.** `tb demo create` does this for you. To import it by hand, replace the two placeholders first — the extension name and the dashboard title. Run this from the project root, `./user-profiles-demo`:

```bash
sed -e "s|__EXTENSION_NAME__|user-profiles-demo|g" \
    -e "s|__DASHBOARD_TITLE__|Tenant Admin Users — Access Management|g" \
  solutions/user-profiles-demo/dashboard-templates/user-profiles.json > /tmp/user-profiles-dashboard.json
tb dashboard save --json /tmp/user-profiles-dashboard.json --remote
```

The template sits in `dashboard-templates/`, not in `dashboards/`. In a solution, `dashboards/` is the dashboard **entity** directory that `tb push` reads, and a file with unreplaced `__…__` tokens there would break the next push.

The dashboard carries the extension **name**, not its slug, and resolves the slug when it loads. Its URLs are relative and the widgets send the caller's own session token, so the exported file imports on any instance without editing.

The rest — the seven endpoints, the profile document, the error codes, the rollback record, the widget JavaScript, and the tests — is in the example's own `README.md`, next to the code.

## Clean up

**Unassign first.** The user groups and permissions that an assign created are normal entities. If you want the platform back the way it was, unassign every user on the demo dashboard before you go on — once the extension is gone, nothing can unassign them.

Then remove the demo with one command. Run it where you ran `tb demo create`:

```bash
tb demo delete
```

It deletes exactly what `tb demo create` created on the server, by the ids saved in the project: the extension, the two demo users, the dashboards, the groups, the devices, the roles, and the `user-profiles` asset where the extension kept the profile documents. It shows the list and asks before it deletes. Anything the demo did not create stays, for example a user group that a profile assignment made — the command names those so you can remove them by hand.

Two things to know:

- **The two demo users are tenant administrators with a password.** Do not leave the demo on a tenant you care about. `tb demo delete` removes both accounts.
- **Use the same server.** The command refuses to run against another server than the one the demo was created on. Pass the same `--profile`, or `--url` and `--api-key`.

The project files stay on your machine. Delete the directory when you are done.

To remove only the extension and keep the rest, run `tb extension server undeploy user-profiles-demo`. The UI has the same action: open the extension row and click **Delete extension**.
