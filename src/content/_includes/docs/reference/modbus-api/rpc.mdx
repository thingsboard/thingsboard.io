To read or write a value on demand, add mappings to the **RPC** list of the <DocLink product={props.product} path="reference/modbus-api/getting-connected">device profile</DocLink> and send a <DocLink product={props.product} path="user-guide/command-and-control">server-side RPC</DocLink> command. The **RPC method name selects the mapping by its key**. The function code of the mapping defines whether the command reads or writes. The mapping fields are described on the <DocLink product={props.product} path="reference/modbus-api/telemetry">Telemetry</DocLink> page.

## Read request

A mapping with a read function code (1 to 4) returns the current value. The command does not need params:

```json
{
  "method": "getSetpoint",
  "params": {}
}
```

ThingsBoard reads the mapped register, converts the value with the type and multiplier of the mapping, and returns:

```json
{
  "value": 42
}
```

## Write request

A mapping with a write function code (5, 6, 15, 16, or 22) writes the value from the params. Send the bare value, or an object with a `value` field, which is what dashboard widgets send:

```json
{
  "method": "setSetpoint",
  "params": 42
}
```

```json
{
  "method": "setSetpoint",
  "params": {
    "value": 42
  }
}
```

After the device confirms the write, ThingsBoard returns:

```json
{
  "result": "ok"
}
```

The value is converted in the same way as for <DocLink product={props.product} path="reference/modbus-api/attributes">shared attribute updates</DocLink>. A mapping with function code 22 and the `BITS` type sets or clears a single bit of a holding register.

For a one-way RPC command, ThingsBoard does not return a body. The command is marked as delivered after the device confirms the request, or as failed.

## Errors

A failed command returns an object with an `error` field:

```json
{
  "error": "Device did not respond in time"
}
```

| Error | Meaning |
|-------|---------|
| `Unknown RPC method '...'` | The RPC list of the device profile has no mapping with this key. |
| `Value is required` | A write command was sent without a value. |
| `Value ... is out of range for ...` | The value does not fit into the type of the mapping. |
| `Device did not respond in time` | No response arrived within the request timeout, including retries. |
| `Modbus exception NN (...)` | The device answered with a Modbus exception. Exception 01 means that the device does not support the function code, and exception 02 that the address does not exist. |
| `Device is not connected` | The connection to the device is not established. |

## Troubleshooting

- **No data and a timeout error:** Check the unit id, the framing, and for serial ports the baud rate, parity, and stop bits. A device ignores requests for another unit id.
- **Not connected:** For TCP, check the host, the port, and the firewall. For a serial port, check that the port exists on the machine that runs the Modbus transport and that the ThingsBoard user can open it.
- **Exception 02 on reads:** The address does not exist on the device. Check whether the device manual uses 1-based register numbers.
- **Wrong numbers:** Check the type, the word order, and the multiplier of the mapping.
- **Slow polling of several devices behind one gateway:** Requests over one connection are sent one at a time. Lower the request timeout of devices that are offline, or increase the poll period.

<Aside type="note">
Modbus devices cannot start a request, so client-side RPC is not supported.
</Aside>
