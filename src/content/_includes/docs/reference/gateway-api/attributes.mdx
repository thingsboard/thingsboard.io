## Publish Client-Side Attributes

Upload client-side attributes for one or more devices.

**Topic:** `v1/gateway/attributes`

```json
{
  "Device A": {"fw_version": "1.0.3", "battery": 87},
  "Device B": {"fw_version": "2.1.0", "battery": 92}
}
```

</ShowFor>

## Request Attribute Values

Subscribe to the response topic first, then publish the request.

**Subscribe:** `v1/gateway/attributes/response`

**Publish:** `v1/gateway/attributes/request`

**Request:**

| Field | Required | Description |
|-------|----------|-------------|
| `id` | Yes | Integer request identifier — echoed in the response |
| `device` | Yes | Name of a device connected through this gateway |
| `clientKeys` | No | Comma-separated client attribute keys to return; use `""` (empty string) to return all client attributes; omit the field entirely to exclude the client scope |
| `sharedKeys` | No | Comma-separated shared attribute keys to return; use `""` (empty string) to return all shared attributes; omit the field entirely to exclude the shared scope |

Omitting **both** `clientKeys` and `sharedKeys` (sending only `id` and `device`) returns **all** client and **all** shared attributes.

```json
{"id": 1, "device": "Device A", "clientKeys": "fw_version,battery", "sharedKeys": "targetFwVersion"}
```

**Response:**

```json
{"id": 1, "device": "Device A", "client": {"fw_version": "1.0.3", "battery": 87}, "shared": {"targetFwVersion": "2.0.1"}}
```

A scope appears in the response only if it returned at least one attribute, so it is absent both when you did not ask for it and when the device has nothing in it.

### Deprecated request format

<Aside type="caution">
The `client` (boolean) + `key`/`keys` fields are deprecated and kept only for backward compatibility. Use `clientKeys`/`sharedKeys` above instead.
</Aside>

| Field | Required | Description |
|-------|----------|-------------|
| `id` | Yes | Integer request identifier — echoed in the response |
| `device` | Yes | Name of a device connected through this gateway |
| `client` | Yes | Boolean flag: set to `true` to request client-side attributes, or `false` to request shared attributes |
| `key` | Yes\* | A single attribute key to return |
| `keys` | Yes\* | Array of attribute keys to return |

\* Send either `key` or `keys`, not both — `key` takes precedence when both are present.

```json
{"id": 1, "device": "Device A", "keys": ["fw_version", "battery"], "client": true}
```

<HostCode product={props.product} lang="bash" code={`mosquitto_rr -d -q 1 -h "{MQTT_HOST}" -p 1883 -t "v1/gateway/attributes/request" -e "v1/gateway/attributes/response" -u "GATEWAY_DEVICE_ACCESS_TOKEN" -m '{"id":1,"device":"Device A","keys":["fw_version","battery"],"client":true}'`} />

This format returns a scope-merged response rather than the scope-separated one — `value` for a single key, `values` for several:

```json
{"id": 1, "device": "Device A", "values": {"fw_version": "1.0.3", "battery": 87}}
```

This format has the limitations below. The `clientKeys`/`sharedKeys` format above has none of them.

- `client` only picks the scope for the keys you list. You cannot ask for **all** attributes of one scope. If you send an empty `keys` array, `client` is ignored and you get both scopes in full.
- When both scopes come back at once, they are merged into a single object. If the same key exists in both, the shared value wins and the client one is lost.
- You must send `key` or `keys`. A request without either is not supported.


## Subscribe to Shared Attribute Updates

Subscribe to receive push notifications when shared attributes change for any downstream device.

**Topic:** `v1/gateway/attributes` (subscribe)

<HostCode product={props.product} lang="bash" code={`mosquitto_sub -h "{MQTT_HOST}" -t "v1/gateway/attributes" -u "$ACCESS_TOKEN"`} />

ThingsBoard delivers updates in this format:

```json
{
  "device": "Device A",
  "data": {"targetFwVersion": "2.0.1", "enabled": true}
}
```
