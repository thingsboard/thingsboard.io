Once an anomaly model is built and marked **READY**, you can set up monitoring to keep it working
continuously. Monitoring automatically checks whether ongoing anomalies are continuing and whether
new anomalies have started — without any manual intervention.

## How It Works

A READY model supports two operations that keep anomaly detection running over time:

```plaintext
  ┌──────────────────────────────────────────────────┐
  │  Anomaly Model (READY)                           │
  └─────────────────┬────────────────────────────────┘
                    │
          ┌─────────┴──────────┐
          ▼                    ▼
  ┌───────────────┐    ┌──────────────────┐
  │    Refresh    │    │    Reprocess     │
  │  (scheduled)  │    │  (on demand)     │
  │               │    │                  │
  │ New / ongoing │    │ Historical data  │
  │ telemetry     │    │ Any date range   │
  └───────────────┘    └──────────────────┘
```

**Refresh** is a recurring scheduled job. It runs automatically at a configured interval, scans new
incoming telemetry, and detects ongoing anomalies. Each run looks back at least one segment length —
and further if an active anomaly is in progress — to correctly determine whether it is continuing
or has ended.

**Reprocess** is a one-time on-demand task. It applies the trained model to any historical date range
you choose, backfilling or updating anomaly data without waiting for scheduled runs. There is no
maximum date range — reprocess can cover years of historical data.

<Aside type="caution">
  Refresh is automatically disabled whenever the anomaly model is rebuilt. Re-enable it manually
  after the rebuild completes.
</Aside>

## How to Set Up Monitoring

<Steps>

1. ### Open the Model

   Navigate to the Anomaly Detection section and open the model you want to monitor. You can do this
   from the **Models** tab by clicking the model row and selecting **Open Model**, or by clicking
   **View >** on a profile in the Summary tab.

   {/* 📸 TODO: Screenshot — Models tab with a model row selected and Open Model button visible */}

2. ### Open the Monitoring Configuration

   In the model's detail view, locate the **Continuous Monitoring** panel on the right side of the
   Result tab. Click **Configure** to open the monitoring configuration dialog.

   {/* 📸 TODO: Screenshot — Result tab with the Continuous Monitoring panel and Configure button visible */}

3. ### Configure Monitoring Settings

   The monitoring configuration dialog has three sections:

   **Periodic Scanning** — enables automatic scheduled anomaly detection:

   | Setting | Description |
   |---------|-------------|
   | **Enable Periodic Scanning** | Master toggle — turns automatic detection on or off |
   | **Frequency** | How often the job runs (e.g. every 1 hour, every 1 day) |
   | **Execute at beginning of time unit** | When on, the job launches at the start of the unit — e.g. *every 1 hour* fires at :00 minutes |
   | **Items** | Which devices or assets to scan — **All in profile** or a specific selection |

   {/* 📸 TODO: Screenshot — Monitoring configuration dialog with Periodic Scanning section visible */}

   You can also configure **Anomaly Score Saving** and **Alarm Creation** from the same dialog.
   See [Save Anomaly Score as Telemetry](#save-anomaly-score-and-score-index-as-telemetry) and
   [Auto Alarm Creation](#auto-alarm-creation) below for details.

4. ### Monitoring Is Now Active

   Once saved, the model runs automatically at the configured interval. New anomalies are detected
   and recorded without any manual action. You can verify that monitoring is active by checking the
   **Continuous Monitoring** panel — it shows the current status of remote scanning, telemetry
   saving, and alarm generation.

   {/* 📸 TODO: Screenshot — Continuous Monitoring panel showing active status indicators */}

   The **System Pulse** on the Summary tab also updates with each scan run, showing green (no
   anomalies) or orange (anomalies found) entries as detection progresses.

</Steps>

## How to Scan Historical Data (Reprocess)

Use Reprocess when you need to apply the model to a specific time range — for example, to validate
results on a new period, or to update anomaly data after changing model settings.

### Option A — From the Models Tab

Open the model from the **Models** tab and click **Run Scan** in the detail panel:

{/* 📸 TODO: Screenshot — Models tab detail panel with Run Scan button highlighted */}

### Option B — From the Model Result View

Inside the model's Result tab, click **Scan Recent Data** in the top-right corner:

{/* 📸 TODO: Screenshot — Model Result tab with Scan Recent Data button highlighted */}

### Configure and Run

Both options open the **Run Reprocess Task** dialog. Set the date range and choose which items to scan:

| Setting | Description |
|---------|-------------|
| **Date Range** | The historical period to process. No maximum limit — can span years. |
| **Items** | **Trained items**, **All in profile**, or a **Specific** selection of devices or assets. |

{/* 📸 TODO: Screenshot — Run Reprocess Task dialog with date range and items settings */}

Click **Run** to start. The task runs in the background and results appear in the Result tab when complete.

<Aside type="caution">
  Reprocess **overwrites** all previously detected anomalies for the selected time range and items.
  Anomaly telemetry is overwritten with new scores; alarm data for the range may be deleted or cleared
  based on your alarm configuration. Use a narrow date range if you want to preserve existing results
  outside it.
</Aside>

## Save Anomaly Score and Score Index as Telemetry

You can configure monitoring to write the **anomaly score** and **anomaly score index** back to
ThingsBoard as device telemetry. This makes anomaly data available for dashboards, rule chains, and
custom alert logic — exactly like any other device measurement.

```plaintext
  Trendz Anomaly Model
         │  Refresh or Reprocess run
         ▼
  ┌─────────────────────────────────────┐
  │  Aggregate at configured frequency  │
  └────────────────┬────────────────────┘
                   │  ThingsBoard API
                   ▼
  ┌─────────────────────────────────────┐
  │  Device telemetry                   │
  │  _EAD_<key>  →  anomaly score        │
  │  _EID_<key>  →  anomaly score index  │
  └─────────────────────────────────────┘
```

### Configuration

In the monitoring configuration dialog, enable **Anomaly Score Saving** and set two parameters:

| Parameter | Description |
|-----------|-------------|
| **Telemetry Key** | Base name for the keys written to ThingsBoard. Two keys are created automatically: `_EAD_<key>` for the anomaly score and `_EID_<key>` for the anomaly score index. |
| **Write Frequency** | How often scores are aggregated and saved. Lower values give finer time resolution but produce more data points. Must be lower than the segment time range. |

{/* 📸 TODO: Screenshot — Monitoring configuration dialog with Anomaly Score Saving section expanded */}

<Aside type="tip">
  Set write frequency to **1 hour or higher** to avoid excessive write pressure on ThingsBoard.
  Finalize both the key name and frequency before enabling saving — changing them after the first
  run produces inconsistent data or orphaned keys.
</Aside>

### Using the Saved Telemetry

Once writing is active, the `_EAD_<key>` and `_EID_<key>` telemetry keys appear on each monitored
device in ThingsBoard. You can verify this in the device's telemetry panel.

{/* 📸 TODO: Screenshot — ThingsBoard device telemetry panel showing _EAD_ and _EID_ keys */}

Use the saved telemetry in:

- **Dashboards** — visualize anomaly score trends alongside operational metrics. See
  <DocLink product={props.product} path="anomaly/visualization">Anomaly Visualizations</DocLink>
  for recommended widget configurations.
- **Rule chains** — apply threshold checks, aggregations, or notifications directly on anomaly
  score keys for fully custom automation beyond built-in alarm creation.
- **Alarm thresholds** — configure ThingsBoard alarm rules on `_EAD_` or `_EID_` keys for
  granular severity control independent of Trendz alarm configuration.

<Aside type="note">
  Telemetry data persists in ThingsBoard even if the anomaly model is later deleted. ThingsBoard
  applies its standard data retention policies to these keys.
</Aside>

## Auto Alarm Creation

Trendz can automatically create ThingsBoard alarms when new anomalies are detected and clear them
when the anomaly ends. Enable this in the monitoring configuration dialog by turning on
**Generate Alerts**.

### Alarm Lifecycle

```plaintext
  Anomaly detected during Refresh or Reprocess
         │
         ▼
  Score ≥ lowest severity threshold?
         │
         ├── No  →  No alarm created (anomaly recorded, not escalated)
         │
         └── Yes →  Alarm created (ACTIVE)
                    Severity = highest matching threshold
                         │
                    ┌────┴──────────────────┐
                    │ Anomaly ends          │ Anomaly deleted
                    ▼                       ▼  (reprocess / rebuild)
                 CLEARED               Cleared or Deleted
                                       (per "On deletion" setting)
```

Each detected anomaly maps to exactly one alarm. The alarm remains active while the anomaly
persists and is cleared automatically when the anomaly ends.

### Configuration

In the monitoring configuration dialog, expand the **Generate Alerts** section:

| Setting | Description |
|---------|-------------|
| **Alarm Type** | The alarm type created in ThingsBoard — used for filtering and routing in rule chains |
| **On deletion** | What happens to the linked alarm when the anomaly is deleted (during reprocess, rebuild, or model deletion): **Clear alarm** or **Delete alarm** |
| **Severity thresholds** | Score boundaries for Warning, Minor, Major, and Critical severities. Each threshold can be disabled independently if it is not needed in your business logic |

{/* 📸 TODO: Screenshot — Generate Alerts section expanded in monitoring configuration dialog */}

Severity thresholds become configurable after the **first model build** — Trendz auto-generates
default values from the score distribution. The generated thresholds are fully editable.

<Aside type="note">
  ThingsBoard rule chains receive these alarms like any other ThingsBoard alarm. Use them to trigger
  notifications, API calls, or custom automation beyond the built-in severity levels.
</Aside>

Once alarms are enabled, you can verify they are being created in the ThingsBoard **Alarms** section
or directly on the device page.

## Best Practices

| Area | Recommendation |
|------|----------------|
| **Avoid alarm storms** | Enable alarm creation only after validating the model on historical data. A poorly tuned model generates hundreds of alarms that overwhelm operators and erode trust in alerting. Start with a high Score Threshold Percent and lower it gradually. |
| **Use Reprocess before enabling live monitoring** | Run reprocess on several historical periods first to confirm the model produces sensible results across different seasons and operating conditions. |
| **Choose an appropriate write frequency** | Match the write frequency to how you intend to use the telemetry. For dashboards showing hourly trends, 1 hour is sufficient. For rule chains reacting to short spikes, use a shorter interval — but be aware of increased write volume. |
| **Disable unused severity tiers** | If your workflow only cares about Critical and Major alarms, disable Warning and Minor thresholds to reduce noise. |
| **Re-enable refresh after rebuilds** | Rebuilding a model resets all refresh settings. After any rebuild, verify that monitoring, score saving, and alarm creation are re-enabled with the correct configuration. |
| **Narrow reprocess ranges** | When validating or backfilling, use the smallest date range that covers your goal. Wide reprocess runs on large fleets can take a long time and will overwrite existing anomaly data for the entire range. |
