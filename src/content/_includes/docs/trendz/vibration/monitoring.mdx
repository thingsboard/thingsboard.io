A vibration model scanned by hand is a snapshot. Monitoring turns it into a service: Trendz rescans the machines
on a period you choose, grades every new sample, and reports what it finds, as telemetry in ThingsBoard, as
alarms, or both.

## What continuous monitoring does

A scheduled run works like a manual scan: it analyzes new samples and grades each machine. Three switches decide
what happens next:

<ImageGallery images={[
  {
    src: '/src/assets/images/trendz/vibration/monitoring-cycle.svg',
    alt: 'One scheduled scan across ThingsBoard and Trendz: new vibration samples are read, each sample is graded, results are stored, chosen metrics are saved to ThingsBoard as telemetry, every alarm rule is checked, alarms are raised or cleared in ThingsBoard, and the Monitoring tab shows the outcome; switches for scheduled scanning, saving metrics, and raising alarms sit beside the steps they control',
    caption: 'One scheduled scan. Each switch turns on the step beside it.',
  },
]} />

| Switch | What the model does with each run |
|--------|-----------------------------------|
| **Scheduled scanning** | Runs the scan itself, every hour, day, or whatever period you set |
| **Save metrics as telemetry** | Writes the metrics of every scanned sample back to ThingsBoard, under keys the model owns |
| **Raise alarms** | Raises a ThingsBoard alarm when an alarm rule is breached |

## Set up continuous monitoring

Monitoring is off on a new model. Turn on **Scheduled scanning**, and the model rescans its machines by itself.

<Steps>
1. Open the model and click **Configure** on the Monitoring card. It sits on the
   <DocLink product={props.product} path='vibration/interface/overview-tab#monitoring-card'>Overview</DocLink> and the
   <DocLink product={props.product} path='vibration/interface/monitoring-tab#monitoring-card'>Monitoring</DocLink> tab.

   <ImageGallery images={[
     {
       src: '/src/assets/images/trendz/vibration/monitoring-open-configure.webp',
       alt: 'Monitoring tab with the Configure button of the Monitoring card highlighted',
       caption: 'Configure opens the monitoring configuration of the model.',
     },
   ]} />

2. The dialog holds the three switches. When all are off, the model is scanned only when you start a scan by
   hand, writes nothing back to ThingsBoard, and raises no alarms.

   <ImageGallery images={[
     {
       src: '/src/assets/images/trendz/vibration/monitoring-config-off.webp',
       alt: 'Monitoring configuration dialog with scheduled scanning, save metrics as telemetry, and raise alarms all switched off',
       caption: 'A model that monitors nothing yet: three switches, all off.',
     },
   ]} />

3. Switch **Scheduled scanning** on and set how the model scans itself.

   | Field | Description |
   |-------|-------------|
   | **Run every** | How often the scan runs, as a count and a unit |
   | **Align window to whole units** | Windows start on whole units: a 6-hour window at 00:00, 06:00, 12:00, 18:00 |
   | **Scope** | **All in profile** covers every item the profile holds, **Scanned items** only the ones already scanned, **Specific** the machines you list |

   <Aside type="tip">
   With **All in profile**, new devices that appear in the profile in ThingsBoard are discovered by Trendz
   automatically, and the model starts monitoring them too.
   </Aside>

   Pick the period from how often the sensors deliver: a scan finds nothing if it runs more often than the
   machines report, and a fault develops unseen if it runs far less often.

   <ImageGallery images={[
     {
       src: '/src/assets/images/trendz/vibration/monitoring-config-schedule.webp',
       alt: 'Monitoring configuration with the Scheduled scanning card highlighted and switched on, showing the Run every fields, the align toggle, and the three scope tabs, while Save metrics as telemetry and Raise alarms stay off',
       caption: 'Scheduled scanning: how often it runs, and which machines it covers.',
     },
   ]} />

4. Click **Save changes**. The model now rescans itself every period and keeps its own results current.
</Steps>

That is enough to keep a model up to date. What a run then does with its results is the other two switches,
each in its own section: [Save metrics as telemetry](#save-metrics-as-telemetry) writes the numbers back to
ThingsBoard, and [Raise alarms](#raise-alarms) turns breached rules into ThingsBoard alarms.

### Save metrics as telemetry

<ImageGallery images={[
  {
    src: '/src/assets/images/trendz/vibration/monitoring-config-telemetry.webp',
    alt: 'Monitoring configuration with the Save metrics as telemetry card highlighted, showing the telemetry key field and the table of metrics with their keys and units',
    caption: 'Switched on: the card names the exact key and unit each metric writes.',
  },
]} />

Switch it on in the same dialog, give the export a **Telemetry key**, and pick the metrics to write in the
**Metrics to save** table. Each scanned sample then writes its metrics at the sample's own timestamp, under keys
built from that key:

| Key | Holds |
|-----|-------|
| `_EVD_<telemetry key>_rms` | Velocity RMS |
| `_EVD_<telemetry key>_gRMS` | Acceleration RMS |
| `_EVD_<telemetry key>_peakToPeak` | Waveform peak-to-peak |
| `_EVD_<telemetry key>_crestFactor` | Crest factor |

On a multi-axis model the axis label sits between the key and the metric,
`_EVD_<telemetry key>_<axis>_<metric>`, and **Axes to save** picks the axes. The `_EVD_` prefix is reserved for
this export, so the keys are never mistaken for the device's own telemetry.

You choose what is written in the **Metrics to save** table:

- **Switch a metric off** to stop writing it. Only the metrics that are on get a key.
- **Change the unit** a metric is written in, for example in/s instead of mm/s for RMS. Crest factor has no unit.

    src: '/src/assets/images/trendz/vibration/monitoring-config-telemetry-metrics.webp',

    caption: 'One switch per metric. Acceleration RMS is off here, so it is not written.',
  },
  {
    src: '/src/assets/images/trendz/vibration/monitoring-config-telemetry-units.webp',
    alt: 'Unit select of the RMS row open, offering millimeters per second and inches per second',
    caption: 'Pick the unit each metric is written in.',
  },
  {

The keys appear on each machine as the next scan writes them, and they are ordinary telemetry from then on:
chart them on a ThingsBoard dashboard, compare them with process data, or read them in a rule chain.

## Alarm rules

An alarm rule tells Trendz when a machine needs attention. Every scan checks each rule on each machine, and a
rule that keeps breaking raises an alarm in ThingsBoard.

Answer three questions from the top down. They pick the kind of rule and what it watches, as set in Step 2
below:

<ImageGallery images={[
  {
    src: '/src/assets/images/trendz/vibration/monitoring-rule-tree.svg',
    alt: 'Decision tree in three steps. 1: a reading crossed a limit, or the analyzer found a fault. 2: for a reading, a metric or a band; for a fault, the ISO zone, a shaft fault, or a bearing defect. 3: which metric (RMS, acceleration RMS, peak-to-peak, crest factor, or any), which band (sub-harmonic, 1x, 2x, harmonics, non-synchronous, or any), which shaft fault, or which bearing race',
    caption: 'From what should raise the alarm to what the rule watches.',
  },
]} />

Every rule then gets severity levels (Step 3) and a confirmation (Step 4), which decides how many samples in a
row must break the rule before the alarm is raised or cleared.

### Step 3. Set severity levels

A rule has four levels: **Warning**, **Minor**, **Major**, and **Critical**. Switch on the ones you need and give
each a limit. Each level must be stricter than the one below it. The worst level a sample meets sets the alarm's
severity.

<ImageGallery images={[
  {
    src: '/src/assets/images/trendz/vibration/monitoring-rule-sev-fixed.webp',
    alt: 'Alarm rules editor with the Severity levels section highlighted: alarm type Vibration level, warning above 7, major above 12, and critical above 18 mm/s',
    caption: 'The Severity levels section of a rule.',
  },
]} />

**Alarm type** is the name of the alarm in ThingsBoard. Rules that share a type raise a single alarm per machine.

**Reading over a limit.** Each level takes its limit from one of three sources:

| Limit       | The level fires when the reading is above |
|-------|--------------------------------------------|
| **Fixed value** | A number you type, for example 7 mm/s |
| **Of its median** | A multiple of the machine's own median, for example 3× |
| **Attribute** | A number stored in an attribute of the machine, for example `velocityWarningLimit` |

With **Of its median**, one rule fits machines that vibrate differently. **Any metric** and **Any band** always
use it.

<ImageGallery images={[
  {
    src: '/src/assets/images/trendz/vibration/monitoring-rule-opt-source.webp',

  },
  {
    src: '/src/assets/images/trendz/vibration/monitoring-rule-sev-median.webp',

**Detected problem.** Each level says what counts:

| Detector | Level options |
|----------|---------------|
| **ISO zone** | **B — acceptable or worse**, **C — alert or worse**, or **D — danger** |
| **Shaft fault**, **Bearing defect** | **Detected**, or **Detected and grown** by a factor |

Use **Detected and grown** on machines that already have a known fault. The level stays quiet until the fault
grows past its baseline by the factor you set.

### Step 4. Set confirmation

Confirmation stops one noisy sample from raising or clearing an alarm.

- **Raise after:** how many breached samples in a row raise the alarm.
- **Clear after:** how many clean samples in a row clear it.

Each machine, rule, and axis has its own alarm. When the severity changes, the alarm keeps its original
**Opened** time, so it shows when the problem started.

### Step 5. Save the rules

Click **Save rules**. The editor does not save until every rule is complete:

- At least one severity level is on, and each level has its limit.
- Each level is stricter than the one below it.
- **Any metric** and **Any band** use median multiples.
- The rule has an **Alarm type**.

If the model has no scan schedule yet, Trendz offers to set up monitoring, because rules only raise alarms when a
scan runs and **Raise alarms** is enabled.

## Early fault detection

Overall metrics react late. A bearing defect shows first at its own fault frequency, while RMS still looks
normal. Trendz tracks both on every scan.

In the IMS bearing test, set 2, Bearing 1 failed with an outer race defect three days after this sample, while its
outer race frequency (BPFO) was already 3 times its baseline:

- **Metrics:** on Feb 16 at 05:12, every metric is within ×1.13 of its median.
- **Fault frequency:** at the same moment, BPFO is already at ×3.1, and it keeps rising.
