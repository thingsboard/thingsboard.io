This guide explains how Trendz Analytics versions are numbered, how long each version is supported,
what kind of upgrade requires downtime, and which Docker tags to use in different environments.
It is written for platform administrators, SREs, DevOps engineers, and technical users who deploy
and maintain Trendz Analytics.

## Trendz Analytics versioning

Trendz Analytics version numbers reflect the scope of changes introduced in each release.
This follows semantic versioning principles, helping you gauge the potential impact of upgrading.
Version numbers have four parts: `MAJOR.MINOR.MAINTENANCE.PATCH`.
For example, version `1.15.0.3` indicates major version 1, minor version 15, maintenance 0, and patch level 3.

The version number is incremented based on the level of change included in the release:

| Level | Changes | Upgrade scripts required |
|---|---|---|
| MAJOR | Breaking changes, removed/deprecated APIs, major migrations, new features | Yes |
| MINOR | New features with backward compatibility | Yes |
| MAINTENANCE | Bug fixes, security vulnerabilities, framework upgrades that may require upgrade scripts | Yes |
| PATCH | Hotfix releases — critical bugs or security fixes; no environment or DB changes | No |

**Examples:**

- `1.15.0.0` — Initial 1.15 LTS release
- `1.15.0.2` — Two hotfixes later; no upgrade scripts required to move within `1.15.0.x`
- `1.15.1.0` — First maintenance release; expect upgrade scripts

## Lifecycle and support

Trendz Analytics maintains **Long-Term Support (LTS)** lines for production users.
Customers on LTS releases can be confident their systems will remain protected and stable.

| Release type | Description | Support duration | Typical frequency |
|---|---|---|---|
| **LTS** | Announced yearly; for stable, long-term production use | **18 months** from initial LTS GA (e.g., 1.15.0.0 release date) | Annually |
| **Standard** | Releases between LTS lines, including new features | **6 months** from initial GA date | Every three months (Minor) |

## Choosing the right version

For production deployments:

1. **Prefer the latest LTS line** in Active Support.
2. Track **PATCH** updates only to stay current with hotfixes (same MAINTENANCE number,
   e.g., `1.15.0.0` → `1.15.0.3`). No upgrade scripts or downtime required.
3. **Schedule maintenance windows** to adopt new **MAINTENANCE** releases
   (e.g., `1.15.0.x` → `1.15.1.0`). Upgrade scripts are required.

## Docker Hub tagging strategy

| Tag | Example | Purpose | Update policy |
|---|---|---|---|
| `M.m.P.p` | `1.15.0.0` | Production | Immutable |
| `M.m.P-latest` | `1.15.0-latest` | Automatic safe patches | Floating (within `1.15.0.x`) |
| `latest` | `latest` | Development / testing (non-LTS) | Floating (latest master release) |

**Recommendations:**

- **Production:** Pin to the immutable full tag (e.g., `1.15.0.0`). You upgrade only when you change the tag.
- **Auto security hotfixes (no downtime):** Use `1.15.0-latest` to automatically receive `1.15.0.1`, `1.15.0.2`, etc., but never jump to `1.15.1.0` this way.
- **Avoid `latest` in production.** It may include breaking changes and is not covered by the LTS policy.

## Compatibility and deprecations

- **API and behavior compatibility** is maintained within a MAJOR version wherever feasible.
  Minor releases may deprecate features but will not break existing integrations without a migration path.
- **Deprecation policy:** Features flagged as deprecated in a Minor release remain available for at
  least one subsequent Minor release before removal (or are guarded by feature flags when possible).
  Deprecations and removals are always documented in the Release Notes.
