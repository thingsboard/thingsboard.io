One hundred thousand MQTT gateways, with five devices behind each of them. The gateways report for their devices, and every one of those devices also has to take commands back. An enterprise partner preparing to launch wanted to know what it takes to run that, and came to us with three questions.

- How do we size a cluster for a fleet like this?
- Can the platform command the whole fleet on a fixed cycle, and keep the guarantee that every command arrives?
- And what does delivery latency look like in a high-availability deployment, where the services talk to each other across availability zones?

We measured all three with telemetry and commands running together, the way production does. A story of measurement over assumption, and proof that collecting data is only part of what ThingsBoard does well.

## Why these questions matter

**Commands vs telemetry.** Most telemetry pipelines are built to tolerate the occasional lost message, and for good reason — one missing reading is a gap in a chart, and the next reading is already on its way. A dropped command has no equivalent. It is a machine that never stopped, a valve that stayed open, a firmware rollout that silently skipped part of the fleet. That is why command delivery needs a guarantee telemetry can live without.

**Gateways vs one connection per device.** Our [published performance benchmarks](/docs/reference/architecture/performance/) measure the [Device API](/docs/reference/mqtt-api/getting-connected/), where every device holds a session of its own. A [Gateway API](/docs/reference/gateway-api/overview/) session speaks for many devices at once, so the platform keeps state for far more devices than it holds connections, and every command has to reach the right device behind the right session. A fleet of gateways is what a large deployment really looks like, and it is the harder shape to serve.

**Three zones vs one.** ThingsBoard services talk to each other through Kafka, and a command makes several hops on its way to a gateway. Spread across three availability zones the way a production fleet is deployed, one broker per zone, most of those hops cross a zone boundary and pay for it. A latency figure measured inside a single zone does not include that delay, so it says nothing about what a three-zone production deployment really sees.

## The test and the results

The partner set the fleet and both command rates, so what the cluster had to carry was fixed before anything was deployed. Both runs used the same fleet, with commands and telemetry on separate rule-engine queues so that neither could slow the other down. In the second run every device got a command every minute instead of every five minutes, which is five times more commands and five times more telemetry.

| setting | both runs |
|---|---|
| MQTT connections | 100,000, open for the full run |
| gateway to device ratio | 1:5 |
| total devices, gateways included | 600,000 |
| tenants | 5 |
| connection security | one-way TLS |
| per device, per cycle | 1 telemetry message and 1 two-way command |
| telemetry delivery | MQTT QoS 0, 21 metric keys per message |
| command delivery | MQTT QoS 1, persistent RPC |
| duration | 1 hour at each rate |

Only the cycle changed between the two runs. That one change multiplies the commands, the telemetry, the database writes and the queue traffic by five, which makes it a fair test of whether the guarantee holds. Here are the results of both runs side by side.

| what differed | first run | second run |
|---|---|---|
| cycle | every 5 minutes | **every minute** |
| commands a minute | 100,000 | **500,000** |
| commands over the hour | 5.5 million | **27.5 million** |
| average delivery time | 200–233 ms | 203–254 ms |
| 99th percentile | 330–376 ms | 317–364 ms |
| telemetry alongside | 35,000 data points a second | 175,000 data points a second |

No command was lost or expired in either run. Five times the load, and the same delivery time. The 99th percentile stayed under 400 ms in both runs, with the cross-zone traffic between services included. Both rates came from the partner's requirement, not from us looking for the point where the cluster gives up.

- **100,000 connections stayed up for the full hour in both runs**, spread across the six transport instances to within ±1.1% and ±1.3% of an even split.
- **Nothing failed on the command path.** No command failed and no command timed out.
- **Nothing failed on the telemetry path.** Not one publish failure from the gateways.
- **Consumer lag never carried over.** Each cycle built a burst of lag, and every burst drained to zero before the next cycle began.
- **The cluster was not overloaded.** Node CPU peaked at 67% in the first run and 75% in the second, and heap was the tightest resource anywhere, at 82% and 84% of its limit in the transport tier.
- **The faster rate needed two changes on the database side** before it stayed clean. [The second run: five times the rate](#the-second-run-five-times-the-rate) describes both.

## How we sized the cluster

We did not start from a blank sheet. Our standard ThingsBoard Private Cloud environments are tuned and tested for up to 100,000 devices, on six MQTT transport instances with three monolith ThingsBoard nodes behind them. This fleet opens the same 100,000 connections, so at first glance the standard cluster should have been enough.

The count that matters is not the connections. Every device behind a gateway is a session in its own right, with its own routing and its own activity state, so the core service tracks 600,000 devices instead of 100,000, and every command is addressed to one of the 500,000 that sit behind the gateways. All of that is state in memory. The transport tier stayed at six instances, the same as the standard sizing. It carries connections, and their number did not change. The pressure landed on the core.

That is also why the monolith had to come apart. In a monolith node the core and the rule engine share one process and one set of resources, so growing one grows the other whether it needs it or not. Here only the core needed it, and it went from three instances to six. The rule engine was comfortable at three and stayed there. The result is the cluster below, two nodes in each of three zones, with the core and the rule engine running as separate services.

![Three availability zones, two nodes each running one MQTT transport, one core and one Valkey pod, with a rule engine and a Kafka broker per zone, in front of a Multi-AZ PostgreSQL instance](/images/blog/500k-guaranteed-iot-device-commands-per-minute/cluster-three-zone-topology.svg)

Splitting them bought more than the right instance counts. Each service is now scaled, restarted and sized on its own, neither one competes with the other for CPU or heap, and taking one side down for a rolling update leaves the other serving traffic. Every tier is spread across three availability zones as well, so losing a zone costs a share of capacity rather than the cluster, and that cross-zone cost sits inside the latency figures above.

## Behind the numbers

One improvement in the platform had to be in place before a run at this scale was possible.

Persistent RPC is what stands behind the guarantee. A command is a row in the database before it is sent anywhere, and every step of its lifecycle is written down too. A command delivered to a gateway at MQTT QoS 1 moves through QUEUED, SENT, DELIVERED and SUCCESSFUL, which is one insert and three updates. At half a million commands a minute that is **two million row writes a minute**.

A separate synchronous write per state was fine while commands were occasional, a firmware trigger or a setpoint change, which is what persistent RPC was built for. At this rate it is not, because every write was committed on the core service's device-actor thread, and that thread waits for the commit instead of doing the rest of the work those devices need.

So we improved how RPC registration and lifecycle updates are processed. Inserts and status updates are now grouped into **batches** and written by a dedicated pool of database writer threads. The same rows and the same durability, but the device actor hands its write off and moves on to the next message. A command still goes out only once the batch reports its row as durable, so nothing is ever sent that was not written down first.

## Inside the runs

#### The first run: one command per device every five minutes

Every five minutes each of the 500,000 devices sent one telemetry message and received one two-way command, a command it had to answer rather than merely receive. That works out to 500,000 telemetry messages and 500,000 commands a cycle, or **100,000 commands a minute**, sustained for an hour. The telemetry went through the Gateway API to the rule engine, which forwarded it to Kafka for the partner's own downstream systems, one of the standard ThingsBoard integration patterns.

#### The second run: five times the rate

The first run finished with room to spare, and the tightest resource in it, heap in the transport tier, is driven mostly by the 100,000 connections rather than by how often commands are sent. Sending them five times more often should not move it much. The point was to find what gave way first.

**It did not hold.** The run reached the target rate and stayed there for about ten minutes. Then the core service started to report that the rows waiting to be written were growing faster than the writer threads could clear them.

```
Queue-N [RPC] is falling behind: queueSize [1711] exceeds batchSize [1000]
```

The message pointed at the database, and the database confirmed it right away. Write latency grew from 23 ms to 171 ms, and the disk queue grew from 9 requests to 50. The disk was at its limit, and not because of space. A 100 GiB `gp3` volume gives 125 MB/s and 3,000 IOPS, the number of write operations it can do each second. The IOPS were the limit we reached. Write throughput stopped at 96–98 MB/s and went no higher.

**A bigger volume, for the IOPS.** A `gp3` volume under 400 GiB lets you change neither number, so we grew it to 400 GiB for the experiment. That raises the baseline to **12,000 IOPS and 500 MB/s**, four times more of both.

We also had a second suspicion, because a persistent command is four writes rather than one. Each state change writes a new copy of the row and leaves the old copy for a background job, autovacuum, to remove, so at half a million commands a minute those old copies arrive very fast. The plan was to see whether the extra IOPS were enough on their own, and to watch the old copies while we did.

**Cleanup was too slow.** About half an hour into the next run the slowdown returned, and this time the commands were delayed by it. The old copies were the reason. Each pass cleaned about 1.7 million of them while 3.1 million more arrived. Autovacuum is rate-limited by default, to roughly 32 MB/s, so that it never competes with live work, and that is too slow for a table changing this fast. We changed two settings on it while the run was going. The pause between cleanup steps went from 2 ms to none, and the point where cleanup starts moved from 10% of the table to 4%.

```sql
ALTER TABLE rpc SET (autovacuum_vacuum_cost_delay = 0, autovacuum_vacuum_scale_factor = 0.04);
```

One cleanup pass went from 227 seconds to about 50, and the old copies fell from a third of the table to less than 1% in under four minutes. The chart below shows what happened. Write throughput had been climbing while the backlog grew, because each pass had more to clear than the one before. It peaked at 198 MB/s as the catch-up ran, 1.6 times above what the old volume allowed, and then settled at 87 MB/s for the rest of the run.

![Database write throughput against the 125 MB/s default gp3 ceiling](/images/blog/500k-guaranteed-iot-device-commands-per-minute/rds-write-throughput.png)

Write operations are the number that had run out. With cleanup keeping up, the run settled at about 2,000 a second. The only thing that needed more was the catch-up, which touched 7,010.

![Database write IOPS against the 3,000 limit of a 100 GiB gp3 volume](/images/blog/500k-guaranteed-iot-device-commands-per-minute/rds-write-iops.png)

Write latency and database CPU show the same change. Latency went from 171 ms at the worst of it to between 4 and 8 ms once cleanup caught up. Database CPU had been growing for twenty minutes while the command rate stayed the same, which means work was building up rather than load increasing, and after the change it went flat and stayed flat until the end of the run.

![Database write latency, annotated at the moment the autovacuum rate cap was lifted](/images/blog/500k-guaranteed-iot-device-commands-per-minute/rds-write-latency.png)

![Database CPU utilisation, annotated at the same moment](/images/blog/500k-guaranteed-iot-device-commands-per-minute/rds-cpu-utilization.png)

**What it cost the commands.** The queue of commands waiting for the core service normally sits between 1,800 and 4,300 messages and drains on every cycle. While cleanup was falling behind it grew to 32,207, and then to 54,918, which at 8,333 commands a second is several seconds of extra waiting for everything behind it. Three minutes after the change it was back in its usual range, and it stayed there for the rest of the run. No command was lost in those minutes, because a persistent command waits in the queue rather than being dropped, but the delivery times in that window are the one part of the run that would not have met the target.

Both changes are deployment settings rather than platform behaviour. The steady state after the fix sat inside what the original 100 GiB volume allowed, so the larger volume is headroom rather than a requirement — what the run really needed was cleanup that keeps up.

## The takeaway

Command and control rarely gets benchmarked at all. It is also the part that carries operational consequences, the fleet-wide firmware push, the demand-response signal, the emergency shutdown. Those are the moments where "we processed 99.9% of messages" is not an acceptable answer.

These two runs show that guaranteed delivery and low latency are not a trade-off on ThingsBoard. Half a million commands a minute, to half a million devices behind 100,000 gateways, across three availability zones — every one persisted, every one accounted for, and a 99th-percentile delivery time well under half a second. On six four-vCPU nodes and a single database instance. That was the requirement we were given, and going further is a matter of scaling the cluster components, not of changing the architecture.
