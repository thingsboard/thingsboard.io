Every platform evaluation reaches the point where telemetry throughput and the number of connections a platform can hold stop being enough. An enterprise partner preparing to launch reached it with three questions.

- How many commands can the platform push out to real hardware at once, and still guarantee that every single one of them arrives?
- How well does the platform carry that when one MQTT session speaks for five devices instead of one?
- And what does delivery latency look like in a high-availability deployment, where the services talk to each other across availability zones?

All three had to be answered on a fleet that keeps sending telemetry at the same time, because that is what production looks like. A story of measurement over assumption, and proof that data collection is only half of what ThingsBoard does well.

## Why these questions matter

**Commands vs telemetry.** The failure modes are not comparable. Most telemetry pipelines are built to tolerate the occasional lost message, and for good reason — one missing reading is a gap in a chart, and the next reading is already on its way. A dropped command has no equivalent. It is a machine that never stopped, a valve that stayed open, a firmware rollout that silently skipped part of the fleet. That is why command delivery needs a guarantee telemetry can live without.

**Gateways vs one connection per device.** Our [published performance benchmarks](/docs/reference/architecture/performance/) measure the [Device API](/docs/reference/mqtt-api/getting-connected/), where every device holds a session of its own. A [Gateway API](/docs/reference/gateway-api/overview/) session speaks for many devices at once, so the platform keeps state for far more devices than it holds connections, and every command has to reach the right device behind the right session. A fleet of gateways is what a large deployment really looks like, and it is the harder shape to serve.

**Three zones vs one.** ThingsBoard services talk to each other through Kafka, and a command makes several hops on its way to a gateway. Spread across three availability zones the way a production fleet is deployed, one broker per zone, most of those hops cross a zone boundary and pay for it. A latency figure measured inside a single zone does not include that delay, so it says nothing about what a three-zone production deployment really sees.

## What we ran

The partner set the fleet and both command rates, so what the cluster had to carry was fixed before anything was deployed. Both runs used the same fleet. In the second one the cycle repeated five times as often, so the commands and the telemetry both rose with it.

| | first run | second run |
|---|---|---|
| MQTT connections | 100,000, open for the full run | 100,000, open for the full run |
| gateway to device ratio | 1:5 | 1:5 |
| total devices, gateways included | 600,000 | 600,000 |
| tenants | 5 | 5 |
| connection security | one-way TLS | one-way TLS |
| per device, per cycle | 1 telemetry message and 1 two-way command | 1 telemetry message and 1 two-way command |
| telemetry delivery | MQTT QoS 0, 21 metric keys per message | MQTT QoS 0, 21 metric keys per message |
| command delivery | MQTT QoS 1, persistent RPC | MQTT QoS 1, persistent RPC |
| duration | 1 hour | 1 hour |
| cycle | every 5 minutes | **every minute** |
| dispatch | batches of 500 commands per API call, ~3 calls a second | batches of 500 commands per API call, **~17 calls a second** |

## How we sized the cluster

We did not start from a blank sheet. Our standard ThingsBoard Private Cloud environments are tuned and tested for up to 100,000 devices, on six MQTT transport instances with three monolith ThingsBoard nodes behind them. This fleet opens the same 100,000 connections, so at first glance the standard cluster should have been enough.

The count that matters is not the connections. Every device behind a gateway is a session in its own right, with its own routing and its own activity state, so the core service tracks 600,000 devices instead of 100,000, and every command is addressed to one of the 500,000 that sit behind the gateways. All of that is state in memory, and it is what the sizing had to answer for. The transport tier stayed at six instances, exactly as the standard sizing has it, because connections are what it carries and there were no more of them than before. The pressure landed on the core.

More core instances was the obvious answer, and it was also the reason the monolith had to go. In a monolith node the core and the rule engine share one process and one set of resources, so growing one grows the other whether it needs it or not. Here only the core needed to grow. The rule engine was comfortable at three instances and stayed there.

![Three availability zones, two nodes each running one MQTT transport, one core and one Valkey pod, with a rule engine and a Kafka broker per zone, in front of a Multi-AZ PostgreSQL instance](/images/blog/500k-guaranteed-iot-device-commands-per-minute/cluster-three-zone-topology.svg)

Splitting them bought more than the right instance counts. Each service is now scaled, restarted and sized on its own, neither one competes with the other for CPU or heap, and taking one side down for a rolling update leaves the other serving traffic, which is what a high-availability deployment asks for in the first place. The core tier went to six instances, both to hold that state and to bring the fleet online quickly.

Every tier is then spread across three availability zones, so losing a zone costs a share of capacity rather than the cluster, and the latency it costs sits inside every figure below.

## The results

Both runs lasted an hour, and both delivered every command they were given.

| | first run | second run |
|---|---|---|
| commands a minute | 100,000 | **500,000** |
| commands over the hour | 5.5 million | **27.5 million** |
| lost or expired | none | none |
| average delivery time | 200–233 ms | 203–254 ms |
| 99th percentile | 330–376 ms | 317–364 ms |
| telemetry alongside | 35,000 data points a second | 175,000 data points a second |

Five times the load, and the same delivery time. The 99th percentile stayed under 400 ms in both runs, with the cross-zone traffic between services included.

- **100,000 connections stayed up for the full hour in both runs**, spread across the six transport instances to within ±1.1% and ±1.3% of an even split.
- **Nothing failed anywhere in the message path.** Not one telemetry publish failure, no queue timeout or failure, and consumer lag drained to zero on every cycle.
- **The cluster was not working hard.** Node CPU peaked at 67% in the first run and 75% in the second, and heap was the tightest resource anywhere, at 82% and 84% of its limit in the transport tier.
- **The faster rate needed two changes on the database side** before it stayed clean, and both are described below.

## Behind the numbers

One change in the platform, and three decisions about how the fleet, the queues and the cluster were laid out. Each one had to be settled before the numbers above meant anything.

#### From one REST call to 500 commands

At the partner's request one call names 500 devices instead of 500 separate calls, to keep HTTP traffic down. The whole fleet is commanded on a cycle, so a handful of calls a second expand into thousands of individually tracked commands.

The batch lands on the queue carrying inbound API calls, and the 500 commands it becomes go onto the queue carrying commands. Both are separate from the telemetry queue, so commands and ingestion never block each other. Every queue is partitioned to divide evenly across the three rule-engine instances.

![One batch call fanning out through the REST API calls queue into 500 individual commands on the RPC calls queue](/images/blog/500k-guaranteed-iot-device-commands-per-minute/rpc-queue-split.svg)

#### Four database writes per command

This one set the ceiling everything else had to get past. A [persistent RPC](/docs/user-guide/command-and-control/) delivered to a gateway subscribed at MQTT QoS 1 is a row that moves through QUEUED, SENT, DELIVERED and SUCCESSFUL — one insert and three updates. At half a million commands a minute that is **two million row writes a minute**, and originally every one of them was committed synchronously on the core service's device-actor thread, which carries all the other work of those devices too and sits idle until the commit returns. That is a ceiling no setting can raise — the wait itself has to come off the command path.

Persistent RPC is what stands behind the guarantee: a command is a row before it is sent anywhere, and every step of its life is written too. A separate synchronous write per state was a fine trade when commands were occasional — a firmware trigger, a setpoint change, a reboot — which is what persistent RPC was built for.

So we changed it. Inserts and status updates are grouped into **batches** and written by a dedicated pool of database writer threads. The same rows and the same durability, but the device actor hands its write off and moves on to the next message instead of waiting for a database commit. A command still goes out only once the batch reports its row as durable, so nothing is ever sent that was not written down first — the wait is a callback now rather than a blocked thread.

#### Onboarding 600,000 device actors

Those actors are not created for free, and a steady-state message rate tells you nothing about how long it takes to bring them up. The requirement was that the fleet comes online quickly, from a cold cluster, after a full restart, and as new sets of gateways and their devices are added.

A device actor is created the first time its gateway connects or announces it, and inside a tenant's actor those creations happen strictly one at a time — each device has to be looked up before its actor can exist. The first lookup goes to PostgreSQL. From then on the device is in the Valkey cache, and the next one costs a fraction of that.

![Device-actor creation inside one tenant actor — mailbox, create, ready, then the next device](/images/blog/500k-guaranteed-iot-device-commands-per-minute/actor-creation-bottleneck.svg)

So a single stream cannot be made faster. It can be multiplied, and two things multiply it. Devices are routed to core instances by device id, and **each core instance runs its own tenant actor**, so one tenant's fleet already comes online in parallel across the cluster. Tenants multiply that again, because each tenant is a separate stream on every instance.

![Devices routed by hash to six core instances, each running five tenant actors — thirty onboarding streams at once](/images/blog/500k-guaranteed-iot-device-commands-per-minute/actor-creation-streams.svg)

Onboarding speed is therefore something you can design, not a fixed property of the platform. Add core instances, or split the fleet across more tenants, and the number of streams rises with it. The same arithmetic sizes a fleet several times larger.

Only one of the two was ours to set. The five-way split came with the fleet as the agreed baseline, and the six core instances came from the cluster sizing described earlier. What the fast-onboarding requirement changed is that their product had to be verified rather than assumed. In these runs the full fleet was connected, announced and ready in about five minutes.

That cost is paid once, on a cold start. In a rolling restart the partitions move to instances that already have those devices cached, so the lookups are cheap and the fleet comes back much faster.

#### Sizing everything to divide evenly

Sizing every tier to divide evenly is the principle worth carrying away, and partitions are where that is easiest to miss. The cluster's partitioned topics belong to two families. Two of them feed the core tier: the requests transports send to core, and the traffic that drives the device actors. The others are the rule engine's queues, partitioned per queue — the command queue from earlier among them, which is where a burst has to spread. Twelve partitions divides cleanly into both tiers, two per core instance and four per rule-engine instance, so no instance is handed a heavier share than its neighbour. Scale a tier and its topics have to be repartitioned with it.

## Inside the runs

#### The first run: one command per device every five minutes

Every five minutes each of the 500,000 devices sent one telemetry message and received one two-way command, a command it had to answer rather than merely receive. That works out to 500,000 telemetry messages and 500,000 commands a cycle, or **100,000 commands a minute**, sustained for an hour. The telemetry went through the Gateway API to the rule engine, which forwarded it to Kafka for the partner's own downstream systems, one of the standard ThingsBoard integration patterns.

#### The second run: five times the rate

The first run finished with room to spare, and the tightest resource in it, heap in the transport tier, is driven mostly by the 100,000 connections rather than by how often commands are sent. Sending them five times more often should not move it much, so we ran the second one on the same infrastructure and changed only the cycle, from five minutes to one. Every other figure below follows from that one change. The point was to find what gave way first.

**It did not hold.** The run reached the target rate and stayed there for about ten minutes. Then the core service started to report that the rows waiting to be written were growing faster than the writer threads could clear them.

```
Queue-N [RPC] is falling behind: queueSize [1711] exceeds batchSize [1000]
```

That message points in one direction, at the database, and the database confirmed it at once. Write latency grew from 23 ms to 171 ms, and the disk queue grew from 9 requests to 50. The disk was at its limit, but not on space and not on bandwidth. A 100 GiB `gp3` volume gives 125 MB/s and 3,000 IOPS, the number of write operations it can do each second. The IOPS were the limit we reached. Write throughput stopped at 96–98 MB/s and went no higher.

**A bigger volume, for the IOPS.** A `gp3` volume under 400 GiB lets you change neither number, so we grew it to 400 GiB for the experiment. That raises the baseline to **12,000 IOPS and 500 MB/s**, four times more of both.

We also had a second suspicion, because a persistent command is four writes rather than one. Each state change writes a new copy of the row and leaves the old copy for a background job, autovacuum, to remove, so at half a million commands a minute those old copies arrive very fast. The plan was to see whether the extra IOPS were enough on their own, and to watch the old copies while we did.

**Cleanup was too slow.** About half an hour into the next run the slowdown returned, and this time the commands were delayed by it. The old copies were the reason. Each pass cleaned about 1.7 million of them while 3.1 million more arrived. Autovacuum is rate-limited by default, to roughly 32 MB/s, so that it never competes with live work, and that is too slow for a table changing this fast. We changed two settings on it while the run was going. The pause between cleanup steps went from 2 ms to none, and the point where cleanup starts moved from 10% of the table to 4%.

```sql
ALTER TABLE rpc SET (autovacuum_vacuum_cost_delay = 0, autovacuum_vacuum_scale_factor = 0.04);
```

One cleanup pass went from 227 seconds to about 50, and the old copies fell from a third of the table to less than 1% in under four minutes. The chart below shows the whole shape of it. Write throughput had been climbing while the backlog grew, because each pass had more to clear than the one before. It peaked at 198 MB/s as the catch-up ran, 1.6 times above what the old volume allowed, and then settled at 87 MB/s for the rest of the run. Even that steady level is about 70% of the old 125 MB/s limit.

![Database write throughput against the 125 MB/s default gp3 ceiling](/images/blog/500k-guaranteed-iot-device-commands-per-minute/rds-write-throughput.png)

The write operations show it from the other side, and they are the number that had run out. With cleanup keeping up, the run settled at about 2,000 a second, two thirds of what the original 100 GiB volume allowed. The only thing that needed more was the catch-up, which touched 7,010.

![Database write IOPS against the 3,000 limit of a 100 GiB gp3 volume](/images/blog/500k-guaranteed-iot-device-commands-per-minute/rds-write-iops.png)

Write latency shows the change most plainly of all, from 171 ms at the worst of it to between 4 and 8 ms once cleanup was winning.

![Database write latency, annotated at the moment the autovacuum rate cap was lifted](/images/blog/500k-guaranteed-iot-device-commands-per-minute/rds-write-latency.png)

Database CPU tells the same story. It had been growing for twenty minutes while the command rate stayed the same, which means work was building up rather than load increasing. After the change it went flat and stayed flat until the end of the run.

![Database CPU utilisation, annotated at the same moment](/images/blog/500k-guaranteed-iot-device-commands-per-minute/rds-cpu-utilization.png)

**What it cost the commands.** The queue of commands waiting for the core service normally sits between 1,800 and 4,300 messages and drains on every cycle. While cleanup was losing the race it grew to 32,207, and then to 54,918, which at 8,333 commands a second is several seconds of extra waiting for everything behind it. Three minutes after the change it was back in its usual range, and it stayed there for the rest of the run. No command was lost in those minutes, because a persistent command waits in the queue rather than being dropped, but the delivery times in that window are the one part of the run that would not have met the target.

Both changes are deployment settings rather than platform behaviour. The steady state after the fix sat inside what the original 100 GiB volume allowed, so the larger volume is headroom rather than a requirement — what the run really needed was cleanup that keeps up.

## The takeaway

Command and control has been the quiet half of IoT platform benchmarking. It is also the half that carries operational consequences: the fleet-wide firmware push, the demand-response signal, the emergency shutdown. Those are the moments where "we processed 99.9% of messages" is not an acceptable answer.

What these two runs establish is that guaranteed delivery and low latency are not a trade-off on ThingsBoard. Half a million commands a minute, to half a million devices behind 100,000 gateways, across three availability zones — every one persisted, every one accounted for, and a 99th-percentile delivery time well under half a second. On six four-vCPU nodes and a single database instance.
