If you've ever managed remote Docker hosts, you know how painful it can be to make changes and monitor the health of your applications. Whether it's a configuration change, an image upgrade, or the 2 a.m. "is it still running?" check, you end up wishing for a single tool that could manage all your remote environments centrally.

Thankfully, there are quite a few tools that can manage edge environments, such as Portainer, Arcane, Watchtower, and Salt. Our customers use them, but still run into problems because these tools are generic by design.

We wanted to go further and build something that natively supports ThingsBoard products: discovery of new versions, one-click upgrades with database migrations and automatic rollback on failure, provisioning of new applications, detection of Compose projects that are already running, and more.

Meet **Remote Agent**: a small Docker container that runs on the remote host, connects back to ThingsBoard, and lets you deploy, update, upgrade, and monitor Docker Compose applications on that host straight from the ThingsBoard UI. One host or hundreds – one click per action, no SSH. Available in [ThingsBoard](/docs/pe/user-guide/agents/) 4.4+ and [ThingsBoard Cloud](/installations/choose-region/).

## How It Works

The agent runs as a Docker container on the remote host. It opens an **outbound** gRPC stream to ThingsBoard — the same port ThingsBoard Edge already uses — and authenticates with a routing key and secret. ThingsBoard sends step-based commands over that stream; the agent executes them against the local Docker Engine and reports progress for every step.

<div style={{maxWidth: '640px', margin: '32px auto'}}><Fragment set:html={architectureSvg} /></div>

Four design decisions make it safe to point at production:

- **No inbound access.** The agent opens no listening ports, so the host needs no public IP, port forwarding, or VPN.
- **Exactly-once execution.** Every step is idempotent, and the agent persists each finished step. The server watches every running operation and resends the current step when no progress arrives, so a dropped message only delays the work. It never loses it or runs it twice. After a reconnect or an agent restart, execution continues from the first unfinished step.
- **No half-finished upgrades.** Before an update or upgrade, the agent snapshots the application and backs up the selected volumes. If a step fails on the host, the agent restores the volumes and the previous containers. If the operation fails on the server side, ThingsBoard sends the rollback itself. Either way, the application ends on its previous working version instead of halfway in between.
- **Plain Docker underneath.** The agent talks to the Docker Engine API directly, so the host needs only Docker: no Compose CLI or files. It uses the standard Docker Compose labels, so your applications remain ordinary Compose projects, and containers you started yourself can be taken over just by labeling them.

## Managing a Single Remote Host

<div style={{margin: '32px 0'}}><Fragment set:html={singleHostSvg} /></div>

Start with one machine. In ThingsBoard, go to **Edge management > Agents**, click **Add new agent**, and copy the generated `docker run` command — the server address and credentials are already filled in. Run it on the host. The agent shows up as **Online**, and from that moment the host is manageable from the UI.

![Connecting a host to ThingsBoard: Add agent on the Agents page, the generated docker run command to run on the host, and the agent appearing Online](/images/blog/thingsboard-remote-agent/connect-agent.webp)

### Deploy any Docker Compose application

Click **Add application** and pick a type:

- **Edge** — a [ThingsBoard Edge](/docs/edge/pe/installation/agent/) instance, wired to its Edge entity and credentials automatically.
- **Gateway** — a [ThingsBoard IoT Gateway](/docs/iot-gateway/installation/agent-installation/), likewise wired to its gateway device.
- **Generic** — any Docker Compose project: an MQTT broker, a database, a dashboard, your own service.

Pick a predefined application profile for the version you want, adjust its Compose configuration if you need to, and click **Install**. Watch the install step by step as the agent pulls images and starts containers, and the application appears in the list.

![Installing an Edge application from the agent's Applications page: Add application, choose the Edge type, pick a predefined Edge profile, compare its Docker Compose template with your edits, and follow the install progress](/images/blog/thingsboard-remote-agent/install-application.webp)

Already running Compose projects on that host? You don't need to redeploy anything. On connect, the agent **discovers** existing Compose projects and reports them, so they become manageable from ThingsBoard as they are.

![A Mosquitto broker discovered on the host next to an installed ThingsBoard Edge application](/images/blog/thingsboard-remote-agent/discovered-application.webp)

### See what's happening — metrics and live logs

The agent continuously reports what runs on the host. On the agent's **Applications** page, the chips at the top show host CPU, memory, and disk — hover one for details — and the chart icon next to them opens the history of every application on the host, stacked.

![Host-wide metrics on the agent's Applications page: the CPU chip with its tooltip, the chart icon, and stacked CPU and memory history for every application on the host](/images/blog/thingsboard-remote-agent/monitor-host.webp)

Click an application to open its details. The same chart icon there breaks CPU and memory down per container, so you see which service is actually busy.

![Application metrics: the application's details page with its Docker Compose configuration, the chart icon, and stacked CPU and memory history per container](/images/blog/thingsboard-remote-agent/monitor-application.webp)

The **Units** tab lists the application's containers, volumes, and networks with their images and state. When something looks off, click the log icon on a container and stream its logs live into the browser, with highlight filters, pause, copy, and download. No `docker logs` over a shaky SSH session.

![Live container logs: the log icon on a container in the Units tab opens the log viewer, streaming the container's logs with a highlight filter, pause, copy, and download](/images/blog/thingsboard-remote-agent/container-logs.webp)

### Update and upgrade without fear

Two actions change a running application, and the difference matters:

- **Update** applies a changed Compose configuration — new environment variables, a re-pulled image, rotated credentials — on the current version.
- **Upgrade** moves a ThingsBoard product, like ThingsBoard Edge or IoT Gateway, to a new version. It's the action that runs the database upgrade scripts.

You don't have to watch release notes to know an upgrade exists. ThingsBoard syncs templates for its products from a public repository, so when a new version ships, the deployed application is marked **Upgrade available** — no platform update required.

Before an update or upgrade starts, the agent snapshots the application and backs up the volumes you select. If any step fails, it restores the volumes and recreates the previous containers: **automatic rollback**, including your data. The same happens if you cancel mid-way. Every step is visible in the event progress view as it runs.

Click **Upgrade** on the application, and ThingsBoard merges the new image version into your configuration automatically. Check the left side — what ThingsBoard suggests from the new template — and merge anything else you need into the right side. Pick the volumes to back up, confirm, and watch the agent stop the old version, migrate the database, and start the new one.

![Upgrading ThingsBoard Edge from 4.3.1.6 to 4.4.0: the Upgrade button, the new template merged into your Docker Compose configuration side by side, the volumes to back up, and the event progress with the database migration running](/images/blog/thingsboard-remote-agent/upgrade-application.webp)

One more upgrade that usually goes wrong by hand: **PostgreSQL major versions**. A Postgres data directory isn't compatible across majors, so changing the image tag alone breaks the database. With Remote Agent, you're free to raise it: the merge above keeps your `postgres:15` while the Edge 4.4 template ships `postgres:16`, and you can take the new major version in the same upgrade or in any later update. When an update or upgrade moves a service based on the official `postgres` image to a new major version, the agent detects it, backs up the volume, dumps the database with the old version, and restores it with the new one — resumable after a crash and rolled back with everything else on failure.

### Keep the agent up to date

The agent upgrades itself, too. When a new agent image is published, click **Upgrade agent**: the agent pulls the image, starts a replacement container with the same settings, hands the host over, and removes the old one. Your applications keep running throughout, and if the handover doesn't complete, the old agent simply keeps serving. See [Agent self-upgrade](/docs/pe/user-guide/agents/self-upgrade/).

## Managing a Fleet That Shares One Configuration

One host is convenient. The real payoff comes with many hosts running the **same** stack: an Edge per hotel, a gateway per plant, the same broker-plus-service bundle at every customer site. Remote Agent is built around two kinds of profiles that make "the same" actually stay the same.

<div style={{margin: '32px 0'}}><Fragment set:html={fleetSvg} /></div>

### Define the Stack Once: Application Profiles

An **application profile** is a reusable application configuration: the type, a template version, the Docker Compose configuration, and custom arguments. Create it once, and every application deployed from it shares that definition. There are two ways to create one:

- **Predefined profiles:** pick a card from **Quick start** — a ready-made ThingsBoard Edge or IoT Gateway profile for a specific version, created in one click with no configuration.
- **Add application profile:** build your own — choose the type and template version, then edit the Docker Compose configuration next to the read-only template. Use it for customized Edge or Gateway setups, or for any other Compose application, like the Mosquitto broker below.

![Creating application profiles: the Quick start panel with predefined profiles created in one click, and Add application profile opening a custom Docker Compose configuration for a Mosquitto broker next to the template](/images/blog/thingsboard-remote-agent/application-profiles.webp)

When you edit the profile, nothing changes behind your back: applications that no longer match are marked out of sync in the **In Sync With App Profile** column, and you choose when to apply the change. When a new Edge or Gateway version arrives, upgrading the profile shows a side-by-side merge of the new template into your configuration, so your customizations carry forward — the same side-by-side view as in the [upgrade above](#update-and-upgrade-without-fear).

### Provision a Fleet with One Command: Agent Profiles

An **agent profile** describes how new hosts join and what they run. Use the **default** profile, or pick a preset — **Edge**, **Gateway**, or **Edge + Gateway** — or configure your own, and ThingsBoard gives you a provisioning command.

Here's the trick: **it's the same command for every machine.** Put it in your setup script, a cloud-init file, or the checklist your field technicians follow. Each host that runs it registers itself as a new agent and, depending on the provisioning strategy, installs the assigned applications automatically. No per-site credentials to generate, no per-site Compose files to copy.

<div style={{maxWidth: '720px', margin: '32px auto'}}><Fragment set:html={provisioningSvg} /></div>

What a fleet runs is a list of application profiles assigned to its agent profile. Click **Assign profile**, pick the profiles — predefined, your own, or a new one created inline — and every agent on that profile gets them; the list also holds the bulk actions for each profile.

![Assigning application profiles to an agent profile: Assign profile, picking the Gateway, Edge, and Mosquitto profiles, and the assigned list with the bulk actions for each profile](/images/blog/thingsboard-remote-agent/assign-profiles.webp)

Then run the provisioning command on a new host. The agent registers itself, and the assigned applications install on their own — each marked **Auto-provisioned**, with the Edge and Gateway entities and their credentials created along the way.

![Provisioning a new host: the agent profile's One application per type strategy and its docker run command, and the new agent's Gateway, Mosquitto, and Edge applications installed automatically with the Auto-provisioned origin](/images/blog/thingsboard-remote-agent/auto-provisioning.webp)

Already have a fleet in the field? Enable **Relate on Auto-Discovery** on the agent profile, and discovered Edge or Gateway applications that match a profile's template are attached to it automatically — bringing an existing fleet under profile management without reinstalling.

### One Click, Every Site: Bulk Actions

With profiles in place, fleet operations become a single action. On the agent profile, pick an application profile and run a **bulk restart, update, upgrade, or delete**. It targets every matching application across every agent that uses that agent profile.

Before anything runs, a pre-flight preview shows how many applications are eligible and why any are skipped — an application on the wrong version, one with an operation already in progress — so there are no surprises halfway through.

![Bulk update of the Local Edge Profile: the Bulk Update action on the agent profile, the dialog with its pre-flight preview of total and eligible applications, and the run started on both applications](/images/blog/thingsboard-remote-agent/bulk-update.webp)

Each targeted application gets its **own** execution, with its own backup and its own rollback. A failure on one host never affects the others, and you follow the whole rollout — done, error, running, pending — from one panel, drilling into any single host's step-by-step progress.

### Staged rollouts: staging first, then production

Because one application profile can be assigned to several agent profiles, staged rollouts come for free. Assign your Edge application profile to a *staging* and a *production* agent profile, bulk upgrade staging, verify, adjust the configuration if needed, then bulk upgrade production — from the same profile, with the same result.

## Before and After

<BlogCallout label="The same tasks, with and without Remote Agent">

| Task | Without Remote Agent | With Remote Agent |
|---|---|---|
| Reach a host behind NAT or a firewall | VPN or inbound port per site | Outbound connection from the agent |
| Deploy a Compose stack | SSH in, copy files, run commands | Pick a profile in the UI, or auto-install on provisioning |
| Upgrade ThingsBoard Edge | Manual backup, migration, and restart per host | One upgrade action with volume backups and automatic rollback |
| Upgrade every site | Repeat the above, host by host | One bulk upgrade, staging first |
| Check why a site is quiet | SSH in, `docker ps`, `docker logs` | Status, metrics, and live logs in the UI |
| Know which sites drifted | Ask around | **In Sync With App Profile** column |

</BlogCallout>

## Get Started in Three Steps

1. **Install the first agent.** Go to **Edge management > Agents > Add new agent** and run the generated command on a host with Docker. See [Install Remote Agent](/docs/pe/user-guide/agents/installation/).
2. **Deploy or adopt an application.** Add an Edge, Gateway, or Generic application — or let the agent discover the ones already running. See [Applications](/docs/pe/user-guide/agents/applications/).
3. **Scale out with profiles.** Create an agent profile, run its provisioning command on the rest of your hosts, and manage them with [bulk actions](/docs/pe/user-guide/agents/bulk-actions/).
